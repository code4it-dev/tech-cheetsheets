Domain-Driven Design

Model the business, not the database — and stop pretending one word means the same thing everywhere.

As of Nov 2026 · Eric Evans, 2003; examples in C# and Python, framework-agnostic

Domain-Driven Design is a way of building software whose structure follows the structure of the business problem instead of the structure of the storage. Its premise is that in a complex domain the expensive part is not the code, it is the understanding — so the model, the conversations and the code should all use exactly the same words, and those words should be allowed to change when the understanding changes.

It comes in two halves that are often confused. Strategic design is about drawing boundaries: splitting a tangled domain into bounded contexts, deciding which ones are core business and which are commodity, and writing down how they talk to each other. Tactical design is the pattern catalogue inside one context: entities, value objects, aggregates, repositories, domain events, domain services. The strategic half is where most of the value is, and the half most teams skip.

DDD is not a framework and has no runtime. It pays off in domains with genuine business complexity — insurance, logistics, trading, billing, healthcare — and is usually a net loss on CRUD applications, reporting tools and simple content sites, where a transaction script and a good ORM are faster to write and easier to read.

Architecture / mental model

A bounded context is where one model and one language are consistent. Outside it, the same word is a different thing — and the translation is explicit.

Key concepts

Ubiquitous languageOne vocabulary shared by developers and domain experts, used in conversation, in documentation and literally in the code.
Domain expertThe person who actually knows how the business works, and whose vocabulary the model is built from.
SubdomainA part of the business problem, classified as core, supporting or generic to decide how much effort it deserves.
Bounded contextAn explicit boundary inside which one model and one language are consistent and unambiguous.
Context mapA diagram and a document describing every bounded context and the political and technical relationship between each pair.
Anti-corruption layerA translation layer that converts another context's model into yours, so their concepts never leak into your domain.
Shared kernelA small model deliberately shared by two contexts, jointly owned and changed only by agreement.
EntityAn object with an identity that persists through change: two entities differ even when every field matches.
Value objectAn immutable object defined entirely by its values, with no identity: two with the same values are interchangeable.
AggregateA cluster of entities and value objects treated as one unit for changes, with a single root as the only entry point.
Aggregate rootThe single entity through which everything inside an aggregate is reached and changed.
InvariantA business rule that must be true before and after every change — the reason an aggregate exists at all.
RepositoryA collection-like abstraction for loading and saving whole aggregates by identity.
Domain eventA record that something business-meaningful has happened, named in the past tense and published after the fact.
Domain serviceA piece of domain logic that does not belong to any single entity or value object, expressed in the ubiquitous language.
Application serviceThe thin orchestration layer: it opens the transaction, loads an aggregate, calls one method on it and saves. No business rules.
Event stormingA workshop where domain experts and developers map the business as a wall of past-tense events, then find boundaries in it.
Anemic domain modelThe anti-pattern where entities are property bags and all behaviour sits in services — DDD vocabulary with none of the benefit.

Essential code patterns

Tactical building blocks (C#)

public readonly record struct Money(decimal Amount, string Currency)
{
    public Money
    {
        if (Amount < 0) throw new DomainException("amount cannot be negative");
        if (Currency.Length != 3) throw new DomainException("ISO currency required");
    }

    public static Money operator +(Money a, Money b) =>
        a.Currency == b.Currency
            ? a with { Amount = a.Amount + b.Amount }
            : throw new DomainException("currency mismatch");
}
A value object: immutable, validated in the constructor, equal by value, with the currency rule impossible to bypass.
public sealed class Order                      // aggregate root
{
    private readonly List<OrderLine> _lines = new();
    private readonly List<IDomainEvent> _events = new();

    public OrderId Id { get; }
    public IReadOnlyList<OrderLine> Lines => _lines;   // read-only on purpose

    public void AddItem(Sku sku, int quantity)
    {
        if (quantity <= 0) throw new DomainException("quantity must be positive");
        if (_lines.Sum(l => l.Quantity) + quantity > 10)
            throw new DomainException("an order cannot hold more than 10 items");

        _lines.Add(new OrderLine(sku, quantity));
        _events.Add(new ItemAdded(Id, sku, quantity));
    }

    public IReadOnlyList<IDomainEvent> ReleaseEvents()
    {
        var e = _events.ToArray(); _events.Clear(); return e;
    }
}
The root owns the invariant and records what happened. Nothing outside can add a line directly.
public interface IOrderRepository
{
    Task<Order?> Get(OrderId id, CancellationToken ct = default);
    Task Add(Order order, CancellationToken ct = default);
    Task Save(Order order, CancellationToken ct = default);
}
One repository per aggregate root, by identity, whole aggregates only — no query methods for screens.
public sealed class AddItemHandler(IOrderRepository repo, IEventBus bus)
{
    public async Task Handle(AddItem cmd, CancellationToken ct)
    {
        var order = await repo.Get(cmd.OrderId, ct)
                    ?? throw new NotFoundException(cmd.OrderId);

        order.AddItem(cmd.Sku, cmd.Quantity);   // the only business call

        await repo.Save(order, ct);
        await bus.Publish(order.ReleaseEvents(), ct);   // after commit
    }
}
An application service: transaction, load, one domain call, save, publish. No rules.

Python

from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Money:
    amount: int          # minor units, never float
    currency: str

    def __post_init__(self):
        if self.amount < 0:
            raise DomainError("amount cannot be negative")

    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise DomainError("currency mismatch")
        return Money(self.amount + other.amount, self.currency)
The same value object in Python: frozen dataclass, validated once, equality by value for free.
class Order:
    MAX_ITEMS = 10

    def __init__(self, order_id: OrderId):
        self.id = order_id
        self._lines: list[OrderLine] = []
        self._events: list[DomainEvent] = []

    def add_item(self, sku: Sku, quantity: int) -> None:
        if quantity <= 0:
            raise DomainError("quantity must be positive")
        if sum(l.quantity for l in self._lines) + quantity > self.MAX_ITEMS:
            raise DomainError("an order cannot hold more than 10 items")
        self._lines.append(OrderLine(sku, quantity))
        self._events.append(ItemAdded(self.id, sku, quantity))
The aggregate root: private children, one public intention, the invariant checked against the whole aggregate.

Boundaries in the repository layout

src/
  Sales/                    # bounded context — owns its schema
    Domain/                 # entities, value objects, events (no framework)
    Application/            # command handlers, ports
    Infrastructure/         # EF Core, HTTP clients, ACL to Shipping
  Shipping/
    Domain/ Application/ Infrastructure/
  Billing/
  SharedKernel/             # Money, DateRange — tiny, stable, jointly owned
Folders follow contexts, not layers-first. Layer folders live inside each context so a boundary violation is visible in a diff.

Pros & cons

Pros

  • Business rules live in one findable place instead of being spread across controllers, triggers and validators.
  • Bounded contexts give a principled way to split a system — and a reason not to split it at the wrong seam.
  • The ubiquitous language makes conversations with domain experts cheap and misunderstandings visible early.
  • Aggregates give explicit, small transaction boundaries, which is what lets the model scale later.
  • The domain layer has no framework dependencies, so it is fast to test without a database.
  • Domain events make integration between contexts loose and auditable.

Cons

  • Real cost in ceremony: many small types, mappers, and more code for the same CRUD screen.
  • Needs sustained access to a domain expert; without one it degenerates into pattern cosplay.
  • Steep learning curve, and the tactical patterns are easy to apply while missing the point.
  • Boundaries drawn wrong early are expensive to move later.
  • Eventual consistency between aggregates surprises stakeholders who expected everything to be immediate.
  • Poor fit for read-heavy, report-shaped work, which needs queries the repository deliberately refuses.

Concrete use cases

Insurance policy administration

Underwriting, claims and billing all say "policy" and mean different things, and the rules change every regulatory season. Three bounded contexts with their own models, plus an anti-corruption layer over the 1990s mainframe, let each team change its rules without renegotiating a shared schema.

Splitting a monolith that resists splitting

A team wants microservices but every candidate service needs the same tables. Event storming reveals that the real boundary runs through the customers table, not around it. They extract contexts one at a time inside a modular monolith first, and only then move the ones that actually need separate deployment.

Logistics planning

"Delivered" means a scan at the door to operations, a signature to customer service and a revenue event to finance. Separate contexts with explicit integration events end a year-long argument about what the status column should contain.

Trading and risk

Position limits, margin rules and settlement windows are genuine invariants with money attached. Aggregates make the transaction boundary explicit, and value objects (Money, Notional, Tenor) remove a whole family of unit and rounding bugs.

Multi-tenant SaaS with per-tenant rules

Tenants want their own approval workflows. Modelling the workflow as a core subdomain with explicit policies — instead of a forest of if (tenantId == ...) — keeps customisation inside one context and out of the rest of the product.

When to use / when not to

if you can explain the whole domain in ten minutes, you do not need DDD

Use it when…

  • The complexity is in the business rules, not in the throughput or the UI.
  • Domain experts disagree with each other — that is the signal that several models are hiding in one.
  • The system will live for years and the rules will keep changing.
  • Several teams need to work in parallel and you need real boundaries between them.
  • You are about to split a monolith and need a principled place to cut.

Avoid it when…

  • The application is forms over data. Use CRUD with a good ORM, or transaction scripts.
  • The hard part is volume, latency or data movement, not rules. Use a pipeline and good data modelling.
  • You have no access to a domain expert. Use a simpler design until you do.
  • It is a short-lived prototype or a one-off migration. Use the shortest thing that works.
  • The team has never done it and there is no time to learn. Use a modular monolith with clear modules and adopt tactical DDD inside the one module that needs it.

Common mistakes & gotchas

Doing only the tactical halfEntities, repositories and value objects applied inside one undivided model give you all of the ceremony and none of the benefit — the god object is now a god aggregate.
Fix: start with event storming and bounded contexts. Tactical patterns are an implementation detail inside a boundary you have already drawn.
One canonical model for the whole companyThe "enterprise Customer" eventually has ninety nullable fields, no invariants and a change-approval committee.
Fix: let each context own its model and translate at the border. Duplication across contexts is correct, not a defect.
Aggregates that are too bigModelling Customer as the root of all their orders means loading thousands of rows to change an address, and two users editing different orders collide.
Fix: group only what must be transactionally consistent. Reference other aggregates by id and connect them with domain events.
Changing several aggregates in one transactionIt works until it does not: long locks, deadlocks and a model that cannot be split later because everything commits together.
Fix: one aggregate per transaction. For the rest, publish a domain event and converge, with an outbox so the event cannot be lost.
Repositories that grow a query APIFindByStatusAndDateAndCustomerWithLines appears, then projections, then paging — and the aggregate is now shaped by screens.
Fix: keep repositories to get/add/save by identity and build a separate read model for queries. This is the moment CQRS starts paying for itself.
Treating the ORM mapping as the modelLetting Entity Framework or Hibernate dictate public setters, parameterless constructors and exposed collections quietly produces an anemic model.
Fix: map to private fields and backing collections; keep the domain free of persistence attributes. If the ORM cannot express the model, that is the ORM's problem, not the model's.
Publishing internal domain events across contextsConsumers start depending on your internal shape, and you cannot refactor your own model without breaking three other teams.
Fix: separate internal domain events from versioned integration events, and treat the integration shape as a published contract.
Boundaries that do not match the teamsIf two teams change the same context, every release becomes a negotiation and the boundary stops being real.
Fix: align one context to one team (Conway's law is not optional). If you cannot, merge the contexts and be honest about it.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs DDD
Domain-Driven Designcomplex, long-lived business rulesHighfree; cost is learning and ceremony—
Transaction scriptsimple, procedural use casesLowfreeOne function per use case; no model, no boundaries — fine until the rules multiply
Active Record / CRUDforms over dataLowfreeThe table is the model; fast to build, no place to put invariants
Clean / hexagonal architecturekeeping frameworks at arm's lengthMediumfreeDependency rules only; says nothing about boundaries or language. Pairs well with DDD
CQRS + event sourcingaudit, temporal queries, high read/write asymmetryHighfree; operational cost realA storage and read strategy, not a modelling method; usually applied inside a DDD context
Modular monolithboundaries without distributionMediumfreeThe deployment shape; DDD supplies the criterion for where the modules go
  • Pick transaction scripts if each use case is a short procedure and the rules rarely interact.
  • Pick CRUD if the business value is in the screens and the data, not in the behaviour.
  • Pick clean architecture alongside DDD — it answers "which way do dependencies point?", not "what is the model?".
  • Pick CQRS once the repository starts growing query methods, and event sourcing only if you need history as a first-class fact.
  • Pick a modular monolith as the first physical shape for your contexts; split out services only when a context needs its own scaling or release cadence.
