Idempotency & deduplication

Exactly-once delivery does not exist. Exactly-once effect does, and this is how you build it.

As of Nov 2026 · examples in C#, Python, SQL and Kafka · the impossibility result is the Two Generals Problem

A sender transmits a request, the receiver processes it, and the acknowledgement is lost. The sender now cannot tell "it never arrived" from "it arrived and the reply vanished" — and no protocol can tell it, because distinguishing those two states would require a message that is itself guaranteed to arrive. That is the Two Generals Problem, and it is why exactly-once delivery is impossible rather than merely difficult.

What you get instead is a choice between two failure modes. At-most-once never duplicates and sometimes loses. At-least-once never loses and sometimes duplicates. Almost every system should pick the second, for one reason: a duplicate is detectable and a loss is not. You can recognise a repeat and discard it; you cannot notice something that never arrived.

Doing that recognition is what the rest of this page is about. An idempotency key lets a server identify a repeated request and replay the original answer instead of doing the work twice. A dedup window decides how long it remembers. Together they give you effectively-once processing — at-least-once delivery whose duplicates have been made harmless, which is what everybody actually means when they say "exactly-once".

Architecture / mental model

delivery never lost, never duplicated impossible Two Generals — not an engineering gap so build the thing people actually mean effectively-once processing at-least-once delivery retry until acknowledged + a key per operation stable across attempts + a dedup store with a window longer than the retry horizon the delivery is still at-least-once — you only made the duplicate harmless And the dedup state must be written in the same transaction as the effect, or you have moved the problem rather than solved it.

Three semantics, one of which cannot be built. The fourth box is what every "exactly-once" system is actually doing.

Key concepts

Idempotent operationOne whose repetition changes nothing beyond the first application — naturally safe to retry.
Idempotency keyA client-generated identifier for one logical operation, stable across every retry of it.
Key scopeWhat the key is unique within — and the thing that decides whether one tenant can affect another.
Request fingerprintA hash of the request body stored with the key, so the same key with different content is rejected rather than silently answered.
Response replayReturning the stored result of the first attempt, so a retry is indistinguishable from the original.
Concurrent duplicatesTwo attempts in flight at once — the case a naive check-then-act misses entirely.
At-most-onceNever retry: no duplicates, and silent loss whenever something goes wrong.
At-least-onceRetry until acknowledged: nothing is lost, and duplicates are guaranteed to happen eventually.
Exactly-once deliveryThe thing that cannot be built — and the phrase to push back on in a design review.
Effectively-onceAt-least-once delivery whose duplicates have been made harmless. What everyone means by exactly-once.
Dedup storeWhere processed keys live — a table or a cache, read and written on the hot path.
Dedup windowHow long a key is remembered. Too short and duplicates slip through; too long and you store everything forever.
Window sizingThe window must outlast every mechanism that could redeliver — retries, broker redelivery, operator replays.
Business key dedupDeduplicating on something the domain already guarantees unique, instead of a separate key with a window.
Inbox patternThe consumer-side table recording processed message ids, written in the same transaction as the work.
Broker-level dedupWhat Kafka and friends provide — real, useful, and bounded to the broker.
Out-of-order writesDuplicates are not the only hazard — a redelivered older message can overwrite a newer state.
External side effectsEmails, charges and webhooks leave your transaction boundary — and your guarantees with it.

Essential code patterns

The store

CREATE TABLE idempotency (
    tenant_id    uuid        NOT NULL,
    endpoint     text        NOT NULL,
    key          text        NOT NULL,
    fingerprint  bytea       NOT NULL,      -- hash of the canonical request body
    state        text        NOT NULL,      -- 'in_flight' | 'done'
    status_code  int,
    response     jsonb,
    created_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, endpoint, key)  -- scoped, never global
);

CREATE INDEX ix_idem_expiry ON idempotency (created_at);   -- for pruning
Scoping to the tenant is a security property, not tidiness: a global key space lets one caller collide with another's key.
-- claim atomically; the unique constraint decides who does the work
INSERT INTO idempotency (tenant_id, endpoint, key, fingerprint, state)
VALUES (@tenant, @endpoint, @key, @fingerprint, 'in_flight')
ON CONFLICT (tenant_id, endpoint, key) DO NOTHING
RETURNING 1;

-- 1 row  -> first attempt, go and do the work
-- 0 rows -> a duplicate: read the existing row and decide what to return
Check-then-act has a race that low-backoff retries hit regularly. Let the database arbitrate instead.

The server side, in C#

app.MapPost("/charges", async (ChargeRequest req, HttpContext ctx, AppDb db) =>
{
    var key = ctx.Request.Headers["Idempotency-Key"].ToString();
    if (string.IsNullOrWhiteSpace(key)) return Results.BadRequest("Idempotency-Key required");

    var tenant      = ctx.User.FindFirstValue("tid")!;     // from the token, never the body
    var fingerprint = SHA256.HashData(JsonSerializer.SerializeToUtf8Bytes(req));

    await using var tx = await db.Database.BeginTransactionAsync();

    var claimed = await db.TryClaimAsync(tenant, "/charges", key, fingerprint);
    if (!claimed)
    {
        var existing = await db.GetIdempotencyAsync(tenant, "/charges", key);

        if (!existing.Fingerprint.SequenceEqual(fingerprint))
            return Results.UnprocessableEntity("key reused with a different body");  // 422

        return existing.State == "done"
            ? Results.Json(existing.Response, statusCode: existing.StatusCode)        // replay
            : Results.StatusCode(409);                                                // in flight
    }

    var charge = await payments.ChargeAsync(req, idempotencyKey: key);   // pass it onward
    await db.CompleteIdempotencyAsync(tenant, "/charges", key, 201, charge);
    await tx.CommitAsync();                 // effect and dedup record commit together

    return Results.Created($"/charges/{charge.Id}", charge);
});
Four outcomes, all explicit: first attempt, replay, in-flight, and key reuse. The commit is what makes it correct.
@app.post("/charges", status_code=201)
async def create_charge(req: ChargeRequest, request: Request, conn=Depends(db)):
    key = request.headers.get("Idempotency-Key")
    if not key:
        raise HTTPException(400, "Idempotency-Key required")

    tenant = request.state.tenant_id                        # from the validated token
    fingerprint = hashlib.sha256(req.model_dump_json().encode()).digest()

    async with conn.transaction():
        claimed = await try_claim(conn, tenant, "/charges", key, fingerprint)
        if not claimed:
            row = await get_idempotency(conn, tenant, "/charges", key)
            if row["fingerprint"] != fingerprint:
                raise HTTPException(422, "key reused with a different body")
            if row["state"] != "done":
                raise HTTPException(409, "in flight")
            return JSONResponse(row["response"], status_code=row["status_code"])

        charge = await payments.charge(req, idempotency_key=key)   # propagate the key
        await complete(conn, tenant, "/charges", key, 201, charge)
        return charge
Note the key being passed on to the payment provider: your idempotency is only as good as the next hop's.

The client side

// generate ONCE per operation, outside the retry loop
var key = Guid.CreateVersion7().ToString();

await pipeline.ExecuteAsync(async ct =>        // Polly: retries, backoff, jitter
{
    using var req = new HttpRequestMessage(HttpMethod.Post, "/charges")
    {
        Content = JsonContent.Create(charge),
    };
    req.Headers.Add("Idempotency-Key", key);   // same value on every attempt
    return await http.SendAsync(req, ct);
});

// generating it inside the loop is the single most common bug:
// three attempts, three keys, three charges.
The key belongs to the intent, not the attempt. Put it outside the retry or the whole mechanism silently does nothing.
key = str(uuid.uuid4())             # once, before the first attempt

@retry(wait=wait_random_exponential(multiplier=0.2, max=5),
       stop=stop_after_attempt(4), reraise=True)
async def charge_once():
    res = await client.post("/charges", json=body,
                            headers={"Idempotency-Key": key})   # closure: same key
    res.raise_for_status()
    return res.json()
Capturing the key in the closure keeps it stable across attempts, which is exactly the property the server relies on.

The consumer side: an inbox

// dedup and the business change in ONE transaction — that is the whole trick
await using var tx = await db.Database.BeginTransactionAsync(ct);

var inserted = await db.Database.ExecuteSqlAsync(
    $"INSERT INTO inbox (message_id) VALUES ({msg.MessageId}) ON CONFLICT DO NOTHING");

if (inserted == 0) { await tx.CommitAsync(ct); return; }   // already handled — ack and move on

await CreateShipmentAsync(msg, ct);
await tx.CommitAsync(ct);
Recording the id in Redis and then writing to the database leaves a crash window that reintroduces the duplicate.
# guard against out-of-order redelivery as well as duplicates
UPDATE order_view
   SET status = :status, seq = :seq
 WHERE order_id = :order_id
   AND seq < :seq;        -- an older redelivery changes nothing

# dedup alone would let a stale retry revert a newer state
Duplicates are only half the problem. A sequence guard makes the write both idempotent and order-insensitive.

Window and pruning

-- window = client retries + broker redelivery + replay margin, then round up
-- 5 min + 1 h + 12 h  ->  24 h

DELETE FROM idempotency
 WHERE created_at < now() - interval '24 hours'
   AND ctid IN (SELECT ctid FROM idempotency
                 WHERE created_at < now() - interval '24 hours' LIMIT 10000);

-- or partition by day and drop partitions: instant, and no vacuum debt
Storage is rate × window. At 1,000/s over 24 hours that is 86M rows, so keep the row narrow and prune on a schedule.
# Redis, when the effect lives elsewhere and a short window is enough
ok = await redis.set(f"idem:{tenant}:{key}", "in_flight", nx=True, ex=86400)
if not ok:
    ...   # duplicate or in flight

# NOTE: this is NOT atomic with your database write. If the process dies
# between the SET and the commit, the key is claimed and the work never happened.
Fast and self-expiring, but a second store. Use it for read-mostly dedup, not where the effect must be transactional.

Kafka, and what it does not cover

# producer: a retry no longer creates a duplicate record
enable.idempotence=true          # producer id + sequence numbers, per partition
acks=all
max.in.flight.requests.per.connection=5

# read-process-write atomically, within Kafka only
transactional.id=orders-processor-1
isolation.level=read_committed   # on the consumer side
Real and useful — and it stops at the broker. A consumer that charges a card still needs its own idempotency key.

Pros & cons

Pros

  • Makes retries safe, which makes every other resilience pattern usable.
  • Turns an ambiguous timeout into a question the client can simply re-ask.
  • Response replay means a retry is transparent — the client gets the original answer.
  • A unique constraint does most of the work; the mechanism is small.
  • Protects against operator replays and broker redelivery, not just client retries.
  • Gives "exactly-once" semantics without pretending exactly-once delivery exists.

Cons

  • A lookup and a write on the hot path of every mutating request.
  • The dedup table grows with traffic and must be pruned deliberately.
  • The window is a correctness boundary that is easy to size wrongly.
  • Only works if the dedup record is atomic with the effect — often it is not.
  • External side effects escape the guarantee entirely.
  • Clients must generate the key correctly, and the common bug is silent.

Concrete use cases

The double charge

A payment request times out after the charge succeeded. The client retries with the same idempotency key, the provider recognises it and returns the original charge object. One charge, and the client gets a definitive answer instead of a guess.

A consumer rebalance

A Kafka consumer group rebalances and redelivers the last few messages. An inbox table keyed on message id means the shipments are not created twice, and the handler simply acknowledges and moves on.

The impatient user

Someone double-clicks "Place order". The browser sends two requests with the same key generated when the form was rendered, and the second gets the first's response — one order, no duplicate-detection logic in the UI.

Replaying a dead-letter queue

After a fix, 40,000 messages are replayed from the dead-letter queue. Those already processed are recognised and skipped; only the genuinely unhandled ones take effect — provided the dedup window covered the outage.

An importer run twice

A nightly import is accidentally started twice. A unique constraint on the source system's primary key makes the second run a no-op, with no window to size and no state to prune.

When to use / when not to

if anything in the path retries, every writer downstream needs this

Use it when…

  • The operation is not naturally idempotent and something might retry it.
  • A timeout would leave the caller unable to tell whether the work happened.
  • You consume from a broker — redelivery is a certainty, not a risk.
  • Money, stock or anything a human would notice is involved.
  • You might ever replay a queue or re-run an import.

Avoid it when…

  • The operation is already idempotent. Use absolute values and upserts — no key needed.
  • A natural unique key exists. Use a unique constraint; it never expires and needs no pruning.
  • Losing an item is genuinely fine. Use at-most-once and skip all of this.
  • Nothing can ever retry — no client retries, no broker, no operator. Use nothing, and be sure.
  • You are tempted to track a key for every read. Use it only on mutations.

Common mistakes & gotchas

Generating the key inside the retry loopEach attempt carries a fresh key, so the server sees three unrelated requests and performs the work three times. The mechanism is present, configured, and doing nothing.
Fix: generate the key once with the intent, before the first attempt, and capture it so every retry sends the same value. Test it by forcing a retry.
Dedup record not atomic with the effectWriting the key to Redis and the data to Postgres leaves a window where a crash keeps one and loses the other — either a duplicate or an operation that is recorded but never happened.
Fix: put the dedup row in the same database and the same transaction as the effect. If they must be separate stores, you need an outbox between them.
Check-then-act"Look up the key; if absent, process" races with itself. Two concurrent retries both find nothing and both do the work — and fast retries make this likely, not theoretical.
Fix: claim atomically with INSERT … ON CONFLICT DO NOTHING or Redis SET NX, and let the unique constraint decide which attempt proceeds.
A window shorter than the retry horizonA five-minute window with a broker that redelivers after an hour means the duplicate arrives looking brand new, and the work runs twice.
Fix: size the window from client retries + broker redelivery + any manual replay, then round up. Twenty-four hours is a good default.
Same key, different body, silently replayedA client reuses a key with a changed amount. Replaying the old response hides the new request entirely, and the caller believes something happened that did not.
Fix: store a fingerprint of the canonical body and return 422 when it differs. Never replay a response for a request you did not actually receive before.
Assuming the broker's "exactly-once" covers youKafka's guarantees end at the broker. The moment a consumer charges a card or sends an email, you are back to at-least-once with no protection.
Fix: treat broker guarantees as covering broker-to-broker only. Every external effect needs its own idempotency key or dedup record.
Deduplicating but ignoring orderA redelivered older message is not a duplicate of anything processed, so dedup lets it through — and it overwrites a newer state.
Fix: carry a sequence or version and guard the write with WHERE seq < @seq, so stale redeliveries are no-ops.
A dedup table nobody prunesAt a thousand operations a second it reaches tens of millions of rows in a day, slows its own lookups and eventually becomes the largest table in the database.
Fix: prune in batches on a schedule, or partition by day and drop partitions. Decide this when you create the table, not when it is 400 GB.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs idempotency keys
Idempotency keys + windowarbitrary client-initiated mutationsMediumfree; a table to prune—
Naturally idempotent designstate updatesVery lowfreeAbsolute values and upserts need no key at all — always prefer this where possible
Business key constraintwhen the domain has a unique idLowfreePermanent, no window, no pruning — strictly better when one exists
At-most-oncemetrics, telemetry, presenceVery lowfreeNo dedup needed because loss is acceptable; silent when it fails
Broker idempotence / transactionsread-process-write inside one brokerMediumfreeStrong within the broker, absent outside it
Two-phase commitlegacy XA resourcesHighfree; heavyTrue atomicity across systems, at the cost of locks and coupled availability
Reconciliationlow-value, detectable driftLowa nightly jobAllows duplicates and fixes them later; fine for reports, not for charges
  • Pick naturally idempotent operations wherever you can choose the shape of the write — it removes the problem instead of managing it.
  • Pick a business key when the domain provides one; no window, no pruning, no expiry edge case.
  • Pick at-most-once deliberately for telemetry, and never by accident for anything else.
  • Pick broker transactions for pipelines that stay inside the broker, and add your own dedup at every exit.
  • Pick reconciliation only where a duplicate is cheap to detect and cheap to undo.
