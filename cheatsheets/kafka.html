Apache Kafka

A distributed, append-only log for events: write once, read by many, replay any time.

As of Nov 2026 · release line 4.x (KRaft only)

Kafka stores streams of records (events such as "order paid" or "user signed up") in topics. A topic is split into partitions, and each partition is an ordered log on disk: new records are appended at the end and get an increasing number, the offset. Records are not removed when they are read; they stay until a retention limit (time or size) is reached.

Producers write records; consumers read them at their own pace and remember how far they got by committing offsets. Many independent applications can read the same topic, and a slow or new consumer can start from the beginning and replay history. Partitions are spread and replicated across several servers (brokers), which gives both horizontal scale and fault tolerance.

Kafka is the backbone of event-driven architectures, change data capture and real-time data pipelines. Since Kafka 4.0 the cluster manages its own metadata with the built-in KRaft protocol; ZooKeeper is gone. It is open source under the Apache 2.0 license, with managed offerings such as Confluent Cloud, Amazon MSK and Azure Event Hubs (Kafka-compatible API).

Architecture / mental model

Think of a topic as a set of append-only log files, copied to several machines. Producers append; consumers keep a bookmark (offset) per partition and read forward.

Key concepts

recordOne event: optional key, value (bytes), timestamp and headers. Kafka does not care about the format; JSON, Avro and Protobuf are common.
topicA named stream of records, like orders or user-signups. Roughly a table name for events.
partitionA topic is split into partitions. Each one is an ordered, append-only log and the unit of parallelism and ordering.
offsetThe position of a record inside a partition (0, 1, 2…). Never reused. Consumers track progress by offset.
brokerA Kafka server. It stores partition replicas on disk and serves producers and consumers. A cluster usually has 3 or more.
KRaft controllerThe built-in Raft quorum that manages cluster metadata and elects partition leaders. Replaced ZooKeeper, which was removed in Kafka 4.0.
replication factorHow many copies of each partition exist on different brokers. 3 is the usual production value.
leader / followerEach partition has one leader replica that handles reads and writes. Followers copy it and take over if it fails.
ISRIn-sync replicas: the followers that are caught up with the leader. Only they can become leader without data loss.
acksProducer setting for durability: 0 (fire and forget), 1 (leader only), all (every in-sync replica, the default since 3.0).
producerClient that writes records. It batches and compresses them, and picks the partition by hashing the key.
consumer groupConsumers sharing a group.id. Partitions are divided among them, so each record is processed by one member of the group.
committed offsetThe group's bookmark per partition, stored in the internal topic __consumer_offsets. A restart resumes from it.
rebalanceReassignment of partitions when consumers join, leave or crash. Processing pauses for affected partitions while it runs.
retentionHow long records are kept: by time (retention.ms, 7 days by default) or size, whether consumed or not.
log compactionAlternative cleanup policy that keeps only the latest record per key. Turns a topic into a changelog or table snapshot.
Kafka Connect / StreamsConnect moves data between Kafka and other systems (databases, S3). Streams is a Java library for processing topics into new topics.

Essential commands & syntax

Setup

docker run -d --name kafka -p 9092:9092 apache/kafka:4.0.0
Single-node KRaft broker for local development. CLI scripts live in /opt/kafka/bin inside the container.
docker exec -it kafka bash
cd /opt/kafka/bin
Open a shell where the kafka-*.sh tools are available. All tools take --bootstrap-server localhost:9092.

Topics

kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 1
Create a topic. Pick the partition count for your peak consumer parallelism; use RF 3 in production.
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
Shows each partition's leader, replicas and ISR.
kafka-configs.sh --bootstrap-server localhost:9092 --alter \
  --entity-type topics --entity-name orders --add-config retention.ms=604800000
Change a topic setting (here retention = 7 days).

Produce & consume

kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders \
  --property parse.key=true --property key.separator=:
Type user-42:paid to send a record with key user-42.
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders \
  --group billing --from-beginning --property print.key=true
Read as a member of group billing, starting from the oldest record.
from confluent_kafka import Producer
p = Producer({"bootstrap.servers": "localhost:9092", "acks": "all"})
p.produce("orders", key="user-42", value='{"status": "paid"}')
p.flush()
Python producer (pip install confluent-kafka). flush() waits for delivery.
from confluent_kafka import Consumer
c = Consumer({"bootstrap.servers": "localhost:9092", "group.id": "billing",
              "auto.offset.reset": "earliest", "enable.auto.commit": False})
c.subscribe(["orders"])
while True:
    msg = c.poll(1.0)
    if msg and not msg.error():
        handle(msg.value())
        c.commit(msg)
Python consumer with manual commit after processing: at-least-once delivery.

Operate & debug

kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group billing
Per partition: current offset, log end offset and LAG. The first thing to check when consumers fall behind.
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group billing \
  --topic orders --reset-offsets --to-earliest --execute
Replay a topic for a group (stop the consumers first). Also --to-datetime, --shift-by.
kafka-topics.sh --bootstrap-server localhost:9092 --list
List all topics, including internal ones like __consumer_offsets.

Pros & cons

Pros

  • Very high throughput (hundreds of MB/s per broker) thanks to sequential disk writes, batching and zero-copy reads.
  • Durable and replicated: records survive broker failures with RF 3 and acks=all.
  • Replayable history: new consumers can start from the beginning, and bugs can be fixed by reprocessing.
  • Decouples services: producers don't know who reads, and many consumer groups read the same data independently.
  • Scales horizontally by adding partitions and brokers.
  • Huge ecosystem: Connect, Streams, Debezium, Flink, and managed services on every cloud.

Cons

  • Operationally heavy: brokers, controllers, disks, partition planning, upgrades and monitoring.
  • Ordering is guaranteed only within a partition, not across a topic.
  • No per-message routing, priorities or delayed delivery like a classic queue.
  • Consumer parallelism is capped by the partition count, and changing it later breaks key-to-partition mapping.
  • Consuming correctly (commits, retries, idempotency, rebalances) is harder than it looks.
  • Overkill for low volumes: a few thousand messages a day don't need a distributed log.

Concrete use cases

Event-driven microservices

An e-commerce platform publishes OrderPlaced to Kafka. Billing, shipping, email and analytics each consume it in their own group, and new services can subscribe without touching the order service.

Change data capture (CDC)

Debezium reads PostgreSQL's write-ahead log and streams every row change into Kafka topics. A search index and a data warehouse stay in sync without dual writes in the application.

Log and metrics pipeline

Thousands of servers ship logs to Kafka, which absorbs traffic spikes. Downstream consumers load them into Elasticsearch and object storage at their own pace.

Real-time stream processing

A bank runs Kafka Streams or Flink over card transactions to flag fraud within seconds, joining the stream with customer profiles from a compacted topic.

Activity tracking

A media site records clicks and page views as events. Recommendation models and dashboards consume the same stream, and history can be replayed to train new models.

When to use / when not to

Rule of thumb: Kafka is a log you can replay, not a to-do list of jobs.

Use it when…

  • Several independent systems need the same stream of events.
  • You need to replay history, rebuild state or backfill a new consumer.
  • Volume is high (thousands to millions of events per second) and must survive broker failures.
  • You are building CDC, data pipelines or stream processing.
  • Per-key ordering matters (all events for user-42 in order).

Avoid it when…

  • You need a simple task queue with per-message acks, retries and delays. Use RabbitMQ or SQS.
  • Volume is low and the team is small. Use Redis Streams or a database table as a queue.
  • You need request/response between services. Use HTTP or gRPC.
  • You need ad-hoc queries over events. Store them in a database or warehouse (fed by Kafka if you like).
  • You can't run it well and have no managed option. Use a managed service such as Confluent Cloud, MSK or Event Hubs.

Common mistakes & gotchas

Number 3 has caused more duplicate emails than any other bug!
Expecting global ordering across a topicRecords in different partitions are read in parallel, in no particular order.
Fix: use a key for everything that must stay ordered (e.g. the order ID), so it always lands in the same partition.
More consumers than partitionsExtra consumers in the group get no partition and sit idle.
Fix: size partitions for peak parallelism up front (e.g. 6–12 for a busy topic).
Committing before processing (or auto-commit)A crash after the commit but before processing loses records. Committing after processing can produce duplicates.
Fix: disable auto-commit, commit after processing, and make handlers idempotent (dedupe by event ID).
Adding partitions to a keyed topichash(key) % partitions changes, so new records for a key land in a different partition than old ones. Per-key ordering breaks.
Fix: over-provision partitions at creation, or migrate to a new topic.
Slow processing triggers endless rebalancesIf poll() isn't called within max.poll.interval.ms (5 minutes by default), the consumer is kicked out and its partitions move.
Fix: process smaller batches (max.poll.records), move slow work to a worker pool, or raise the interval.
Replication factor 1 in productionLosing one disk or broker loses the partition's data.
Fix: RF 3, min.insync.replicas=2, acks=all.
Sending large payloadsThe default maximum message size is about 1 MB. Big messages slow down the whole cluster.
Fix: put files in object storage and send a reference (the claim-check pattern).
Ignoring consumer lagConsumers fall behind silently until retention deletes records they never read.
Fix: alert on lag per group (kafka-consumer-groups.sh --describe, Burrow, or your cloud's metrics).

  • Pick RabbitMQ if you need a job queue with per-message acks, routing keys, priorities or delays.
  • Pick Redpanda if you want the Kafka API and ecosystem but fewer moving parts to operate.
  • Pick Pulsar if you need strong multi-tenancy or geo-replication built in.
  • Pick Kinesis or Event Hubs if you're all-in on one cloud and don't want to run brokers.
  • Pick Redis Streams or NATS if volumes are modest and simplicity matters more than long retention.
