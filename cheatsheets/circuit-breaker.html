Circuit breaker

Stop calling the thing that is broken. You are not helping it, and it is destroying you.

As of Nov 2026 · named by Michael Nygard in Release It!, 2007 · examples use Polly, Resilience4j and Envoy

When a dependency starts failing, the instinct of most code is to keep calling it — and to retry. Each call now costs a full timeout instead of 20 milliseconds, so the caller's threads, connections and memory fill up with work that is guaranteed to fail. Within a minute the caller is also unavailable, including for requests that never needed the broken dependency at all. That is a cascading failure, and it is how one small outage becomes a site-wide one.

A circuit breaker is a small state machine wrapped around a dependency. While calls succeed it is closed and traffic flows. When the failure rate crosses a threshold it opens, and every subsequent call fails immediately without touching the network — one millisecond instead of two seconds. After a cooldown it goes half-open, letting a handful of trial calls through: if they succeed it closes again, and if they fail it reopens.

Note what it does not do: it does not fix the dependency, and it does not make your feature work. It converts a slow, expensive, resource-consuming failure into a fast, cheap, predictable one — which is precisely what you need in order to do something sensible instead, whether that is a fallback value, a cached answer or a degraded page. Its natural partner is the bulkhead, which bounds how much of your capacity any one dependency can occupy in the first place.

Key concepts

Circuit breakerA state machine around a dependency that stops calling it once it is clearly failing, and probes later to see whether it recovered.
ClosedThe normal state: calls pass through and their outcomes are recorded in a rolling window.
OpenThe tripped state: calls fail immediately without touching the dependency.
Half-openThe trial state: a strictly limited number of calls are allowed through to test whether the dependency has recovered.
Failure thresholdThe rate and volume of failures that trip the breaker — expressed as a percentage over a minimum number of calls.
Minimum throughputThe requirement that enough calls have been seen before the breaker is allowed to trip.
Rolling windowThe recent history the failure rate is computed over — by count or by time.
What counts as a failureThe most consequential configuration choice, and the one most often left at its default.
Slow-call breakerTripping on latency as well as errors, because a dependency that answers in eight seconds is broken even if it answers correctly.
TimeoutThe prerequisite: a breaker cannot count a failure that never finishes.
BulkheadA bounded pool per dependency, so no single one can occupy all your workers while it fails.
FallbackWhat you actually do when the breaker is open — the part that turns a fast failure into a working product.
Breaker per dependencyOne breaker per downstream service — and often per endpoint — never one global breaker.
Outlier detectionPassive per-instance health checking: eject the single bad replica instead of tripping on the whole service.
Retries and breakersThey interact badly unless you decide which sits inside which.
Half-open stampedeThe failure where recovery itself re-breaks the dependency, over and over.
ObservabilityState transitions are incidents in their own right, and should be visible as events rather than inferred from error graphs.

Essential code patterns

The whole stack, in order (.NET / Polly)

var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    // 5 — do something useful when it fails
    .AddFallback(new FallbackStrategyOptions<HttpResponseMessage> {
        FallbackAction = _ => Outcome.FromResultAsValueTask(CachedCatalogue()) })
    // 3 — stop calling once it is clearly broken
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<HttpResponseMessage> {
        FailureRatio      = 0.5,                        // 50% …
        MinimumThroughput = 20,                         // … of at least 20 calls
        SamplingDuration  = TimeSpan.FromSeconds(30),
        BreakDuration     = TimeSpan.FromSeconds(30),
        ShouldHandle      = args => ValueTask.FromResult(IsTransient(args.Outcome)),
    })
    // 2 — bound how much of me this dependency may occupy
    .AddConcurrencyLimiter(permitLimit: 5)
    // 1 — a call that never ends is never counted
    .AddTimeout(TimeSpan.FromSeconds(2))
    .Build();
Polly applies strategies outermost-first, so this reads bottom-up at execution time: timeout, bulkhead, breaker, fallback.
static bool IsTransient(Outcome<HttpResponseMessage> o) =>
    o.Exception is TimeoutRejectedException or HttpRequestException
    || (int?)o.Result?.StatusCode >= 500;      // 5xx only

// NOT failures: 400, 404, 409, 422 — the dependency answered correctly.
// Counting those lets one client with bad input disable a feature for everyone.
The single most important line of breaker configuration, and the one most often left at a permissive default.

Slow calls are failures (Java / Resilience4j)

CircuitBreakerConfig.custom()
    .slidingWindowType(SlidingWindowType.TIME_BASED)
    .slidingWindowSize(30)                 // seconds
    .minimumNumberOfCalls(20)
    .failureRateThreshold(50)              // percent
    .slowCallRateThreshold(50)             // percent …
    .slowCallDurationThreshold(Duration.ofSeconds(2))   // … slower than this
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .permittedNumberOfCallsInHalfOpenState(3)           // the probe limit
    .build();
A dependency returning 200s in eight seconds will exhaust your workers without raising a single error. The slow-call threshold is what catches it.

Go

cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "payments",
    MaxRequests: 3,                         // probes allowed in half-open
    Interval:    30 * time.Second,          // rolling window
    Timeout:     30 * time.Second,          // break duration
    ReadyToTrip: func(c gobreaker.Counts) bool {
        return c.Requests >= 20 &&
            float64(c.TotalFailures)/float64(c.Requests) > 0.5
    },
    OnStateChange: func(name string, from, to gobreaker.State) {
        log.Warn("breaker", "dep", name, "from", from, "to", to)   // alert on this
    },
})

resp, err := cb.Execute(func() (any, error) { return client.Do(req) })
if errors.Is(err, gobreaker.ErrOpenState) { return cachedCatalogue(), nil }
`MaxRequests` is the probe limit, and `ReadyToTrip` carries the minimum-throughput guard that stops a quiet endpoint tripping on one bad call.

In the mesh: eject bad instances

# Envoy — a breaker trips on the whole service; this ejects one bad host
outlier_detection:
  consecutive_5xx: 5
  interval: 10s
  base_ejection_time: 30s
  max_ejection_percent: 50        # never eject everything

circuit_breakers:                  # Envoy's "breaker" is really a bulkhead
  thresholds:
    - priority: DEFAULT
      max_connections: 100
      max_pending_requests: 50
      max_requests: 100
      max_retries: 3               # caps retry amplification at the proxy
One unhealthy pod out of six produces a 17% error rate — too low to trip a service-level breaker, and exactly what outlier detection is for.

# retry INSIDE the breaker  → 3 retries = 3 recorded failures = trips 3× too fast
# retry OUTSIDE the breaker → retries the instant rejections = a busy loop

A breaker opening is one of the highest-signal events available — it almost always precedes the user-visible symptoms.

Pros & cons

Pros

  • Stops a failing dependency from consuming the caller's threads, connections and memory.
  • Contains the blast radius: one broken feature instead of a whole service.
  • Gives the struggling dependency silence, which is often what it needs to recover.
  • Produces a fast, deterministic failure that a fallback or degraded mode can rely on.
  • State transitions are high-signal alerts that usually precede user-visible symptoms.
  • Available as a few lines of configuration in every mainstream library and proxy.

Cons

  • Fixes nothing on its own — without a fallback it just fails faster.
  • Misconfigured thresholds either never trip or disable healthy features.
  • Counting 4xx as failures lets one client's bad input break everybody's feature.
  • Needs enough traffic to see a rate; quiet endpoints need health checks instead.
  • Half-open probes can stampede a recovering service across a large fleet.
  • Interacts badly with retries unless the ordering is deliberate.

Concrete use cases

A payment provider degrading

The provider starts timing out at two seconds. Without a breaker every worker fills with payment calls and the whole storefront stops. With one, payment calls fail in a millisecond, browsing is untouched, and checkout shows an honest "try again shortly" instead of hanging.

One bad pod out of six

A single replica has a corrupted cache and returns 500s. The aggregate error rate is 17% — too low to trip a breaker. Outlier detection in the mesh ejects that instance for thirty seconds and the error rate returns to zero without anyone being paged.

Optional enrichment on a hot path

A personalisation service is nice to have and frequently slow. A tight timeout, a bulkhead of three, and an aggressive breaker mean it either answers in 50 ms or is skipped entirely — and the page renders either way.

Letting a database recover

A database is overwhelmed and every query times out. Retrying keeps it pinned. The breaker opens, queries stop entirely for thirty seconds, the backlog drains, and a probe finds it healthy — a recovery that could not have happened under continuous load.

Third-party API with a monthly incident

A shipping-rates API fails for twenty minutes every few weeks. The breaker opens, a cached rate table serves as the fallback, and customers see slightly stale shipping prices instead of a broken checkout. Nobody is paged.

When to use / when not to

timeout first, then bulkhead, then breaker — a breaker without a timeout protects nothing

Use it when…

  • You call a remote dependency that can fail or slow down independently of you.
  • A dependency's failure would otherwise exhaust your threads, connections or pool.
  • There is something sensible to do instead — a cache, a default, a reduced feature.
  • The dependency benefits from being left alone while it recovers.
  • Traffic is high enough that a failure rate is statistically meaningful.

Avoid it when…

  • The call is local and in-process. Use ordinary error handling.
  • Traffic is too low to compute a rate. Use active health checks and timeouts.
  • The dependency is slow rather than failing, and you can simply go slower. Use backpressure.
  • The problem is your own overload, not theirs. Use load shedding.
  • One instance is bad rather than the whole service. Use outlier detection in the proxy or load balancer.
  • There is no possible fallback and the feature is critical. Use a breaker with a short break and accept that it only protects the caller.

Common mistakes & gotchas

No timeout underneath itA breaker can only count calls that finish. With no timeout — the default in several HTTP clients — calls hang indefinitely, the breaker stays closed, and your workers disappear one by one.
Fix: set a timeout on every call, covering connect, TLS, send and read, and keep it below your own deadline. The breaker is the third layer, not the first.
Counting 4xx as failuresOne client sending malformed requests drives the failure rate past the threshold, the breaker opens, and a perfectly healthy dependency becomes unavailable for every other caller.
Fix: only timeouts, connection errors, 5xx and slow calls count. 400, 404, 409 and 422 mean the dependency answered correctly.
Ignoring slow successesAn error-only breaker sits closed while a dependency returns 200s in eight seconds and quietly consumes every worker you have. This is the most common cascading failure in practice.
Fix: add a slow-call threshold, or a timeout that converts slowness into a countable failure. Slow is broken.
A breaker with no fallbackYou have replaced a slow error with a fast error. Your infrastructure is happier; the user sees the same broken page.
Fix: decide the fallback before configuring the breaker — stale cache, a default, or omitting the section. If there genuinely is none, say so explicitly in the UI.
Half-open stampedeFifty instances trip together and probe together thirty seconds later. The recovering service is hit by a synchronised burst, dies, and the cycle repeats indefinitely.
Fix: cap concurrent probes at one to three per instance, jitter the break duration, and lengthen it after each failed probe.
Retry on the wrong sideRetries inside the breaker make it trip three times faster than configured; retries outside it loop on instant rejections.
Fix: record one outcome per logical call, and mark the open-circuit exception as non-retryable in your retry policy.
One breaker for everythingA shared breaker couples unrelated dependencies, so a failing recommendations service disables your payment calls.
Fix: one breaker per dependency, and per endpoint when their cost or reliability differ. Add outlier detection for per-instance problems.
Tripping on a quiet endpointAt 02:00 an endpoint gets two calls, one fails, and a 50% failure rate disables the feature until the morning.
Fix: require a minimum throughput — typically twenty calls — before the breaker may trip at all.

MechanismBest forComplexityCost / licenseKey difference vs a circuit breaker

Bulkheadcontaining blast radiusLowfreeCaps how much you lose while failing; does not stop calling. Use both

Load sheddingyour own overloadMediumfreeRefuses inbound work; a breaker refuses outbound calls

  • Pick a timeout first, always — it is the foundation everything else is built on.
  • Pick a bulkhead alongside the breaker; it protects you during the window before the threshold is reached.
  • Pick outlier detection when failures are concentrated in one instance rather than the service.
  • Pick backpressure when the dependency still works and you can simply go at its pace.
  • Pick retries only for short transient errors, with jitter and a budget — and never inside the breaker.
