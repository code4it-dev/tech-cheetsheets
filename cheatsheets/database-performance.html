Database performance

Index, then query, then schema, then cache, then replicate, then partition — and only then shard.

As of Nov 2026 · examples are PostgreSQL 18 flavoured; the principles carry to MySQL, SQL Server and most engines

Almost every "the database is slow" incident has the same small set of causes: a query reading far more rows than it returns, an N+1 loop in the application, a connection pool that is the wrong size for the work, or a working set that stopped fitting in RAM. The fixes are cheap and local. The expensive fixes — partitioning, sharding, a second datastore — are the ones teams reach for first, and they rarely address the actual cause.

So the useful mental model is a ladder, climbed in order of cost. Add the missing index. Fix the query that cannot use one. Change the schema so the hot path is one row. Cache what is read far more than written. Move reads to a replica. Partition when a single table is too large to maintain. Shard only when one machine genuinely cannot hold the write load — because sharding gives up joins, transactions and most of your operational simplicity.

Underneath all of it is one invariant worth memorising: a query is fast when it touches few pages, and a system is stable when concurrency is bounded. Indexes are about the first. Connection pools are about the second, and are governed by Little's Law rather than by optimism.

Architecture / mental model

Cheap fixes are local and reversible; expensive ones change your data model forever. Work down the list, not up it.

Key concepts

B-tree indexA balanced tree that turns "find rows matching this value" into a handful of page reads instead of a full table scan.
SelectivityThe fraction of rows a predicate keeps. Low fraction means an index helps; high fraction means it does not.
Composite indexAn index on several columns, usable only from the leftmost column onwards — the "leftmost prefix" rule.
Covering indexAn index that contains every column the query needs, so the table itself is never read.
Query planThe strategy the planner chose, and the only reliable way to know why a query is slow.
Sequential scanReading every page of a table in order — slow for a needle, and the right choice for a haystack.
N+1 queriesOne query to fetch a list, then one more per item — the most common application-side performance bug.
Connection poolA bounded set of reusable database connections shared by application threads.
Pool sizingHow many connections you actually need: arrival rate times time held, by Little's Law — usually a much smaller number than teams expect.
PartitioningSplitting one logical table into physical pieces inside the same database, by range, list or hash.
Partition pruningThe planner skipping partitions that cannot contain matching rows — where the speed-up actually comes from.
ShardingSpreading one dataset across independent databases, each owning a subset of the rows.
Shard keyThe column that decides which shard a row lives on — the single most consequential and least reversible choice in a sharded system.
Read replicaA copy of the primary that serves reads, with a replication lag you must design around.
Lock contentionTransactions waiting on each other's row or table locks — latency that no index will fix.
Working setThe pages actually touched by your queries. Performance falls off a cliff when it stops fitting in RAM.
Bloat & vacuumDead row versions left by updates and deletes, and the background work that reclaims them.

Essential commands & SQL

Find the problem

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, total FROM orders
WHERE customer_id = 4711 AND placed_at > '2026-01-01';
The plan plus what actually happened. Compare estimated and actual rows, and watch the buffer counts.
SELECT calls, mean_exec_time, total_exec_time, rows, query
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  20;
Total time, not mean time: the query that takes 3 ms and runs a million times is usually the real problem.
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       n_live_tup, n_dead_tup
FROM   pg_stat_user_tables
ORDER  BY seq_tup_read DESC LIMIT 20;
Tables being scanned sequentially, and dead-tuple counts that reveal bloat.
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM   pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY 3 DESC;
Indexes nobody has used: pure write tax and wasted cache. Drop them (after checking every replica).
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start AS age, left(query, 60)
FROM   pg_stat_activity
WHERE  state <> 'idle' ORDER BY age DESC;
Live sessions, what they are waiting on, and the long transaction that is blocking vacuum.

Indexes

CREATE INDEX CONCURRENTLY ix_orders_cust_date
    ON orders (customer_id, placed_at DESC);
Equality column first, range/sort column second. CONCURRENTLY avoids locking writes — it is slower and can fail, so check validity afterwards.
CREATE INDEX CONCURRENTLY ix_orders_cust_date_inc
    ON orders (customer_id, placed_at DESC) INCLUDE (total, status);

CREATE INDEX CONCURRENTLY ix_orders_open
    ON orders (placed_at) WHERE status = 'open';
A covering index for an index-only scan, and a partial index that only stores the rare, hot subset.
ANALYZE orders;                                  -- refresh statistics
ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 500;
REINDEX INDEX CONCURRENTLY ix_orders_cust_date;  -- rebuild a bloated index
Fix the planner's information before adding more indexes — many "missing index" problems are mis-estimates.

Partitioning

CREATE TABLE orders (
    id bigint, customer_id bigint, placed_at timestamptz NOT NULL, total numeric
) PARTITION BY RANGE (placed_at);

CREATE TABLE orders_2026_11 PARTITION OF orders
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
Range partitioning by time: the key must be in the predicate for pruning to work, and in the primary key.
-- retention becomes metadata, not a 400M-row DELETE
ALTER TABLE orders DETACH PARTITION orders_2025_11;
DROP TABLE orders_2025_11;

-- confirm pruning actually happens
EXPLAIN SELECT count(*) FROM orders WHERE placed_at >= '2026-11-01';
The real win of partitioning: instant retention, and plans that touch one partition instead of thirty-six.

Connection pools

# Npgsql (.NET) — small pool, fail fast
Host=db;Database=app;Maximum Pool Size=15;Minimum Pool Size=2;
Timeout=5;Command Timeout=10;Connection Idle Lifetime=300
Remember to multiply by the number of instances: 10 pods x 15 = 150 connections at the server.
# HikariCP (JVM)
maximumPoolSize = 20          # cores * 2 + effective spindles
connectionTimeout = 3000      # ms — fail fast instead of piling up
leakDetectionThreshold = 20000
A small pool is a concurrency limiter. Raising it when it saturates moves the queue onto the database.
# PgBouncer in transaction mode, in front of Postgres
[databases]
app = host=db dbname=app
[pgbouncer]
pool_mode = transaction
default_pool_size = 20
max_client_conn = 2000
Lets thousands of clients share a few dozen server connections. Transaction mode forbids session state — no server-side prepared statements or advisory locks across statements.
// dotnet add package Npgsql
await using var source = NpgsqlDataSource.Create(
    "Host=db;Database=app;Maximum Pool Size=15;Timeout=5;Command Timeout=10");

await using var conn = await source.OpenConnectionAsync(ct);   // returned on dispose
await using var cmd  = new NpgsqlCommand("SELECT total FROM orders WHERE id = $1", conn)
{
    Parameters = { new NpgsqlParameter { Value = orderId } },
};

var total = (decimal?)await cmd.ExecuteScalarAsync(ct);
NpgsqlDataSource owns the pool; await using returns the connection even on an exception. A leaked connection is a pool of one.
from psycopg_pool import ConnectionPool

pool = ConnectionPool(DSN, min_size=2, max_size=15, timeout=5)

with pool.connection() as conn:           # always context-managed
    with conn.cursor() as cur:
        cur.execute("SELECT total FROM orders WHERE id = %s", (order_id,))
A leaked connection is a pool of one. Context managers, and leak detection, are not optional.

Safety rails

ALTER ROLE app SET statement_timeout = '10s';
ALTER ROLE app SET idle_in_transaction_session_timeout = '30s';
ALTER ROLE app SET lock_timeout = '3s';
Three settings that convert a slow query into a failed request instead of a full outage.

Pros & cons

Pros of working down the ladder

  • Indexes and query fixes are reversible, local and usually deliver the largest single improvement.
  • Right-sizing the pool costs one config change and prevents an entire class of cascading failure.
  • Partitioning turns retention and maintenance from multi-hour jobs into metadata operations.
  • Replicas scale reads without touching the schema or the application's data model.
  • Every step keeps one logical database, so joins and transactions still work.
  • The diagnosis tools are built in: the plan and the statistics views tell you where the time went.

Cons and costs

  • Every index is a tax on every write and competes for the buffer cache.
  • Partitioning only helps if the partition key is in your predicates; otherwise it is pure overhead.
  • Sharding loses cross-shard joins, transactions and unique constraints, and multiplies all operations.
  • Replicas add lag, so read-your-own-writes has to be handled explicitly.
  • Plans change on their own as data grows — tuning is never finished.
  • Tuning in a staging environment with 1% of the data regularly produces the wrong conclusion.

Concrete use cases

The 2 a.m. "pool exhausted" page

Errors say the connection pool timed out, so someone raises it from 20 to 100 and latency gets worse. The plan shows a deploy removed an index; queries went from 40 ms to 900 ms, so the number of connections needed went from 4 to 90. Restoring the index fixes the pool incident without touching the pool.

A list page that got slow as the company grew

A dashboard query was fine at 200,000 rows and takes 3 seconds at 20 million. The plan shows a sequential scan: the index exists but the query wraps the column in a function, so it cannot be used. Rewriting the predicate restores a 4 ms index scan.

Retention on an events table

A nightly DELETE FROM events WHERE created_at < now() - interval '90 days' runs for hours, bloats the table and starves autovacuum. Range-partitioning by week turns it into DROP TABLE per partition: instant, no bloat, no vacuum debt.

Reports crushing the transactional database

Analysts run heavy aggregations against the primary and checkout latency rises at month end. Routing those queries to a read replica isolates them completely; the lag of a few hundred milliseconds is irrelevant for a report.

A multi-tenant table with one enormous tenant

Average query time looks fine while the largest tenant times out. List-partitioning by tenant_id with the whales on their own partitions — and per-tenant limits — fixes the tail without sharding the whole system.

When to use / when not to

measure first: read the plan, then change one thing, then measure again

Reach for each step when…

  • Index: the plan shows a sequential scan and the predicate keeps under ~5% of the rows.
  • Query rewrite: rows examined vastly exceeds rows returned, or the request issues dozens of round trips.
  • Pool sizing: connection waits appear, or Little's Law says you need more than you have.
  • Cache / replica: reads dominate writes by an order of magnitude and some staleness is acceptable.
  • Partition: a single table has grown past comfortable maintenance, and queries filter on the partition key.
  • Shard: one primary cannot absorb the write volume or the data no longer fits, after everything above.

Avoid when…

  • Indexing a low-cardinality column for a query that returns half the table. Use a partial index, or nothing.
  • Partitioning a table whose queries never filter on the key. Use better indexes.
  • Sharding to make queries faster. Use indexes, caching and replicas — sharding addresses write and storage limits, not latency.
  • Enlarging the pool because it saturates. Use a faster query, or load shedding.
  • Tuning against a staging database with 1% of production data. Use a production-sized copy or the real plans.

Common mistakes & gotchas

Wrapping an indexed column in a functionWHERE lower(email) = ? or WHERE date(created_at) = ? cannot use a plain index on the column, so a perfectly good index sits unused while the table is scanned.
Fix: index the expression (CREATE INDEX ... ON t (lower(email))), or rewrite the predicate as a range: created_at >= d AND created_at < d + 1.
Enlarging the pool when it saturatesMore connections means more concurrent queries on the same cores, so each gets slower, so each is held longer — the classic congestion collapse.
Fix: keep the pool small, fail fast on acquisition, and fix the thing that made queries slower. A pool is a concurrency limiter, and that is a feature.
One index per columnSix single-column indexes serve fewer queries than two well-ordered composite ones, while costing six times the write amplification and cache.
Fix: design indexes from your actual query shapes, equality columns first. Drop indexes with zero scans in pg_stat_user_indexes.
Partitioning on the wrong keyPartitioning by hash of the id while every query filters by date means no pruning at all: all the maintenance cost, none of the benefit, plus more planning time.
Fix: partition on what the predicates use, verify with EXPLAIN that one partition is scanned, and keep the partition count in the dozens, not thousands.
Choosing a timestamp as the shard keyAll of today's writes land on one shard, so you have the complexity of sharding and the throughput of a single machine.
Fix: shard on something with natural locality and even spread (hashed tenant_id or user_id), and model your top queries against it before committing.
Long transactions holding everything hostageA transaction opened before an HTTP call keeps locks and blocks vacuum for as long as the remote service takes, which bloats tables and stalls replicas.
Fix: never make a network call inside a transaction, and set idle_in_transaction_session_timeout so a stuck session cannot do it anyway.
Trusting averagesA mean query time of 20 ms hides a p99 of 4 seconds, and the p99 is what users and timeouts actually experience.
Fix: alert on percentiles and on total_exec_time from pg_stat_statements, not on means.
Creating indexes without CONCURRENTLY in productionA plain CREATE INDEX takes a lock that blocks writes for the whole build — minutes to hours on a large table.
Fix: use CREATE INDEX CONCURRENTLY, and check pg_index.indisvalid afterwards, because a concurrent build that fails leaves an invalid index behind.

ApproachBest forComplexityCost / licenseKey difference vs indexing and tuning

Read replicasread scaling, report isolationLowextra instancesMore capacity for the same queries; adds replication lag, no help for writes
Partitioningvery large tables, retentionMediumfreeMaintenance and locality rather than raw speed; needs the key in your predicates
Shardingwrite volume beyond one machineHighfree; operational cost largeThe only way past a single primary; loses joins and transactions

  • Pick caching when the same answers are read far more often than the data changes.
  • Pick read replicas when the queries are fine but there are too many, or reports are disturbing live traffic.
  • Pick partitioning when retention and maintenance hurt more than query latency does.
  • Pick sharding only when a single primary cannot absorb the writes — and expect to redesign your queries.
  • Pick a bigger machine without shame while you fix the real cause; vertical scaling is cheap compared to a rushed shard.
  • Pick a specialised store (search index, columnar warehouse, time-series DB) when an access pattern is fundamentally alien to a row store.
