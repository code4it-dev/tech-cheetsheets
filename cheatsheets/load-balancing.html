L4 vs L7 load balancing

One reads the envelope, the other opens the letter. That single difference explains every trade-off between them.

As of Nov 2026 · examples use nginx, HAProxy, Envoy, YARP and Kubernetes Gateway API

A layer 4 balancer works on TCP and UDP. It sees the five-tuple — source address and port, destination address and port, protocol — picks a backend, and forwards packets. It never looks inside, which is exactly why it is fast: the decision is made once per connection, often in the kernel or on dedicated hardware, and it works for any protocol including ones that have not been invented yet.

A layer 7 balancer terminates the connection and the TLS session, parses the request, and only then chooses. Now it can route on host, path, method, header or cookie; retry a failed request somewhere else; add X-Forwarded-For; rate limit per user; and balance per request rather than per connection. The cost is CPU, latency, per-connection state and a protocol it has to understand.

The question is almost never "which one" — most real systems run both, with L4 at the edge absorbing volume and L7 behind it making decisions. The question worth asking is where the boundary sits, and the trap worth knowing is that HTTP/2 and gRPC quietly break connection-level balancing: one long-lived connection carries thousands of requests, so an L4 balancer that spreads connections perfectly can still send 90% of your traffic to one backend.

Architecture / mental model

request, not per connection can: route, retry, rewrite, rate limit, cache costs: TLS work, CPU, state, latency and in practice, both — in that order client → DNS/anycast → L4 (volume, DDoS, any protocol) → L7 (routing, retries, per-request) → your service

L4 is a decision about a connection. L7 is a decision about a request. Everything else follows from which unit you can see.

Key concepts

L4 load balancingChoosing a backend from the TCP/UDP five-tuple, then forwarding packets without inspecting them.
L7 load balancingTerminating the connection, parsing the request, and choosing a backend per request.
Five-tuple hashingHow an L4 balancer picks: hash the connection's identity and map it onto a backend.
Request-level balancingChoosing per request rather than per connection — the thing HTTP/2 makes essential.
HTTP/2 imbalanceThe classic gRPC-behind-an-L4-balancer problem: even connections, wildly uneven load.
TLS terminationWhere encryption ends — and the thing that decides whether L7 features are available at all.
Balancing algorithmsRound robin, least connections, least response time — and why the obvious one is rarely best.
Power of two choicesSample two backends at random and take the less loaded one — nearly optimal, with no global state.
Health checksHow a balancer learns a backend is unfit — actively by probing, or passively by watching real traffic.
Connection drainingRemoving a backend gently: stop sending new work, let in-flight requests finish.
Slow startRamping traffic to a new backend instead of giving it a full share immediately.
Session affinityPinning a client to a backend — useful, and a constraint you pay for in every other dimension.
Consistent hashingMapping keys to backends so that adding or removing one moves only a small fraction of them.
Preserving the client IPBehind a balancer every request appears to come from the balancer — unless you arrange otherwise.
Direct server returnAn L4 technique where responses bypass the balancer and go straight to the client.
Global load balancingChoosing a region or a point of presence before any connection is made — DNS or anycast.
Retries at the balancerAn L7 balancer can resend a failed request to another backend — which is powerful and easy to misconfigure.
Where it runsHardware, cloud service, software proxy or sidecar — the same decisions at different places.

Essential config & code

L4: forward, do not look

# HAProxy in TCP mode — works for Postgres, Redis, gRPC, anything
frontend pg_in
    bind *:5432
    mode tcp                      # no parsing, no HTTP features
    default_backend pg_pool

backend pg_pool
    mode tcp
    balance leastconn
    option tcp-check              # the only health check available here
    server pg1 10.0.0.11:5432 check inter 2s
    server pg2 10.0.0.12:5432 check inter 2s backup
In mode tcp there is no path, no header and no retry — only a connection and a destination.
# Kubernetes: a Service is L4. This is kube-proxy/IPVS, not an HTTP proxy.
apiVersion: v1
kind: Service
spec:
  type: ClusterIP
  sessionAffinity: ClientIP        # L4 affinity: hashes the source address
  ports: [{ port: 80, targetPort: 8080 }]

# Which is why gRPC between pods via a Service load balances badly:
# one connection, one backend, for its whole lifetime.
The most common surprise in Kubernetes networking. A Service balances connections; your gRPC client opens one.

L7: parse, then decide

# nginx — routing by path, with per-request balancing over HTTP/1.1 keepalives
upstream api     { least_conn; server 10.0.1.11:8080; server 10.0.1.12:8080;
                   keepalive 32; }
upstream static  { server 10.0.2.11:8080; server 10.0.2.12:8080; }

server {
    listen 443 ssl http2;
    ssl_certificate /etc/ssl/site.pem;

    location /api/   { proxy_pass http://api;
                       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
                       proxy_next_upstream error timeout http_503; }   # retry elsewhere
    location /static/ { proxy_pass http://static; proxy_cache static_cache; }
}
Everything here needs the request parsed: the path match, the header, the cache and the retry.
# Envoy — per-request balancing for HTTP/2, plus passive health checking
clusters:
  - name: orders
    type: STRICT_DNS
    lb_policy: LEAST_REQUEST          # two random choices under the hood
    typed_extension_protocol_options:
      envoy.extensions.upstreams.http.v3.HttpProtocolOptions:
        explicit_http_config: { http2_protocol_options: {} }
    outlier_detection:                # eject a backend that starts failing
      consecutive_5xx: 5
      base_ejection_time: 30s
      max_ejection_percent: 50
    common_lb_config:
      healthy_panic_threshold: { value: 50 }   # below 50% healthy, ignore health and spray
Envoy balances each HTTP/2 stream separately, which is the fix for the imbalance in the second animation.

An L7 balancer in C#

// YARP — a reverse proxy you configure in code or JSON
builder.Services.AddReverseProxy().LoadFromMemory(
    routes:
    [
        new RouteConfig { RouteId = "api",    ClusterId = "api",
                          Match = new RouteMatch { Path = "/api/{**catch-all}" } },
        new RouteConfig { RouteId = "canary", ClusterId = "canary", Order = -1,
                          Match = new RouteMatch { Path = "/api/{**catch-all}",
                                                   Headers = [new RouteHeader {
                                                       Name = "x-canary", Values = ["1"] }] } },
    ],
    clusters:
    [
        new ClusterConfig
        {
            ClusterId = "api",
            LoadBalancingPolicy = LoadBalancingPolicies.PowerOfTwoChoices,
            HealthCheck = new HealthCheckConfig
            {
                Active = new ActiveHealthCheckConfig
                { Enabled = true, Interval = TimeSpan.FromSeconds(5), Path = "/healthz" },
            },
            Destinations = new Dictionary<string, DestinationConfig>
            {
                ["d1"] = new() { Address = "http://10.0.1.11:8080/" },
                ["d2"] = new() { Address = "http://10.0.1.12:8080/" },
            },
        },
    ]);

app.MapReverseProxy();
Header-based canary routing and per-request balancing, both of which need the request parsed — the definition of L7.

The picker, in both languages

// power of two choices: sample two at random, take the lighter one
sealed class P2CPicker(IReadOnlyList<Backend> backends)
{
    public Backend Pick()
    {
        if (backends.Count == 1) return backends[0];

        var a = backends[Random.Shared.Next(backends.Count)];
        var b = backends[Random.Shared.Next(backends.Count)];

        // InFlight is a local counter — no global view, so no herding
        return a.InFlight <= b.InFlight ? a : b;
    }
}
Six lines. It gets most of least-connections' quality with purely local state, which is why Envoy and Finagle default to it.
import random

def pick_p2c(backends):
    """Two random samples, take the less loaded. O(log log n) max load."""
    if len(backends) == 1:
        return backends[0]
    a, b = random.sample(backends, 2)
    return a if a.in_flight <= b.in_flight else b

def pick_least_conn(backends):
    """Accurate — and every balancer picks the SAME idle backend at once."""
    return min(backends, key=lambda x: x.in_flight)     # herding across replicas
The contrast is the point: perfect information produces a stampede when many balancers act on it simultaneously.

Draining, in the right order

// 1. fail readiness so the balancer stops sending   2. wait   3. then drain
app.MapGet("/healthz/ready", () => _shuttingDown ? Results.StatusCode(503) : Results.Ok());

lifetime.ApplicationStopping.Register(() =>
{
    _shuttingDown = true;                  // balancer notices on its next probe
    Thread.Sleep(TimeSpan.FromSeconds(10)); // give it time — this is the step people skip
});                                         // then the host drains in-flight requests
Without the wait, the instance disappears before the balancer has noticed, and every deploy emits a burst of 502s.

Diagnosing an imbalance

# requests per backend, not connections per backend — the distinction that matters
kubectl exec deploy/envoy -- curl -s localhost:15000/stats \
  | grep 'cluster.orders.*upstream_rq_total'

# if one backend has most of the requests while connections look even,
# you are balancing connections under HTTP/2
kubectl exec deploy/envoy -- curl -s localhost:15000/clusters | grep -E 'cx_active|rq_active'
Connection counts look healthy in exactly the case that matters. Always check request counts per backend.

Pros & cons

L4 — strengths

  • Extremely fast: decisions in the kernel or in hardware, at line rate.
  • Protocol-agnostic — databases, custom binary protocols, UDP, anything.
  • End-to-end TLS stays intact; the balancer never holds a certificate.
  • Very low latency added, and little per-connection state.
  • Absorbs volumetric attacks well, which is why it belongs at the edge.
  • Direct server return lets modest hardware front enormous bandwidth.

L4 — limits

  • Balances connections, so HTTP/2 and gRPC distribute badly.
  • No routing by path, host, header or cookie.
  • Cannot retry a request elsewhere — it never saw a request.
  • Health checks are shallow: a port is open, or it is not.
  • Client IP needs the PROXY protocol or DSR to survive.
  • No per-user rate limiting, caching or header manipulation.

L7 — strengths

  • Balances per request, which is correct under HTTP/2 and gRPC.
  • Routes on host, path, method, header or cookie — canaries and A/B included.
  • Retries, timeouts, circuit breaking and rate limiting at the edge.
  • Rich health signals, including passive ejection of failing instances.
  • Terminates TLS centrally, so certificates live in one place.
  • Adds X-Forwarded-For and request ids for free.

L7 — costs

  • CPU and latency per request, plus TLS termination work.
  • Per-connection and per-request state, so memory scales with load.
  • Must understand the protocol — useless for arbitrary TCP.
  • Decrypts your traffic, which is a trust and compliance decision.
  • Another process to run, tune, upgrade and debug.
  • A bad config change at this tier is a site-wide outage.

Concrete use cases

gRPC that will not spread

Three gateway replicas talk to twelve backends through a Kubernetes Service, and one backend sits at 90% CPU while others idle. Each gateway holds one HTTP/2 connection, and the L4 Service pinned it. A sidecar or an L7 proxy balancing per request fixes it immediately.

Fronting a database

Postgres replicas need a single endpoint. There is no HTTP to parse, so an L4 balancer in TCP mode with a leastconn policy and a TCP health check is exactly right — and an L7 proxy would be both useless and slower.

Canary by header

Route requests carrying x-canary: 1 to the new version and everything else to the stable pool. This requires reading the header, so it is only possible at L7 — and it makes a canary a config change rather than a deployment.

Absorbing an attack

A volumetric flood arrives. The L4 tier soaks it at line rate with no per-request parsing, while the L7 tier behind it continues doing path routing for legitimate traffic at a far lower volume.

502s on every deploy

Each rollout produces a burst of errors because instances vanish while requests are in flight. Failing readiness first, waiting for the balancer to notice, and only then draining removes them entirely — the missing step was the wait.

When to use / when not to

ask what unit you need to balance: a connection, or a request?

Use L4 when…

  • The protocol is not HTTP — databases, message brokers, custom binaries, UDP.
  • Throughput and latency matter more than routing intelligence.
  • TLS must stay end-to-end and the balancer should hold no keys.
  • You are absorbing volume or an attack at the edge.
  • Connections are short-lived, so connection balancing approximates request balancing.

Use L7 when…

  • Traffic is HTTP/2 or gRPC — connection balancing will not distribute it.
  • You need routing by path, host or header, or canary releases.
  • You want retries, timeouts or rate limiting applied centrally.
  • Backends differ in capability, so requests must go to the right pool.
  • You need real client identity, request ids and useful access logs.

Common mistakes & gotchas

Balancing HTTP/2 at L4Connections distribute perfectly while requests do not distribute at all. One backend takes most of the traffic, and newly scaled instances receive none until someone opens a new connection.
Fix: balance per request with an L7 proxy or a sidecar. If you cannot, set a max connection age or max requests per connection so clients re-dial periodically.
Health checks that are too shallow or too deepA TCP connect says only that a port is open. A readiness check that calls a shared database fails every instance at once when that database is slow — the check becomes the outage.
Fix: liveness stays shallow, readiness covers only what this instance needs, and dependency problems are handled with outlier detection rather than mass ejection.
No wait before drainingThe instance stops accepting connections before the balancer has noticed it is unhealthy, so in-flight and newly routed requests fail. Every deploy emits 502s.
Fix: fail readiness first, wait longer than the probe interval, then drain. The wait is the step almost everyone omits.
Trusting X-Forwarded-ForIt is a client-supplied header. Rate limits, geo-rules and audit logs built on an untrusted value are bypassed by setting the header.
Fix: count hops from the right, trusting only the proxies you control, and strip inbound copies at the edge. Use the PROXY protocol for L4.
Sticky sessions by defaultAffinity gives up even distribution, easy scale-out and clean draining — usually to avoid moving session state that could have lived in Redis.
Fix: make instances stateless and drop affinity. Keep it only for genuinely stateful connections, and use cookie-based affinity rather than source IP.
Least-connections across many balancersEach balancer independently sees the same idle backend and sends to it, so the "least loaded" instance is instantly the most loaded. Perfect information, herd behaviour.
Fix: power of two choices. Two random samples, take the lighter — nearly as good, with no global view and no stampede.
No slow startA cold instance gets a full share immediately, runs slowly, and with least-connections attracts even more traffic because it has few open connections.
Fix: enable slow start with a 30–60 second ramp, and make sure readiness only passes once caches and pools are warm.
Retries at the balancer and in the clientThe proxy retries twice, the client retries three times, and the service retries as well. The multiplier is the product, and nobody owns the number.
Fix: pick one layer. If the balancer retries, make clients fail fast, and set a retry budget at the proxy so a broad failure cannot multiply load.

  • Pick L4 only when there is no HTTP to parse — a database, a broker, a custom protocol.
  • Pick L7 only for a small HTTP estate where one proxy tier comfortably handles the volume.
  • Pick client-side balancing for gRPC between your own services; it removes a hop and balances per request.
  • Pick a sidecar when you want per-request balancing everywhere without touching application code.
  • Pick anycast for the global tier, with L4 and L7 behind it doing the actual work.
