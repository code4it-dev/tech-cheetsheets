Azure API Management

One front door for every API you own — and a place to put all the things that are not business logic.

As of Nov 2026 · classic tiers (Developer, Basic, Standard, Premium) plus the v2 tiers and Consumption

Once you have more than a couple of APIs, the same concerns reappear in every one of them: authentication, rate limits, caching, CORS, request validation, logging, a consistent error shape, a developer-facing catalogue. Azure API Management (APIM) is the managed gateway that takes those concerns out of your services and puts them in one configurable place.

The core of it is the policy pipeline: a small XML document, attached at global, product, API or operation scope, that runs on every request in four phases — inbound, backend, outbound and on-error. Policies validate a JWT, throttle a caller, look up a cached response, rewrite a URL, add a managed-identity token, transform a payload or return a mock. Your backend sees only what survives all of that.

Around the gateway sit the pieces that make an API a product: products group APIs and carry quotas, subscriptions issue keys, the developer portal publishes documentation and a try-it console, and revisions and versions let you change an API without breaking the clients already using it.

Architecture / mental model

The gateway is the only public surface. Everything cross-cutting happens in the policy pipeline, so backends stay small and the API contract stays stable even when they change.

Key concepts

gatewayThe component that actually receives traffic, runs policies and forwards to backends. Everything else in APIM configures it.
API and operationAn API is a façade with a base path; an operation is one method and URL template within it. Policies can attach to either.
policy pipelineFour sections — inbound, backend, outbound, on-error — evaluated in order on every request. This is where APIM does its work.
policy scopePolicies attach at four levels — global, product, API, operation — and <base /> decides where the outer level's policies run.
policy expressionsInline C# in @(...) or @{ ... } with access to context. The escape hatch that makes policies programmable.
productA bundle of APIs with its own terms, policies and quotas, which developers subscribe to. The commercial packaging layer.
subscriptionA pair of keys issued to a consumer for a product (or a single API, or all APIs). The default unit of identity and throttling.
validate-jwtThe inbound policy that verifies a bearer token's signature, issuer, audience, expiry and claims — before your backend sees the request.
rate limits and quotarate-limit protects against bursts over seconds; quota enforces a volume over days or months. They solve different problems.
response cachingEither the built-in cache-lookup / cache-store pair, or fine-grained cache-lookup-value for arbitrary values. Served from the gateway, so the backend is never called.
backendA named, reusable target: a URL, credentials and optionally a pool with load balancing and a circuit breaker. Referenced by set-backend-service.
backend authenticationHow the gateway proves itself to your API: managed identity, client certificate, or a secret from a named value. Never a key the client supplied.
named valuesThe configuration store: plain strings, secrets, or references to Key Vault, usable in any policy as {{name}}.
revisionsNon-breaking changes to an API, staged and tested at ?rev=N before one of them becomes current. Same URL for clients.
versionsBreaking changes, exposed deliberately: /v1 and /v2 live side by side, with their own policies and lifecycles.
developer portalThe auto-generated, customisable site where consumers read the docs, sign up for a product and try calls in the browser.
self-hosted gatewayThe gateway as a container you run yourself — on-premises, in another cloud, or in Kubernetes — managed from the same Azure control plane.
tiers and unitsThe pricing tier fixes the feature set (VNet, multi-region, portal, SLA) and the capacity unit fixes throughput. Changing tier later is disruptive.
diagnosticsWhat you can see: Application Insights traces, Azure Monitor metrics, resource logs, and the request trace in the test console.

Essential commands & syntax

Policies you will write on day one

<cors allow-credentials="false">
  <allowed-origins><origin>https://app.contoso.com</origin></allowed-origins>
  <allowed-methods><method>GET</method><method>POST</method></allowed-methods>
  <allowed-headers><header>*</header></allowed-headers>
</cors>
Global inbound CORS. The developer portal's try-it console needs this too.
<validate-jwt header-name="Authorization" failed-validation-httpcode="401">
  <openid-config url="https://login.microsoftonline.com/{tenant}/v2.0/.well-known/openid-configuration" />
  <audiences><audience>api://contoso-orders</audience></audiences>
</validate-jwt>
Rejects unauthenticated calls at the edge. Always set audiences.
<rate-limit-by-key calls="600" renewal-period="60"
    counter-key="@(context.Subscription?.Id ?? context.Request.IpAddress)"
    retry-after-header-name="Retry-After" />
Per-subscription throttle, falling back to the caller's IP for anonymous APIs.
<set-backend-service backend-id="orders-pool" />
<rewrite-uri template="/api/v3/order?id={orderId}" />
<authentication-managed-identity resource="api://contoso-orders" />
Routes to a pooled backend, reshapes the URL and authenticates with no stored secret.
<set-header name="Ocp-Apim-Subscription-Key" exists-action="delete" />
<set-header name="Authorization" exists-action="delete" />
Strips the client's credentials so they never reach the backend.
<return-response>
  <set-status code="200" reason="OK" />
  <set-header name="Content-Type"><value>application/json</value></set-header>
  <set-body>{"id":10427,"status":"shipped"}</set-body>
</return-response>
A mock response: front-end teams can build against the API before the backend exists.
<on-error>
  <base />
  <return-response>
    <set-status code="502" reason="Bad Gateway" />
    <set-body>@($"{{\"error\":\"upstream\",\"traceId\":\"{context.RequestId}\"}}")</set-body>
  </return-response>
</on-error>
One error shape for every failure, with a trace id the caller can quote in a support ticket.

Azure CLI

az apim create -g rg-apis -n contoso-apim -l westeurope \
  --publisher-email apis@contoso.com --publisher-name Contoso --sku-name Developer
Creates an instance. Classic tiers take 30–45 minutes — start it and go do something else.
az apim api import -g rg-apis -n contoso-apim --path orders \
  --specification-format OpenApi --specification-path ./orders.openapi.json --api-id orders
Imports an API from OpenAPI, bringing operations, schemas and descriptions with it.
az apim api policy import -g rg-apis -n contoso-apim --api-id orders \
  --policy-format xml --value "@policies/orders.xml"
Applies an API-scoped policy document from a file in source control.
az apim nv create -g rg-apis -n contoso-apim --named-value-id orders-backend-key \
  --display-name orders-backend-key --secret true \
  --value-from-key-vault "https://kv-contoso.vault.azure.net/secrets/orders-key"
Creates a Key Vault-backed named value so no secret lives in APIM itself.
az apim show -g rg-apis -n contoso-apim --query "publicIPAddresses"
The IP partners will allow-list. It changes if you change tier — keep that in mind.

Calling and testing

curl -s https://contoso.azure-api.net/orders/10427 \
  -H "Ocp-Apim-Subscription-Key: $KEY" -H "Authorization: Bearer $TOKEN"
A normal call: subscription key for metering, bearer token for identity.
curl -s "https://contoso.azure-api.net/orders;rev=2/10427" -H "Ocp-Apim-Subscription-Key: $KEY"
Calls a non-current revision directly, to test it before promoting.
curl -sD - https://contoso.azure-api.net/orders/10427 -o /dev/null \
  -H "Ocp-Apim-Subscription-Key: $KEY" | grep -iE "ratelimit|retry-after|x-cache"
Checks that your throttle and cache headers actually reach the client.

Infrastructure as code (Bicep)

resource pool 'Microsoft.ApiManagement/service/backends@2023-09-01-preview' = {
  parent: apim
  name: 'orders-pool'
  properties: {
    type: 'Pool'
    pool: { services: [ { id: backendA.id, priority: 1, weight: 50 }
                        { id: backendB.id, priority: 1, weight: 50 }
                        { id: backendC.id, priority: 2 } ] }
    circuitBreaker: { rules: [ { name: 'trip5xx', failureCondition: {
      count: 5, interval: 'PT30S', statusCodeRanges: [ { min: 500, max: 599 } ] },
      tripDuration: 'PT1M' } ] }
  }
}

Pros & cons

Pros

  • Cross-cutting concerns move out of every service into one auditable, versioned place.
  • Auth, throttling, caching and transformation are configuration, not code you maintain per API.
  • A stable public contract in front of backends you are free to rewrite, split or replace.
  • Products, subscriptions and the developer portal turn a set of endpoints into a sellable API product.
  • Backends can stay entirely private, with the gateway as the only internet-facing surface.
  • Mocks, revisions and weighted backend pools make safe rollout and parallel development easy.

Cons

  • Expensive relative to a plain reverse proxy, and the Premium features are a steep step up.
  • Policy XML with embedded C# is awkward to test, review and debug compared with real code.
  • Classic-tier deployment and scaling are measured in tens of minutes.
  • It is a single point of failure in front of everything, so its blast radius is your whole API estate.
  • Rate-limit and cache state is per gateway unit, which surprises people at scale.
  • Strong Azure lock-in: policies and products do not port to another gateway.

Concrete use cases

A monolith being strangled

A legacy ASP.NET monolith is being broken into services. APIM fronts the old application, and as each endpoint is rewritten, set-backend-service routes that one operation to the new service. Clients see one unchanging URL throughout, and a weighted pool lets each cut-over start at 5% of traffic.

Selling an API to partners

A logistics company exposes tracking data. Products define Free, Pro and Partner tiers with different quotas; the developer portal handles sign-up, documentation and key issuance; quota-by-key enforces the monthly allowance. Billing reads the per-subscription metrics rather than instrumenting the backend.

A SOAP backend with modern clients

An insurance core system speaks SOAP and will not change. APIM imports the WSDL, exposes a REST façade, and xml-to-json plus a few set-body policies convert payloads in both directions. New mobile clients call clean JSON and never learn what is behind it.

Protecting an LLM endpoint

Calls to a model deployment are expensive and have hard token limits. APIM validates the JWT, applies a token-aware rate limit per subscription, caches identical prompts, and load-balances across several deployments with a circuit breaker so one throttled region does not fail the whole feature.

One gateway, many teams

Fifteen teams each own APIs. A global policy adds CORS, a correlation id and a standard error envelope; each team owns its own API-scoped policy file in its own repository, promoted by an APIOps pipeline. Nobody edits production in the portal, and every change arrives as a reviewed pull request.

When to use / when not to

One API and one consumer? You want a reverse proxy. Many APIs and many consumers? You want this.

Use it when…

  • Several APIs, owned by several teams, need one consistent front door.
  • External consumers need keys, quotas, documentation and self-service sign-up.
  • You want auth, throttling and caching enforced uniformly and provably, not per service.
  • Backends must stay private, or sit in several networks and clouds.
  • You are modernising something legacy and need a stable façade while it changes underneath.
  • Per-consumer usage data is a product or billing requirement.

Avoid it when…

  • You have one API and one internal client. Use Azure Front Door or Application Gateway for TLS and routing.
  • The need is purely CDN and WAF. Use Front Door or a CDN; they are cheaper and closer to the user.
  • All traffic is service-to-service inside one Kubernetes cluster. Use a service mesh or an ingress controller.
  • You want to run the gateway anywhere, cheaply, with config in Git. Use Kong, Envoy or APISIX.
  • The budget does not stretch to the tier whose features you actually need. Developer tier has no SLA — use something else rather than run production on it.
  • You would be moving real business logic into policies. Keep it in the service, where it can be tested.

Common mistakes & gotchas

Forgetting <base />An API-scoped policy without <base /> silently discards every global and product policy — your CORS, your correlation id, your product quota. Nothing errors; things just stop applying.
Fix: always include <base />, first in inbound and backend, last in outbound and on-error. Make it a review checklist item.
Treating the subscription key as authenticationIt identifies an application for metering, nothing more. In a browser app it is visible in the network tab, and it is frequently pasted into tickets and logs.
Fix: use OAuth 2.0 with validate-jwt for identity and keep the subscription key for quotas. Never put a subscription key in client-side code you cannot rotate.
Assuming rate limits are globalCounters are per gateway unit and per region. A 600/min limit on a four-unit gateway admits roughly 2,400/min, which only shows up once you scale out — usually during the incident that made you scale out.
Fix: size the limit per unit deliberately, or enforce the real cap downstream with a shared counter. Document which one your number is.
Caching a personalised responsecache-lookup with vary-by-developer="false" on an endpoint that returns the caller's own data serves one customer's response to another. It is a data breach, and it looks exactly like a cache working well.
Fix: vary by every dimension that changes the response, or do not cache authenticated responses at all. Review every cache-store as if it were a security change.
Reading the body without preserveContentcontext.Request.Body.As<JObject>() consumes the stream, so the backend receives an empty body. GETs work perfectly and every POST breaks.
Fix: As<JObject>(preserveContent: true) whenever the body must continue downstream, and the same on the response side.
Editing production in the portalPolicies drift from source control, nobody knows who changed what, and the next infrastructure-as-code deployment reverts a fix somebody made at 2am.
Fix: treat the portal as read-only for production. Keep policies in Git and promote them with APIOps, Bicep or Terraform. Grant portal write access sparingly.
Leaving backends publicly reachableThe gateway enforces auth and limits, but if the backend has a public URL, anyone who finds it bypasses all of it — including your rate limits and your JWT validation.
Fix: private endpoints or VNet integration, plus a gateway-supplied credential (managed identity or a client certificate) that the backend requires.
Running production on the Developer tierIt is the cheapest tier with the full feature set, which makes it tempting. It carries no SLA and is taken down for platform maintenance without warning.
Fix: Developer for non-production only. If Basic or Standard is unaffordable, the right answer is a simpler gateway, not an unsupported one.
Expecting a tier change to be in-placeMoving between tiers often means a new instance, a new IP address and a migration — discovered after partners have allow-listed the old address.
Fix: choose the tier from the features you will need within a year, use a custom domain from day one, and never publish the raw *.azure-api.net host to partners.

Alternatives

ToolBest forComplexityCost / licenseKey difference vs APIM
Azure API Managementmany APIs, external consumers, full API product lifecycleMedium–highper instance + units—
Azure Front Doorglobal routing, WAF, CDN, TLS terminationLowper GB + requestsEdge network, not an API gateway: no products, keys or policy pipeline
Application Gatewayregional L7 load balancing with WAFLow–mediumper hour + capacityRouting and WAF only; no API lifecycle features at all
Kongportable, plugin-rich gateway on any infrastructureMediumOSS or enterpriseRuns anywhere, config in Git; you operate it, and the developer portal is a paid add-on
Envoy / Istio ingressservice-to-service traffic inside KubernetesHighOSSMesh-native, extremely fast; no products, subscriptions or portal
Apache APISIXhigh-throughput open-source gatewayMediumOSSDynamic config, good performance; a smaller managed ecosystem
Container Apps / AKS ingressa single app that only needs routing and TLSLowincludedEnough when "gateway" really means "reverse proxy"
  • Pick Front Door if the requirement is global performance, caching and WAF rather than API lifecycle.
  • Pick Application Gateway if you need regional L7 routing with a WAF and nothing more.
  • Pick Kong or APISIX if the gateway must run outside Azure, or the licence cost matters more than the managed experience.
  • Pick a service mesh if the traffic you are governing is service-to-service inside a cluster.
  • These stack: Front Door for the edge and WAF, APIM behind it for API concerns, and a mesh inside the cluster is a common and sensible layering.
