Multitenancy strategies

One system, many customers — the only real question is where you draw the isolation line.

As of Nov 2026 · the strategies are stable; examples are .NET 10 (LTS), EF Core and PostgreSQL

A multi-tenant system serves many customers from one set of running code. That is what makes SaaS economics work: one deployment, one on-call rota, one upgrade, amortised across thousands of tenants. The architectural question is not whether to share — it is how much, and the answer lives almost entirely in the data layer.

There are four answers in practice. Put every tenant's rows in one table behind a discriminator column; give each tenant its own schema in a shared database; give each tenant its own database; or group tenants into pools of shared databases and promote the big ones. They differ in isolation, in what a noisy neighbour can do to you, in what a migration costs, in whether you can restore one customer, and in how much each tenant costs you per month.

Everything else — resolving which tenant a request belongs to, keeping caches from mixing tenants, enforcing per-tenant limits, onboarding and offboarding — sits on top and is largely the same whichever you pick. The four animations below run the same request, the same noisy neighbour and the same restore through each strategy, so the trade-offs are visible side by side.

What that actually tells you:

  • Shared schema and database-per-tenant are the two honest extremes. One optimises cost and operational simplicity, the other isolation and compliance. Everything in between is a compromise, and schema-per-tenant in particular gets the worst of both at scale: N migrations without the isolation that would justify them.
  • The migration row is the one that decides your ceiling. A shared schema deploys in seconds forever. Schema- or database-per-tenant turns every release into a fan-out job with partial failures, retries and version skew — and that is what caps you at hundreds of tenants rather than thousands.
  • Sharded pools is where most SaaS ends up, because it is the only option that lets you choose the blast radius per tenant: small customers share, big ones get promoted, and both run the same code with the same migrations.

Choosing, in one line each:

  • Shared schema for a new product, many small tenants, no per-tenant compliance requirement. Start here.
  • Sharded pools once you can no longer tolerate every customer sharing one blast radius — design the tenant catalogue early so this is a config change, not a rewrite.
  • Database per tenant for a few large, demanding or regulated customers, or when contracts require data residency and separate keys.
  • Schema per tenant only when you have a bounded, small number of tenants and a strong reason — it is the least common end state for a reason.

Key concepts

tenantThe unit of isolation and usually of billing: a customer organisation, not a user. Getting this definition wrong is expensive to undo.
tenant resolutionDeciding which tenant a request belongs to, before anything touches data. The first middleware in the pipeline, and a security boundary.
discriminator columnA tenant_id on every tenant-owned table. The entire isolation mechanism of the shared-schema model.
global query filterApplying the tenant predicate automatically in the ORM so no developer has to remember it. Necessary, and not sufficient.
row-level securityThe database enforcing the tenant predicate itself, so a forgotten filter returns nothing instead of everything. The backstop worth the setup.
shared schemaOne database, one set of tables, every tenant's rows together. The cheapest model and the default starting point.
schema per tenantOne database, one schema per tenant, each with its own copy of the tables. A middle ground that gets squeezed from both sides.
database per tenantEach tenant gets its own database. The strongest isolation, the simplest restore, and a cost that scales with your customer count.
pooled modelTenants grouped into a handful of shared-schema databases, with the option to promote a big tenant to its own. Where most SaaS converges.
tenant catalogueThe small shared table mapping each tenant to where it lives, plus its plan, region and status. The one piece every strategy needs.
noisy neighbourOne tenant consuming shared resources and degrading everyone else. The problem isolation is really protecting against.
per-tenant migrationRunning schema changes across N schemas or N databases. The hidden operational cost that caps how far the isolated models scale.
restore granularityCan you restore one tenant to yesterday without touching anyone else? Nobody asks until a customer deletes something important.
data residencyContractual or legal requirements that a tenant's data stays in a region. A requirement that effectively picks your strategy for you.
tenant-aware cachingEvery cache key carries the tenant. Miss this and you serve one customer's data to another from memory rather than from the database.
per-tenant limitsQuotas and rate limits keyed on the tenant, so one customer cannot consume the capacity the others are paying for.
provisioningCreating everything a new tenant needs. Cheap in a shared schema, a workflow of its own once tenants get their own storage.
tenant lifecycleSuspend, reactivate, export, delete. The operations nobody designs up front and everybody needs within the first year.
cost per tenantWhat one tenant costs you per month. The number that decides whether your pricing works and which tenants deserve isolation.

Code & syntax

Resolving the tenant

app.Use(async (ctx, next) =>
{
    var fromToken = ctx.User.FindFirstValue("tid");
    var fromHost  = ctx.Request.Host.Host.Split('.') is [var slug, _, _] ? slug : null;

    if (fromToken is null) { ctx.Response.StatusCode = 401; return; }
    if (fromHost is not null && !string.Equals(fromHost, fromToken, StringComparison.OrdinalIgnoreCase))
    { ctx.Response.StatusCode = 403; return; }          // host and token disagree

    ctx.RequestServices.GetRequiredService<TenantContext>().Set(fromToken);
    await next();
});
Trust the signed token, treat the URL as a claim to verify. An unresolved tenant is a hard failure, never a default.
@asynccontextmanager
async def tenant_connection(pool, tenant_id: UUID):
    async with pool.connection() as conn:
        # set once per checkout; every RLS policy reads it on every statement
        await conn.execute("SELECT set_config('app.tenant_id', %s, false)", (str(tenant_id),))
        try:
            yield conn
        finally:
            await conn.execute("SELECT set_config('app.tenant_id', '', false)")
The reset in finally is the important half: pooled connections are reused, and a stale app.tenant_id is a cross-tenant data leak.
current_tenant: ContextVar[Tenant] = ContextVar("current_tenant")

@app.middleware("http")
async def resolve_tenant(request: Request, call_next):
    slug = request.headers.get("host", "").split(".")[0]
    tenant = await tenants.get(slug)
    if tenant is None:
        return JSONResponse({"error": "unknown tenant"}, status_code=404)

    token = current_tenant.set(tenant)      # ContextVar survives await, unlike a global
    try:
        return await call_next(request)
    finally:
        current_tenant.reset(token)         # never leak a tenant into the next request
A ContextVar is the asyncio-safe equivalent of an AsyncLocal: a module-level global would leak one tenant’s context into another’s request.
builder.Services.AddMultiTenant<AppTenantInfo>()
    .WithHostStrategy("__tenant__.*")
    .WithClaimStrategy("tid")
    .WithEFCoreStore<CatalogueDbContext, AppTenantInfo>()
    .WithPerTenantAuthentication();

Shared schema: filter, index, and the database backstop

protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Invoice>().HasQueryFilter(i => i.TenantId == _tenant.Id);
    b.Entity<Invoice>().HasIndex(i => new { i.TenantId, i.CreatedAt });   // tenant first
}
The filter is applied to every LINQ query. The index order is what keeps it fast with thousands of tenants.
public override int SaveChanges()
{
    foreach (var e in ChangeTracker.Entries<ITenantOwned>().Where(e => e.State == EntityState.Added))
        e.Entity.TenantId = _tenant.Id;                 // never trust the caller to set it
    return base.SaveChanges();
}
Stamp the tenant on insert. A client-supplied tenantId in a request body is an attack, not a convenience.
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
The backstop: raw SQL, Dapper, a stored procedure or a psql session all get filtered. FORCE makes it apply to the table owner too.
-- must run on every pooled connection checkout, not once at startup
SELECT set_config('app.tenant_id', @tenantId, false);
The classic row-level-security bug: a pooled connection keeps the previous request's tenant setting.
ALTER TABLE order_lines
  ADD CONSTRAINT fk_order_lines_order
  FOREIGN KEY (tenant_id, order_id) REFERENCES orders (tenant_id, id);
A composite foreign key makes a cross-tenant reference a constraint violation instead of a leak.

await Parallel.ForEachAsync(tenants, new ParallelOptions { MaxDegreeOfParallelism = 8 },

    {

The per-tenant migration runner: bounded parallelism, resumable, and a recorded version per tenant so failures can be retried alone.

The catalogue and pooled routing

CREATE TABLE tenants (
  tenant_id  uuid PRIMARY KEY,
  slug       text UNIQUE NOT NULL,
  shard      text NOT NULL,              -- 'shard-01' or 'dedicated'
  status     text NOT NULL,              -- active | suspended | read-only | migrating
  region     text NOT NULL,
  plan       text NOT NULL,
  schema_version int NOT NULL
);
The whole routing layer. Build it on day one, even when every row says shard-01.
var tenant = await cache.GetOrCreateAsync($"tenant:{slug}",

if (tenant.Status is "suspended") return Results.StatusCode(402);

The catalogue is on every request, so cache it — and honour the status before any query runs.

Pros & cons

Pros of sharing more

  • Cost per tenant falls to cents, which is what makes a free tier and small customers viable.
  • One migration, one backup, one set of dashboards — operations do not grow with the customer count.
  • Onboarding is an INSERT, so self-service signup is instant.
  • Cross-tenant reporting and analytics are ordinary queries.
  • Capacity is pooled, so one tenant's quiet week pays for another's busy one.
  • One code path for everybody, so a bug is found once and fixed once.

Cons of sharing more

  • Isolation rests on a predicate, and one forgotten filter is a cross-tenant data breach.
  • A noisy neighbour degrades everyone, with no structural defence.
  • Restoring a single tenant means extracting rows from a full backup.
  • Per-tenant residency, encryption keys and some compliance answers are simply unavailable.
  • One incident has every customer in its blast radius.
  • Enterprise deals stall on "is our data in the same table as theirs?", and the honest answer is yes.

Concrete use cases

A new SaaS with a free tier

Thousands of signups, most of which never become paying customers. Shared schema with row-level security: a tenant costs cents, onboarding is instant, and a free tenant that never logs in again costs nothing. A tenant catalogue is built on day one with every row pointing at the single shard, so pools are a configuration change later.

Enterprise customer demanding isolation

A bank will sign a seven-figure contract if its data is in its own database, in the EU, with a customer-managed key. The tenant is promoted from a shard to a dedicated database: the catalogue row changes, the application code does not, and 20,000 other tenants stay pooled.

The import that took everyone down

One customer uploads three years of history. A FIFO job queue means every other tenant's exports sit behind it for an hour, and the connection pool is exhausted by long transactions. The fix is per-tenant: fair round-robin queuing, a cap on concurrent heavy jobs, and a statement timeout — none of which is about the database layout.

"Can you restore our data to Tuesday?"

A customer deletes a project and asks for a restore. In a shared schema this means restoring the full backup to a side instance and extracting one tenant's rows, so the team ships soft deletes with a 30-day window instead — which turns the common case into an UPDATE and leaves true restores for genuine disasters.

Outgrowing one database

At 40,000 tenants one PostgreSQL instance is at its limit and every incident affects every customer. Tenants are split across eight shards of 5,000, assigned least-loaded at signup rather than by hash so they can be moved. Migrations go from one run to eight, and the blast radius of an incident drops by 87%.

When to use / when not to

Start shared, build the catalogue anyway, and isolate the tenants who pay for it.

Share more when…

  • Tenants are numerous and small, and many will never pay you anything.
  • Cost per tenant has to be measured in cents for the pricing to work.
  • Self-service signup must be instant.
  • No contract requires residency, separate keys or physical separation.
  • Cross-tenant analytics are a product feature rather than an afterthought.
  • Your team is small and cannot operate thousands of databases.

Isolate more when…

  • A contract requires data residency or customer-managed keys. Use database per tenant.
  • Tenants differ in size by orders of magnitude. Use pools plus promotion.
  • Restoring one customer must be routine. Use database per tenant.
  • One incident affecting every customer is unacceptable. Use sharded pools to bound it.
  • Tenants are few, large and pay enough to cover the cost. Dedicated storage is affordable and simpler to reason about.
  • Regulation demands a separation you can draw for an auditor. A WHERE clause will not survive the meeting.

Common mistakes & gotchas

Raw SQL bypassing the query filterA report needs a window function, so it uses FromSqlRaw or Dapper. Global query filters do not apply, nothing errors, and the report quietly returns every tenant's rows to whoever opened it.
Fix: enable row-level security so the database enforces the predicate whatever issued the statement. Failing that, ban raw SQL outside an audited helper that takes the tenant as a required parameter.
Background jobs with no tenant in scopeA nightly job runs outside a request, so nothing resolved a tenant. The filter compares against an empty context and either returns nothing or — worse, with a nullable comparison — everything.
Fix: make tenant context required rather than optional, so an unset tenant throws. Loop over tenants explicitly, creating a scope and setting the tenant for each one.
Row-level security and connection poolingset_config runs once when the connection opens rather than on every checkout. A pooled connection carries the previous request's tenant, so one tenant occasionally sees another's data — intermittently, under load, and impossible to reproduce locally.
Fix: set the tenant setting on every checkout, in a connection interceptor, and assert it matches the ambient tenant before executing. Test it with a pool size of one and concurrent requests.
Cache keys without the tenantEvery query is correctly filtered, then the result is cached under product:42. The second tenant to ask for product 42 gets the first tenant's data out of memory, and no database control can see it happen.
Fix: compose keys from ambient tenant context inside a cache wrapper so a raw key cannot be passed. Add a test asserting every key produced starts with the tenant prefix.
Trusting a tenant id from the request bodyAn endpoint accepts tenantId in the payload "for flexibility". Changing one field in a request now reads or writes another customer's data.
Fix: the tenant comes from the signed token only. Stamp it server-side on insert, ignore it on input, and return 403 when a supplied tenant disagrees with the resolved one.
Indexes without the tenant firstCREATE INDEX ON invoices (created_at) looks right and performs fine with ten tenants. At five thousand, every tenant's query scans everyone else's rows before filtering, and the whole system slows together.
Fix: tenant_id is the first column of essentially every index. Review the plans with production-like tenant counts, not with your seed data.
Hashing tenants to shardsshard = hash(tenantId) % 8 is one line and makes moving a tenant impossible without rehashing everyone — which is exactly what you need when one tenant outgrows its shard or buys isolation.
Fix: store the mapping explicitly in the catalogue. Assign least-loaded at signup, and keep the ability to change one row to move one tenant.
No plan for per-tenant migrationsSchema- or database-per-tenant is chosen for isolation, and the first release that touches the schema takes four hours, fails for 3% of tenants and leaves the fleet on two different versions.
Fix: expand and contract so both shapes work during the rollout, a resumable runner with bounded parallelism, a recorded schema version per tenant, and an alert on drift.
Deletion that only deletes rowsA tenant exercises its right to erasure. The rows go, and the data stays in backups, logs, the search index, the warehouse and three third-party processors.
Fix: write down everywhere tenant data lands, and make deletion a workflow across all of them with a backup retention window the contract reflects. Rehearse it before you are asked.

  • Pick shared schema to start, and add row-level security immediately rather than eventually.
  • Pick sharded pools when one blast radius for every customer stops being acceptable — usually long before you hit a technical limit.
  • Pick database per tenant for the specific customers whose contracts pay for it, not for everyone.
  • Consider cell-based architecture when sharding the database is no longer enough and you need the whole stack partitioned.
  • Avoid single-tenant deployments unless the customer is paying for an installation, because you are agreeing to operate N products.
  • These compose, and the common end state is pools for most tenants, dedicated databases for a handful, and one tenant catalogue routing both.
