Azure Durable Functions

Write a long-running workflow as ordinary code, and let replay make it survive restarts.

As of Nov 2026 · extension v3.x (in-process and .NET isolated) · Durable Task Scheduler backend generally available

Plain serverless functions are stateless and short-lived, which makes multi-step processes awkward: you end up stitching functions together with queues, storing progress in a table, and writing your own retry, timeout and compensation logic. Durable Functions is the extension to Azure Functions that removes all of that plumbing.

You write an orchestrator function that looks like normal, sequential code — call this, await it, loop, branch, wait for approval, time out after three days — and the runtime makes it durable. Every decision the orchestrator takes is appended to a history, the function is unloaded from memory whenever it is waiting, and it is replayed from the top when new results arrive. Your code looks synchronous; the execution is event-sourced.

It is available for C# (in-process and isolated worker), JavaScript and TypeScript, Python, PowerShell and Java, and it runs on every Azure Functions hosting plan. The same engine underneath, the Durable Task Framework, also powers Durable Task Scheduler — a managed backend with a real monitoring dashboard — and Azure Container Apps' durable workflows.

Architecture / mental model

The orchestrator is a pure decision-maker; activities do the I/O; everything that happened is an event in the history, which is why the workflow survives a process crash, a deploy or a three-day wait.

Comparing the patterns

All five run on the same engine — an orchestrator that is replayed, and activities that are not. What differs is the shape of the workflow and therefore which failure you have to think about.

PatternShapeWhat it buys youThe thing that bitesUse it for
Chainingawait, await, awaitcheckpointing between every step, for freenon-deterministic code between the awaitsmulti-step processes: order fulfilment, onboarding
Fan-out / fan-inschedule many, WhenAllparallelism across every worker, per-item retriesthousands of tasks bloat one history — batch or sub-orchestratebatch processing, per-file or per-region work
Async HTTP API202 + a status URLno held connection, no gateway timeoutcallers that poll too aggressivelyany operation longer than a few seconds
Human interactionevent vs timer, WhenAnywaiting days costs nothingan uncancelled timer keeps the instance Runningapprovals, confirmations, escalation
Monitorpoll, timer, ContinueAsNewa polling loop with no cron job and no state tableforgetting ContinueAsNew — the history grows until it failswatching an external job to completion
Aggregator (entities)a keyed actor, not an orchestrationserialised operations per key, no lockingdifferent model — entities are not replayedper-device or per-cart state, counters

Two things to take from that table:

  • The first five are the same mechanism wearing different clothes. Every one of them is an orchestrator awaiting a durable task and being replayed when it completes. Once the replay animation makes sense, the rest are just different things to await: an activity, a set of activities, an external event, a timer.
  • The aggregator is the odd one out. An entity is not replayed, has no beginning or end, and processes one operation at a time per key. If you find yourself writing an orchestration that never finishes and only accumulates state, you want an entity instead.

Key concepts

orchestrator functionThe workflow itself, written as sequential code. It decides what to call and in what order, and is replayed from the start every time it resumes.
activity functionA single unit of real work: call an API, write to a database, send an email. Ordinary code, no determinism rules, executed at least once.
client functionAny ordinary function — HTTP, queue, timer — that starts, queries, terminates or raises events against orchestration instances.
entity functionA small, addressable piece of durable state — a counter, a cart, a device shadow — that processes operations one at a time per entity key.
replayEach time an orchestrator resumes, it runs again from the first line. Completed awaits return their recorded result instead of re-executing.
determinismReplayed code must take exactly the same decisions every time. Anything that could return a different value on the second run breaks the orchestration.
historyThe append-only list of events for one instance: what was scheduled, what completed, what failed. It is the only state the workflow has.
task hubThe named container for all the queues, tables and blobs an application uses. Two apps sharing a task hub will steal each other's work.
instance idThe unique key of one orchestration run. Supply your own to get deduplication for free.
durable timersctx.CreateTimer() instead of Task.Delay. The orchestrator unloads and is woken at the deadline — minutes, days or months later.
external eventsWaitForExternalEvent parks the orchestration until something outside — a human, a webhook, another system — raises a named event.
fan-out / fan-inSchedule many activities without awaiting, then Task.WhenAll. The platform parallelises across every available worker.
sub-orchestrationAn orchestrator calling another orchestrator. The unit of composition, and the way to keep any single history small.
ContinueAsNewRestart the orchestration with fresh input and an empty history. The only correct way to write an eternal or long-looping workflow.
retry policyDeclarative retries on an activity or sub-orchestration call: attempts, delay, backoff, timeout. The orchestrator owns them, so they survive a crash.
versioningChanging orchestrator code while instances are mid-flight. The in-flight ones replay against your new code, and a changed shape breaks them.
storage backendWhere the history and queues live: Azure Storage by default, or Durable Task Scheduler, Netherite or MSSQL.
status and managementQuerying, suspending, terminating, rewinding and purging instances — through HTTP, the client API, the CLI or the dashboard.

The patterns, in C#

// function chaining
var a = await ctx.CallActivityAsync<string>("StepOne", input);
var b = await ctx.CallActivityAsync<string>("StepTwo", a);
return await ctx.CallActivityAsync<string>("StepThree", b);
Sequential steps where each depends on the previous result.
// fan-out / fan-in
var tasks = items.Select(i => ctx.CallActivityAsync<long>("Process", i)).ToList();
var results = await Task.WhenAll(tasks);
Parallel work across every available worker, then aggregation.
// human interaction with a deadline
using var cts = new CancellationTokenSource();
var approval = ctx.WaitForExternalEvent<bool>("Approved");
var timeout  = ctx.CreateTimer(ctx.CurrentUtcDateTime.AddDays(3), cts.Token);
if (approval == await Task.WhenAny(approval, timeout)) { cts.Cancel(); /* ... */ }
Waits up to three days for an approval, escalating on timeout. Cancel the loser.
// saga: compensate on failure
try { await ctx.CallActivityAsync("ReserveStock", o); await ctx.CallActivityAsync("ChargeCard", o); }
catch (TaskFailedException) { await ctx.CallActivityAsync("ReleaseStock", o); throw; }
Compensation is just a catch block, replayed as durably as the forward path.
ctx.SetCustomStatus(new { step = "awaiting-approval", since = ctx.CurrentUtcDateTime });
Attaches progress to the instance so a status query shows something meaningful.

Python

import azure.durable_functions as df

def orchestrator(context: df.DurableOrchestrationContext):
    order = context.get_input()
    payment = yield context.call_activity("ChargeCard", order)
    tracking = yield context.call_activity("ShipOrder", order)
    return {"payment": payment, "tracking": tracking}

main = df.Orchestrator.create(orchestrator)
Same model with generators: every yield is a durable await, and the function is replayed identically.
tasks = [context.call_activity("Process", i) for i in items]
results = yield context.task_all(tasks)
Fan-out / fan-in in Python: task_all and task_any replace WhenAll and WhenAny.

Operating instances (HTTP management API)

curl -s "$BASE/runtime/webhooks/durabletask/instances/order-10427?code=$KEY&showHistory=true"
Full status plus the event history — the first thing to look at when a workflow misbehaves.
curl -X POST "$BASE/runtime/webhooks/durabletask/instances/order-10427/raiseEvent/Approved?code=$KEY" \
  -H "Content-Type: application/json" -d 'true'
Delivers an external event to a parked orchestration.
curl -X POST ".../instances/order-10427/terminate?reason=duplicate&code=$KEY"
curl -X POST ".../instances/order-10427/suspend?reason=upstream-outage&code=$KEY"
Terminate kills the instance; suspend pauses it so you can resume once a dependency recovers.
curl -X DELETE ".../instances?createdTimeTo=2026-09-01T00:00:00Z&runtimeStatus=Completed&code=$KEY"
Purges old completed instances. Schedule this — history is kept forever otherwise.

Pros & cons

Pros

  • Workflow logic reads as ordinary code: loops, conditionals, try/catch, not a state machine in JSON.
  • State, checkpointing and recovery are free — no progress table, no "where was I" logic.
  • Waiting is genuinely free: a three-day timer or a pending approval costs storage, not compute.
  • Durable retries and compensation survive the worker process dying mid-retry.
  • Fan-out across hundreds of workers is three lines, and fan-in is WhenAll.
  • The history is a readable transcript of exactly what happened, which makes debugging unusually pleasant.

Cons

  • The replay model is genuinely unintuitive, and every new team member writes a non-deterministic orchestrator first.
  • Versioning in-flight instances is a real operational burden, not an edge case.
  • Debugging is odd: breakpoints hit repeatedly, and logs duplicate unless you use a replay-safe logger.
  • Per-step latency is higher than a direct call — each activity is a queue hop plus a history write.
  • Payload size is constrained by the history; large data needs out-of-band storage.
  • It ties the workflow to Azure Functions. Portable alternatives exist, but migration means rewriting.

Concrete use cases

Order fulfilment saga

Reserve stock, charge the card, book the courier, send confirmation — four systems, any of which can fail. The orchestrator calls each as an activity with its own retry policy, and a catch block compensates in reverse order. A crash halfway through resumes exactly where it stopped instead of leaving a half-charged order.

Document approval with a deadline

An expense claim over a threshold waits for a manager's approval. The orchestrator races WaitForExternalEvent("Approved") against a three-day timer, escalating to the department head on timeout. Nothing is running for those three days; the entire workflow is one row in a table and a scheduled message.

Batch processing a nightly drop

Ten thousand files land in Blob Storage each night. The orchestrator fans out in batches of 200 to sub-orchestrations, each fanning out to per-file activities. The platform scales workers out and back in, failures retry individually, and the final fan-in writes a single summary report.

Polling an external job to completion

A rendering service accepts a job and returns a job id. Instead of a cron job scanning a table, the orchestrator loops: call a status activity, wait on a durable timer, ContinueAsNew every hundred polls. It stops the instant the job finishes, and the polling state needs no storage of its own.

Per-device state with entities

A fleet of IoT devices sends readings at different rates. A DeviceState entity per device accumulates readings, exposes a current aggregate and signals an orchestrator when a threshold is crossed. Operations on one device serialise automatically, so there is no locking and no lost update.

When to use / when not to

If you were about to add a "status" column and a cron job to chase it, this is what you wanted.

Use it when…

  • A process has several steps that must all eventually happen, across minutes, days or months.
  • You need reliable compensation: step 3 failed, so undo steps 2 and 1.
  • The workflow waits on humans, webhooks or external jobs, and polling would be wasteful.
  • You want parallel fan-out with aggregation and per-item retries, without writing a coordinator.
  • You are already on Azure Functions and the team knows C#, Python or TypeScript.
  • You need an auditable record of what the process did and when.

Avoid it when…

  • The work is one short step. Use a plain Azure Function with a queue trigger.
  • The workflow is mostly connector glue across SaaS systems. Use Azure Logic Apps, where those connectors already exist.
  • You need sub-millisecond coordination or very high per-step throughput. Use direct calls or a stream processor over Apache Kafka.
  • Your workflow must run outside Azure or stay portable. Use Temporal or Dapr Workflow, which share the model without the hosting lock-in.
  • Non-technical users must author or change the flow. Use a designer-based tool; orchestrators are code and belong to developers.
  • The team cannot absorb the determinism rules. The failure mode is subtle and shows up in production — a state machine in a database is less clever and easier to reason about.

Common mistakes & gotchas

Doing I/O in the orchestratorAn HttpClient call or a database query inside an orchestrator runs again on every replay — so a "send email" step sends four emails — and it breaks determinism the moment the response differs.
Fix: every side effect goes in an activity. Install Microsoft.DurableTask.Analyzers so the compiler tells you before production does.
DateTime.UtcNow and Guid.NewGuid() in orchestrator codeThey return something different on each replay, so the orchestrator takes a different branch than the history records, and the instance fails with a non-determinism error — often days after the deploy.
Fix: ctx.CurrentUtcDateTime and ctx.NewGuid(). For randomness, generate it in an activity and return it, so the value is recorded.
Deploying a changed orchestrator while instances are in flightAn instance parked on a timer resumes against the new code, replay diverges from its history, and it fails. The instances that break are the long-running ones you care about most.
Fix: version side-by-side (ProcessOrderV2), or use a new task hub for the new version and drain the old one. Never reorder or insert steps in a live orchestrator.
Sharing a task hub between environmentsStaging and production point at the same storage account with the same hubName. A staging worker picks up a production work item and runs it against the wrong database.
Fix: a distinct hubName per environment, ideally a distinct storage account. Locally, use "hubName": "%UserName%Hub" so developers do not collide.
Assuming an activity runs exactly onceDelivery is at-least-once. A worker that completes the work and dies before reporting the result causes the activity to run again — charging the card twice.
Fix: make activities idempotent with a deduplication key derived from the instance id and step name, and enforce it where the side effect happens.
Putting large payloads through activitiesInputs and outputs are serialized into the history, so a 10 MB response is written once and re-read on every replay. Orchestrations get slow, then expensive, then they fail.
Fix: write the payload to Blob Storage and pass a URL or blob name. Keep activity inputs and outputs to kilobytes.
Never cancelling the losing durable timerAfter Task.WhenAny(approval, timeout) picks the approval, the timer is still pending, so the instance stays Running until the three days elapse and your dashboard is full of phantom work.
Fix: hold a CancellationTokenSource for the timer and cancel it as soon as the other task wins.
Never purging completed instancesHistory is retained indefinitely. Task hubs grow to millions of rows, queries slow down, storage costs climb, and the dashboard becomes unusable.
Fix: a timer-triggered function calling PurgeInstancesAsync for completed instances older than your retention period. Decide the period before you launch, not after.
Logging normally inside an orchestratorEvery log line appears once per replay, so a six-step workflow writes the first line six times. Log volume, and your confidence in the logs, both suffer.
Fix: ctx.CreateReplaySafeLogger<T>(), which suppresses output during replay. Check ctx.IsReplaying if you need the distinction yourself.

Plain queues + a state tabletwo or three steps, full controlLow to write, high to maintaininfrastructure onlyYou write the checkpointing, retries, timeouts and compensation yourself
MassTransit / NServiceBus sagasmessage-driven .NET systems already on a busMediumOSS / commercialSaga state is an explicit entity reacting to messages, not replayed code
  • Pick Logic Apps if the workflow is mostly connecting SaaS products and a non-developer should be able to read it.
  • Pick Temporal if you want this programming model without tying it to Azure Functions, and you can run or buy the server.
  • Pick Step Functions if you are on AWS; the concepts transfer, the authoring experience does not.
  • Pick Dapr Workflow if your services already run on Kubernetes with Dapr and you want the same model in-process.
  • Pick plain queues if the process is two steps and will stay two steps. The moment it needs timeouts and compensation, you are reimplementing this.
