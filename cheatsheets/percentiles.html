Percentiles

The average is a number nobody experienced. Percentiles are measurements of real requests.

As of Nov 2026 · the maths is permanent; the tooling notes cover Prometheus, OpenTelemetry and Azure Monitor

Latency is not normally distributed. A web request is usually fast and occasionally terrible, so the distribution has a long right tail: a handful of requests take fifty times the typical one, because they hit a cold cache, a garbage collection pause, a lock, a retry or a slow disk. Summarise that with a mean and you produce a number that sits above most of your requests and below the ones that are actually hurting.

A percentile cuts the sorted measurements at a position: p99 is the value below which 99% of them fall. Every percentile is a real request that a real user actually waited for. p50 describes the typical experience, p99 describes the experience that generates support tickets, and p99.9 describes the one that loses the customer.

They turn up everywhere once you start looking: latency SLOs, capacity planning, API gateway dashboards, database query times, queue wait, GC pauses, file sizes and response payloads. The arithmetic is trivial. The traps — averaging percentiles, averaging over the wrong window, measuring with a tool that hides queueing, forgetting what fan-out does to a tail — are where the real content is.

Architecture / mental model

One distribution, five summaries. p50 is the typical request, p99 is the one that files a ticket, and the mean describes neither.

Key concepts

percentileThe value below which a given percentage of sorted measurements fall. p99 = 1.4 s means 99% of requests finished in under 1.4 seconds.
p50 / medianThe middle measurement: half the requests were faster, half slower. The honest answer to "how fast is it normally?"
p90 / p95 / p99The tail. p99 is the standard target for user-facing latency SLOs; p99.9 is where infrastructure problems live.
mean vs medianThe mean is pulled by outliers; the median is not. For long-tailed data the mean is a number almost nobody experienced.
long tailThe small fraction of requests that are dramatically slower than the rest. Not noise, and not removable by averaging it away.
histogram and bucketsHow percentiles are actually computed at scale: count observations into predefined ranges, then interpolate. Cheap, aggregatable, approximate.
quantile estimationData structures — t-digest, HDR histogram, DDSketch — that give accurate percentiles in a few kilobytes, with mergeable state.
percentiles don't averageYou cannot average p99s across instances, regions or time windows. The result is not a percentile of anything.
aggregation windowA percentile is always "over what period". Change the window and you change the number, sometimes by a lot.
sample sizeYou need roughly 100 samples to see p99 at all, and far more for it to be stable. Below that the number is theatre.
tail amplificationWhen one user action depends on many calls, the probability of hitting the tail multiplies. Fan-out turns a rare event into a common one.
coordinated omissionA measurement bug where the tool stops sending requests while the system is stalled, so the queueing delay every real user felt is never recorded.
tail toleranceTechniques that make a slow request stop mattering: hedging, timeouts with degradation, and reducing how much depends on how much.
SLI and SLOAn indicator is what you measure; an objective is the target. Latency SLOs are almost always expressed as a percentile over a window.
error budgetThe amount of failure the SLO permits. 99.9% over 30 days is 43 minutes of budget, and spending it is allowed.
percentile vs percentagep99 = 1.4 s does not mean "99% as good" or "1% of requests failed". It is a position in a sorted list, not a proportion of anything.
trimmed statisticsDropping the extreme values before averaging. Useful for benchmarking noise, dangerous for production monitoring.

Essential commands & syntax

Prometheus / PromQL

histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))
The correct fleet-wide p99: sum the buckets across instances first, then take the quantile.
histogram_quantile(0.99, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))
p99 per route. Keep le in the by clause or the query silently returns nothing useful.
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[28d]))
  / sum(rate(http_request_duration_seconds_count[28d]))
Threshold SLO: the fraction of requests under 300 ms. Easier to alert on than a percentile value.
# in the exporter: buckets around the SLO, not the defaults
buckets = [.005, .01, .025, .05, .1, .2, .3, .5, 1, 2, 5, 10]
A boundary exactly at your SLO threshold (0.3) is what makes the query above exact.

Azure Monitor / Application Insights (KQL)

requests
| where timestamp > ago(1d) and name == "GET /orders/{id}"
| summarize count(), p50=percentile(duration,50), p95=percentile(duration,95),
            p99=percentile(duration,99) by bin(timestamp, 15m)
| render timechart
Percentiles over 15-minute bins. Keep count() next to them so you can spot bins with too few samples.
requests
| summarize good=countif(duration < 300), total=count()
| extend slo = 100.0 * good / total
The threshold form of the same SLO, which is what an error budget is computed from.
requests | where duration > 2000 | project timestamp, name, duration, operation_Id
The point of percentiles is to find these. Take the operation_Id into the end-to-end transaction view.

Python

import numpy as np
d = np.array(latencies_ms)
print(np.percentile(d, [50, 90, 95, 99]))     # linear interpolation
print(np.percentile(d, 99, method="lower"))    # nearest rank, a real observation
Two methods, two answers. method="lower" matches what most monitoring tools report.
import statistics
statistics.median(d), statistics.mean(d)       # compare them: the gap is the tail
If the mean is far above the median, the distribution is long-tailed and the mean is the wrong summary.
from hdrh.histogram import HdrHistogram
h = HdrHistogram(1, 60_000, 3)                 # 1 ms .. 60 s, 3 significant digits
for v in latencies_ms: h.record_value(int(v))
h.get_value_at_percentile(99.9)
Constant memory, mergeable across threads and processes, accurate deep into the tail.

.NET

static readonly Meter Meter = new("Contoso.Orders");

    Meter.CreateHistogram<double>("orders.request.duration", unit: "ms");

Duration.Record(sw.Elapsed.TotalMilliseconds, new KeyValuePair<string, object?>("route", "orders/{id}"));
Records into a histogram instrument; OpenTelemetry exports the buckets and the backend computes percentiles.
.AddView("orders.request.duration", new ExplicitBucketHistogramConfiguration
    { Boundaries = [5, 10, 25, 50, 100, 200, 300, 500, 1000, 2000, 5000] })
Overrides the default buckets so there is a boundary at your SLO threshold.

SQL

SELECT DISTINCT
  PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY duration_ms) OVER () AS p50,
  PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY duration_ms) OVER () AS p99
FROM request_log WHERE ts > now() - interval '1 day';
PERCENTILE_CONT interpolates; PERCENTILE_DISC returns an actual observed row.
SELECT route, count(*) AS n,
       percentile_disc(0.99) WITHIN GROUP (ORDER BY duration_ms) AS p99
FROM request_log GROUP BY route HAVING count(*) > 1000;
The HAVING clause is the point: do not report a p99 computed from too few rows.

Load testing without coordinated omission

wrk2 -t4 -c100 -d60s -R2000 --latency https://api.contoso.com/orders/1
-R fixes the request rate rather than waiting for responses, so queueing delay is actually measured.
k6 run --vus 50 --duration 60s script.js   # then read p(95), p(99) from the summary
Use a constant-arrival-rate executor rather than a fixed number of iterations, for the same reason.

Pros & cons

Pros

  • Every percentile is a real request a real user waited for — not a statistical artefact.
  • Immune to outliers in the way that matters: one slow request cannot distort p50.
  • Makes SLOs expressible, measurable and arguable in concrete terms.
  • Reading p50 against p99 diagnoses the problem class before you open a trace.
  • Works on anything with a distribution: latency, payload size, queue depth, GC pauses, cost per request.
  • Computable at scale from mergeable histograms and sketches, in kilobytes.

Cons

  • They cannot be averaged or combined, which almost every default dashboard gets wrong.
  • High percentiles need large samples; on low-traffic endpoints they are noise.
  • Bucketed and sketched percentiles are approximations, with error that is easy to forget.
  • They describe the distribution but say nothing about which requests were slow — you still need traces.
  • Measurement tools silently distort them through coordinated omission.
  • They are not additive, so they cannot be used for capacity or cost arithmetic.

Concrete use cases

Catching a regression an average hid

A deploy adds a synchronous audit write on 3% of requests. The mean moves from 94 ms to 101 ms — well inside normal variation — while p95 jumps from 180 ms to 2,100 ms. Only the percentile dashboard shows it, and the shape (a flat p50 with an exploding tail) points straight at a code path rather than a general slowdown.

Writing a latency SLO that survives review

"The API should be fast" becomes "99% of GET /orders/{id} complete in under 300 ms, measured at the gateway, over 28 days". A histogram boundary is added at exactly 300 ms, the error budget works out to 43 minutes a month, and alerts fire on burn rate rather than on instantaneous value.

Sizing a connection pool

A service with p50 20 ms and p99 900 ms at 500 req/s needs enough concurrency for the tail, not the median. Little's Law on the mean (roughly 94 ms) suggests 47 connections; sizing for the tail says far more. The percentile spread is what tells you the pool is the thing that will saturate.

Diagnosing a bimodal distribution

A chart shows two clusters: one at 25 ms and one at 2,025 ms, with almost nothing in between. The gap is exactly the 2-second client timeout, so the slow group is retries. Percentiles identified the shape; the fix was retry budgeting and jitter, which is also what the rate limiting page recommends.

Proving a tail fix actually worked

After adding hedged requests at the p95 delay, p50 is unchanged, p99 falls from 900 ms to 180 ms, and backend load rises by 4%. That is exactly the expected trade, and it is only visible because p50 and p99 were tracked separately — an average would have shown a modest improvement and hidden both the win and its cost.

When to use / when not to

Describing experience? Percentile. Adding things up? Mean. Never the other way round.

Use percentiles when…

  • You are describing what users experience: latency, load time, queue wait.
  • The distribution is skewed, which for anything time-related it almost always is.
  • You are setting or reporting an SLO.
  • You need to distinguish "normally slow" from "occasionally terrible".
  • You have enough samples — roughly 1,000 in the window for a credible p99.
  • You want a number that corresponds to an actual request you can go and trace.

Avoid them when…

  • You need to add things up: total cost, total CPU, total bytes. Use the sum or the mean.
  • There are only a handful of samples. Report the raw values, or widen the window.
  • The question is "how often did it fail", not "how slow was it". Use a rate or a ratio.
  • You only have per-instance percentiles and cannot merge the distributions. Fix the pipeline first; averaging them is worse than nothing.
  • The data is genuinely symmetric and outlier-free. The mean and standard deviation say more.
  • You need to know which requests were slow and why. Percentiles point; traces and profiles answer.

Common mistakes & gotchas

Averaging percentiles across instancesavg(p99) over ten pods is not the fleet p99 and is not a percentile of anything. One sick instance with 1% of the traffic can make the whole fleet look broken, or a healthy majority can hide a broken minority.
Fix: sum the histogram buckets (or merge the sketches) first, then compute the quantile once — histogram_quantile(0.99, sum by (le) (...)), never avg(histogram_quantile(...)).
Reporting p99 from a handful of samplesOn an endpoint serving ten requests a minute, the one-minute p99 is just the slowest of ten. It swings wildly, triggers alerts at random, and teaches everyone to ignore the dashboard.
Fix: require roughly 1,000 samples in the window for p99. Widen the window on low-traffic endpoints, and show "insufficient data" rather than a confident wrong number.
Coordinated omission in load testsA closed-loop generator stops sending while the server is stalled, so the queueing delay never appears in the results. Reported p99s can be ten times better than reality.
Fix: use an open-loop, constant-rate generator (wrk2 -R, k6 constant-arrival-rate, Gatling injection profiles), or correct with HdrHistogram's expected-interval recording.
Histogram buckets that end too lowIf the top bucket is le="1.0" and the real tail is at 8 seconds, every slow request falls into +Inf and histogram_quantile cannot see past 1 second. Your p99 is pinned to the top bucket and looks suspiciously stable.
Fix: extend the buckets well past the worst latency you have ever seen, and put a boundary exactly at your SLO threshold. Check +Inf minus the top bucket: it should be near zero.
Measuring at the wrong placeThe service reports p99 = 80 ms while users see 3 seconds. The service's timer starts after TLS, queueing, load-balancer wait and request parsing, and stops before the response is written.
Fix: measure as close to the user as possible — real user monitoring in the browser, or at least at the edge — and treat per-service numbers as diagnosis, not as the SLI.
Comparing percentiles across different windows"p99 was 300 ms last week and is 900 ms today" compares a 7-day window with a 5-minute one. Nothing regressed; the windows differ, and shorter windows always look spikier.
Fix: state the window beside every percentile on every dashboard, and compare like with like. Put the sample count next to it too.
Forgetting fan-out when setting targetsEach service hits its 1% tail budget, the page calls ten of them, and 10% of page loads are slow. Every team's dashboard is green and the product is not.
Fix: derive per-service targets from the end-to-end goal and the fan-out factor, and always have one SLO measured on the complete user-visible operation.
Discarding outliers because they look like noiseTrimming the top 1% before charting produces a beautiful, stable graph that has had every incident deleted from it.
Fix: trim only when outliers are measurement artefacts, and never for production experience. Trace the slow requests instead — they are the most informative data you have.

Apdexa single executive-facing satisfaction scoreLowtrivialFolds latency into one 0–1 number; easy to report, hard to debug from

  • Pick the mean when the quantity is additive — money, bytes, CPU seconds.
  • Pick a threshold ratio for SLOs: it aggregates cleanly and converts directly into an error budget.
  • Pick a heatmap when you suspect two populations; percentiles average the bimodality away.
  • Pick traces the moment a percentile tells you something is wrong — percentiles find the problem, traces explain it.
  • The usual production set is: a threshold-based SLO, p50 and p99 on the dashboard, a heatmap for shape, and traces for the outliers.
