Event store

Store what happened, not what is. Everything else is a fold over the facts.

As of Nov 2026 · examples use PostgreSQL, Marten and KurrentDB 26.0 LTS (renamed from EventStoreDB at 25.0)

An ordinary database stores the current state and destroys the previous one on every update: after UPDATE orders SET status='shipped', the fact that it was ever pending is gone unless somebody thought to log it. An event store inverts that. It keeps an append-only sequence of immutable facts — OrderPlaced, ItemAdded, OrderShipped — and derives current state by replaying them. Nothing is ever updated or deleted; the log is the system of record.

Events are grouped into streams, normally one per aggregate (order-42). Loading an aggregate means reading its stream and folding the events into state; writing means appending new events with the version you expected to find, which gives you optimistic concurrency for free. Snapshots keep long streams fast, and subscriptions let any number of readers — projections, process managers, other contexts, the warehouse — follow the log at their own pace.

The payoff is that you cannot lose information you did not know you needed: history, audit and temporal queries are properties of the storage rather than features someone has to add. The bill is paid in schema versioning (a 2024 event must still be readable in 2034), storage that only grows, and a team that has to think in facts rather than rows. It is usually applied to one or two bounded contexts, not to a whole system.

Architecture / mental model

One log, many readers. The aggregate's state and every read model are projections of the same facts — and all of them can be thrown away and rebuilt.

Key concepts

EventAn immutable record that something happened, named in the past tense and never modified after it is written.
StreamThe ordered sequence of events for one thing — normally one stream per aggregate instance.
Append-onlyThe single rule: events are added at the end and never updated or deleted.
Stream versionThe sequence number of an event within its stream — the basis for both ordering and concurrency control.
Optimistic concurrencyAppending with the version you expected to find, so a concurrent writer is rejected instead of silently overwriting.
FoldingRebuilding current state by applying every event in order to an empty starting value. Also called rehydration or replay.
SnapshotA stored copy of folded state at a given version, so long streams do not have to be replayed from the beginning.
Global positionThe order of an event across the whole store, used by anything that reads more than one stream.
SubscriptionA reader that follows the log — from the beginning, from a position, or from now — and is pushed new events as they arrive.
CheckpointThe position a subscriber has processed up to, stored next to whatever it produced.
ProjectionAny derived view built by folding events — a read model, a report, a search index, an aggregate's own state.
Schema versioningEvents are forever, so the code must keep reading the shapes it wrote years ago.
UpcastingTranslating an old event shape into the current one as it is read, so the rest of the code only sees the latest version.
Correction eventHow you fix a mistake in an append-only world: append the opposite, do not edit the past.
Crypto-shreddingDeleting personal data from an immutable log by encrypting it per subject and destroying the key.
Temporal queryAsking what the state was at a past moment, by folding only the events up to it.
Storage growthThe log only ever grows, so replay time, storage cost and archiving are planned work, not surprises.

Essential code patterns

An event store in PostgreSQL

CREATE TABLE events (
    global_seq  bigserial PRIMARY KEY,         -- order across all streams
    stream_id   text        NOT NULL,
    version     int         NOT NULL,          -- order within the stream
    type        text        NOT NULL,
    schema_ver  int         NOT NULL DEFAULT 1,
    data        jsonb       NOT NULL,
    metadata    jsonb       NOT NULL,          -- who, when, correlation
    created_at  timestamptz NOT NULL DEFAULT now(),
    UNIQUE (stream_id, version)                -- this is the concurrency control
);

CREATE INDEX ix_events_stream ON events (stream_id, version);
You do not need a specialised database to start. The unique constraint on (stream_id, version) is optimistic concurrency.
-- append, rejecting the write if someone else got there first
INSERT INTO events (stream_id, version, type, data, metadata)
SELECT $1, $2 + row_number() OVER (), e.type, e.data, $5
FROM   jsonb_to_recordset($3) AS e(type text, data jsonb)
WHERE  (SELECT coalesce(max(version), 0) FROM events WHERE stream_id = $1) = $2;
-- 0 rows inserted => wrong expected version => reload, re-decide, retry
Expected version checked and events written in one statement. Zero rows means a concurrent writer won — reload and decide again.

The aggregate (C#)

public sealed class Order
{
    public int Version { get; private set; }
    private readonly List<OrderLine> _lines = new();

    // Decide: may reject. All invariants live here.
    public IEnumerable<object> AddItem(Sku sku, int qty)
    {
        if (qty <= 0) throw new DomainException("quantity must be positive");
        if (_lines.Sum(l => l.Qty) + qty > 10)
            throw new DomainException("an order cannot hold more than 10 items");
        yield return new ItemAdded(sku, qty);
    }

    // Apply: never rejects. The event already happened.
    private void Apply(object e)
    {
        switch (e) {
            case OrderPlaced:      /* ... */ break;
            case ItemAdded a:      _lines.Add(new OrderLine(a.Sku, a.Qty)); break;
            case ItemRemoved r:    _lines.RemoveAll(l => l.Sku == r.Sku); break;
        }
        Version++;
    }

    public static Order Rehydrate(IEnumerable<object> events)
    {
        var o = new Order();
        foreach (var e in events) o.Apply(e);     // the fold
        return o;
    }
}
Two methods with two different contracts. Decide validates and returns events; Apply only mutates and can never fail.
// load → decide → append with the version you read
var events  = await store.ReadStream($"order-{id}");
var order   = Order.Rehydrate(events);
var newOnes = order.AddItem(sku, qty).ToArray();

try   { await store.Append($"order-{id}", expectedVersion: order.Version, newOnes); }
catch (WrongExpectedVersion) { /* reload, RE-DECIDE, retry — do not just re-append */ }
The retry must re-run the decision: the event that beat you may have made your command invalid.

Subscriptions and projections

def project(batch, conn):
    with conn.transaction():
        for e in batch:
            HANDLERS.get(e.type, noop)(conn, e)
        conn.execute(
            "UPDATE checkpoint SET position = %s WHERE name = 'order_list'",
            (batch[-1].global_seq,),
        )            # rows and checkpoint in ONE transaction
Atomic rows-plus-checkpoint is what makes a subscription safe to restart at any moment.
# rebuild a projection from the beginning — a replay, not a migration
TRUNCATE order_list_view;
UPDATE checkpoint SET position = 0 WHERE name = 'order_list';
# build v2 alongside v1, let it catch up, then switch the queries over
Read-side schema changes stop being migrations. This is the operational superpower of an event store.

Upcasting old events

static object Upcast(string type, int schemaVer, JsonNode data) => (type, schemaVer) switch
{
    // v1 had no currency - every order back then was in EUR
    ("OrderPlaced", 1) => new OrderPlaced(data["total"]!.GetValue<decimal>(), "EUR"),
    ("OrderPlaced", 2) => data.Deserialize<OrderPlaced>()!,
    _                  => throw new UnknownEventVersion(type, schemaVer),
};
Applied on read, so the aggregate and every projection only see the newest shape. The stored bytes are never touched.

Using a dedicated store

// KurrentDB (renamed from EventStoreDB at 25.0) — .NET client
await client.AppendToStreamAsync(
    $"order-{id}",
    StreamRevision.FromInt64(expectedVersion),
    events.Select(ToEventData));

await foreach (var e in client.SubscribeToAll(FromAll.Start))
    Project(e);                      // catch-up subscription over the global log
Streams, expected version and $all subscriptions are first-class rather than hand-rolled.
// Marten — event sourcing on PostgreSQL, projections included
session.Events.Append($"order-{id}", expectedVersion, new ItemAdded(sku, qty));
await session.SaveChangesAsync();

var order = await session.Events.AggregateStreamAsync<Order>(streamId);
Often the pragmatic middle ground: event sourcing semantics without operating a second database.

Operations

-- streams long enough to need a snapshot
SELECT stream_id, count(*) FROM events
GROUP BY stream_id HAVING count(*) > 1000 ORDER BY 2 DESC LIMIT 20;

-- how far behind each projection is
SELECT name, (SELECT max(global_seq) FROM events) - position AS lag FROM checkpoint;
Two queries that catch the two things that go wrong: aggregates that got too long, and projections that stopped.

Pros & cons

Pros

  • Complete history by construction — audit, provenance and "what did we believe then?" are free.
  • New questions can be answered retroactively, because the facts were kept even when nobody was asking.
  • Every derived view is rebuildable, so read-side schema changes become replays instead of migrations.
  • Optimistic concurrency falls out of the stream version; no locks are held between read and write.
  • Append-only writes are sequential and fast, with no in-place updates or update conflicts.
  • Debugging is exceptional: replay a real history into a test and watch the bug occur.

Cons

  • Event schemas are forever; upcasting is permanent, unglamorous maintenance work.
  • "Give me all orders over €500" is impossible without a projection — you cannot query the log usefully.
  • Deletion is genuinely hard, so GDPR needs crypto-shredding designed in from the start.
  • Unfamiliar model: most teams need weeks before the design stops fighting them.
  • Storage and replay time only grow, which becomes an operational constraint if ignored.
  • Eventual consistency between the log and every read model, with all the usual consequences.

Concrete use cases

A ledger that has to balance

Financial systems already think in immutable postings and correcting entries. Modelling them as events rather than mutable balances removes a whole category of "how did this number get here?" investigations, because the number is the fold and the fold is the evidence.

Regulated audit requirements

An insurer must show what the system knew at the moment a claim was assessed. With state-based storage this is a bolted-on audit table that is always slightly wrong. With an event store it is a fold over events up to a timestamp.

The question nobody asked in time

Two years in, product asks how often customers add an item and remove it within a minute. Nobody ever recorded that metric — but ItemAdded and ItemRemoved are all still there, so a new projection replayed from offset zero answers it for the whole history.

Collaborative editing and reconstruction

Several users change a document or an order concurrently. Events record each intention separately rather than the last writer's final state, so conflicts can be reasoned about and the sequence can be replayed to explain exactly what happened.

Device and telemetry history

A fleet of machines emits state changes. Streams per device give a natural history, temporal queries answer "what was it doing at 03:14?", and snapshots keep the current-state load cheap on devices with millions of events.

When to use / when not to

adopt it where history is the product — one or two contexts, not the whole system

Use it when…

  • History, audit or "what did we know then?" is a genuine business requirement.
  • The domain already thinks in events — ledgers, trading, insurance, logistics, workflow.
  • Several views of the same data are needed and you expect to add more later.
  • The why of a change matters as much as the resulting value.
  • You are already doing CQRS and the write model is naturally a sequence of decisions.

Avoid it when…

  • The application is CRUD and nobody will ever ask what changed. Use a relational table.
  • You only need an audit trail. Use an audit log or temporal tables beside normal storage.
  • The data is mostly read and rarely changes. Use a plain database and caching.
  • Personal data dominates and erasure is frequent. Use state-based storage, or design crypto-shredding before writing a line.
  • The team is new to it and the deadline is short. Use CQRS without event sourcing — most of the benefit, far less of the cost.

Common mistakes & gotchas

CRUD eventsOrderUpdated with a full entity snapshot is a row disguised as an event. It carries no intent, so no projection can tell what changed or why, and the whole model collapses back into state storage with extra steps.
Fix: name events after business decisions — AddressCorrected, DiscountApplied — and carry only what changed. If you cannot name it in business language, you have not found the event yet.
Querying the event log"Find all orders over €500" has no answer in an append-only log, and the first attempt is always a desperate jsonb scan over every event ever written.
Fix: every query gets a projection. The log is for writing and replaying; read models are for reading. That is not a workaround, it is the design.
Validation inside ApplyThrowing while applying an event is a contradiction — the event already happened — and it makes replays fail on history that was perfectly valid when it was written.
Fix: all validation goes in the decide step, before the event exists. Apply only mutates state and can never reject anything.
Breaking event schemasRenaming a field or changing its meaning breaks every replay of every event written before the change — and you find out during a rebuild, usually at the worst moment.
Fix: additive changes only. For anything else write an upcaster, and test it against real old payloads rather than against the current class.
Aggregates with unbounded streamsA stream that grows forever eventually takes seconds to load, and snapshots only postpone the problem.
Fix: give aggregates a lifecycle. Close the stream per period or per business cycle and start a new one; add snapshots only for the ones that genuinely must stay open.
Snapshots treated as truthA bug in the fold logic is baked into every snapshot, and since nobody replays from zero any more, the wrong state becomes permanent.
Fix: snapshots are a cache. Version them with the fold logic, and delete and rebuild them whenever it changes.
No plan for deletion"We never delete" and the right to erasure collide about a year in, when the log already holds plaintext personal data in a million events.
Fix: decide up front — keep personal data out of events and reference it, or encrypt it per subject so the key can be destroyed later.
Never rehearsing a full replayThree years of events, a projector bug, and the first complete rebuild turns out to take eleven hours — discovered during the incident, not before it.
Fix: rebuild in CI regularly and track the duration. Partition projections or parallelise the replay long before the number becomes frightening.

ApproachBest forComplexityCost / licenseKey difference vs an event store

State table + outboxmost servicesLowfreeCurrent state is the truth; events are notifications, and history is only what you remembered to keep

KurrentDB (formerly EventStoreDB)event sourcing as the primary modelMediumOSS and commercial editionsPurpose-built: streams, $all, catch-up and persistent subscriptions as primitives
DynamoDB single-tableserverless, very high scaleMediumpay per requestConditional writes give expected-version semantics; subscriptions via Streams, with more assembly required
  • Pick a state table plus an outbox for most services — it is the honest default, and CQRS works fine on top of it.
  • Pick temporal tables or an audit log if you only need "who changed what", not the intent behind it.
  • Pick Kafka for pipelines, not as a system of record: without per-stream expected version you lose the concurrency guarantee that makes aggregates safe.
  • Pick Marten to get event sourcing without adding a database to your operational surface.
  • Pick KurrentDB when event sourcing is the primary model and you want streams, subscriptions and replay as first-class features.
