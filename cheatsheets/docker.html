Docker

Package an app with everything it needs, then run it the same way on any machine.

As of Nov 2026 · Docker Engine 29.x

"It works on my machine" happens because apps depend on things outside their code: a language runtime, system libraries, config files, environment variables. Docker packages all of that into an image, a read-only snapshot of a filesystem plus the command to start. The same image runs identically on a laptop, a CI runner and a production server.

A container is a running instance of an image. It is not a virtual machine: it is an ordinary Linux process that the kernel isolates with namespaces (its own process tree, network and filesystem view) and limits with cgroups (CPU and memory). Containers share the host kernel, so they start in milliseconds and use far less memory than VMs.

Docker popularised containers in 2013 and today the image format and runtime are open standards (OCI). Developers use Docker Engine on Linux or Docker Desktop on Windows and macOS, push images to registries like Docker Hub, and run them in production on orchestrators such as Kubernetes. Docker Engine is open source (Apache 2.0); Docker Desktop is free for personal use and small businesses, and paid for larger companies.

Architecture / mental model

The CLI is only a remote control. The daemon stores images, and each container is just an isolated process running from an image plus a thin writable layer.

Key concepts

imageA read-only template: a stack of filesystem layers plus metadata (start command, env vars, exposed ports). Built once, run anywhere.
containerA running (or stopped) instance of an image: an isolated process with its own writable layer. Many containers can run from one image.
layerThe filesystem changes made by one Dockerfile instruction. Layers are content-addressed, cached and shared between images.
DockerfileA text file of instructions (FROM, COPY, RUN, CMD…) that describes how to build an image.
build cacheDocker reuses a layer when its instruction and inputs are unchanged. Once one step changes, every later step is rebuilt.
registryA server that stores and distributes images: Docker Hub, GitHub Container Registry, ECR, ACR, or a private one.
tag / digestnginx:1.27 is a movable tag; nginx@sha256:… is an immutable digest. Pin digests (or exact tags) in production.
volumeStorage managed by Docker that lives outside the container's writable layer, so data survives when the container is removed.
bind mountMaps a host folder into a container (-v ./src:/app). Handy for live code reloading in development.
networkVirtual network for containers. On a user-defined bridge network, containers reach each other by name (http://api:8000).
port mapping-p 8080:80 forwards host port 8080 to port 80 inside the container. Without it the service is unreachable from outside.
Docker ComposeDefines a multi-container app (services, networks, volumes) in compose.yaml and starts it with one command.
multi-stage buildSeveral FROM stages in one Dockerfile: compile in a big image, copy only the result into a small final image.
.dockerignoreLists files not sent to the build (.git, node_modules, .env). Faster builds and no leaked secrets.
dockerdThe Docker daemon. It exposes the API that the CLI and Compose call, and manages images, networks and volumes.
containerd / runcThe lower-level runtimes Docker uses: containerd manages container lifecycles, runc creates the process following the OCI spec.
namespaces / cgroupsLinux kernel features behind containers: namespaces isolate what a process can see, cgroups limit what it can use.

Essential commands & syntax

Run & inspect

docker run -d --name web -p 8080:80 nginx:1.27
Start a container in the background with a name and a port mapping.
docker run --rm -it python:3.13 bash
Throwaway interactive container, deleted on exit (--rm).
docker ps -a
List containers, including stopped ones.
docker logs -f web
Follow a container's stdout and stderr.
docker exec -it web sh
Open a shell inside a running container.
docker stop web && docker rm web
Stop (SIGTERM, then SIGKILL after 10 s) and remove a container.
docker stats · docker inspect web
Live CPU and memory per container; full JSON configuration of one.

Build & ship

FROM python:3.13-slim AS base
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 1000
CMD ["python", "app.py"]
A cache-friendly Python Dockerfile: dependencies before code, non-root user, exec-form CMD.
docker build -t myapp:1.0 .
Build an image from the Dockerfile in the current folder.
docker tag myapp:1.0 ghcr.io/acme/myapp:1.0
docker push ghcr.io/acme/myapp:1.0
Name the image for a registry and upload it (docker login ghcr.io first).
docker image ls · docker history myapp:1.0
List local images; show the layers of one with their sizes.

Compose & data

services:
  api:
    build: .
    ports: ["8000:8000"]
    environment: [REDIS_URL=redis://cache:6379]
    depends_on: [cache]
  cache:
    image: redis:8
    volumes: [cache-data:/data]
volumes:
  cache-data:
compose.yaml: an API plus a Redis cache, reachable by service name, with a named volume.
docker compose up -d --build
docker compose logs -f api
docker compose down
Build and start everything, follow one service's logs, stop and remove the containers.
docker volume ls · docker system prune
List volumes; free disk space from stopped containers, dangling images and unused networks.
import docker
client = docker.from_env()
c = client.containers.run("redis:8", detach=True, ports={"6379/tcp": 6379})
print(c.name, c.status)
Python SDK (pip install docker): the same API the CLI uses, handy for test fixtures.

Pros & cons

Pros

  • Same artifact from laptop to production: no more "works on my machine".
  • Starts in milliseconds and uses MBs, not GBs, because there is no guest OS.
  • Dependencies are isolated per app: two services can need different Python or library versions.
  • Huge catalog of ready images (databases, brokers, runtimes) for local development.
  • Images are versioned and immutable, so rollbacks are just "run the previous tag".
  • Standard format (OCI) understood by every cloud and orchestrator.

Cons

  • Weaker isolation than VMs: all containers share the host kernel.
  • Container filesystems are ephemeral; persistent data needs volumes and care.
  • On Windows and macOS containers run inside a hidden Linux VM, so file sharing can be slow.
  • Images grow large and slow to ship without multi-stage builds and slim bases.
  • One host only: scheduling, self-healing and scaling across machines need an orchestrator.
  • Docker Desktop requires a paid subscription for larger companies.

Concrete use cases

Local development stack

A new developer clones the repo and runs docker compose up. PostgreSQL, Redis and the API start with the right versions in a minute, without installing anything else.

Reproducible CI builds

GitHub Actions builds and tests inside the same image used in production. The pipeline publishes a tagged image only if tests pass.

Packaging microservices

Each team ships its service as an image with its own runtime (Python 3.13, Node 22, .NET 9). The platform only needs to know how to run containers.

Integration tests with real dependencies

Testcontainers starts a throwaway Kafka or database container per test run, so tests hit real software instead of mocks.

Running tools without installing them

Run a specific CLI version, such as docker run --rm -v .:/w -w /w node:22 npm test, and leave the host untouched.

When to use / when not to

Rule of thumb: one process per container, and no data you can't lose inside it.

Use it when…

  • An app has non-trivial dependencies that must be identical everywhere.
  • You want a one-command local environment for a team.
  • You deploy to Kubernetes, ECS, Cloud Run or any container platform.
  • You need disposable, clean environments for tests and CI.
  • Several apps on one server need different runtime versions.

Avoid it when…

  • You need strong isolation for untrusted code. Use VMs or gVisor/Firecracker.
  • The app is a desktop GUI or needs deep hardware access. Install it natively.
  • You need to schedule containers across many machines. Add an orchestrator such as Kubernetes.
  • A tiny script or static site with no dependencies. Plain hosting is simpler.
  • Your organisation can't license Docker Desktop. Use Podman or Docker Engine inside WSL.

Common mistakes & gotchas

Number 1 makes builds take minutes instead of seconds.
Copying source code before installing dependenciesAny code change invalidates the cache from that line on, so every build reinstalls all packages.
Fix: copy the dependency manifest, install, then COPY . . last.
Storing data in the container filesystemdocker rm or a recreate wipes the writable layer, and with it your database.
Fix: use named volumes for anything that must persist.
Using :latest in productionThe tag moves, so two servers can run different code and rollbacks become guesswork.
Fix: deploy immutable tags (version or git SHA) or digests.
Secrets baked into imagesCOPY .env or ARG TOKEN stays in a layer even if a later step deletes it, and anyone with the image can read it.
Fix: add .dockerignore, use build secrets (--secret) and inject runtime secrets as env vars or mounted files.
Running as rootContainers run as root by default; a breakout or a bad mount gives root access to the host files.
Fix: add a non-root USER in the Dockerfile and drop capabilities you don't need.
Shell-form CMD ignores stop signalsCMD python app.py runs under /bin/sh, which doesn't forward SIGTERM; the app is killed after 10 s instead of shutting down cleanly.
Fix: use exec form CMD ["python", "app.py"].
"localhost" inside a containerIt means the container itself, not your machine or another container.
Fix: use the service name on a shared network (redis://cache:6379), or host.docker.internal for the host.
Disk filling up silentlyOld images, stopped containers and build cache pile up to tens of GB.
Fix: docker system df to see usage, docker system prune regularly.

Alternatives

ToolBest forComplexityCost / licenseKey difference vs Docker
DockerBuilding and running containers on one hostLowEngine: Apache 2.0 · Desktop: paid above small-business limits—
PodmanDrop-in Docker CLI replacementLowApache 2.0, free Podman DesktopNo daemon, rootless by default, can run pods and generate Kubernetes YAML
containerd + nerdctlMinimal runtime on serversMediumApache 2.0 (CNCF)The runtime under Docker and Kubernetes, without Docker's extra tooling
Virtual machinesStrong isolation, other OSesMediumHyper-V, KVM free; VMware paidFull guest OS and kernel: heavier and slower to start, but isolated
LXC / IncusLong-lived "system" containersMediumApache 2.0 / LGPLContainers that behave like small VMs with init and multiple services
BuildpacksImages without writing a DockerfileLowApache 2.0 (CNCF)Detects the language and builds an OCI image automatically
  • Pick Podman if you need rootless containers or can't use Docker Desktop's license.
  • Pick containerd if you run servers or Kubernetes nodes and don't need the Docker CLI.
  • Pick VMs if you run untrusted workloads or need a different kernel or OS.
  • Pick LXC/Incus if you want lightweight machines rather than single-process apps.
  • Pick Buildpacks if teams shouldn't maintain Dockerfiles at all.
