Semantic caching

A normal cache asks "have I seen this exact key?". A semantic cache asks "have I answered this question before, in any words?".

As of Nov 2026 · examples use Redis vector search, pgvector and Microsoft.Extensions.AI

Two users ask "how do I reset my password?" and "I forgot my password, what now?". A key-value cache sees two unrelated strings and calls the model twice. A semantic cache embeds the question, searches for a previous question whose vector is close enough, and if one exists returns that stored answer — in tens of milliseconds, for the price of one embedding call instead of one generation.

The mechanism is small: embed, nearest-neighbour search, compare against a similarity threshold, serve or fall through. The difficulty is entirely in the threshold and the scoping. Set the threshold loose and the cache answers a question nobody asked; scope it badly and user A's answer is served to user B. Unlike an exact cache, a semantic cache can be wrong, which changes it from an optimisation into a correctness decision.

It is most valuable where traffic is repetitive and answers are stable: support and FAQ bots, documentation search, internal assistants, classification pipelines. In those workloads hit rates of 20–40% are ordinary, and each hit removes a two-second, few-cent call and replaces it with a 30 ms lookup.

Architecture / mental model

Cache-aside, with similarity search instead of a key lookup — and one extra failure mode that a key lookup does not have.

Key concepts

Similarity thresholdThe cosine score above which a stored question is treated as "the same question".
False hitServing a cached answer to a question that only looks similar — a wrong answer delivered fast.
Cache namespaceThe partition key that keeps answers from leaking across tenants, users, models and prompt versions.
Hit rateThe share of requests served from the cache — the number that decides whether any of this is worth it.
Savings arithmeticThe back-of-the-envelope that says whether the cache pays for itself.
InvalidationRemoving cached answers when the underlying knowledge, prompt or model changes.
NormalisationCanonicalising the question before embedding so trivial variations collapse to one key.
Exact-match tierA plain hash lookup in front of the semantic cache, catching identical questions for free.
Reranked verificationA cheap second check, after the vector match, that the two questions really are the same question.
Prompt cachingThe provider-side cache of a shared prompt prefix — a different mechanism, often confused with this one.
Negative cachingRemembering that a question had no good answer, so you do not pay to fail twice.
Cold startAn empty cache serves nothing, and the first hours look like pure added latency.
Caching retrieval vs caching answersYou can cache the final text, or just the retrieved chunks — and the trade-offs are different.
EvictionHow entries leave a cache that would otherwise grow without limit.
ObservabilityLogging the similarity, the matched entry and the served source on every request — the only way false hits become visible.

Essential code

The three tiers

// C# — exact tier, then semantic tier, then generate
public sealed class SemanticCache(IDatabase redis, IEmbeddingGenerator<string, Embedding<float>> embedder)
{
    private const double Threshold = 0.95;

    public async Task<(string Answer, string Source)> GetOrCreateAsync(
        string question, CacheScope scope, Func<Task<string>> generate)
    {
        var norm = Normalise(question);
        var ns   = scope.Key();                       // tenant + model + promptVersion + locale

        // 1. exact tier — sub-millisecond, zero risk
        var exactKey = $"sc:{ns}:x:{Sha256(norm)}";
        if (await redis.StringGetAsync(exactKey) is { HasValue: true } hit)
            return (hit!, "exact");

        // 2. semantic tier
        var vector = (await embedder.GenerateAsync([norm]))[0].Vector;
        var match  = await NearestAsync(ns, vector, limit: 1);
        if (match is { Similarity: >= Threshold } m && Verify(norm, m.Question))
            return (m.Answer, "semantic");

        // 3. miss — pay once, store for everyone after
        var answer = await generate();
        await redis.StringSetAsync(exactKey, answer, TimeSpan.FromHours(24));
        await StoreAsync(ns, vector, norm, answer, TimeSpan.FromHours(24));
        return (answer, "miss");
    }

    private static string Normalise(string q) =>
        string.Join(' ', q.ToLowerInvariant().Trim().TrimEnd('?', '!', '.')
                          .Split(' ', StringSplitOptions.RemoveEmptyEntries));
}
Exact before semantic, verification before serving, and the namespace in every key. The shape is cache-aside with a different lookup.
# Python — same three tiers with redis-py
import hashlib, re
from dataclasses import dataclass

THRESHOLD = 0.95

def normalise(q: str) -> str:
    return " ".join(q.lower().strip().rstrip("?!.").split())

def get_or_create(question: str, scope: str, generate) -> tuple[str, str]:
    norm = normalise(question)
    exact_key = f"sc:{scope}:x:{hashlib.sha256(norm.encode()).hexdigest()}"

    if (cached := r.get(exact_key)) is not None:
        return cached.decode(), "exact"

    vector = embed(norm)
    match = nearest(scope, vector, limit=1)
    if match and match.similarity >= THRESHOLD and verify(norm, match.question):
        return match.answer, "semantic"

    answer = generate()
    r.setex(exact_key, 86_400, answer)
    store(scope, vector, norm, answer, ttl=86_400)
    return answer, "miss"
Identical logic. The interesting lines are verify and scope — everything else is plumbing.

The vector store behind it

# Redis — a vector index over cached questions, partitioned by namespace
FT.CREATE idx:semcache
  ON HASH PREFIX 1 "sc:v:"
  SCHEMA
    ns        TAG                                  # the hard partition
    question  TEXT
    answer    TEXT NOSTEM
    chunks    TAG                                  # cited chunk ids, for targeted purge
    embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 1536 DISTANCE_METRIC COSINE

# query: nearest neighbour WITHIN one namespace — a pre-filter, not a post-filter
FT.SEARCH idx:semcache "(@ns:{t42_gpt41mini_v7_enGB})=>[KNN 1 @embedding $vec AS score]"
  PARAMS 2 vec "$BLOB" RETURN 3 question answer score DIALECT 2
The @ns tag filter runs before the KNN search, so one tenant's entries can never be candidates for another's query.
-- Postgres alternative: pgvector, with the cited chunks kept for invalidation
CREATE TABLE semantic_cache (
  id          bigserial PRIMARY KEY,
  ns          text        NOT NULL,
  question    text        NOT NULL,
  answer      text        NOT NULL,
  embedding   vector(1536) NOT NULL,
  cited_chunks text[]     NOT NULL DEFAULT '{}',
  hits        int         NOT NULL DEFAULT 0,
  created_at  timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz NOT NULL
);
CREATE INDEX ON semantic_cache USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON semantic_cache (ns, expires_at);
CREATE INDEX ON semantic_cache USING gin (cited_chunks);

-- lookup
SELECT question, answer, 1 - (embedding <=> $1) AS similarity
FROM semantic_cache
WHERE ns = $2 AND expires_at > now()
ORDER BY embedding <=> $1
LIMIT 1;

-- targeted invalidation when a document is re-ingested
DELETE FROM semantic_cache WHERE cited_chunks && $1;   -- array overlap
Storing the cited chunk ids is what turns "we changed a document" into a precise purge instead of a full flush.

Guarding against false hits

// C# — cheap rules that catch the classic false-hit pairs before anything expensive
private static readonly Regex Tokens = new(@"\b([A-Z]{2,}|\d[\d\-/]*|INV-\w+)\b");

private static bool Verify(string incoming, string cached)
{
    // 1. identifiers, numbers and codes must match exactly, in both directions
    var a = Tokens.Matches(incoming).Select(m => m.Value).ToHashSet();
    var b = Tokens.Matches(cached).Select(m => m.Value).ToHashSet();
    if (!a.SetEquals(b)) return false;

    // 2. negation must match — embeddings barely move for "not"
    static bool Negated(string s) => Regex.IsMatch(s, @"\b(not|never|cannot|can't|without)\b");
    if (Negated(incoming) != Negated(cached)) return false;

    return true;
}
Twelve lines that remove the two failure modes responsible for most false hits: swapped identifiers and flipped negations.

Pros & cons

Pros

  • Removes the whole generation call, not part of it — typically 1–3 s and most of the cost.
  • Catches paraphrases, which is the majority of real repetition in natural language traffic.
  • Break-even hit rate is under 1%, because embeddings are hundreds of times cheaper than generation.
  • Works as a capacity buffer: cached answers keep flowing during provider rate limits or outages.
  • Entirely in your infrastructure, so it works across models and providers.
  • The cache of refused questions is a free content-gap report.

Cons

  • It can serve a wrong answer, which an exact cache structurally cannot.
  • The threshold must be derived from labelled data and re-derived after any embedding model change.
  • Scoping bugs are data leaks: one missing tenant filter crosses a boundary.
  • Adds 10–25 ms and an embedding call to every request, including misses.
  • Invalidation is harder than in a key cache: you must know which documents an answer used.
  • Near-useless for personalised, multi-turn or agentic traffic.
  • Hides model improvements — a better model's answers are not served while old entries live.

Concrete use cases

Public FAQ assistant

A help centre bot answers the same forty intents in a thousand phrasings. Hit rate settles near 60%, the public scope means no per-user partitioning, and cached answers return in 30 ms — which also makes the bot feel faster than the search it replaced.

Documentation search over a stable corpus

An internal docs assistant on a corpus that changes weekly. Answers are cached for 24 hours, keyed by prompt version and index version, and purged by cited chunk id whenever a page is republished.

Surviving a rate limit

A provider starts returning 429s at peak. Cached answers continue to serve a third of traffic unaffected, turning a total outage into partial degradation while the rest of the requests queue — the same idea as graceful degradation, applied to spend.

Classification and extraction pipelines

Millions of near-duplicate support emails classified into twenty categories. Outputs are short and stable, so a long TTL and a moderate threshold remove most of the model calls, with a rules check on extracted identifiers to prevent cross-contamination.

Evaluation and CI runs

A golden set of 200 questions runs on every pull request. A semantic cache keyed on prompt version makes unrelated changes cost nothing, while a prompt change bumps the version and re-runs everything — which is exactly the behaviour you want.

When to use / when not to

if a wrong answer is expensive, raise the threshold until the cache is almost useless. then ask if you need it.

Use it when…

  • Traffic is head-heavy: a few hundred intents cover most requests.
  • Answers are impersonal — the same question deserves the same answer for everyone in scope.
  • The underlying corpus changes on a timescale of hours or days, not seconds.
  • Latency matters and a 25 ms answer is meaningfully better than a 2 s one.
  • You are rate limited or cost constrained and have measured a hit rate above a few percent.

Avoid it when…

  • Answers depend on the individual user or live data. Cache the retrieval result instead of the answer.
  • A wrong answer is unacceptable — medical, legal, financial. Use an exact-match cache only.
  • Traffic is open-ended or multi-turn, so almost nothing repeats. Use prompt caching and a cheaper model.
  • You cannot reliably scope entries per tenant or per permission set. Fix the scoping first.
  • You have no evaluation set, so a regression from a false hit would be invisible. Build that first.
  • The expensive part is retrieval, not generation. Cache the search, or use an ordinary Redis key cache.

Common mistakes & gotchas

Picking the threshold by feel0.9 looks like a high number, so it gets used. In most embedding spaces almost any two questions on the same topic score above 0.9, and the cache starts answering questions that were never asked.
Fix: label 200–500 real question pairs as same/different, plot precision and recall against the threshold, and pick the point where precision is acceptable. Re-run it whenever the embedding model changes.
No tenant or permission scopeThe cache key is the question text, so a question asked in tenant A returns an answer built from tenant A's documents to a user in tenant B. It is a data leak with a cache hit rate graph that looks excellent.
Fix: namespace every entry by tenant and visibility scope, and apply it as a pre-filter inside the vector query. Add a test that proves a cross-tenant lookup returns nothing.
Ignoring negation and numbers"Can I return an item after 30 days?" and "Can I return an item after 60 days?" are nearly the same vector. So are a question and its negation. Both serve confidently wrong answers.
Fix: a verification step that compares extracted numbers, dates, identifiers and negation words, and rejects the match when they differ. It is a regex and a set comparison.
Caching the answer when the data is liveStock levels, prices, open tickets and account balances get frozen into cached text, and the system confidently reports yesterday's number for a day.
Fix: cache the retrieval result, not the answer, for anything time-sensitive; or exclude those intents from the cache entirely with a classifier on the question.
Flushing the whole cache on deployEvery release throws away a warm cache, so hit rate restarts at zero and the first hour after each deploy is slow and expensive.
Fix: put the prompt and model version in the namespace. Entries from the previous version stop matching and expire naturally; nothing has to be deleted.
No way to tell a cached answer from a fresh oneA user reports a wrong answer. Nobody can tell whether the model produced it just now or the cache served it from a different question three days ago, so the investigation starts from nothing.
Fix: log source, similarity and matched entry id on every request, and propagate a cache.source attribute into your traces.
Changing the embedding model in placeNew entries are written with new-model vectors while old entries hold old-model vectors. Distances between the two spaces are meaningless, so the threshold no longer means what it meant.
Fix: include the embedding model id in the namespace. New entries simply form a new partition, and the old one expires.
Caching whole conversationsIn a multi-turn assistant the cache key is the full history, which is unique almost every time. Hit rate is near zero and the embedding call is pure overhead.
Fix: cache on the condensed standalone question produced by query rewriting, not on the raw transcript — or accept that this workload does not cache and spend the effort on prompt caching.

  • Pick an exact-match cache as tier one always — it is cheaper, safer and catches a surprising share of traffic.
  • Pick prompt caching when the repetition is in your system prompt and tool catalogue rather than in user questions.
  • Pick precomputed answers when a small set of questions dominates and the answers deserve human review.
  • Pick retrieval caching whenever the answer must reflect live data or differ per user.
  • Pick a smaller model when the hit rate measurement comes back in low single digits — your traffic simply does not repeat.
