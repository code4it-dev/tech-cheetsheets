JWT & token handling

Signed, not secret. Verifiable, not revocable. Everything else follows from those two facts.

As of Nov 2026 · RFC 7519 (JWT), RFC 7515 (JWS), RFC 7517 (JWK), RFC 8725 (BCP) · examples in C# and Python

A JSON Web Token is three Base64URL segments joined by dots: a header saying how it was signed, a payload of claims, and a signature over the first two. Its single advantage is that anyone holding the issuer's public key can verify it offline — no database lookup, no call to an auth service, no shared session store. That is what lets a token minted in one place be trusted by a hundred services.

Two properties cause most of the trouble. First, a signed JWT is not encrypted: the payload is readable by anyone who has the token, including the browser and anyone who finds it in a log. Second, a JWT cannot be revoked — validation is a pure function of the token and a public key, so nothing you do server-side can make an already-issued token stop working before it expires.

The rest is validation discipline. The checks have an order, several are routinely skipped, and the two famous attacks — alg: none and algorithm confusion — both work by persuading your library to take instructions from the very token it is meant to be checking. Use a maintained library, pin the algorithms yourself, and validate the audience.

Architecture / mental model

your pinned algorithm list 2 · iss — exactly the issuer you expect 3 · aud — minted for this service 4 · exp / nbf — with a small skew allowance 5 · scope / roles — may it do this? 6 · your own rules — may this user touch this record? nothing in a JWT says "still valid" — it only says "not yet expired"

Stateless validation is the whole point and the whole cost: no lookup needed, and no way to take it back.

Key concepts

JWSA signed JWT — the kind you almost always mean. Three segments, integrity-protected, publicly readable.
JWEAn encrypted JWT, five segments instead of three — for when the claims themselves must be hidden.
HeaderThe first segment: which algorithm signed the token and which key to verify it with.
PayloadThe claims — and a reminder that Base64URL is an encoding, not a protection.
Registered claimsThe standard seven: iss, sub, aud, exp, nbf, iat, jti — each with a defined meaning and a reason to check it.
SignatureThe only part that makes the other two trustworthy, and the only part an attacker cannot forge.
Symmetric vs asymmetricHS256 shares one secret; RS256 and ES256 split signing from verification. The choice decides who can mint tokens.
JWKSThe issuer's public keys as JSON, fetched over HTTPS and cached — what makes rotation invisible.
alg confusionForging a token by changing the header so the verifier uses an algorithm — and a key — the attacker controls.
Expiry & clock skewexp and nbf decide whether a token is current — and servers whose clocks disagree decide whether that works.
RevocationThe thing a JWT cannot do. Validation is offline, so nothing server-side can stop an issued token early.
jti & replayThe token's unique id — the hook for one-time use and for denylists.
AudienceWhich service the token was minted for — and the check whose absence turns one compromise into many.
Token confusionAccepting a token of the wrong kind — an ID token where an access token belongs, or a refresh token at an API.
Token sizeJWTs are sent on every request, and a fat one costs bandwidth, cache space and sometimes a 431.
StorageWhere a browser keeps a token, and why every option is a trade rather than a solution.
Sender-constrained tokensBinding a token to the client that obtained it, so a stolen copy cannot be used — DPoP or mTLS.
Don't write your ownToken validation is a solved problem with many sharp edges — use a maintained library and configure it.

Essential code & commands

Validating one properly

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "https://login.example.com";   // discovery + JWKS, cached and rotated
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer           = true,
            ValidIssuer              = "https://login.example.com",
            ValidateAudience         = true,
            ValidAudience            = "api://orders",        // the skipped check
            ValidateLifetime         = true,
            ValidateIssuerSigningKey = true,
            ValidAlgorithms          = ["RS256", "ES256"],    // pinned — never from the header
            ClockSkew                = TimeSpan.FromSeconds(30),  // not the 5-minute default
            RequireExpirationTime    = true,
            RequireSignedTokens      = true,                  // rejects alg: none outright
        };
    });
Six lines of policy. ValidAlgorithms and ValidAudience are the two that turn a generic verifier into a safe one.
import jwt                                   # PyJWT
from jwt import PyJWKClient

jwks = PyJWKClient("https://login.example.com/.well-known/jwks.json",
                   cache_keys=True, lifespan=3600)       # cache, refresh on new kid

def validate(token: str) -> dict:
    key = jwks.get_signing_key_from_jwt(token).key
    return jwt.decode(
        token,
        key,
        algorithms=["RS256", "ES256"],        # REQUIRED — pinned, not read from the header
        issuer="https://login.example.com",
        audience="api://orders",              # raises if it does not match
        leeway=30,                            # clock skew, in seconds
        options={"require": ["exp", "iat", "iss", "aud"],
                 "verify_signature": True, "verify_exp": True, "verify_aud": True},
    )
PyJWT makes algorithms mandatory precisely because omitting it was the bug. options["require"] rejects tokens that simply leave a claim out.

What not to write

// every line of this is a vulnerability
var parts   = token.Split('.');
var header  = JsonSerializer.Deserialize<Header>(Base64UrlDecode(parts[0]));
var payload = JsonSerializer.Deserialize<Claims>(Base64UrlDecode(parts[1]));

if (payload.Exp < DateTimeOffset.UtcNow.ToUnixTimeSeconds()) return Unauthorized();
if (payload.Role == "admin") return AdminPanel();     // the signature was never checked

// no signature verification · algorithm taken on trust · no issuer · no audience
Decoding without verifying is fine for a log line and nothing else. The payload is attacker-controlled until the signature says otherwise.
# and the Python version of the same mistake
import base64, json
payload = json.loads(base64.urlsafe_b64decode(token.split(".")[1] + "=="))
if payload["role"] == "admin":        # unsigned, unverified, attacker-supplied
    ...

# jwt.decode(token, options={"verify_signature": False})  — debugging only, never a decision
Both forms show up in real code, usually written to "just read the user id" and then quietly relied on for authorization.

Issuing one, when it is genuinely yours to issue

// a short-lived, narrowly scoped token signed with an asymmetric key
var handler = new JsonWebTokenHandler();
var token = handler.CreateToken(new SecurityTokenDescriptor
{
    Issuer   = "https://login.example.com",
    Audience = "api://orders",
    Expires  = DateTime.UtcNow.AddMinutes(10),          // minutes, not days
    Claims   = new Dictionary<string, object>
    {
        ["sub"]   = userId,
        ["scope"] = "orders.read",
        ["jti"]   = Guid.CreateVersion7().ToString(),    // so it can be denylisted
    },
    SigningCredentials = new SigningCredentials(rsaKey, SecurityAlgorithms.RsaSha256),
});
Asymmetric signing means consumers can verify without being able to mint. With HS256 every validator is also an issuer.
import jwt, uuid, datetime as dt

token = jwt.encode(
    {
        "iss":   "https://login.example.com",
        "aud":   "api://orders",
        "sub":   user_id,
        "scope": "orders.read",
        "jti":   str(uuid.uuid4()),
        "iat":   dt.datetime.now(dt.UTC),
        "exp":   dt.datetime.now(dt.UTC) + dt.timedelta(minutes=10),
    },
    private_key_pem,                 # the private half only
    algorithm="RS256",
    headers={"kid": "a1b2c3"},       # so verifiers can pick the right public key
)
Always set kid when you issue. Without it, rotating your signing key means a flag day for every consumer.

Inspecting a token

# decode the payload without verifying — for debugging only
cut -d. -f2 <<< "$TOKEN" | base64 -d 2>/dev/null | jq .

# which key signed it?
cut -d. -f1 <<< "$TOKEN" | base64 -d 2>/dev/null | jq '{alg, kid, typ}'

# and the keys the issuer currently publishes
curl -s https://login.example.com/.well-known/jwks.json | jq '.keys[] | {kid, alg, kty}'
Use a local decode rather than pasting a production token into a website — it is a live credential until it expires.

Short lifetimes, plus a denylist where it matters

// revocation for the few tokens worth the state
public async Task<bool> IsRevokedAsync(string jti, DateTimeOffset exp)
    => await cache.KeyExistsAsync($"revoked:{jti}");

public async Task RevokeAsync(string jti, DateTimeOffset exp)
    => await cache.StringSetAsync($"revoked:{jti}", "1",
                                  expiry: exp - DateTimeOffset.UtcNow);  // self-cleaning
The denylist only has to outlive the token, so it stays small. Do this for refresh and high-value tokens, not for every access token.

Pros & cons

Pros

  • Validated offline against a public key — no lookup, no shared session store, no coupling.
  • Any number of services can trust tokens minted by one issuer.
  • Compact enough for an HTTP header, and URL-safe by construction.
  • Standardised claims make generic validation possible across providers.
  • Asymmetric signing means verifiers cannot forge what they verify.
  • JWKS and kid allow key rotation with no coordinated deployment.

Cons

  • Cannot be revoked — only expired, which makes lifetime a security decision.
  • Readable by anyone holding it; "encoded" is not "encrypted".
  • A bearer credential: theft equals full access for the remaining lifetime.
  • Validation has many steps and several have well-known exploits when skipped.
  • Grows easily, and a fat token breaks proxies and cookie limits.
  • Browser storage has no genuinely safe option without a backend.

Concrete use cases

One issuer, forty services

An identity provider mints access tokens; every service validates them locally against the cached JWKS. No service calls the provider per request, and adding a service means configuring an audience rather than provisioning credentials.

A gateway that validates once

The API gateway verifies the signature, issuer, audience and expiry, then forwards the request with the claims it extracted. Internal services trust the gateway and skip the cryptography — provided nothing can reach them directly.

Single-use password reset links

A short-lived JWT with a jti and a ten-minute expiry. The jti is recorded on first use, so clicking the link twice fails — a one-shot credential with no table of reset tokens to manage.

Service-to-service with no shared secret

Each service presents a token signed by the platform's identity. Verification needs only the public keys, so there is no secret to distribute, rotate or leak, and a compromised service cannot mint tokens for others.

Carrying tenant context

The token includes a tenant claim, and every service reads the tenant from the validated token rather than from a header or the URL — which is what stops a user asking for another tenant's data by editing a request.

When to use / when not to

short lifetimes, pinned algorithms, checked audience — the rest is detail

Use it when…

  • Several services must trust credentials issued somewhere else.
  • Per-request validation has to be local and fast.
  • You are already using OAuth or OIDC — the tokens are JWTs anyway.
  • You need short-lived, self-contained, single-use artefacts like reset links.
  • Verifiers must not be able to mint tokens, so asymmetric signing matters.

Avoid it when…

  • It is one application with its own users. Use a server session and a cookie — revocation is then free.
  • You need immediate revocation. Use opaque tokens with introspection, or very short lifetimes.
  • The data must be hidden from the holder. Use a lookup by sub, or JWE if it genuinely must travel.
  • You are tempted to track every token's jti. Use sessions; you have rebuilt them with extra steps.
  • You would write the signing and validation yourself. Use a maintained library.

Common mistakes & gotchas

Trusting the header's algorithmLetting the token say how it should be verified enables both alg: none and algorithm confusion, where the attacker signs with the public key as an HMAC secret.
Fix: pin an allow-list in configuration — ValidAlgorithms in .NET, the mandatory algorithms= in PyJWT — and never use one key with two algorithms.
Not validating the audienceSignature-only validation accepts every token your issuer ever signed: tokens for other services, ID tokens meant for a client, tokens obtained by another application.
Fix: always set the expected audience, and use token exchange rather than forwarding a token to a downstream service.
Putting secrets in the payloadBase64URL is an encoding. Anyone with the token — the browser, a log aggregator, a support engineer — can read every claim in it.
Fix: treat the payload as public. Carry identifiers and look sensitive data up server-side; reach for JWE only when something truly must travel hidden.
Expecting revocation to workDeactivating a user does not invalidate their token. It keeps working until exp, because the API never asks anyone.
Fix: keep access tokens to minutes, revoke the refresh token, and add a jti denylist for the few tokens where the window is unacceptable.
Five-minute clock skewSeveral libraries default to it, which silently extends every token's usable life by five minutes past expiry.
Fix: set it to about 30 seconds and run NTP. If you need more than that, fix the clocks rather than the validator.
Decoding to read a claim, then relying on itCode that decodes the payload "just to get the user id" tends to become code that authorizes on it, and the signature was never checked.
Fix: verify first, read second. If you need an unverified peek for logging, name the function so it cannot be mistaken for validation.
Tokens in localStorageReadable by any script on the page, so one XSS or one bad dependency is a complete account takeover for the token's lifetime.
Fix: a BFF holding tokens server-side with an httpOnly, SameSite cookie to the browser. If that is impossible, keep tokens in memory only and accept the reload cost.
Stuffing claims until the token breaksGroup lists and permission sets push tokens past 8 KB, and proxies start returning 431 or truncating headers — usually for your largest customer first.
Fix: carry sub, tenant and a few roles. Look up anything large server-side and cache it; a token is a credential, not a profile.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs JWT
JWT (JWS)stateless, cross-service credentialsMediumfree—
Opaque tokens + introspectionwhen revocation must be immediateMediumfree; a call per requestRandom string, state at the issuer: instantly revocable, but every validation is a network call
Server sessionsa single applicationLowa session storeRevocation is free and nothing is readable by the client; does not cross service boundaries
PASETOavoiding JWT's footgunsLowfreeVersioned, no algorithm negotiation — so no alg confusion; far less ecosystem support
Macaroonsdelegation with attenuationHighfreeHolders can narrow a token's scope without the issuer; powerful, rarely supported
mTLSservice-to-service identityMediumcertificate infrastructureIdentity at the transport layer, not a bearer credential; no claims, no user delegation
API keyssimple server-to-serverVery lowfreeOne long-lived secret, no expiry, no claims — revocable, but opaque and easily leaked
  • Pick opaque tokens when a compromised session must die immediately and you can afford the introspection call.
  • Pick server sessions for a single application — they are simpler and revocation costs nothing.
  • Pick PASETO if you control both ends and want a format with no algorithm negotiation to get wrong.
  • Pick mTLS for machine identity; it is stronger than any bearer token because it cannot be replayed.
