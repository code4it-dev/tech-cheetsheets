Outbox pattern

You cannot commit a database and a broker together. So write the message as a row, and let it ride along.

As of Nov 2026 · examples use PostgreSQL, Kafka and Debezium; the idea is engine-agnostic

Almost every service that owns data also has to tell someone about it: save the order and publish OrderPlaced. These are two different systems with two different transaction managers, so "do both or neither" is not something you can simply write down. This is the dual write problem, and left alone it produces two failures that are both silent: an event that was never published, and an event published for work that then rolled back.

The transactional outbox removes the second system from the critical path. The event is written as an ordinary row into an outbox table in the same transaction as the state change, so it is atomic by construction — one commit, one database, no new guarantees needed. A separate relay then reads that table and publishes to the broker, retrying until it succeeds.

What you buy is that no event is ever lost and no event is ever invented. What you pay is that delivery becomes at-least-once: the relay can crash after publishing and before marking the row sent, so every consumer must be idempotent. That trade — duplicates instead of losses — is almost always the right one, because duplicates can be detected and losses cannot.

Architecture / mental model

The message becomes data first and a message second. Everything after the commit is retryable, because the fact is already durable.

Key concepts

Dual writeWriting to two systems that cannot share a transaction — the problem the outbox exists to remove.
Outbox tableAn ordinary table in the service's own database where outgoing messages are inserted inside the business transaction.
RelayThe separate process that reads unsent outbox rows and publishes them to the broker, retrying until it succeeds.
Polling publisherThe simplest relay: periodically select unsent rows, publish them, mark them sent.
Change data captureTailing the database's own replication log instead of polling, so the outbox is published with no extra queries.
At-least-onceThe delivery guarantee an outbox gives you: every message arrives, and some arrive more than once.
Idempotent consumerA consumer for which processing the same message twice has the same effect as processing it once.
Inbox tableThe mirror image of the outbox: the consumer records processed message ids, in the same transaction as its own state change.
Message idA stable identifier generated once, when the outbox row is written — never when it is published.
OrderingMessages are published in outbox id order, and keyed by aggregate id so a consumer sees one entity's events in sequence.
LagThe age of the oldest unsent outbox row — the one metric that tells you the pattern is working.
Poison messageA row the relay can never publish, which blocks everything behind it if the relay insists on order.
RetentionDeleting published rows, so the outbox does not quietly become the largest table in the database.
Two-phase commitThe distributed protocol that would make a dual write atomic — and the reason almost nobody uses one.
Listen to yourselfA variant where the producing service also consumes its own published event, instead of updating state directly.

Essential code patterns

The table

CREATE TABLE outbox (
    id            bigserial PRIMARY KEY,       -- publication order
    message_id    uuid        NOT NULL UNIQUE, -- consumer dedup key
    aggregate_id  uuid        NOT NULL,        -- partition key
    type          text        NOT NULL,
    payload       jsonb       NOT NULL,
    occurred_at   timestamptz NOT NULL DEFAULT now(),
    sent_at       timestamptz,
    attempts      int         NOT NULL DEFAULT 0
);

CREATE INDEX ix_outbox_unsent ON outbox (id) WHERE sent_at IS NULL;
A partial index on unsent rows keeps the relay's query fast even when the table holds millions of published rows.
BEGIN;
  INSERT INTO orders (id, customer_id, total) VALUES (...);
  INSERT INTO outbox (message_id, aggregate_id, type, payload)
       VALUES (gen_random_uuid(), $order_id, 'OrderPlaced', $payload);
COMMIT;        -- both rows, or neither. no broker involved.
The entire pattern in four lines: the message becomes data, committed atomically with the state it describes.

The relay

BEGIN;
SELECT id, message_id, aggregate_id, type, payload
FROM   outbox
WHERE  sent_at IS NULL
ORDER  BY id
LIMIT  100
FOR UPDATE SKIP LOCKED;     -- lets several relay instances run safely
-- publish each row, then:
UPDATE outbox SET sent_at = now() WHERE id = ANY($ids);
COMMIT;
Publish first, mark second. A crash in between republishes — at-least-once, which is the guarantee you want.
-- wake the relay immediately instead of waiting for the next poll
NOTIFY outbox_new;
-- relay: LISTEN outbox_new, and keep a 1s poll as a safety net
Removes polling latency without removing the poll — the poll is what recovers after a missed notification.
-- the metric that matters
SELECT now() - min(occurred_at) AS oldest_unsent
FROM   outbox WHERE sent_at IS NULL;
Alert on the age of the oldest unsent row. Everything else can look healthy while nothing is being delivered.
-- retention: delete published rows in small batches
DELETE FROM outbox
WHERE id IN (SELECT id FROM outbox
             WHERE sent_at < now() - interval '7 days' LIMIT 10000);
Or partition the outbox by day and drop partitions — instant, and no vacuum debt.

C#

public async Task Handle(PlaceOrder cmd, CancellationToken ct)
{
    var order = Order.Place(cmd.CartId, cmd.CustomerId);
    db.Orders.Add(order);

    foreach (var e in order.ReleaseEvents())
        db.Outbox.Add(new OutboxRow {
            MessageId   = Guid.CreateVersion7(),
            AggregateId = order.Id,
            Type        = e.GetType().Name,
            Payload     = JsonSerializer.Serialize(e),
        });

    await db.SaveChangesAsync(ct);   // ONE transaction — no broker call here
}
The handler never touches the broker. An EF Core SaveChanges interceptor can add the outbox rows automatically so nobody can forget.

Consumer side: the inbox

CREATE TABLE inbox (
    message_id   uuid PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);
One column does the work: the primary key is the deduplication.
def handle(msg, conn):
    with conn.transaction():
        inserted = conn.execute(
            "INSERT INTO inbox (message_id) VALUES (%s) ON CONFLICT DO NOTHING",
            (msg.message_id,),
        ).rowcount
        if not inserted:
            return                      # already processed — ack and move on
        create_shipment(conn, msg)      # same transaction as the dedup marker
Dedup marker and business change commit together, which turns at-least-once delivery into exactly-once processing.

No relay at all: CDC

{
  "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
  "table.include.list": "public.outbox",
  "transforms": "outbox",
  "transforms.outbox.type":
      "io.debezium.transforms.outbox.EventRouter",
  "transforms.outbox.route.by.field": "type",
  "transforms.outbox.table.field.event.key": "aggregate_id"
}
Debezium's outbox event router tails the WAL, unwraps each row into a proper event and keys it by aggregate — no polling, millisecond latency, no relay code.

Pros & cons

Pros

  • No event is ever lost and no event is ever published for work that rolled back.
  • Uses only a local transaction — no distributed protocol, no 2PC, no new guarantees from the broker.
  • The service keeps working when the broker is down; messages drain when it returns.
  • The broker call leaves the request path, so latency and tail latency improve.
  • Works with any broker and any database that has transactions.
  • The outbox doubles as an audit trail and a replay source while rows are retained.

Cons

  • Delivery becomes at-least-once, so every consumer must be idempotent — including ones other teams own.
  • Another moving part to run, monitor and alert on: the relay and its lag.
  • Publication latency grows by the poll interval unless you use CDC or notifications.
  • The table grows fast and needs real retention, or it becomes your largest table.
  • Strict ordering needs care once more than one relay instance runs.
  • Does not help across two databases — that is a saga, not an outbox.

Concrete use cases

Orders that never reached shipping

A handful of orders a week are paid for and never shipped. The handler commits the order and then publishes, and the gap between those two statements is exactly where the pod gets rescheduled. An outbox row written in the same transaction removes the gap entirely.

Shipments for orders that do not exist

The opposite bug: the service publishes first so the event is never lost, and then a unique-constraint violation rolls the order back. Downstream, a shipment and an invoice already exist for nothing. The outbox makes a rolled-back transaction leave no trace.

Broker outage without an incident

Kafka is unavailable for twenty minutes. Because nothing in the request path talks to it, the API keeps serving 200s and the outbox simply grows; when the broker returns the relay drains the backlog in order. The only visible signal was the lag metric.

Feeding a CQRS read model

A projection must never miss an event or it is permanently wrong. Reading from the outbox (directly or via CDC) guarantees the projector sees every committed change, and the message id gives it a free deduplication key.

Tail latency in the request path

p99 checkout latency is dominated by an occasional slow broker publish. Moving the publish out of the transaction and into the relay takes the broker off the critical path; p99 drops to the database's own numbers.

When to use / when not to

if a commit and a publish appear in the same method, you already need this

Use it when…

  • A state change in your database must reliably result in a message to someone else.
  • Losing an event would cause real, hard-to-detect inconsistency — money, stock, shipments.
  • You want to stay available when the broker is not.
  • You are feeding a read model or a projection that must not miss anything.
  • You already have a transactional database next to the thing emitting events.

Avoid it when…

  • Losing the occasional message is genuinely fine — metrics, analytics pings. Use fire-and-forget publishing.
  • The service has no database. Use the broker as the system of record, or an idempotent retry from the caller.
  • You are event-sourced already. Use the event store as the outbox; a second copy adds nothing.
  • The work spans two services' databases and must be undone on failure. Use a saga with compensating actions.
  • Consumers genuinely cannot be made idempotent and duplicates are unacceptable. Use a broker with transactional producers within one cluster, and accept the narrower scope.

Common mistakes & gotchas

Publishing inside the transactionCalling the broker before COMMIT feels atomic and is not: the publish can succeed and the transaction still roll back, and meanwhile the broker's latency is holding your database locks.
Fix: never call the broker inside a transaction. Write the row, commit, and let the relay do the network work.
Generating the message id at publish timeA republished row then carries a new id, so consumers cannot recognise the duplicate and every at-least-once delivery becomes a real duplicate.
Fix: generate the id when the outbox row is written, inside the business transaction, and never change it — including on replay from a dead-letter table.
Assuming consumers are idempotentThe pattern guarantees delivery, not deduplication. A consumer that increments a balance will drift quietly after every relay restart.
Fix: make it an explicit contract. Ship an inbox table or upsert-by-key in every consumer, and test by replaying the same message twice.
No retention policyThe outbox becomes the biggest table in the database, the relay's own query slows down, backups grow, and autovacuum falls behind.
Fix: delete published rows in batches after a few days, or partition by day and drop partitions. Decide this on day one.
Not monitoring lagEvery other signal stays green while the relay is crash-looping: the API returns 200, the database commits, the business logic is fine — and nobody downstream has heard anything for an hour.
Fix: alert on the age of the oldest unsent row. It is the only metric that observes this failure.
One poison row blocking everythingA payload the broker rejects is retried forever, and strict ordering means the entire backlog stops behind it while error counts look constant.
Fix: bound the retries, move the row to a dead-letter table with the error, alert, and keep going.
Several relays destroying orderingTwo instances publish rows 5 and 6 concurrently, and the consumer sees OrderShipped before OrderPlaced.
Fix: partition relay work by aggregate id, or make handlers tolerate out-of-order arrival with version checks. SKIP LOCKED prevents collisions, not reordering.
Expecting it to coordinate two servicesAn outbox makes your database and your messages atomic. It does nothing about a remote service that accepted a call and then failed.
Fix: for multi-service workflows use a saga with explicit compensating actions; the outbox is how each step of that saga publishes reliably.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs the outbox
Transactional outboxreliable events from a service that owns a databaseMediumfree; a relay to run—
Dual writenothing, honestlyLowfreeSimplest and silently wrong; loses or invents events
Two-phase commit (XA)legacy brokers and XA databasesHighfree; heavyTrue atomicity, at the cost of latency, blocking and coupled availability
Change data capture onlypublishing from existing tablesMediuma connector clusterNo outbox table; events mirror rows, so you publish your schema rather than your intent
Event sourcingservices where history is the modelHighfree; real ops costThe event store is the outbox; no second write at all
Broker transactionsKafka-to-Kafka pipelinesMediumfreeAtomic within one broker cluster; does not include your database
Listen to yourselfevent-driven coresMediumfreeOnly the event is written; own state becomes eventually consistent
  • Pick CDC on your business tables if you only need to mirror data and can live with publishing your schema shape.
  • Pick event sourcing if you already store events — then skip the outbox entirely.
  • Pick broker transactions for read-process-write pipelines that never leave the broker.
  • Pick a saga when the problem is coordinating several services, not publishing reliably from one.
  • Pick 2PC only if you are already in an XA world and cannot make consumers idempotent.
