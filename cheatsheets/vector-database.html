Vector database

Every other index answers "equal to". This one answers "near" — and it is allowed to be slightly wrong about it.

As of Nov 2026 · examples use pgvector, Qdrant and Postgres

A vector database stores high-dimensional embeddings and answers one question fast: which stored vectors are closest to this one? A B-tree cannot help — there is no ordering in 1,536 dimensions — and a brute-force scan compares the query against every row, which is exact but linear. So these systems use approximate nearest-neighbour indexes that trade a few percent of recall for one to three orders of magnitude of speed.

That trade is the defining property, and it is unlike any other database you run. Your index has a recall knob, it is not set to 100%, and when it is set badly the system does not error — it quietly returns worse results. A RAG pipeline with low recall looks like a model problem from the outside.

The second thing that makes them distinctive is filtered search: "nearest neighbours, but only this tenant's documents". Combining a graph traversal with a selective predicate is genuinely hard, and it is the single biggest difference in behaviour between engines. The third is memory: vectors are large, indexes are usually in RAM, and sizing is simple arithmetic that is worth doing before you choose anything.

Architecture / mental model

An in-memory graph over vectors, a payload store for filters, and one dial that trades recall against latency.

Key concepts

Approximate nearest neighbourTrading a few percent of correctness for one to three orders of magnitude of speed.
HNSWA layered graph of "small world" links: long hops at the top, short ones at the bottom.
ef_searchThe size of the candidate list during the layer-0 walk — the one knob that trades recall for latency at query time.
IVFPartition the space into clusters, search only the few nearest clusters.
Recall@kThe share of the true top-k that your index actually returned — the number nobody measures and everybody should.
Distance metricCosine, inner product or L2 — and it must match what the embedding model was trained for.
Filtered searchCombining "nearest" with "where" — the feature that most differentiates engines in practice.
PayloadThe JSON stored next to each vector: tenant, permissions, source, date, and the text itself.
QuantisationStoring smaller, lossier copies of the vectors so more of them fit in memory.
Memory sizingArithmetic you can do in two minutes that decides your architecture.
Embedding dimensionsHow long each vector is — and the fact that you can often shorten it for free.
Segments and compactionHow writes land, why deletes are tombstones, and why a collection gets slower with churn.
FreshnessHow quickly a new or changed vector becomes searchable, and the deletion path nobody builds.
Multi-tenancyOne collection with a tenant filter, or one collection per tenant — and when to switch.
OversamplingRetrieve more than you need, then rescore the few exactly — the universal recall repair.
Hybrid searchRunning keyword search alongside vector search and fusing the results.
Brute forceNo index at all — and the right answer far more often than vendors suggest.

Essential commands & code

Postgres with pgvector — start here

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id          text PRIMARY KEY,                 -- "doc-412#2": deterministic, so upsert is free
  doc_id      text        NOT NULL,
  tenant_id   text        NOT NULL,
  content     text        NOT NULL,
  embedding   vector(1536) NOT NULL,
  tsv         tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
  updated_at  timestamptz NOT NULL DEFAULT now()
);

-- build the index AFTER the bulk load: much faster, and a better graph
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

CREATE INDEX ON chunks USING gin (tsv);          -- the keyword half of hybrid search
CREATE INDEX ON chunks (tenant_id);              -- the filter
CREATE INDEX ON chunks (doc_id);                 -- for delete-by-document

SET hnsw.ef_search = 100;                        -- per session: recall vs latency
One table holds vectors, payload, keyword index and filters — which is the entire argument for not running a separate system.
-- query: filter INSIDE the search, never after
SELECT id, content, 1 - (embedding <=> $1) AS similarity
FROM chunks
WHERE tenant_id = $2                      -- Postgres decides: index scan, or exact for small tenants
ORDER BY embedding <=> $1                 -- <=> cosine distance; must match the operator class
LIMIT 20;

-- is the index actually being used? the plan is the only honest answer
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM chunks WHERE tenant_id = 'acme' ORDER BY embedding <=> $1 LIMIT 20;
--  Index Scan using chunks_embedding_idx  → good
--  Seq Scan + Sort                        → exact, correct, and linear: fine if the tenant is small

-- churn check: tombstones make searches slower while the row count stays flat
SELECT n_live_tup, n_dead_tup, last_autovacuum FROM pg_stat_user_tables WHERE relname = 'chunks';
A missing index scan is not always a bug — for a selective filter the planner choosing an exact scan is the correct, higher-recall answer.

# Qdrant — a collection with int8 quantisation and rescoring
curl -X PUT http://localhost:6333/collections/docs -H 'Content-Type: application/json' -d '{
  "vectors": { "size": 1536, "distance": "Cosine" },
  "hnsw_config": { "m": 16, "ef_construct": 100 },
  "quantization_config": {
    "scalar": { "type": "int8", "always_ram": true }
  },
  "optimizers_config": { "default_segment_number": 4 }
}'

# index the fields you filter on — without this, filtering falls back to a scan
curl -X PUT http://localhost:6333/collections/docs/index -H 'Content-Type: application/json' \
  -d '{ "field_name": "tenant_id", "field_schema": "keyword" }'

# search: filter + oversample + rescore with the full-precision vectors
curl -X POST http://localhost:6333/collections/docs/points/search -H 'Content-Type: application/json' -d '{
  "vector": [0.021, -0.44, "..."],
  "filter": { "must": [ { "key": "tenant_id", "match": { "value": "acme" } } ] },
  "limit": 20,
  "params": { "hnsw_ef": 128, "quantization": { "rescore": true, "oversampling": 3.0 } },
  "with_payload": ["url", "title"]
}'
Quantise to fit in RAM, then oversample and rescore to get the recall back. The payload index is the line people forget.
// C# — upsert with a deterministic id, then the matching delete path
var points = chunks.Select((c, i) => new PointStruct
{
    Id      = new PointId { Uuid = Deterministic($"{docId}#{i}") },   // same input → same id → upsert
    Vectors = vectors[i].Vector.ToArray(),
    Payload =
    {
        ["tenant_id"]  = tenantId,
        ["doc_id"]     = docId,
        ["chunk_index"]= i,
        ["url"]        = c.Url,
        ["updated_at"] = DateTimeOffset.UtcNow.ToUnixTimeSeconds(),
    },
}).ToList();

await client.UpsertAsync("docs", points);

// the step everyone skips: a shrinking document leaves orphans behind
await client.DeleteAsync("docs", filter: MatchKeyword("doc_id", docId) &
                                         Range("chunk_index", gte: chunks.Count));

// and the one that keeps you out of a compliance conversation
await client.DeleteAsync("docs", filter: MatchKeyword("doc_id", retractedDocId));
Deterministic ids turn re-ingestion into an upsert; the trailing delete and the retraction delete are what keep the index honest.

Measuring what actually matters

# recall@k against brute force — thirty lines, run it once per config change
import numpy as np

def brute_force(q: np.ndarray, vectors: np.ndarray, k: int) -> set[int]:
    """Ground truth. Slow, exact, and the only honest baseline."""
    sims = vectors @ q / (np.linalg.norm(vectors, axis=1) * np.linalg.norm(q))
    return set(np.argsort(-sims)[:k].tolist())

def measure(queries, vectors, k=10, ef_values=(40, 100, 200, 400)):
    truth = [brute_force(q, vectors, k) for q in queries]
    for ef in ef_values:
        client.update_collection("docs", hnsw_config={"ef": ef})
        hits, t0 = 0, time.perf_counter()
        for q, want in zip(queries, truth):
            got = {p.id for p in search(q, k=k)}
            hits += len(got & want)
        ms = (time.perf_counter() - t0) / len(queries) * 1000
        print(f"ef_search={ef:4}  recall@{k}={hits / (k * len(queries)):.3f}  {ms:5.1f} ms")

# ef_search=  40  recall@10=0.952   1.8 ms
# ef_search= 100  recall@10=0.981   3.4 ms
# ef_search= 200  recall@10=0.994   6.9 ms      ← usually the right trade
# ef_search= 400  recall@10=0.998  13.1 ms
This table is the whole tuning exercise. Without it, "retrieval feels bad" turns into weeks of changing embedding models.
# sizing, before you choose anything
def ram_gb(n_vectors: int, dims: int, m: int = 16, bytes_per_dim: int = 4) -> float:
    per_vector = 1.1 * (bytes_per_dim * dims + 8 * m)     # vectors + HNSW graph
    return n_vectors * per_vector / 1024 ** 3

print(f"{ram_gb(1_000_000, 1536):.1f} GB")                 #  6.9 GB  float32
print(f"{ram_gb(1_000_000, 1536, bytes_per_dim=1):.1f} GB")#  1.9 GB  int8
print(f"{ram_gb(10_000_000, 768, bytes_per_dim=1):.1f} GB")#  9.0 GB  int8, half the dims

# 10M vectors on one machine, or 69 GB and a cluster.
# Halving dimensions and quantising usually costs 2-4% recall. Measure it, then decide.
Two minutes of arithmetic decides whether this is a Postgres table, a single node or a distributed cluster.

Pros & cons

Pros

  • Similarity search over millions of vectors in single-digit milliseconds.
  • Filters, payloads and permissions applied inside the search rather than after it.
  • Recall is a dial you can set per query, so cheap and expensive queries can differ.
  • Quantisation makes order-of-magnitude memory savings available for a few percent of recall.
  • Hybrid search in one engine, so keyword and semantic retrieval share filters and freshness.
  • Incremental inserts: new content is searchable in seconds, with no rebuild.

Cons

  • Approximate by construction, and it never tells you when recall is poor.
  • Memory-hungry: indexes want RAM, and vectors are large.
  • Filtered search behaves very differently between engines and at different selectivities.
  • Deletes are tombstones, so churn degrades performance until compaction.
  • Changing the embedding model or dimensions means rebuilding everything.
  • Another stateful system to run, back up, monitor and secure — often for data that fits in Postgres.
  • Benchmarks are run on clean public datasets and rarely predict your filtered, multi-tenant workload.

Concrete use cases

Retrieval for RAG

The most common use by a wide margin: chunk embeddings with tenant and ACL payloads, hybrid retrieval, top-50 to a reranker. The quality of the whole assistant is capped by this index's recall, which is why it is worth measuring on day one.

Semantic product search

"Waterproof jacket for hiking in spring" matches products whose descriptions never use those words. Filters on stock, region and price run in the same query, and a keyword lane catches searches by exact SKU.

Deduplication at ingest

Before storing a new support ticket or article, search for anything above 0.97 similarity. Catches near-duplicates that a hash never would — reposts, reformats, minor edits — in a couple of milliseconds.

Recommendations

Item and user embeddings in one collection; "more like this" is a nearest-neighbour query from an item's own vector, with filters for availability and region. No model call at request time at all.

The store behind a semantic cache

A semantic cache is a vector index over past questions, partitioned hard by tenant and prompt version. Small, high-churn, and extremely latency-sensitive — often a different collection, tuned differently, from the RAG one.

When to use / when not to

under 100k vectors? it's a column in postgres. don't buy a cluster for a table.

Use a dedicated one when…

  • You have millions of vectors and the index no longer fits comfortably beside your OLTP workload.
  • Query volume is high enough that vector search competes with transactions for resources.
  • You need quantisation, per-query recall tuning or distributed sharding.
  • Filtered search at low selectivity is central, and you need an engine that switches strategies well.
  • Hybrid search, reranking and multi-vector records should be features rather than code you write.

Avoid one when…

  • You have fewer than ~100k vectors. Use pgvector, or even an exact scan.
  • The data already lives in Postgres and joins matter. Use pgvector and keep one system.
  • Queries are exact lookups by id or keyword. Use an ordinary index or full-text search.
  • You need transactions across vectors and business rows. Keep them in the same database.
  • Nobody will own a new stateful service. The operational cost outlives the enthusiasm.
  • You have not measured recall yet — you may be solving a problem you do not have.

Common mistakes & gotchas

Never measuring recallThe index is "working": queries return results, latency is good, nobody sees an error. Recall is 0.83 and a sixth of all answers are built from the wrong chunks.
Fix: run a few hundred queries with the index disabled to get ground truth, compare top-k overlap, and print the recall-versus-ef_search table. Repeat it whenever the configuration or the data distribution changes.
Post-filtering a permission predicateTop-50 is taken globally and then filtered to the user's tenant. A small tenant gets two results, or none, and the latency looks fine — so it reads as "we have no content" rather than as a bug.
Fix: push the filter into the search, index the filter fields, and add a test proving a tenant-B user can never retrieve a tenant-A row.
Mismatched metric and operator classThe index is built with vector_l2_ops and queried with <=>. Postgres silently ignores the index and does an exact scan: correct, and a hundred times slower — or, with the wrong metric, simply wrong.
Fix: pick cosine for text embeddings, build the index with the matching operator class, and check the plan with EXPLAIN after creating it.
Mixing embedding models in one collectionThe model was upgraded and new rows use new vectors while old rows keep old ones. The two live in different spaces, so distances are meaningless and quality degrades without any error.
Fix: make the model name and dimension part of the collection's identity. Build a new collection, backfill, switch reads atomically, drop the old one.
Building the index before the bulk loadTen million rows are inserted one at a time into an existing HNSW graph. The load takes all night and produces a worse graph than building it afterwards would have.
Fix: load first, create the index second, and raise maintenance memory for the build. Most engines also offer an explicit "indexing off during load" mode.
No deletion pathDocuments are upserted happily, but retracted and deleted ones stay. They keep being retrieved and cited, and a compliance request has no answer.
Fix: deterministic ids, delete by document id on removal, prune chunks beyond the new chunk count, and run a periodic reconcile that diffs source ids against index ids.
Ignoring tombstonesA high-churn collection gets steadily slower and uses more memory while the row count is flat. Deleted vectors are still nodes in the graph, still traversed, still resident.
Fix: monitor the deleted ratio, compact when it exceeds about 20%, and for Postgres make sure autovacuum is actually keeping up on that table.
Quantising without rescoringBinary quantisation cuts memory 32× and recall falls off a cliff. The saving is real and so is the damage, and nothing reports the second one.
Fix: oversample by 4–16× and rescore the candidates with full-precision vectors. Measure recall before and after — this is exactly the knob that needs evidence.
Trusting public benchmarksA vendor chart shows 99% recall at 20,000 queries per second — on a clean one-million-vector public dataset, unfiltered, single-tenant, with the index warm.
Fix: benchmark your own vectors, your own filters, your own tenant distribution and your own update rate. Filtered multi-tenant performance is where engines genuinely diverge.
Buying a cluster for 80,000 rowsA new stateful service is deployed, with backups, monitoring and an on-call rotation, to hold a collection a laptop could scan exactly in 20 ms.
Fix: start in Postgres with pgvector, measure, and migrate when the arithmetic — not the roadmap — says the index no longer fits.

  • Pick pgvector by default. One system, real transactions, filters that are just WHERE clauses.
  • Pick Elasticsearch or OpenSearch if you already run it — hybrid search comes nearly free.
  • Pick Redis for a semantic cache or any small, hot, latency-critical collection.
  • Pick a dedicated engine when the sizing arithmetic says tens of millions of vectors, or when filtered multi-tenant search is the core of the product.
  • Pick a library like FAISS only inside a batch pipeline, where there is no serving, no filtering and no freshness requirement.
