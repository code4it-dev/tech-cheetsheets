CQRS

Writes and reads want opposite things from a schema. Stop making one model do both jobs badly.

As of Nov 2026 · named by Greg Young, 2010; examples in C#, SQL and Python

Command Query Responsibility Segregation says that the model you use to change state and the model you use to read state do not have to be the same object, the same schema, or even the same database. Writes want normalisation, invariants and small transactions; reads want pre-joined, denormalised rows that a screen can render without thinking. One model forced to serve both ends up compromising on each.

The pattern is a spectrum, not a switch. At the cheapest level it is just two sets of classes against one database — commands going through aggregates, queries going through plain SQL or a thin DTO projection. One step further, the read side gets its own denormalised tables or materialised views in the same store. At the far end it gets its own database, fed asynchronously by projections from the write side's events, and the two scale independently.

Two things CQRS is not: it is not event sourcing (they are often used together and are entirely separable), and it is not an architecture for a whole system. It is applied per bounded context, usually to the one or two contexts where the read and write shapes genuinely diverge, while the rest of the application stays plain CRUD.

Architecture / mental model

Same data, two shapes. The projector is the only bridge, and it runs after the write has already committed.

Key concepts

CommandA request to change state, named as an imperative, that can be rejected and returns no business data.
QueryA request for data that changes nothing and returns a shape built for a specific screen or caller.
Command handlerThe single entry point that executes one command: load the aggregate, call one method, save, publish.
Write modelThe model optimised for change: aggregates, invariants, small transactions and a normalised schema.
Read modelA denormalised, screen-shaped store of the same data, built from the write side and treated as disposable.
ProjectionThe code that turns write-side events into read-model rows, and the process that runs it.
CheckpointThe position in the event stream a projection has processed up to, stored alongside the read model.
Eventual consistencyThe read model trails the write model by a short, bounded delay instead of being updated in the same transaction.
Read-your-writesThe guarantee that a user immediately sees the effect of their own change — the first thing CQRS breaks.
Levels of CQRSThe spectrum from two sets of classes over one table to two separate databases — you can stop anywhere.
Event sourcingStoring state as an append-only log of events rather than as current rows — frequently paired with CQRS, and independent of it.
OutboxWriting outgoing events into a table inside the same transaction as the state change, then publishing them from there.
IdempotencyApplying the same event twice must leave the read model in the same state as applying it once.
RebuildDropping a read model and replaying the event history to recreate it — the operational superpower of CQRS.
Query handlerThe read-side counterpart to a command handler: one per query, returning a DTO, with no domain model in sight.

Essential code patterns

The two sides (C#)

public sealed record PlaceOrder(Guid CommandId, Guid CartId, Guid CustomerId);

public sealed class PlaceOrderHandler(IOrderRepository repo, IOutbox outbox)
{
    public async Task<Guid> Handle(PlaceOrder cmd, CancellationToken ct)
    {
        var order = Order.Place(cmd.CartId, cmd.CustomerId);   // invariants here
        await repo.Add(order, ct);
        await outbox.Enqueue(order.ReleaseEvents(), ct);       // same transaction
        return order.Id;                                        // id only, not state
    }
}
Write side: domain model, invariants, events into the outbox in the same transaction. Returns an identity, never a view.
public sealed record OrderListItem(
    Guid OrderId, string CustomerName, decimal Total, string Status, DateTime PlacedAt);

public sealed class OrderListQuery(IDbConnection db)
{
    public Task<IEnumerable<OrderListItem>> Handle(Guid customerId, int page) =>
        db.QueryAsync<OrderListItem>(
            """
            SELECT order_id, customer_name, total, status, placed_at
            FROM   order_list_view
            WHERE  customer_id = @customerId
            ORDER  BY placed_at DESC
            LIMIT 20 OFFSET @offset
            """,
            new { customerId, offset = page * 20 });
}
Read side: one flat SQL statement against a pre-joined table. No ORM, no aggregates, no mapping layers.

The read model and its projection

CREATE TABLE order_list_view (
    order_id       uuid PRIMARY KEY,
    customer_id    uuid NOT NULL,
    customer_name  text NOT NULL,      -- denormalised on purpose
    total          numeric(12,2) NOT NULL,
    status         text NOT NULL,
    placed_at      timestamptz NOT NULL,
    last_seq       bigint NOT NULL     -- guards against duplicate events
);

CREATE INDEX ix_olv_customer ON order_list_view (customer_id, placed_at DESC);
One table per screen, every join already done, indexed by exactly what the screen filters and sorts on.
INSERT INTO order_list_view
    (order_id, customer_id, customer_name, total, status, placed_at, last_seq)
VALUES (@id, @cust, @name, @total, 'placed', @at, @seq)
ON CONFLICT (order_id) DO UPDATE
   SET status = EXCLUDED.status,
       total  = EXCLUDED.total,
       last_seq = EXCLUDED.last_seq
 WHERE order_list_view.last_seq < EXCLUDED.last_seq;
An idempotent projection write: upsert by key, guarded by a sequence number, so a replayed event changes nothing.
-- level 2 without a projector at all
CREATE MATERIALIZED VIEW order_list_view AS
SELECT o.id AS order_id, c.name AS customer_name, SUM(l.price * l.qty) AS total, ...
FROM orders o JOIN customers c ON ... JOIN order_lines l ON ...
GROUP BY o.id, c.name;

REFRESH MATERIALIZED VIEW CONCURRENTLY order_list_view;
The cheapest read model: the database maintains it. No projector code, no checkpoint, refresh lag instead of event lag.

Outbox and projector (Python)

with conn.transaction():                       # one transaction
    conn.execute("INSERT INTO orders ...", order_row)
    conn.execute(
        "INSERT INTO outbox (id, type, payload, seq) VALUES (%s,%s,%s,%s)",
        (event.id, "OrderPlaced", json.dumps(event.payload), event.seq),
    )
# a separate relay publishes rows from `outbox` and marks them sent
State and event committed together: the read model can never miss a change or see one that rolled back.
def project(batch):
    with conn.transaction():
        for event in batch:
            HANDLERS[event.type](conn, event)
        conn.execute(
            "UPDATE projection_checkpoint SET offset = %s WHERE name = 'order_list'",
            (batch[-1].offset,),
        )                                   # checkpoint in the SAME transaction
Rows and checkpoint committed atomically — the difference between at-least-once delivery and a correct read model.
-- rebuild, with no downtime
CREATE TABLE order_list_view_v2 (LIKE order_list_view INCLUDING ALL);
UPDATE projection_checkpoint SET offset = 0 WHERE name = 'order_list_v2';
-- let it catch up, verify, then point the queries at v2 and keep v1 for rollback
Read-side schema changes become replays instead of migrations.

Observability

# the only read-path metric that really matters
projection_lag_seconds{projection="order_list"}
# alert when the read model is staler than the window you promised
Publish the lag, alert on it, and put the promised window in the API docs — an unstated window is the real bug.

Pros & cons

Pros

  • Reads get exactly the shape the screen needs, usually one indexed lookup instead of a multi-table join.
  • The write model stays clean: no fields or relations added just to make a report work.
  • Read and write sides scale, cache and fail independently — a reporting spike cannot slow down checkout.
  • Read models are disposable, so read-side schema changes become replays rather than migrations.
  • Each read model can use the right store: SQL, Redis, a search index, a columnar warehouse.
  • Clear seams make the code easy to navigate: one class per intention, one query per screen.

Cons

  • Eventual consistency arrives at level 3 and immediately breaks read-your-own-writes.
  • More moving parts: projectors, checkpoints, an outbox, lag monitoring, rebuild tooling.
  • The same data exists in several shapes, so a projector bug produces visibly wrong numbers.
  • Rebuild time grows with history and becomes an operational constraint if ignored.
  • Easy to over-apply — most CRUD screens are worse off with two models.
  • Debugging spans two stores and an asynchronous hop, which raises the bar for tracing.

Concrete use cases

A list screen that joins seven tables

The orders page takes 1.8 seconds because it joins orders, lines, products, customers, addresses, shipments and payments. A single order_list_view table, maintained by a projection, turns it into one indexed read of a few milliseconds — without touching the write model at all.

Reporting load crushing the transactional database

Analysts run heavy aggregations against the same tables that take checkout writes, and lock contention shows up as checkout latency. A separate read store fed by projections isolates the two completely, and the analysts get a schema designed for their queries.

Search that SQL cannot do

Users want faceted, typo-tolerant search over the catalogue. A projection into Elasticsearch gives that without turning the product aggregate into a search document, and the index can be rebuilt whenever the analyser configuration changes.

Reads enormously outnumbering writes

A public timetable gets thousands of reads per write. The read model is a denormalised key-value store behind a CDN, refreshed by projection; the write model stays a small, strongly consistent relational schema that a handful of editors use.

Several consumers, several shapes

The mobile app, the call-centre screen and the partner API all want different views of the same orders. Three read models projected from one write model beats one API trying to satisfy all three with nested includes and sparse fieldsets.

When to use / when not to

start at level 1 and only climb when a measurement makes you — most systems never need level 3

Use it when…

  • The read shape and the write shape genuinely differ, and the joins are visible in your latency numbers.
  • Read and write loads differ by an order of magnitude or more.
  • One domain model is being distorted by screens and reports.
  • You need several different views of the same data, possibly in different stores.
  • You are already inside a bounded context with aggregates, and repositories are sprouting query methods.

Avoid it when…

  • The application is simple CRUD and the screens mirror the tables. Use a single model with an ORM.
  • Every screen must reflect writes instantly and you cannot change the UX. Use level 1 CQRS at most, or a materialised view refreshed in-transaction.
  • The team has no appetite for projectors, lag monitoring and rebuilds. Use read replicas and better indexing.
  • The real problem is one slow query. Use an index, a denormalised column or a cache first.
  • You are applying it to the whole system rather than one context. Use it per bounded context, where it pays.

Common mistakes & gotchas

Assuming CQRS means event sourcingTeams adopt an event store, snapshots and event versioning when all they wanted was a fast list screen, and the project stalls on accidental complexity.
Fix: decide them separately. A projection fed by ordinary change events from a relational write is a complete, common and much cheaper CQRS.
Applying it to the whole systemEvery CRUD screen gets a command, a handler, a projection and a read table, and the codebase triples in size for no benefit.
Fix: apply it per bounded context, usually to one or two. Plain CRUD alongside CQRS in the same application is a correct design, not an inconsistency.
No answer for read-your-own-writesThe user submits, lands on a list that has not caught up, and submits again. Duplicates created by architecture.
Fix: pick a mitigation per screen — return the data from the command, wait on a version token, read own data from the write side, or make the UI explicitly asynchronous.
Non-idempotent projectionsDelivery is at-least-once, so total = total + x double-counts after any restart, rebalance or retry, and the numbers drift quietly.
Fix: upsert by key, write absolute values, and guard with a per-row sequence number. Test by replaying the same batch twice.
Publishing events outside the transactionThe write commits and the broker call fails, so the read model is permanently stale; or the event is published and the write rolls back, so the read model shows a lie.
Fix: use an outbox table written in the same transaction, or change data capture. Never call the broker from inside the handler.
No lag metric"It's eventually consistent" becomes an excuse rather than a specification, and nobody notices when a stalled projector leaves the read model hours behind.
Fix: export projection lag in seconds and in events, alert on it, and publish the promised window in your API documentation.
Querying through the write modelSomeone adds GetAllOrdersWithLines to the repository because it was convenient, and the separation quietly disappears.
Fix: keep repositories to get/add/save by identity, and put every screen query on the read side — enforced by an architecture test if necessary.
Never rehearsing a rebuildThree years in, the projector has a bug and the first full replay turns out to take eleven hours against retained history nobody checked.
Fix: rebuild in CI regularly, measure the time, and add snapshots or partial replays before it matters. Build the new read model alongside the old one.

  • Pick CQS first — it costs nothing and gets most of the clarity benefit.
  • Pick a single model if the screens mirror the tables and the joins are cheap.
  • Pick materialised views when you want a denormalised read model without owning a projector.
  • Pick read replicas when the queries are fine but there are too many of them.
  • Pick caching when a handful of hot answers dominate; reach for CQRS when the shape, not the volume, is the problem.
  • Pick event sourcing only if history itself is a requirement — then CQRS comes along almost for free.
