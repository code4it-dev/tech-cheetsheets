RAG

The model does not know your data. RAG is the machinery that puts the right paragraph in front of it, just in time.

As of Nov 2026 · examples use Microsoft.Extensions.AI, pgvector and Azure AI Search

Retrieval-Augmented Generation answers a question by first finding the relevant text in a corpus you control, then asking a language model to answer using only that text. The model supplies fluency and reasoning; your index supplies the facts. Nothing is memorised, so when a document changes the answer changes with it — no retraining, no fine-tuning, no model release.

Mechanically it is two pipelines. Ingestion runs offline: split documents into chunks, turn each chunk into an embedding vector, store vector plus text plus metadata. Query runs per request: embed the question, search for nearby chunks, rerank them, paste the survivors into the prompt with the question, generate, and cite.

The uncomfortable truth of RAG is that almost every failure is a retrieval failure, not a generation failure. If the answer is not in the retrieved chunks, no model can produce it, and a good model will confidently produce something else. Teams reach for a bigger LLM when the actual fix is better chunking, a hybrid index or a reranker — which cost a fraction as much.

Architecture / mental model

An index built offline, read online. The model is the last box, and the least interesting one.

Key concepts

ChunkingSplitting documents into retrievable units small enough to be precise and large enough to be self-contained.
EmbeddingA fixed-length vector of floats whose geometry encodes meaning: similar text lands nearby.
Vector searchFinding the nearest chunk vectors to the query vector, approximately, in sublinear time.
Hybrid searchRunning dense vector search and keyword (BM25) search together, then fusing the two ranked lists.
Reciprocal Rank FusionCombining ranked lists by summing 1/(k + rank) instead of trying to compare incompatible scores.
RerankerA cross-encoder that reads the query and each candidate chunk together and scores true relevance.
Top-kHow many chunks you retrieve, and how many survive into the prompt — two different numbers.
Grounding & citationsInstructing the model to answer only from the supplied chunks, and to point at which one.
Query rewritingTurning the user's raw message into one or more good search queries before retrieving.
Metadata filteringRestricting the search to chunks the user is allowed to see, in the right tenant, language and date range.
Context window budgetThe token accounting that decides how many chunks you can actually afford per request.
Lost in the middleModels attend most to the beginning and end of a long context, and least to what sits in between.
Parent-document retrievalMatching on small chunks but sending the larger surrounding section to the model.
Index freshnessKeeping the index in step with the source, including deletions, without rebuilding it nightly.
FaithfulnessWhether every claim in the answer is actually supported by the retrieved context.
Context recallThe share of questions whose answer-bearing chunk appeared in the retrieved set at all.
Agentic RAGLetting the model decide when to search, what to search for, and whether to search again.

Essential code

Ingestion — chunk, embed, upsert

// C# — Microsoft.Extensions.AI + pgvector via Npgsql
using Microsoft.Extensions.AI;

IEmbeddingGenerator<string, Embedding<float>> embedder = /* DI */;

static IEnumerable<(int Index, string Text)> Chunk(string doc, int size = 500, int overlap = 75)
{
    var words = doc.Split(' ', StringSplitOptions.RemoveEmptyEntries);
    for (int i = 0, n = 0; i < words.Length; i += size - overlap, n++)
        yield return (n, string.Join(' ', words.Skip(i).Take(size)));
}

var chunks = Chunk(document).ToList();
var vectors = await embedder.GenerateAsync(chunks.Select(c => c.Text));

await using var batch = new NpgsqlBatch(conn);
foreach (var (chunk, vector) in chunks.Zip(vectors))
{
    var cmd = new NpgsqlBatchCommand("""
        INSERT INTO chunks (id, doc_id, idx, content, embedding, tenant_id, updated_at)
        VALUES ($1, $2, $3, $4, $5, $6, now())
        ON CONFLICT (id) DO UPDATE
          SET content = EXCLUDED.content,
              embedding = EXCLUDED.embedding,
              updated_at = now();
        """);
    cmd.Parameters.AddWithValue($"{docId}#{chunk.Index}");   // deterministic id = free upsert
    cmd.Parameters.AddWithValue(docId);
    cmd.Parameters.AddWithValue(chunk.Index);
    cmd.Parameters.AddWithValue(chunk.Text);
    cmd.Parameters.AddWithValue(new Vector(vector.Vector));
    cmd.Parameters.AddWithValue(tenantId);
    batch.BatchCommands.Add(cmd);
}
await batch.ExecuteNonQueryAsync();

// and the step everyone forgets:
await conn.ExecuteAsync("DELETE FROM chunks WHERE doc_id = $1 AND idx >= $2",
                        docId, chunks.Count);
Deterministic ids make re-ingestion an upsert; the trailing delete removes chunks that the new, shorter version no longer has.
# Python — openai + psycopg + pgvector
from dataclasses import dataclass
from openai import OpenAI
from pgvector.psycopg import register_vector
import psycopg

client = OpenAI()

@dataclass(frozen=True)
class Chunk:
    index: int
    text: str

def chunk(doc: str, size: int = 500, overlap: int = 75) -> list[Chunk]:
    words = doc.split()
    step = size - overlap
    return [Chunk(n, " ".join(words[i:i + size]))
            for n, i in enumerate(range(0, len(words), step))]

chunks = chunk(document)
resp = client.embeddings.create(model="text-embedding-3-small",
                                input=[c.text for c in chunks])

with psycopg.connect(DSN) as conn:
    register_vector(conn)
    with conn.cursor() as cur:
        cur.executemany("""
            INSERT INTO chunks (id, doc_id, idx, content, embedding, tenant_id, updated_at)
            VALUES (%s, %s, %s, %s, %s, %s, now())
            ON CONFLICT (id) DO UPDATE
              SET content = EXCLUDED.content,
                  embedding = EXCLUDED.embedding,
                  updated_at = now()
        """, [(f"{doc_id}#{c.index}", doc_id, c.index, c.text,
               d.embedding, tenant_id)
              for c, d in zip(chunks, resp.data)])
        cur.execute("DELETE FROM chunks WHERE doc_id = %s AND idx >= %s",
                    (doc_id, len(chunks)))
Same shape: batch the embedding call (one request for many chunks is far cheaper than many requests), then upsert and prune.

Retrieval — hybrid, fused, filtered

-- Postgres: dense + BM25-ish full text, fused with RRF, tenant filter inside both
WITH dense AS (
  SELECT id, content, row_number() OVER (ORDER BY embedding <=> $1) AS rank
  FROM chunks
  WHERE tenant_id = $2                      -- filter INSIDE the search, never after
  ORDER BY embedding <=> $1                 -- <=> is cosine distance
  LIMIT 50
),
sparse AS (
  SELECT id, content,
         row_number() OVER (ORDER BY ts_rank_cd(tsv, websearch_to_tsquery($3)) DESC) AS rank
  FROM chunks
  WHERE tenant_id = $2 AND tsv @@ websearch_to_tsquery($3)
  LIMIT 50
)
SELECT COALESCE(d.id, s.id) AS id,
       COALESCE(d.content, s.content) AS content,
       COALESCE(1.0 / (60 + d.rank), 0) + COALESCE(1.0 / (60 + s.rank), 0) AS rrf
FROM dense d FULL OUTER JOIN sparse s USING (id)
ORDER BY rrf DESC
LIMIT 25;
One query, two retrievers, reciprocal rank fusion with k=60. The 25 survivors go to the reranker.
// C# — Azure AI Search does hybrid + semantic reranking server-side
var options = new SearchOptions
{
    VectorSearch = new()
    {
        Queries = { new VectorizedQuery(queryVector) { KNearestNeighborsCount = 50, Fields = { "embedding" } } }
    },
    Filter = $"tenant_id eq '{tenantId}'",
    QueryType = SearchQueryType.Semantic,                  // cross-encoder rerank
    SemanticSearch = new() { SemanticConfigurationName = "default" },
    Size = 5,
    Select = { "id", "content", "url", "title" },
};

var results = await searchClient.SearchAsync<Chunk>(userQuery, options);   // text => BM25, vector => ANN

var context = string.Join("\n\n", await results.Value.GetResultsAsync()
    .Where(r => r.SemanticSearch?.RerankerScore > 1.5)      // cut-off: better empty than wrong
    .Select(r => $"[{r.Document.Id}] {r.Document.Content}")
    .ToListAsync());
Passing both the text and the vector is what makes it hybrid; RerankerScore is the cut-off that lets you answer "I don't know".

Generation — grounded, cited, refusable

// C# — the prompt contract is the whole trick
var messages = new List<ChatMessage>
{
    new(ChatRole.System, """
        Answer using ONLY the context below.
        Cite the id of every claim like [doc-412#2].
        If the context is insufficient, reply exactly: I don't have enough information.
        """),
    new(ChatRole.User, $"Context:\n{context}\n\nQuestion: {question}"),
};

var answer = await chatClient.GetResponseAsync(messages,
    new ChatOptions { Temperature = 0.1f, MaxOutputTokens = 800 });

// verify every citation actually came from the context we sent
var cited = Regex.Matches(answer.Text, @"\[([\w\-#]+)\]").Select(m => m.Groups[1].Value);
var invented = cited.Except(retrievedIds).ToList();
if (invented.Count > 0) logger.LogWarning("Hallucinated citations: {Ids}", invented);
Low temperature, an explicit refusal string, and a cheap regex check that catches invented citations in production.
# Python — the same contract, plus a trivial faithfulness gate
SYSTEM = (
    "Answer using ONLY the context below.\n"
    "Cite the id of every claim like [doc-412#2].\n"
    "If the context is insufficient, reply exactly: I don't have enough information."
)

answer = client.chat.completions.create(
    model="gpt-4.1-mini",
    temperature=0.1,
    messages=[
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"},
    ],
).choices[0].message.content

cited = set(re.findall(r"\[([\w\-#]+)\]", answer))
if not cited and "I don't have enough information" not in answer:
    log.warning("uncited answer — treat as unverified: %s", answer[:200])
An answer with no citations and no refusal is the shape a hallucination takes; log it and you will find your retrieval gaps.

Index & evaluation

-- pgvector: HNSW index, and the recall knob
CREATE EXTENSION IF NOT EXISTS vector;

ALTER TABLE chunks ADD COLUMN embedding vector(1536);
ALTER TABLE chunks ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('english', content)) STORED;

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
CREATE INDEX ON chunks USING gin (tsv);
CREATE INDEX ON chunks (tenant_id, doc_id);

SET hnsw.ef_search = 100;      -- per-session recall vs latency knob
Build the index after the bulk load, not before; ef_search is the first thing to raise when recall looks bad.
# Measure context recall before you tune anything else
golden = [("how long do I have to request a refund?", "doc-412#2"), ...]

hits = sum(expected in [c.id for c in retrieve(q, k=5)] for q, expected in golden)
print(f"recall@5 = {hits / len(golden):.0%}")      # this is your ceiling

hits50 = sum(expected in [c.id for c in retrieve(q, k=50)] for q, expected in golden)
print(f"recall@50 = {hits50 / len(golden):.0%}")   # gap vs recall@5 => add a reranker
Fifteen lines that tell you whether to fix chunking, ranking or the prompt. Run it in CI.

Pros & cons

Pros

  • Answers reflect your data as of now — edit a document, the answer changes.
  • Citations make answers checkable, which is what makes them usable in regulated work.
  • No training: a corpus, an embedding call and an index get you a working system in a day.
  • Access control is enforced at retrieval, per user, with the data never entering model weights.
  • Far cheaper than fine-tuning to keep current, and trivially reversible.
  • Each stage is separately measurable and separately fixable.

Cons

  • Retrieval quality caps everything, and it is harder to get right than it looks.
  • Adds 200 ms–1 s of latency: embed, search, rerank, then a long prompt to process.
  • Context tokens dominate the bill — you pay for the chunks on every request.
  • A confident wrong answer from bad context is worse than no answer at all.
  • An extra data pipeline to build, monitor and reconcile, including deletions.
  • Multi-hop and aggregate questions ("how many contracts expire in Q2?") fit the model badly.
  • The index is a copy of your data, with its own ACL and compliance surface.

Concrete use cases

Support agent assistant

Agents answer policy questions by searching a wiki that changes weekly. RAG over the wiki plus the customer's own ticket history answers in seconds with a link to the exact paragraph, so the agent can verify before sending. Fine-tuning would be stale by the next release.

Internal documentation search

Ten years of Confluence, SharePoint and Google Docs nobody can find anything in. Hybrid retrieval with per-document ACLs gives every employee an answer scoped to what they may see, and citations make the stale pages visible for the first time.

Contract and policy Q&A

Legal needs "what does this contract say about termination?" with the clause attached. Chunking by clause, retrieving with a reranker and demanding citations turns an hour of reading into thirty seconds — and the citation is the deliverable, not the prose.

Product-aware chat

A storefront assistant answers from the live catalogue: specifications, stock, shipping rules. Metadata filters keep it to the user's region and language, and because the index is rebuilt from the catalogue, price changes propagate without touching the model.

Developer assistant over a private codebase

Chunked per function with the file path and signature prepended, so "where do we validate VAT numbers?" returns the function plus its tests. Hybrid search matters here more than anywhere: half the queries are exact symbol names.

When to use / when not to

use RAG for facts. use fine-tuning for form. they fix different problems.

Use it when…

  • Answers must come from a corpus the model has never seen — private, internal or very recent.
  • The corpus changes often enough that retraining would never keep up.
  • Users need to verify answers, so citations are a requirement rather than a nicety.
  • Different users may see different documents, so access control must be applied per query.
  • The corpus is far larger than any context window, or too expensive to resend every time.

Avoid it when…

  • The whole corpus fits comfortably in the context window and rarely changes. Use prompt stuffing, possibly with prompt caching.
  • You need a different style, format or tone rather than different facts. Use fine-tuning or a better prompt.
  • The question is an aggregate or a join over structured data. Use text-to-SQL against the database.
  • Answers must be exact and auditable with no generation at all. Use search and show the document.
  • The task needs multi-step reasoning across many documents. Use an agent harness with retrieval as one tool.
  • Latency budget is under ~150 ms. Use semantic caching in front, or precomputed answers.

Common mistakes & gotchas

Blaming the model for a retrieval failureThe answer is wrong, so the team upgrades the model, raises the temperature, rewrites the prompt — and nothing improves, because the correct chunk was never in the context.
Fix: log the retrieved chunk ids with every answer, and measure context recall on a golden set. If recall@5 is 70%, no prompt will save you.
Vector search onlyEverything works in the demo and then a user searches for an order number, an error code or a product SKU and gets five semantically adjacent, useless chunks.
Fix: hybrid search. Run BM25 alongside the vector query and fuse with RRF. It is usually one query change and the largest single quality jump available.
Chunking by character countThe default 1,000-character splitter cuts tables in half, separates headings from their content, and produces chunks that are meaningless out of context — "the limit is 30 days" with no subject.
Fix: split on structure, then size. Prepend the document title and heading path to every chunk. Read fifty random chunks out loud; if you cannot tell what they are about, neither can the retriever.
Filtering after retrievalTop-k is taken globally, then rows the user may not see are dropped. A user with narrow permissions gets two results instead of five, or worse, the text reaches the prompt and is paraphrased into the answer.
Fix: push tenant and ACL predicates into the search itself, and verify with a test that a user from tenant B can never retrieve a chunk from tenant A.
No deletion pathDocuments are upserted happily, but a retracted policy or an offboarded employee's notes stay in the index for ever — and get cited.
Fix: deterministic chunk ids, delete-by-doc-id on removal, prune trailing chunks when a document shrinks, and a periodic reconcile that diffs index ids against source ids.
Raising k to fix qualityRecall improves, answers get worse. More chunks means more distractors, a longer prompt, higher cost, and the right passage buried in the middle where the model attends least.
Fix: retrieve wide but rerank down to 3–8, and order the best chunk first. If recall@50 is far above recall@5, the problem is ranking, not retrieval.
Changing the embedding model in placeNew vectors are written with a new model while old ones remain. The two live in different spaces, scores become meaningless, and quality degrades quietly rather than failing loudly.
Fix: treat the embedding model as part of the index identity. Build a new index, backfill, switch reads atomically, then drop the old one.
No way to say "I don't know"With no score cut-off and no refusal instruction, the model always answers — including from the five least-irrelevant chunks when the corpus simply does not contain the answer.
Fix: a reranker score threshold plus an explicit refusal string in the system prompt, and alert on how often it fires. A rising refusal rate is a content gap worth knowing about.
Shipping without an evaluation setEvery change is judged by trying three questions by hand. Improvements and regressions are indistinguishable, and the system drifts.
Fix: 50–200 real questions with known answer chunks, scored in CI for context recall, faithfulness and answer relevance. It takes a day and pays for itself in the first week.

Alternatives

ApproachBest forComplexityCostKey difference vs RAG
RAGlarge, changing, private corporaMediumindex + context tokens—
Long-context stuffingsmall, stable corporaVery lowhigh per requestNo index at all; you pay for the whole corpus on every call and quality falls as it grows
Prompt cachinga fixed corpus reused constantlyLowcheap reads, cached writesStuffing made affordable — still bounded by the window, still no per-user filtering
Fine-tuningstyle, format, domain toneHightraining + hostingChanges behaviour, not knowledge; cannot cite, cannot be updated per document
Text-to-SQLstructured, aggregate questionsMediumlow per queryExact answers over tables; useless over prose
GraphRAGmulti-hop, entity-heavy corporaHighexpensive ingestionBuilds an entity graph first, so it can answer "how are X and Y connected"
Agentic searchopen-ended research questionsHighseveral calls per answerThe model decides when and what to search, repeatedly; slower and non-deterministic
  • Pick long-context stuffing when the corpus is a handful of documents — a product manual, a single policy — and simplicity beats everything.
  • Pick fine-tuning when the complaint is "it doesn't sound like us" rather than "it doesn't know that".
  • Pick text-to-SQL for counting, summing and filtering — questions whose answer is a number, not a paragraph.
  • Pick GraphRAG when questions span many documents and relationships, and you can afford a much heavier ingestion step.
  • Pick agentic RAG only once single-shot RAG is measurably good and you can name the question types that need more hops.
