Saga pattern

You cannot roll back a transaction that already committed in someone else's database. You can only do something that undoes it in business terms.

As of Nov 2026 · Garcia-Molina & Salem, 1987; examples in C#, Python and workflow engines

A business operation that spans several services — book a trip, onboard a customer, fulfil an order — cannot be one ACID transaction, because each service owns its own database and two-phase commit is unavailable, slow, or both. A saga replaces it with a sequence of local transactions: each step commits in its own service, and each step that can fail has a matching compensating transaction that semantically undoes it.

The word "semantically" is the whole pattern. You do not roll back a card charge; you issue a refund, and both appear on the customer's statement. You do not delete a hotel reservation; you cancel it, possibly incurring a fee. Compensation is a new business fact, not a technical undo — which means every compensating action is a design decision somebody in the business has to agree to.

Sagas come in two shapes. Choreography has each service react to the previous one's events, with no coordinator: simple to start, impossible to see. Orchestration puts the flow in one explicit state machine that issues commands: more visible, more testable, and a component that knows about everybody. Most teams start with the first and move to the second at around the fifth step.

Architecture / mental model

Four local transactions, three semantic undos, and one point of no return that decides the order of everything else.

Key concepts

SagaA business transaction spread across several services as a sequence of local transactions, each with a way to be undone in business terms.
Local transactionOne step: a single ACID transaction inside one service, which commits and becomes permanent immediately.
Compensating transactionA new transaction that undoes a previous step's effect in business terms — never a rollback.
Semantic rollbackThe acknowledgement that undoing is a business act with its own trail, not the erasure of what happened.
Pivot transactionThe step after which the saga can no longer be undone — everything before it must be compensatable, everything after it must be retriable.
Retriable stepA step after the pivot: it may fail temporarily but must eventually succeed, so it is retried rather than undone.
ChoreographyEach service reacts to the previous one's events and publishes its own. No coordinator exists.
OrchestrationA coordinator owns the flow as an explicit state machine and tells each service what to do.
Process managerThe implementation of an orchestrator: a stateful object that receives events, decides the next command, and remembers where it is.
Saga logDurable storage of which step a saga reached, so a crash resumes instead of losing the business process.
Correlation idThe identifier carried through every message so that replies can be matched to the saga that is waiting for them.
Lost isolationThe property a saga gives up: its half-finished state is visible to everybody while it runs.
CountermeasuresThe standard techniques for coping with a saga's missing isolation, from cheap to thorough.
IdempotencyEvery step and every compensation must tolerate being executed more than once.
Stuck sagaAn instance that stopped: a reply never arrived, a step keeps failing, or a compensation cannot complete.
TimeoutThe deadline on each step, after which the saga gives up waiting and takes a decision.

Essential code patterns

Orchestration (C#)

public enum BookingState
{
    AwaitingHotel, AwaitingPayment, AwaitingFlight, Confirmed,
    CompensatingPayment, CompensatingHotel, Failed
}

public sealed class BookingSaga
{
    public Guid SagaId { get; init; }
    public BookingState State { get; private set; } = BookingState.AwaitingHotel;
    private readonly List<string> _compensated = new();   // never compensate twice
}
An explicit state machine, not a set of boolean flags. The compensation states are states too — a saga is as often going backwards as forwards.
public async Task<ICommand?> Handle(IEvent e, CancellationToken ct) => (State, e) switch
{
    (BookingState.AwaitingHotel,   HotelReserved r) => Advance(BookingState.AwaitingPayment, new ChargeCard(SagaId, r.Total)),
    (BookingState.AwaitingPayment, CardCharged c)   => Advance(BookingState.AwaitingFlight,  new BookFlight(SagaId)),
    (BookingState.AwaitingFlight,  FlightBooked)    => Advance(BookingState.Confirmed,       null),

    // failures unwind in reverse, one compensation at a time
    (BookingState.AwaitingFlight,  FlightRejected)  => Advance(BookingState.CompensatingPayment, new RefundCard(SagaId)),
    (BookingState.CompensatingPayment, CardRefunded) => Advance(BookingState.CompensatingHotel,  new CancelReservation(SagaId)),
    (BookingState.CompensatingHotel,   ReservationCancelled) => Advance(BookingState.Failed, new MarkOrderFailed(SagaId)),

    _ => null,   // unexpected message for this state — log, do not throw
};
The whole flow, forwards and backwards, in one readable block. This is what choreography cannot give you.
// state change and next command committed together — outbox, not a broker call
await using var tx = await db.BeginTransactionAsync(ct);
saga.Apply(evt);
db.Sagas.Update(saga);
if (next is not null) db.Outbox.Add(OutboxRow.For(next, saga.SagaId));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
If the orchestrator dies here, the saga state and the pending command are either both there or both absent — never half.

Choreography (Python)

# hotel service — reacts to an event, publishes the next one
@on("OrderCreated")
def reserve_room(evt, conn):
    with conn.transaction():
        if already_handled(conn, evt.message_id):      # idempotent
            return
        reservation = reserve(conn, evt.order_id, evt.dates)
        publish(conn, "HotelReserved", order_id=evt.order_id,
                reservation_id=reservation.id, saga_id=evt.saga_id)

@on("BookingFailed")                                    # compensation, also an event handler
def cancel_room(evt, conn):
    with conn.transaction():
        cancel_if_present(conn, evt.order_id)           # no-op if already cancelled
No coordinator — and note the compensation logic now lives in every participant, which is exactly how choreography stops scaling.

The saga log

CREATE TABLE saga (
    saga_id      uuid PRIMARY KEY,
    type         text        NOT NULL,
    state        text        NOT NULL,
    data         jsonb       NOT NULL,         -- ids gathered so far
    compensated  text[]      NOT NULL DEFAULT '{}',
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    timeout_at   timestamptz                   -- the step deadline
);

CREATE INDEX ix_saga_live ON saga (timeout_at)
    WHERE state NOT IN ('Confirmed', 'Failed');
A partial index on live sagas keeps both the timeout sweeper and the operations console fast.
-- the alert that catches a saga nobody noticed had stopped
SELECT state, count(*), max(now() - updated_at) AS oldest
FROM   saga
WHERE  state NOT IN ('Confirmed', 'Failed')
GROUP  BY state
ORDER  BY oldest DESC;
Age of the oldest in-flight saga per state. Nothing else observes a stuck saga — no request is pending and no error is logged.
-- the timeout sweeper, run every minute
SELECT saga_id, state FROM saga
WHERE  timeout_at < now()
  AND  state NOT IN ('Confirmed', 'Failed')
FOR UPDATE SKIP LOCKED;
A step that waits forever is the most common way a saga fails. Every state needs a deadline and a decision.

Countermeasure: semantic lock

-- the intermediate state is explicit, and every reader must handle it
ALTER TABLE orders
  ADD CONSTRAINT ck_status
  CHECK (status IN ('PENDING', 'CONFIRMED', 'FAILED'));

-- readers refuse to act on a saga still in flight
UPDATE orders SET status = 'REFUNDED'
WHERE  id = $1 AND status = 'CONFIRMED';   -- 0 rows if still PENDING
Cheapest and most useful countermeasure for a saga's missing isolation — and the "processing…" in your UI is the same idea.

Let somebody else hold the state

# Temporal / Durable Functions style: the orchestrator reads as plain code,
# and the engine persists every step so a crash resumes mid-flow
async def booking_saga(ctx, req):
    hotel = await ctx.call(reserve_room, req)
    try:
        payment = await ctx.call(charge_card, req)
        await ctx.call(book_flight, req)
    except StepFailed:
        await ctx.call(refund_card, payment)      # compensations, in reverse
        await ctx.call(cancel_room, hotel)
        raise
A durable execution engine turns the state machine back into a try/except. The saga log, timeouts and replay become the platform's problem.

Pros & cons

Pros

  • Allows a business process to span services that each own their own database, with no distributed transaction.
  • No locks held across services, so throughput and availability survive a slow or absent participant.
  • A participant being down delays the saga instead of failing the whole operation.
  • Compensations are explicit business decisions, which usually improves the product as well as the code.
  • The saga log gives a complete, auditable history of every attempt and reversal.
  • Works with any broker and any database — no XA, no vendor requirement.

Cons

  • Isolation is gone: intermediate state is visible to everyone and needs explicit countermeasures.
  • Every step needs a compensating action designed, agreed with the business and tested.
  • Failure handling dominates the code — the unhappy paths are most of the work.
  • Debugging spans several services and many asynchronous hops.
  • Choreographed sagas become invisible; orchestrated ones add a component that knows about everybody.
  • Needs real operational tooling: timeouts, stuck-saga alerts, and a console for manual intervention.

Concrete use cases

Trip booking across providers

Hotel, flight and car come from three systems, none of which share a transaction. Each is reserved in turn and released by its own cancellation API if a later step fails — with the card charge placed deliberately late, so the common failures happen before any money moves.

Order fulfilment

Reserve stock, take payment, create the shipment, notify the warehouse. The pivot is the payment; everything after it is retried until it succeeds, because unwinding a dispatched parcel is not a software problem any more.

Customer onboarding

Create the account, run KYC, open the ledger, issue the card. A KYC rejection two days later compensates by closing the ledger and marking the account rejected — a flow with a human-scale timeout that no synchronous request could have survived.

Subscription upgrade

Change the plan, adjust entitlements, charge the prorated difference, inform the partner. A declined card compensates by restoring the previous plan and entitlements — and the semantic lock on the subscription is what stops support from changing it mid-flight.

Payout approval

A payout needs two approvals, a compliance check and a bank transfer. The orchestrator holds the state for days, times out to escalation rather than compensation, and gives operations a console showing exactly which approval everything is waiting on.

When to use / when not to

if one database could hold it all, use a transaction — a saga is what you do when you can't

Use it when…

  • A business operation spans services or systems that cannot share a transaction.
  • Each step has a meaningful business-level undo that someone can agree to.
  • The process is long-lived — minutes, hours or days — so holding anything open is impossible.
  • Partial completion with explicit compensation is acceptable to the business.
  • You need a visible, auditable history of what was attempted and reversed.

Avoid it when…

  • All the data lives in one database. Use a local transaction — it is free and actually atomic.
  • The steps genuinely cannot be undone. Use a different decomposition, or move the irreversible step last.
  • The business insists on true all-or-nothing visibility. Use one service that owns the whole operation.
  • The services were split along the wrong seam and every operation spans all of them. Use EventStorming to redraw the boundaries.
  • You do not want to own orchestrator state, retries and replay. Use a durable execution engine such as Temporal or Azure Durable Functions.

Common mistakes & gotchas

Designing the happy path firstThe forward flow takes a day and the failure handling takes three weeks, because every compensation turns out to need a business decision nobody has made.
Fix: write the compensation beside each step as you design it. If you cannot name one, that step belongs after the pivot — and that changes the order of everything.
Forgetting isolation is goneMid-saga state is public. A support agent refunds an order the saga is about to compensate, and the customer gets two refunds.
Fix: add a semantic lock. Make PENDING an explicit status that every reader, every screen and every API must handle.
Compensations that can failThere is nothing to compensate a compensation with. A refund that permanently fails leaves the saga stranded and a human on the phone.
Fix: design compensations to retry until they succeed, keep them idempotent, and escalate to a human rather than giving up. Anything genuinely fallible goes after the pivot.
No pivot identifiedIrreversible actions end up in the middle — a confirmation email sent at step 2 — and the saga can no longer unwind cleanly.
Fix: name the pivot explicitly. Push emails, dispatches and filings to the end, and make everything before it compensatable.
Choreography past four stepsThe flow exists only as the sum of everyone's subscriptions, nobody can draw it, and adding a step means editing three services and hoping.
Fix: move to orchestration when the flow exceeds about four steps, branches, or when you cannot answer "where is order 42?". The hub coupling is worth it.
Treating a timeout as a failureThe payment provider did not reply in ninety seconds. That does not mean the charge failed — compensating blindly can refund money that was never taken, or leave money taken with no booking.
Fix: on timeout, query the participant for the real outcome before deciding. A timeout is missing knowledge, not knowledge of failure.
No stuck-saga alertA saga stops and nothing notices: no request is pending, nobody is waiting on a response, no error is logged — just a customer whose money is in limbo.
Fix: alert on the age of the oldest in-flight saga per state, give every state a timeout, and build the operations console before you need it.
Business rules in the orchestratorPricing, eligibility and validation drift into the coordinator, which quietly becomes the god service the microservices were meant to avoid.
Fix: the orchestrator owns sequence, timeouts and compensation order. Everything else belongs to the aggregate in the owning service.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs a saga
Sagabusiness processes spanning servicesHighfree; real operational cost—
Local transactioneverything in one databaseVery lowfreeActually atomic and isolated; only possible if one service owns all the data
Two-phase commit (XA)legacy XA resourcesHighfree; heavyReal atomicity, at the cost of locks across the network and coupled availability
Durable execution (Temporal, Durable Functions)long workflows you do not want to hand-rollMediumservice or self-hostedSame pattern, but state, retries and replay are the engine's problem
TCC (try-confirm-cancel)reservable resourcesHighfreeParticipants reserve first and confirm later, so isolation is partly recovered — every service must support it
Merge the servicesa boundary drawn in the wrong placeLowfreeRemoves the distributed problem entirely; often the correct answer
Accept inconsistencylow-value, reconcilable processesVery lowfreeNo compensation logic; a nightly reconciliation job fixes the drift
  • Pick a local transaction whenever the data could live in one service — most sagas exist because a boundary was drawn badly.
  • Pick durable execution if you want sagas without owning the saga log, the timeout sweeper and the replay machinery.
  • Pick TCC when every participant can hold a reservation, and you need stronger isolation than compensation gives.
  • Pick merging the services if almost every operation spans the same three of them; that is a boundary problem, not a transaction problem.
  • Pick reconciliation for low-value flows where a nightly job fixing the drift is cheaper than compensations nobody will test.
