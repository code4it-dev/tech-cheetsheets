OpenID Connect

OAuth tells an API what you may do. OIDC tells an app who you are — and they are not the same token.

As of Nov 2026 · OpenID Connect Core 1.0 (2014, errata set 2) · built on OAuth 2.0, certified by the OpenID Foundation

OAuth 2.0 deliberately says nothing about identity. An access token means "the bearer may read this calendar"; it does not reliably say who the user is, when they authenticated or how. For years everyone built their own answer on top, usually by calling a vendor-specific "who am I" endpoint, and most of those answers were insecure in the same way.

OpenID Connect standardises that layer. It adds one scope (openid), one new token (the ID token, a JWT describing the authentication event), a set of standard claims, a UserInfo endpoint, a discovery document and a nonce to bind the token to the login attempt. Everything else — the redirect, the code, the token endpoint — is still plain OAuth.

The distinction worth keeping in your head: the ID token is for the client that asked for the login, and the access token is for the API. They have different audiences, different lifetimes and different jobs, and swapping them is the single most common and most serious OIDC mistake. The other hard part is not login at all — it is logout, because a successful SSO leaves you with one session at the identity provider and one at every application.

Architecture / mental model

the login: who, when, how, for which client nonce  ·  UserInfo endpoint  ·  standard claims discovery  ·  JWKS  ·  session management & logout OAuth 2.0 underneath, unchanged authorization code + PKCE  ·  redirect URIs  ·  state  ·  token endpoint  ·  refresh tokens  ·  scopes ID token → your client aud = your client_id answers: who logged in, when, how read it once, create a session, discard it never send it to an API access token → the API aud = the API's identifier answers: what may the bearer do opaque to your client, by design never parse it for identity

Two tokens come back from one login. Which one you send where is the whole of OIDC security in one sentence.

Key concepts

ID tokenA signed JWT describing an authentication event: who logged in, when, how, and for which client.
Access tokenThe OAuth credential for calling an API. Present in an OIDC response, but a different token with a different audience.
openid scopeThe one word that turns an OAuth authorization request into an OIDC authentication request.
nonceA random value the client sends and finds echoed inside the ID token, binding that token to this login attempt.
ClaimsThe statements inside the ID token or from UserInfo — name, email, roles, tenant.
UserInfo endpointAn OAuth-protected endpoint returning claims about the user, called with the access token.
DiscoveryA well-known JSON document describing every endpoint, algorithm and capability of the provider.
JWKSThe provider's public signing keys, published as JSON so your app can verify tokens without any shared secret.
ValidationThe ordered set of checks an ID token must pass before you believe a single claim in it.
Single sign-onOne authentication at the provider giving the user access to many applications without logging in again.
prompt & max_ageParameters that control whether the user is asked to authenticate again, and how recently they must have done so.
acr & amrHow strongly and by what method the user authenticated — the basis for step-up authentication.
IdP sessionThe provider's own session cookie — the thing that actually makes SSO work, and the thing your logout does not touch.
RP-initiated logoutThe application sends the user to the provider's end-session endpoint to terminate the IdP session too.
Back-channel logoutThe provider POSTs a signed logout token directly to each application's server, with no browser involved.
Subject identifiersub — the stable, issuer-scoped user id, and the only claim safe to key your data on.
Hybrid flowReturning an ID token in the redirect alongside the code. Legacy, and rarely the right answer now.

Essential requests & code

The request, and what comes back

GET /authorize
  ?response_type=code
  &scope=openid%20profile%20email%20api%3A%2F%2Fcalendar%2Fread
  &client_id=s6BhdRkqt3
  &redirect_uri=https%3A%2F%2Fapp.example%2Fcallback
  &state=af0ifjsldkj               # checked against the request
  &nonce=n-0S6_WzA2Mj               # checked inside the token
  &code_challenge=E9Melhoa2OwvFrEM…&code_challenge_method=S256

# the openid scope is what makes this an authentication request at all
Identical to an OAuth request plus openid and nonce. Everything else — PKCE, state, exact redirect URI — still applies.
{
  "token_type":    "Bearer",
  "expires_in":    300,
  "access_token":  "eyJhbGciOiJSUzI1NiIs…",   // aud: api://calendar — for the API
  "id_token":      "eyJhbGciOiJSUzI1NiIs…",   // aud: s6BhdRkqt3   — for you
  "refresh_token": "8xLOxBtZp8"
}
Two tokens, two audiences. The only thing your client parses is the ID token.
{
  "iss":       "https://login.example.com",
  "sub":       "248289761001",          // key your user records on (iss, sub)
  "aud":       "s6BhdRkqt3",            // your client_id
  "exp":       1763640000,
  "iat":       1763639700,
  "nonce":     "n-0S6_WzA2Mj",          // must equal what you stored
  "auth_time": 1763639690,              // when they actually authenticated
  "amr":       ["pwd", "otp"],          // how — password plus a one-time code
  "email":     "ada@example.com",
  "email_verified": true                // without this, do not match on email
}
The decoded ID token. Note what is absent: no scopes, no permissions — it describes a login, not an authorization.

Being a relying party

builder.Services
    .AddAuthentication(o =>
    {
        o.DefaultScheme          = CookieAuthenticationDefaults.AuthenticationScheme;
        o.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
    })
    .AddCookie(o => o.Cookie.SameSite = SameSiteMode.Lax)
    .AddOpenIdConnect(o =>
    {
        o.Authority     = "https://login.example.com";   // discovery + JWKS from here
        o.ClientId      = "s6BhdRkqt3";
        o.ClientSecret  = builder.Configuration["Oidc:Secret"];
        o.ResponseType  = "code";                        // not "id_token", not hybrid
        o.UsePkce       = true;
        o.SaveTokens    = true;                          // keep them server-side
        o.GetClaimsFromUserInfoEndpoint = true;          // once, at login
        o.Scope.Clear();
        foreach (var s in new[] { "openid", "profile", "email" }) o.Scope.Add(s);

        o.TokenValidationParameters = new()
        {
            ValidateIssuer   = true,
            ValidateAudience = true,
            ValidAudience    = "s6BhdRkqt3",             // the ID token is for YOU
            ClockSkew        = TimeSpan.FromSeconds(30), // not the 5-minute default
            NameClaimType    = "name",
            RoleClaimType    = "roles",
        };
    });
The handler validates signature, issuer, audience, expiry and nonce for you. Tightening ClockSkew from the default five minutes is worth doing.
from authlib.integrations.starlette_client import OAuth

oauth = OAuth()
oauth.register(
    name="idp",
    server_metadata_url="https://login.example.com/.well-known/openid-configuration",
    client_id="s6BhdRkqt3",
    client_secret=os.environ["OIDC_SECRET"],
    client_kwargs={"scope": "openid profile email",
                   "code_challenge_method": "S256"},
)

@app.get("/callback")
async def callback(request: Request):
    token = await oauth.idp.authorize_access_token(request)   # checks state + PKCE
    claims = token["userinfo"]            # Authlib validated iss, aud, exp and nonce
    request.session["user"] = {"iss": claims["iss"], "sub": claims["sub"],
                               "email": claims.get("email")}
    return RedirectResponse("/")
Authlib reads the discovery document and validates the ID token, nonce included. Store (iss, sub) — not the email.

Logging out properly

// 1 — end your own session AND the provider's
app.MapPost("/logout", async (HttpContext ctx) =>
{
    await ctx.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
    await ctx.SignOutAsync(OpenIdConnectDefaults.AuthenticationScheme);  // end_session
});

// 2 — accept logout for sessions ended elsewhere
app.MapPost("/bff/backchannel-logout", async (HttpContext ctx, ILogoutTokenValidator v) =>
{
    var form  = await ctx.Request.ReadFormAsync();
    var token = await v.ValidateAsync(form["logout_token"]);   // signature, iss, aud, events
    await sessions.RevokeAsync(token.Sub, token.Sid);          // kill this user's session
    return Results.Ok();
});
Signing out locally only is the most common logout bug: the IdP session survives and the next click silently signs the user back in.
# the same two halves in Python
@app.post("/logout")
async def logout(request: Request):
    id_token = request.session.get("id_token")
    request.session.clear()                                   # 1. local session
    meta = await oauth.idp.load_server_metadata()
    return RedirectResponse(                                   # 2. the IdP session
        f"{meta['end_session_endpoint']}"
        f"?id_token_hint={id_token}"
        f"&post_logout_redirect_uri={quote(POST_LOGOUT_URI)}"  # must be registered
    )
id_token_hint tells the provider which session to end, and avoids an "are you sure?" interstitial.

Inspecting a provider

curl -s https://login.example.com/.well-known/openid-configuration | jq '{
  issuer, authorization_endpoint, token_endpoint, userinfo_endpoint,
  jwks_uri, end_session_endpoint,
  backchannel_logout_supported, code_challenge_methods_supported,
  id_token_signing_alg_values_supported, subject_types_supported
}'
The fastest way to learn what a provider actually supports — including whether back-channel logout and pairwise subjects are available.

Pros & cons

Pros

  • A standard, interoperable answer to "who is this user?", instead of a per-vendor one.
  • The ID token is self-contained and verifiable offline against published keys.
  • Single sign-on across applications with one authentication.
  • Discovery and JWKS make endpoint and key rotation invisible to applications.
  • auth_time, acr and amr support step-up authentication for sensitive operations.
  • Certified implementations exist for every language, so you need not write the hard parts.

Cons

  • The ID token / access token distinction is subtle and routinely got wrong.
  • Validation has many steps, and skipping one is usually a vulnerability rather than a bug.
  • Logout is genuinely hard: N+1 sessions, and front-channel mechanisms broken by browsers.
  • Claims beyond the standard set are provider-specific, so portability is partial.
  • SSO means one compromised identity session reaches every connected application.
  • Local development against a hosted provider is awkward — redirect URIs, HTTPS, cookies.

Concrete use cases

"Sign in with Google"

You want identity, not calendar access. Request openid profile email, validate the ID token, key the user on (iss, sub), and create your own session. No password to store, no reset flow to build.

Internal SSO across a dozen apps

One identity provider, twelve applications, one login per day. Each app redirects, the provider recognises its own session, and the user is back in under a second with no prompt.

Enterprise customers with their own IdP

A B2B product federates to each customer's provider. Users keep their corporate credentials and MFA policy, and the tenant arrives as a claim — which the application validates rather than trusting the subdomain.

Step-up before a payment

Browsing works with an ordinary session. Confirming a transfer re-runs authorization with max_age=300 and a stronger acr_values, so the provider prompts for MFA and auth_time proves it happened.

Logout that actually logs out

A shared workstation needs "sign out" to mean it. RP-initiated logout ends the IdP session, and back-channel logout notifies the other eleven applications server-to-server so none of them silently resumes.

When to use / when not to

ID token to your app, access token to the API — get that right and most of the rest follows

Use it when…

  • You need to know who the user is, not just what an app may do.
  • Users should sign in once and reach several applications.
  • You would rather not store passwords at all.
  • Enterprise customers need to bring their own identity provider.
  • You need evidence of how and when someone authenticated.

Avoid it when…

  • You only need API authorization with no user identity. Use plain OAuth 2.0.
  • It is one application with its own users and no SSO. Use a session cookie and a password or passkey.
  • Two services need to authenticate to each other. Use client credentials or mTLS — there is no user to identify.
  • The customer requires SAML. Use SAML, or a provider that bridges it.
  • You are considering writing the provider. Use an existing one; this is not a component to build.

Common mistakes & gotchas

Sending the ID token to an APIIt is addressed to your client, not to the API. A correct API rejects it on audience — and an API that checks only the signature accepts it, which means any client of that issuer can call you as any of its users.
Fix: ID token to your app, access token to the API. If you need a token for an API, request its scope and use what comes back in access_token.
Parsing the access token for identityIt is opaque to you by contract, even when it happens to decode. Providers change the format, and your login breaks for reasons unrelated to your code.
Fix: read identity from the ID token or UserInfo. Treat the access token as a string you forward and nothing else.
No nonce, or never checking itWithout it an ID token captured from another session or another flow can be replayed at your callback, and every other check will pass.
Fix: generate a random nonce per login attempt, store it with the session, and compare it to the token's claim. state does not cover this.
Keying users on emailEmail addresses change and get reassigned, and an unverified one lets an attacker register the victim's address at a sloppy provider and take over the account.
Fix: key on (iss, sub). If you must match on email for account linking, require email_verified and prefer an explicit linking step.
Local logout onlyClearing your own cookie leaves the IdP session intact, so the next protected page silently signs the user straight back in — which looks like logout being broken.
Fix: end both. Sign out locally and redirect to end_session_endpoint with id_token_hint and a registered post-logout URI.
Relying on front-channel logoutIt loads a hidden iframe per application, which depends on third-party cookies — now blocked by default in every major browser. It fails silently, so it looks like it works.
Fix: implement back-channel logout, where the provider POSTs a logout token to each application's server. Test it; silence is not success.
Ignoring azp with multiple audiencesWhen a token carries several audiences, the azp claim names the client it was issued to. Checking only that your id appears in aud lets a token minted for a different client be replayed at your login.
Fix: if azp is present, require it to equal your client id. Good libraries do this; confirm yours does.
Treating the ID token as a sessionStoring it in a cookie and re-reading it on every request turns a short-lived login receipt into a long-lived bearer credential, with no revocation.
Fix: validate once, create your own session with your own lifetime and revocation, and throw the ID token away — except the copy kept for id_token_hint at logout.

  • Pick plain OAuth when there is no user to identify — machine-to-machine traffic needs no ID token.
  • Pick SAML only when a customer requires it; bridge it at the provider rather than in your application.
  • Pick passkeys as the authentication method inside OIDC, not as a replacement for it.
  • Pick session cookies for a single app with its own users — federation you do not need is pure cost.
