CQS

Asking a question should not change the answer.

As of Nov 2026 · Bertrand Meyer, Object-Oriented Software Construction, 1988; examples in C#, Python and HTTP

Command-Query Separation is a one-sentence design rule: every method should either change state or return a result, but never both. Methods that change something are commands and return nothing. Methods that answer a question are queries, return a value and leave the world exactly as they found it. Call a query twice and you get the same answer; call it zero times and nothing is different.

The payoff is that you can read a call site and know whether it is dangerous. var n = basket.ItemCount; is obviously safe to move, cache, retry, log, run inside a debugger watch window or delete. var job = queue.Pop(); is none of those things, and the only reason you know is that you happen to remember what Pop does. Multiply that uncertainty by a codebase and it becomes the reason refactoring feels risky.

CQS is a method-level discipline that costs nothing to adopt and applies in any language and any paradigm. Its architectural big brother is CQRS, which takes the same idea and applies it to entire models and data stores — a far larger decision. CQS is the one you should default to; CQRS is the one you should justify.

Key concepts

Command (CQS)A method that changes observable state and returns nothing.
Query (CQS)A method that returns a value and leaves observable state untouched.
Side effectAny change a method makes beyond returning its value — the thing CQS is organising.
Benign side effectAn internal change that no caller can observe — caching, lazy initialisation, metrics — which keeps a method a query.
Mixed methodA method that both returns a value and mutates state — the thing CQS asks you to split.
Pragmatic exceptionsThe cases where mixing is correct — atomic operations, iterators, builders — and CQS yields deliberately.
Referential transparencyThe property that an expression can be replaced by its value without changing the program — what CQS buys you for queries.
Pure functionA function with no side effects whose result depends only on its arguments — a stricter cousin of the CQS query.
IdempotencyDoing something twice has the same effect as doing it once — what a command needs if it is ever retried.
HTTP semanticsGET as query, POST/PUT/PATCH/DELETE as command — CQS baked into the protocol since 1997.
MemoizationCaching a query's result so repeated calls are cheap — only safe because the method is a query.
CQRSThe architectural scaling of CQS: separate models, and possibly separate stores, for writing and reading.
Design by ContractMeyer's broader method, which CQS exists to serve: preconditions and postconditions you can state because queries are honest.
TestabilityThe practical dividend: commands are verified by checking state, queries by checking return values — never both at once.

Essential code patterns

Splitting a mixed method (C#)

// before — reads like a query, behaves like a command
public Job Pop()
{
    var job = _items[0];
    _items.RemoveAt(0);
    return job;                 // returns AND mutates
}
The shape to look for: a return statement in a method that also changes a field.
// after — two methods, two obligations
public Job? Peek() => _items.Count > 0 ? _items[0] : null;   // query
public void Dequeue() => _items.RemoveAt(0);                  // command

var job = queue.Peek();
if (job is not null) { Process(job); queue.Dequeue(); }
The call site is now longer and honest: the removal happens on a line that says so — and after processing succeeded.
// the deliberate exception: atomicity forbids splitting
public bool TryDequeue(out Job job)   // documented as a mutation
{
    lock (_gate) { /* read and remove as one indivisible step */ }
}
Keep the mixed method where a race would otherwise appear, and make the name say that it mutates.

Commands, queries and benign effects

public sealed class Basket
{
    private Money? _cachedTotal;

    public int ItemCount => _lines.Count;                 // query
    public Money Total() => _cachedTotal ??= Sum(_lines); // query, benign cache

    public void AddItem(Sku sku, int qty)                 // command
    {
        _lines.Add(new Line(sku, qty));
        _cachedTotal = null;                              // invalidate
    }
}
A memoised query stays a query: the cache is invisible to callers, and the command that invalidates it returns nothing.
// the pragmatic exception almost everyone accepts
public Guid Create(NewOrder data)   // command that returns the new identity
{
    var order = Order.From(data);
    _repo.Add(order);
    return order.Id;                // an identity, not a view of state
}
Returning the id of something you just created is not a query — the caller could not have known it beforehand.

Python

class Counter:
    def __init__(self) -> None:
        self._n = 0

    @property
    def value(self) -> int:      # query: repeatable, safe in a log line
        return self._n

    def increment(self) -> None:  # command: returns nothing
        self._n += 1

# bad: next_id() looks free and is not
# good: counter.increment(); id = counter.value
Properties for queries, plain methods returning None for commands — the convention makes the split visible at the call site.
from functools import cached_property

class Order:
    @cached_property
    def total(self) -> int:      # memoised query
        return sum(l.price * l.qty for l in self.lines)

    def add_line(self, line) -> None:
        self.lines.append(line)
        self.__dict__.pop("total", None)   # invalidate the cache
`cached_property` is a benign side effect — as long as the command that changes the data clears it.

Over HTTP

GET    /orders/42            # query  — safe, idempotent, cacheable
GET    /orders?status=open   # query  — safe
POST   /orders               # command — not safe, not idempotent
PUT    /orders/42/status     # command — not safe, idempotent
DELETE /orders/42            # command — not safe, idempotent

# never: GET /orders/42/delete
The protocol already encodes CQS. A GET with side effects breaks caches, prefetchers and automatic retries all at once.
POST /orders
Idempotency-Key: 9f1c7a2e-...      # client-generated, stored server-side

# a retried POST with the same key returns the original result
# instead of creating a second order
Commands cannot be safe, so make them idempotent instead — the standard way to survive a retry on an unreliable network.

Enforcing it

# code review heuristics that catch most violations
#  1. a method with a return type that also assigns to a field
#  2. a getter or property that is not safe to call twice
#  3. a name starting with Get/Is/Has/Find that mutates
#  4. an assertion or log line that would break if removed
No tool enforces CQS; these four questions in review catch nearly every accidental violation.

Pros & cons

Pros

  • You can read a call site and know whether it is dangerous, without opening the method.
  • Queries become safe to cache, memoize, retry, parallelise, log and evaluate in a debugger.
  • Tests get an obvious shape: assert on a return value, or assert on state — never both.
  • Refactoring is lower risk: a line you can delete is visible from its type.
  • Costs nothing — no infrastructure, no runtime, no consistency trade-off.
  • Makes assertions and contracts trustworthy, which is why Meyer introduced it.

Cons

  • Some call sites become two lines where one would do.
  • Concurrency genuinely requires mixed methods, so the rule has real exceptions you must recognise.
  • Standard library and framework APIs violate it constantly, so your codebase will never be uniform.
  • The split can introduce a race if the two calls are not protected together.
  • Nothing enforces it — no compiler, no linter — so it survives only on review discipline.
  • Applied dogmatically it produces awkward APIs that fight the language's idioms.

Concrete use cases

A logging line that consumed work

A developer adds log.Debug($"next: {queue.Pop()}") while debugging. Jobs start disappearing in production, and only under the log level that enables that line. Splitting into Peek() and Dequeue() makes the mistake impossible to write.

Retry policy on an HTTP client

A client library retries idempotent calls automatically. Because reads are genuine GETs and writes carry an idempotency key, retries are correct by construction — no per-endpoint allowlist, no duplicate withdrawals.

Caching a page at the CDN

An endpoint is marked cacheable, and the CDN starts serving a stored copy. It only works because the handler is a pure query; the same change applied to an endpoint that quietly recorded a view count would have broken the counter invisibly.

Debugging a live incident

An engineer evaluates order.Total() in a debugger watch window while paused in production. With CQS that is free; with a mixed method, inspecting the state would have changed it — the worst possible moment to find out.

Preparing for CQRS

A team wants to split read and write models in one context. Because the codebase already separates commands from queries at method level, the migration is mostly moving existing query methods behind a read model instead of untangling them first.

When to use / when not to

default to yes — it is free. The skill is recognising the handful of places to break it.

Use it when…

  • Always, as the default for new code in any language or paradigm.
  • Designing a public API, where callers cannot see your implementation.
  • Anything will be retried, cached or evaluated by a debugger, a logger or an assertion.
  • You are writing contracts, invariants or property-based tests.
  • You expect to adopt CQRS later and want the seams to already exist.

Avoid it when…

  • The operation must be atomic. Use a documented mixed method such as TryDequeue or compare-and-swap.
  • The language idiom demands it — iterators, streams, next(). Use the idiom; fighting it costs more than it saves.
  • You are wrapping a third-party API that mixes freely. Use an adapter that presents a clean split rather than rewriting their semantics.
  • The split would require exposing internal state to make the query possible. Use one method and a very explicit name.
  • You are tempted to jump straight to separate read and write databases. Use CQRS — deliberately, and only where measured.

Common mistakes & gotchas

Confusing CQS with CQRSA team reads "separate commands and queries", stands up a projection pipeline and an eventual-consistency window, and inherits a large operational cost for a rule that was free.
Fix: CQS separates methods and costs nothing; CQRS separates models and stores and costs a lot. Adopt the first by default, the second with evidence.
Getters that mutateA property that lazily loads, resets a flag, or advances a cursor turns every if (x.Thing != null) into a side effect, and debuggers evaluating it change program behaviour.
Fix: lazy initialisation is fine only while it is unobservable. Anything a caller can detect belongs in a method named as a command.
Splitting something that must be atomicTurning TryDequeue into Peek plus Dequeue creates a window where two threads peek the same item and both process it.
Fix: keep the atomic operation, or protect the two calls with one lock. CQS yields to correctness, and that is not a failure of the rule.
GET endpoints with side effectsA "delete" or "approve" link implemented as a GET gets fired by a crawler, a browser prefetch, a link preview or a retry — the classic self-inflicted data loss.
Fix: GET and HEAD must be safe. Use POST/PUT/DELETE for anything that changes state, and add an idempotency key so retries are harmless.
Commands that return the full new stateOrder Update(...) returning the updated order looks convenient, then quietly becomes the only way callers read state, and the two concerns fuse again.
Fix: return nothing, or at most the new identity. If the caller needs the state, let them query for it — which also keeps the read path cacheable.
Treating it as an absolute lawRewriting iterators, builders and interop wrappers to obey the rule produces APIs that fight the language and that nobody wants to call.
Fix: treat it as a strong default. Break it consciously, name the method so the mutation is obvious, and write down why.
Memoizing a mixed methodAdding a cache in front of something that also mutates means the side effect happens once and is skipped forever after — usually discovered weeks later.
Fix: before caching anything, confirm it is a query. If it is not, the cache is a behaviour change, not an optimisation.
Hiding effects behind innocent namesGetOrCreateUser, FindOrInsert, EnsureLoaded all mutate while starting with a reading verb, which is exactly the confusion CQS is trying to remove.
Fix: if it can create, say so — CreateIfMissing. Reserve Get, Is, Has and Find for methods that genuinely change nothing.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs CQS
CQSany codebase, as a defaultVery lowfree—
CQRSdiverging read and write shapesMedium–Highfree; operational cost realSeparates models and stores, not methods; introduces eventual consistency
Pure functions / functional corelogic-heavy domainsMediumfreeStricter: no state reads either, effects pushed to the edges
Immutabilityvalue-heavy modelsLowfreeRemoves mutation instead of segregating it; "changes" return new objects
Effect systems / IO typesHaskell, Scala, F#HighfreeThe compiler enforces the split that CQS leaves to review
No rulescripts, throwaway codeNonefreeFine briefly; every call site becomes unreadable at scale
  • Pick CQRS when the read shape and the write shape genuinely diverge — not because the acronym is similar.
  • Pick a functional core if the domain is computation-heavy and you want the stronger guarantee.
  • Pick immutability for value objects; it makes most of the CQS question disappear, since there is nothing to mutate.
  • Pick an effect system if your language has one — it turns the convention into a compile error.
