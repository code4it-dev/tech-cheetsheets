Kubernetes

You declare what should run; it keeps a fleet of machines making that true, forever.

As of Nov 2026 · release line 1.36

Running one container on one server is easy. Running hundreds across dozens of servers is not: which machine has room, what happens when a machine dies, how do containers find each other, how do you roll out a new version without downtime? Kubernetes (K8s) is the system that answers those questions for you.

You describe the desired state in YAML ("3 replicas of web:1.4, reachable on port 80, each needing half a CPU") and send it to the API server. Controllers then run a reconcile loop: they compare desired and actual state and act until they match. They schedule containers onto nodes, restart crashed ones, replace lost machines and roll out new versions gradually.

Kubernetes was open-sourced by Google in 2014 and is now the CNCF's flagship project (Apache 2.0). Most teams use a managed control plane such as AKS, EKS or GKE, and run containers built with Docker or any OCI-compatible tool. For local learning, kind, minikube and k3d run a whole cluster on a laptop.

Architecture / mental model

Everything is an object in the API server. Controllers watch objects and nudge reality toward them; kubelets on each node actually start the containers.

Key concepts

clusterA set of machines (nodes) plus a control plane that manages them as one big computer for containers.
nodeA worker machine (VM or physical) that runs pods. Each runs a kubelet, kube-proxy and a container runtime.
podThe smallest deployable unit: one or more containers that share an IP address and volumes and are always scheduled together.
vCPUThe CPU unit Kubernetes counts in: 1 CPU = one vCPU or hyperthread = 1000 millicores (1000m).
requests & limitsPer-container CPU and memory settings: requests are reserved for scheduling, limits are the hard ceiling.
DeploymentDeclares how many replicas of a stateless pod should run and rolls out new versions gradually.
ReplicaSetKeeps exactly N identical pods running. Deployments create and manage ReplicaSets for you.
ServiceA stable virtual IP and DNS name that load-balances to the Ready pods matching a label selector.
Ingress / Gateway APIHTTP(S) routing from outside the cluster to Services by host name and path, with TLS termination.
namespaceA virtual folder inside a cluster for grouping and isolating objects, quotas and permissions.
labels & selectorsKey/value tags on objects (app=web) and the queries that pick objects by them. The glue of Kubernetes.
ConfigMap & SecretConfiguration and credentials stored separately from the image and injected as env vars or files.
PersistentVolumeClaimA pod's request for durable storage ("10Gi, read-write"), fulfilled by a PersistentVolume from a StorageClass.
StatefulSetLike a Deployment, but each pod gets a stable name, stable DNS and its own persistent volume.
DaemonSetRuns one copy of a pod on every node (or a chosen subset), for node-level agents.
probesHealth checks the kubelet runs: liveness restarts a stuck container, readiness controls traffic, startup protects slow boots.
HPAHorizontal Pod Autoscaler: adds or removes replicas based on CPU, memory or custom metrics.
HelmThe package manager for Kubernetes: templated YAML bundles ("charts") installed and upgraded as releases.

Essential commands & syntax

Setup & context

kind create cluster --name dev
Local cluster running inside Docker containers (also: minikube, k3d, Docker Desktop's built-in Kubernetes).
kubectl config get-contexts
kubectl config use-context dev
List clusters you can talk to and switch between them. Always check before running destructive commands.
kubectl config set-context --current --namespace=shop
Default namespace for later commands, instead of typing -n shop each time.

Deploy

apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: web
          image: ghcr.io/acme/web:1.4
          ports: [{ containerPort: 8000 }]
          resources:
            requests: { cpu: 250m, memory: 256Mi }
            limits: { memory: 512Mi }
---
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  selector: { app: web }
  ports: [{ port: 80, targetPort: 8000 }]
web.yaml: a Deployment with resource requests plus a Service in front of it.
kubectl apply -f web.yaml
Create or update objects to match the file. Safe to run repeatedly.
kubectl set image deployment/web web=ghcr.io/acme/web:1.5
kubectl rollout status deployment/web
kubectl rollout undo deployment/web
Roll out a new image, watch it, and roll back if something's wrong.
kubectl scale deployment/web --replicas=5
Change the replica count by hand (an HPA would override it).

Inspect & debug

kubectl get pods -o wide · kubectl get all -A
Pods with their node and IP; everything in every namespace.
kubectl describe pod web-7d9f8c-x2k4q
Details and Events at the bottom: why it's Pending, failing probes, image pull errors.
kubectl logs -f deploy/web --previous
Follow logs; --previous shows the crashed container's last run.
kubectl exec -it deploy/web -- sh
Shell inside a running container.
kubectl port-forward svc/web 8080:80
Reach a Service from your laptop at localhost:8080, no Ingress needed.
kubectl get events --sort-by=.lastTimestamp
kubectl top pods
Recent cluster events in order; live CPU and memory usage (needs metrics-server).
from kubernetes import client, config
config.load_kube_config()
for p in client.CoreV1Api().list_namespaced_pod("shop").items:
    print(p.metadata.name, p.status.phase)
Python client (pip install kubernetes), using the same kubeconfig as kubectl.

Pros & cons

Pros

  • Self-healing: crashed containers restart, lost nodes' pods are rescheduled automatically.
  • Zero-downtime rolling updates and one-command rollbacks.
  • Declarative YAML in Git: environments are reproducible and reviewable.
  • Bin-packs many services onto shared machines, using hardware efficiently.
  • Same API on every cloud and on-premises; huge ecosystem (Helm, Argo CD, Prometheus, Istio).
  • Autoscaling of pods (HPA, KEDA) and of nodes (Cluster Autoscaler, Karpenter).

Cons

  • Steep learning curve: dozens of object types, networking and storage concepts.
  • Operational overhead even when managed: upgrades every few months, add-ons, security patches.
  • Easy to misconfigure: missing requests, bad probes or open RBAC cause outages and breaches.
  • Debugging spans many layers (app, container, pod, node, network, cloud).
  • Baseline cost: control plane, system pods and spare capacity before your app runs.
  • Overkill for a handful of services or a small team.

Concrete use cases

Microservices platform

A retailer runs 60 services owned by 10 teams on one AKS cluster per environment. Each team gets a namespace, quotas and its own Argo CD app; the platform team owns ingress, observability and upgrades.

Spiky web traffic

A ticketing site's HPA scales the checkout Deployment from 4 to 40 pods during a sale, and Karpenter adds nodes for them. Both scale back down at night.

Batch and ML jobs

A data team submits Jobs and CronJobs for nightly ETL and model training on a GPU node pool that scales to zero when idle.

Hybrid and multi-cloud

A manufacturer runs the same Helm charts on-premises (on factory servers with k3s) and in the cloud, so the deployment process is identical everywhere.

Preview environments

Every pull request gets its own namespace with the full app deployed, so reviewers click a URL instead of running it locally. It's deleted on merge.

When to use / when not to

Rule of thumb: adopt it when you have more services than people who want to manage servers.

Use it when…

  • You run many containerised services that need scheduling, scaling and self-healing.
  • You need zero-downtime deploys and fast rollbacks as routine.
  • Several teams share infrastructure and need isolation and self-service.
  • You want one deployment model across clouds or on-premises.
  • You already have (or can buy) the skills: a platform team or a managed service.

Avoid it when…

  • You have a few services and a small team. Use Azure Container Apps, Cloud Run or ECS Fargate.
  • Everything runs on one server. Use Docker Compose.
  • The app is a classic monolith with a database. Use a PaaS such as App Service or Heroku.
  • Workloads are event-driven and short. Use serverless functions.
  • Nobody owns upgrades and security. An unmaintained cluster is a liability.

Common mistakes & gotchas

Click any key concept above for the deep dive. vCPU and probes explain half of these.
No resource requests or memory limitsThe scheduler packs pods blindly, nodes run out of memory, and random pods get evicted or OOMKilled.
Fix: set CPU and memory requests on every container and a memory limit; enforce with LimitRanges.
Liveness probe checks dependenciesWhen the database is slow, every pod fails liveness and restarts together, turning a slowdown into an outage.
Fix: liveness checks only the process itself; put dependency checks in readiness.
Using :latest image tagsPods on different nodes run different code, and kubectl rollout undo can't go back.
Fix: immutable tags (version or git SHA) and imagePullPolicy: IfNotPresent.
Running only one replicaNode upgrades and evictions take the app down, even though Kubernetes is "highly available".
Fix: at least 2 replicas, a PodDisruptionBudget and topology spread across zones.
Secrets treated as encryptedSecrets are base64; anyone who can read them in the namespace can decode them.
Fix: enable encryption at rest, tight RBAC, and an external secret store.
Ignoring graceful shutdownOn rollout, pods get SIGTERM while the Service may still route to them for a few seconds; in-flight requests fail.
Fix: handle SIGTERM, add a short preStop sleep, and set terminationGracePeriodSeconds to cover your longest request.
Running kubectl against the wrong clusterA delete meant for dev hits production because the context was still set.
Fix: show the context in your prompt (kube-ps1), use separate kubeconfigs, and restrict prod access with RBAC.
Falling behind on upgradesEach minor version is supported for about a year; skipping versions makes upgrades painful and APIs disappear.
Fix: upgrade on a schedule, one minor version at a time, and test with kubectl deprecations tools such as Pluto.

Alternatives

ToolBest forComplexityCost / licenseKey difference vs Kubernetes
KubernetesMany services, many teams, any cloudHighApache 2.0; managed AKS, EKS, GKE—
Docker ComposeOne host: dev and small productionLowApache 2.0No multi-node scheduling or self-healing across machines
Azure Container Apps / Cloud Run / ECS FargateRunning containers without managing a clusterLowPay per useServerless containers: no nodes, less control, scale to zero
HashiCorp NomadSimple orchestration of containers and non-container jobsMediumBSL 1.1Single binary, smaller scope; integrates with Consul and Vault
Docker SwarmSmall clusters with Compose-like filesLowApache 2.0Built into Docker, simple, but a much smaller ecosystem
k3sEdge, IoT, small or on-prem clustersMediumApache 2.0Certified Kubernetes in a single lightweight binary
  • Pick Docker Compose if everything fits on one machine.
  • Pick Container Apps, Cloud Run or Fargate if you want containers in production without a platform team.
  • Pick Nomad if you need to schedule mixed workloads with less complexity.
  • Pick Swarm only for small, simple setups that already use Compose files.
  • Pick k3s if you need real Kubernetes on small hardware or at the edge.
