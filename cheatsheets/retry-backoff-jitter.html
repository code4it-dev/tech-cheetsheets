Retry, backoff & jitter

Retrying is the cheapest way to survive a blip, and the cheapest way to turn one into an outage.

As of Nov 2026 · examples use Polly 8 and Tenacity; the jitter analysis is AWS's, from 2015

Networks drop packets, instances get rescheduled, leaders fail over. A large share of distributed-system errors are transient, and simply trying again a moment later fixes them — which is why retry is the first resilience pattern anyone adds and the one most likely to be added carelessly.

Two separate questions decide whether it helps. Should you retry? — is this error actually transient, is the operation safe to repeat, and is there budget left. And how should you space the attempts? — which is where exponential backoff and, crucially, jitter come in. Getting the first wrong corrupts data; getting the second wrong turns a two-second blip into a congestion collapse.

The single most important fact on this page is that exponential backoff without jitter does not solve the thundering herd. If a thousand clients fail at the same instant and each waits exactly one second, a thousand retries arrive at the same instant. Backoff spaces the spikes out; only randomness breaks up the spike itself. The second most important fact is that retries multiply through layers: three layers each retrying three times turns one user action into twenty-seven requests, arriving precisely when the system can least afford them.

A retry is a decision, a delay and a limit. Most retry bugs are a missing limit.

Key concepts

Transient errorA failure likely to go away on its own — the only kind worth retrying.
Idempotency requirementA retry is only safe if repeating the operation cannot do the work twice.
Exponential backoffDoubling the wait after each failure, so a persistent problem is not hammered.
JitterRandomising the wait so that clients which failed together do not return together.
Thundering herdMany clients retrying in unison, producing a spike far above capacity exactly when the system is weakest.
Retry amplificationRetries at several layers multiplying rather than adding — the reason one blip becomes an outage.
Retry budgetA cap on retries as a fraction of total traffic, so the system cannot retry itself to death.
Attempt limit & capHow many tries, and the longest a single wait may become.
Deadline awarenessRetrying only while there is time left in the caller's budget, rather than a fixed number of times.
Timeout interactionRetries multiply the timeout: three attempts at two seconds is a six-second wait unless something stops it.
Retry-AfterThe server telling you when to come back — and the one input that beats any backoff formula.
Circuit breaker interactionRetry handles a blip; a breaker handles an outage. They need to be arranged deliberately.
Hedged requestsSending a second request before the first has failed, to cut tail latency rather than to handle errors.
Where to retryOne layer, chosen deliberately — not everywhere a library made it easy.
Dead letterWhere a message goes when the retries are exhausted, so the queue keeps moving.
ObservabilityCounting attempts separately from requests, so retries are visible before they become an incident.

Essential code patterns

The whole pattern, correctly ordered

var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    // 3 — stop entirely once it is clearly not transient
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<HttpResponseMessage>
    {
        FailureRatio = 0.5, MinimumThroughput = 20,
        BreakDuration = TimeSpan.FromSeconds(30),
    })
    // 2 — retry, exponentially, with jitter
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
    {
        MaxRetryAttempts = 3,
        BackoffType      = DelayBackoffType.Exponential,
        UseJitter        = true,                    // the line that matters
        Delay            = TimeSpan.FromMilliseconds(200),
        MaxDelay         = TimeSpan.FromSeconds(2),
        ShouldHandle     = args => ValueTask.FromResult(IsTransient(args.Outcome)),
    })
    // 1 — a call that never ends can never be retried
    .AddTimeout(TimeSpan.FromSeconds(2))
    .Build();
Polly applies strategies outermost-first, so at run time this is timeout, then retry, then breaker — one recorded outcome per logical call.
static bool IsTransient(Outcome<HttpResponseMessage> o) =>
    o.Exception is TimeoutRejectedException or HttpRequestException
    || o.Result?.StatusCode is HttpStatusCode.RequestTimeout
                           or HttpStatusCode.TooManyRequests
                           or HttpStatusCode.ServiceUnavailable
                           or HttpStatusCode.GatewayTimeout;

// NOT retryable: 400, 401, 403, 404, 409, 422 — repeating them changes nothing
// and a retried 401 should instead refresh the token, exactly once
The predicate is where most retry bugs live. Retrying a 400 forever looks, from the server's side, indistinguishable from an attack.

The same thing in Python

from tenacity import (retry, stop_after_attempt, wait_random_exponential,
                      retry_if_exception_type, before_sleep_log)

@retry(
    retry=retry_if_exception_type((httpx.TimeoutException, httpx.ConnectError)),
    wait=wait_random_exponential(multiplier=0.2, max=2),   # full jitter, capped at 2 s
    stop=stop_after_attempt(3),
    before_sleep=before_sleep_log(log, logging.WARNING),   # make retries visible
    reraise=True,                                          # surface the real error
)
async def fetch_order(order_id: str) -> Order:
    res = await client.get(f"/orders/{order_id}", timeout=2.0)   # per-attempt timeout
    res.raise_for_status()
    return Order(**res.json())
wait_random_exponential is full jitter — random(0, min(max, multiplier × 2ⁿ)). Plain wait_exponential is the version that keeps the herd in step.

The jitter strategies, written out

static readonly Random Rng = Random.Shared;

TimeSpan NoJitter(int n)      => Min(Cap, Base * Math.Pow(2, n));          // don't
TimeSpan FullJitter(int n)    => Rng.NextDouble() * Min(Cap, Base * Math.Pow(2, n));
TimeSpan EqualJitter(int n)   => { var t = Min(Cap, Base * Math.Pow(2, n));
                                   return t / 2 + Rng.NextDouble() * t / 2; }
TimeSpan Decorrelated(double prev) => Min(Cap, Base + Rng.NextDouble() * (prev * 3 - Base));

// AWS measured these: full jitter gave the lowest contention and completion time.
// Equal jitter guarantees a minimum wait; decorrelated keeps growing and self-limits.
Four one-liners. The only wrong answer is the first, and it is the one most libraries still make the default.
import random

def full_jitter(attempt, base=0.2, cap=2.0):
    return random.uniform(0, min(cap, base * 2 ** attempt))

def equal_jitter(attempt, base=0.2, cap=2.0):
    t = min(cap, base * 2 ** attempt)
    return t / 2 + random.uniform(0, t / 2)

def decorrelated(prev, base=0.2, cap=2.0):
    return min(cap, random.uniform(base, prev * 3))

>>> [round(full_jitter(n), 2) for n in range(5)]
[0.07, 0.31, 0.44, 1.21, 1.88]      # same client, five different waits
Note what the output shows: even one client's waits are unpredictable, which is exactly what stops a thousand of them colliding.

Honour Retry-After, then jitter it

static TimeSpan NextDelay(HttpResponseMessage res, int attempt)
{
    // the server knows more about its recovery than your curve does
    if (res.Headers.RetryAfter?.Delta is { } delta)
        return delta + TimeSpan.FromMilliseconds(Random.Shared.Next(0, 500));  // jitter it
    if (res.Headers.RetryAfter?.Date is { } at)
        return at - DateTimeOffset.UtcNow + TimeSpan.FromMilliseconds(Random.Shared.Next(0, 500));

    return FullJitter(attempt);
}
Every rejected client got the same Retry-After value. Sleeping exactly that long recreates the herd the header was meant to prevent.

Budget, not just attempts

# Envoy — a per-request attempt limit AND a fleet-wide budget
retry_policy:
  retry_on: "5xx,reset,connect-failure"
  num_retries: 2                       # bounds one request's latency
  retry_back_off: { base_interval: 0.1s, max_interval: 2s }
  retry_budget:
    budget_percent: { value: 20 }      # retries may not exceed 20% of active requests
    min_retry_concurrency: 3
The attempt limit protects one request; the budget protects the dependency. A system-wide failure needs the second.
// a budget in code: a token bucket refilled by successes
sealed class RetryBudget(double ratio = 0.1, int minPerSecond = 3)
{
    private readonly SlidingWindow _ok = new(TimeSpan.FromSeconds(10));
    private readonly SlidingWindow _retries = new(TimeSpan.FromSeconds(10));

    public bool TryConsume()
    {
        var allowed = Math.Max(minPerSecond, _ok.Count * ratio);
        if (_retries.Count >= allowed) return false;   // out of budget: fail now
        _retries.Add();
        return true;
    }
    public void RecordSuccess() => _ok.Add();
}
When everything is failing there are no successes, so the budget empties and retries stop — which is precisely when they were doing harm.

Respect the deadline

async Task<T> WithRetries<T>(Func<CancellationToken, Task<T>> call, CancellationToken ct)
{
    for (var attempt = 0; ; attempt++)
    {
        try { return await call(ct); }
        catch (Exception ex) when (IsTransient(ex) && attempt < MaxAttempts)
        {
            var delay = FullJitter(attempt);
            // do not start an attempt we cannot finish inside the caller's budget
            if (RemainingBudget(ct) < delay + ExpectedAttemptDuration) throw;
            await Task.Delay(delay, ct);
        }
    }
}
A retry begun 50 ms before the caller gives up costs a connection and a worker to produce a result nobody reads.

Make them visible

attempts_total / requests_total        # the attempt multiplier — 1.0 is healthy
retries_exhausted_total{dep="orders"}  # genuine failures, not blips
retry_budget_rejected_total            # the budget is doing its job
dead_letter_depth                      # poison messages

# alert when the multiplier exceeds ~1.1 for a sustained period:
# a dependency is degrading, and scaling up will make it worse
Without this, a degrading dependency looks like a traffic increase — and the instinctive response feeds the amplification.

Pros & cons

Pros

  • Removes a large class of transient failures for a few lines of configuration.
  • Exponential backoff adapts automatically from a blip to a sustained outage.
  • Jitter turns a synchronised spike into smooth load at no cost.
  • Budgets make the aggregate effect bounded and predictable.
  • Hedging uses the same machinery to cut tail latency.
  • Every mainstream library implements it; you configure rather than build.

Cons

  • Retrying non-idempotent work duplicates it, and timeouts are ambiguous by nature.
  • Retries multiply through layers, turning degradation into collapse.
  • Without jitter, backoff preserves the herd it was supposed to break up.
  • Multiplies user-visible latency unless deadlines are enforced.
  • Hides a chronically failing dependency behind "it usually works eventually".
  • Libraries retry silently by default, so the real multiplier is rarely what you think.

Concrete use cases

A database failover

The primary fails over and connections drop for four seconds. Three attempts with jittered exponential backoff ride straight through it: users see a slightly slow request instead of an error page, and nothing is paged.

A rate-limited partner API

The partner returns 429 with Retry-After: 30. Honouring the header plus a small random offset means your fleet returns spread across a few seconds rather than all at the thirty-second mark.

The outage that scaling made worse

A dependency degrades, every layer retries, and traffic appears to triple. The team scales up, which adds load to the failing dependency. An attempt-multiplier metric would have shown the "traffic" was their own retries.

Double charges from a timeout

A payment call times out after the charge succeeded but before the response arrived. The retry charges again. An idempotency key on the request would have let the provider recognise the repeat and return the original result.

Tail latency on a read path

p50 is 20 ms and p99 is 400 ms because one replica is slow. Hedging at the p95 and taking the first response cuts p99 to near p50, for about 5% extra load and no error handling at all.

When to use / when not to

transient, idempotent, budgeted, jittered — four boxes, and all four must be ticked

Use it when…

  • The failure is genuinely transient — a timeout, a reset, a failover, a 503.
  • The operation is idempotent, or carries an idempotency key.
  • The caller has time left in its deadline for another attempt.
  • No other layer in the path is already retrying the same thing.
  • You want to hide a slow replica behind a hedged duplicate request.

Avoid it when…

  • The error is deterministic — 400, 404, 422. Use a clear error response; retrying changes nothing.
  • The operation is not safe to repeat. Use idempotency keys first, then retry.
  • The dependency is down rather than flaky. Use a circuit breaker and stop calling.
  • Another layer already retries. Use that one and make yours fail fast.
  • You are overloaded yourself. Use load shedding — retries make an overload worse by definition.

Common mistakes & gotchas

Backoff without jitterA thousand clients fail together and each waits exactly one second, so a thousand retries arrive together. Doubling the delay moves the spike; it never shrinks it.
Fix: full jitter — random(0, min(cap, base × 2ⁿ)). In Polly set UseJitter = true; in Tenacity use wait_random_exponential.
Retrying at every layerClient, gateway and service each retry three times, so one user action becomes twenty-seven calls at a dependency that is already failing.
Fix: retry at exactly one layer, and audit the ones you did not write — SDK defaults, mesh policies and database drivers all retry silently.
Retrying non-idempotent operationsA timeout is ambiguous: the work may have completed and only the response been lost. Retrying a payment on a timeout is how customers get charged twice.
Fix: attach an idempotency key so the server recognises the repeat, or restrict retries to genuinely idempotent operations.
No retry budgetAn attempt limit bounds one request. When everything is failing, a limit of three still triples the load on the thing that is already on fire.
Fix: add a budget — retries capped at around 10% of successful traffic. When successes stop, the budget empties and retries stop with it.
Ignoring the deadlineThree attempts at a two-second timeout, plus backoff, is a seven-second wait. The user gave up at two and pressed refresh, creating a second request.
Fix: propagate a deadline and check it before each attempt. Size per-attempt timeouts so attempts plus waits fit inside it.
Retrying 4xx400, 404 and 422 are deterministic: the same request will fail identically forever. A retry loop on them is indistinguishable from an attack at the receiving end.
Fix: an explicit allow-list of retryable outcomes. Treat 401 specially — refresh the token once, then give up.
Invisible retriesWhen attempts are not counted separately from requests, a degrading dependency looks like a traffic spike — and the team scales up, feeding the amplification.
Fix: export the attempt multiplier and alert when it rises above about 1.1. Record the attempt number on trace spans too.
Retry as a substitute for fixing itA dependency that needs three attempts to succeed is broken. Retries hide it until the day they stop being enough.
Fix: alert on retries_exhausted and on a sustained multiplier. A retry policy is a shock absorber, not a repair.

  • Pick a circuit breaker once "transient" has lasted more than a few seconds — retries past that point are pure harm.
  • Pick idempotency keys before retrying anything that writes; they are what makes the retry legal.
  • Pick a queue when nobody is waiting — durable redelivery beats in-process retries every time.
  • Pick failover when the problem is one instance; retrying the same bad host just wastes the budget.
  • Pick graceful degradation for optional work: a page without recommendations beats a page that took seven seconds to fail.
