Queueing theory

Waiting is not caused by being out of capacity. It is caused by being nearly out of capacity, at random moments.

As of Nov 2026 · Erlang 1909, Kendall 1953, Kingman 1961 · the maths behind every capacity decision you make

Little's Law tells you that L = λW — and refuses to say anything about why W is what it is. Queueing theory answers that question, and the answer is uncomfortable: waiting time is governed by utilisation and variability, not by average capacity. A server with 20% headroom is not 20% away from trouble; by the time it is 90% utilised, requests already wait ten times longer than they take to serve.

The central result for a single server is W = S / (1 − ρ). At 50% utilisation you wait twice the service time. At 90%, ten times. At 99%, a hundred times. Nothing breaks on the way: the server is doing exactly the work it always did at exactly the rate it always did, while latency goes vertical. This is why "CPU is at 85%, we're fine" is one of the most expensive sentences in operations.

The second result is Kingman's formula, which says the wait is multiplied by variability: two systems with identical utilisation and identical average service times can differ by a factor of ten because one has a predictable workload and the other does not. And the third — pooling — says that one queue feeding three servers beats three queues each feeding one, with no extra hardware at all.

Key concepts

Utilisationρ = λ / (cμ): the fraction of capacity in use, and the single number that drives waiting time.
Arrival rateλ — how often work arrives, and, just as importantly, how evenly.
Service rateμ — how fast one server completes work; S = 1/μ is the service time.
Kendall notationA/S/c — the shorthand that names a queueing model: arrival process, service distribution, number of servers.
M/M/1The single-server model, and the source of W = S / (1 − ρ).
M/M/cSeveral interchangeable servers sharing one queue — and dramatically better than the same servers with separate queues.
PoolingSharing one queue across many servers instead of giving each its own — the cheapest latency improvement in queueing.
Coefficient of variationc = σ/mean — how irregular arrivals or service times are, and the second dial on waiting time.
Kingman's formulaThe practical approximation for a realistic queue: wait = utilisation factor × variability factor × service time.
InstabilityAt ρ ≥ 1 there is no steady state: the queue grows without bound and no formula applies.
Queue disciplineThe order work is taken in — which changes nothing about the average and everything about who suffers.
Erlang CThe formula for "what fraction of arrivals have to wait at all" with c servers — the basis of staffing maths.
Heavy tailA service-time distribution where rare, very expensive requests dominate the average — and break the tidy formulas.
Little's LawL = λW — the identity that connects every quantity here, and the one result that needs no assumptions.
Waiting vs sojourn timeWq is time queueing; W is time in the system, including service. Mixing them up changes answers by a lot.
Bounded queuesReal systems are M/M/c/K: the queue has a maximum, and arrivals beyond it are rejected rather than queued.
Measuring itWhich numbers to collect so that the theory becomes usable rather than decorative.

Essential formulas

Single server (M/M/1)

static double W (double lam, double mu) => 1 / mu / (1 - lam / mu);  // time in system
static double Wq(double lam, double mu) => W(lam, mu) - 1 / mu;      // queueing only

foreach (var rho in new[] { 0.5, 0.8, 0.9, 0.95, 0.99 })
    Console.WriteLine($"{rho,5}  {20 / (1 - rho),7:F1} ms");         // S = 20 ms

// 0.50     40.0 ms        0.95    400.0 ms
// 0.80    100.0 ms        0.99  2,000.0 ms   <- same work, 100x the latency
The single-server model in two expressions. Check rho < 1 before trusting any of it.
rho = lam / mu                 # utilisation; must be < 1 or nothing below applies
W   = (1/mu) / (1 - rho)       # time in system  (service + queueing)
Wq  = W - 1/mu                 # time queueing only
L   = rho / (1 - rho)          # requests in the system
Lq  = rho**2 / (1 - rho)       # requests waiting

# sanity: L == lam * W   (Little's Law — if this fails, your inputs are wrong)
Five lines that give the right order of magnitude in seconds. Worth knowing by heart.
>>> for rho in (0.5, 0.8, 0.9, 0.95, 0.99):
...     print(rho, round(20 / (1 - rho), 1), "ms")
0.5   40.0 ms
0.8  100.0 ms
0.9  200.0 ms
0.95 400.0 ms
0.99 2000.0 ms      # same 20 ms of work, 100x the latency
The whole argument against running interactive systems hot, in five lines of output.

Many servers (M/M/c) and Erlang C

static double Factorial(int n) => Enumerable.Range(1, n).Aggregate(1.0, (a, b) => a * b);

// Probability an arrival has to wait. a = lam/mu, the offered load in erlangs.
static double ErlangC(int c, double a)
{
    var top = Math.Pow(a, c) / Factorial(c) * (c / (c - a));
    var bot = Enumerable.Range(0, c).Sum(k => Math.Pow(a, k) / Factorial(k)) + top;
    return top / bot;
}

static double WqMmc(double lam, double mu, int c)
{
    if (lam / mu >= c) throw new ArgumentException("unstable: rho >= 1");
    return ErlangC(c, lam / mu) / (c * mu - lam);
}

Console.WriteLine(WqMmc(lam: 2.4, mu: 1.0, c: 3));   // 1.0787 — vs 4.0 for one server
The pooling gain, computed: three servers at the same utilisation wait roughly a quarter as long as one.
from math import factorial

def erlang_c(c: int, a: float) -> float:
    """Probability an arrival has to wait. a = lam/mu (offered load in erlangs)."""
    top = (a**c / factorial(c)) * (c / (c - a))
    bot = sum(a**k / factorial(k) for k in range(c)) + top
    return top / bot

def wq_mmc(lam: float, mu: float, c: int) -> float:
    a = lam / mu
    assert a < c, "unstable: rho >= 1"
    return erlang_c(c, a) / (c * mu - lam)

# three servers at rho = 0.8, service time 1.0
>>> wq_mmc(lam=2.4, mu=1.0, c=3)
1.0787...                      # vs 4.0 for a single server at the same rho
The pooling gain, computed. Same utilisation per server, roughly a quarter of the wait.
# how many servers to keep queueing under 50 ms?
def servers_needed(lam, mu, target_wq):
    c = int(lam / mu) + 1
    while wq_mmc(lam, mu, c) > target_wq:
        c += 1
    return c

>>> servers_needed(lam=300, mu=125, target_wq=0.05)   # 300/s, 8 ms each
3
Capacity planning that answers a latency question rather than a utilisation question.

Realistic queues: Kingman

// VUT: variability x utilisation x time. Works for any distribution.
static double KingmanWq(double rho, double ca, double cs, double s) =>
    rho / (1 - rho) * ((ca * ca + cs * cs) / 2) * s;

KingmanWq(rho: 0.8, ca: 1,   cs: 1,   s: 0.020);   // 0.080 — M/M/1 baseline
KingmanWq(rho: 0.8, ca: 1,   cs: 3,   s: 0.020);   // 0.400 — heavy-tailed service
KingmanWq(rho: 0.8, ca: 0.3, cs: 0.3, s: 0.020);   // 0.007 — smoothed, no new hardware
The variability lever, priced. Dropping cs from 3 to 0.3 beats any capacity you could reasonably buy.
def kingman_wq(rho: float, ca: float, cs: float, S: float) -> float:
    """VUT: variability x utilisation x time. Works for any distribution."""
    return (rho / (1 - rho)) * ((ca**2 + cs**2) / 2) * S

>>> kingman_wq(rho=0.8, ca=1, cs=1, S=0.020)      # M/M/1 baseline
0.080                                              # 80 ms
>>> kingman_wq(rho=0.8, ca=1, cs=3, S=0.020)      # heavy-tailed service
0.400                                              # 400 ms — same rho, 5x the wait
>>> kingman_wq(rho=0.8, ca=0.3, cs=0.3, S=0.020)  # smoothed arrivals and work
0.0072                                             # 7 ms — no new hardware
The variability lever, priced. Reducing cs from 3 to 0.3 beats any amount of capacity you could reasonably buy.
# estimate the coefficient of variation from your own data
import statistics as st
cs = st.pstdev(service_times) / st.mean(service_times)

# cs ≈ 0    perfectly regular      (fixed-cost work)
# cs ≈ 1    exponential            (the "random" baseline)
# cs > 2    heavy tailed           (expect queueing far worse than M/M/1)
Compute this once for your hottest endpoint. If it is above 2, variability — not capacity — is your latency problem.

Sizing a bounded queue

# real queues have a maximum. Little's Law turns a latency budget into a size.
K = service_rate * max_wait_seconds       # 800/s × 0.025 s = 20 slots
max_wait = K / service_rate               # and back again

# then decide what happens at the boundary: block, drop, or reject upstream
Choosing K is choosing your worst-case queueing latency. Everything else about backpressure follows from that number.

When the formulas stop applying

# simulate instead — 30 lines beats a wrong closed form
import random, heapq

def simulate(lam, service_sampler, c, n=200_000):
    clock, free = 0.0, [0.0] * c          # when each server is next free
    heapq.heapify(free)
    waits = []
    for _ in range(n):
        clock += random.expovariate(lam)   # arrival
        earliest = heapq.heappop(free)
        start = max(clock, earliest)
        waits.append(start - clock)        # queueing time
        heapq.heappush(free, start + service_sampler())
    waits.sort()
    return waits[len(waits)//2], waits[int(len(waits)*0.99)]   # p50, p99

>>> simulate(lam=2.4, service_sampler=lambda: random.expovariate(1.0), c=3)
(0.44, 5.6)      # the p99 is what users feel — and no formula gave you it
Closed forms give means. Simulation gives distributions, handles priorities, retries and heavy tails, and is usually the honest answer.

Pros & cons

Pros

  • Explains why latency explodes before capacity runs out — the single most useful performance insight there is.
  • Turns capacity planning into a latency question rather than a utilisation target.
  • Identifies three distinct levers (utilisation, variability, service time) so you can compare their cost.
  • Predicts the effect of a change before you build it, in a few lines of arithmetic.
  • Quantifies pooling, which is usually a free improvement.
  • Prices architectural constraints like sharding and session affinity honestly.

Cons

  • The tidy formulas assume Poisson arrivals and exponential service; real traffic is neither.
  • Closed forms give averages, and users experience the tail.
  • Everything assumes a steady state, so nothing applies during the overload you most care about.
  • Real systems have feedback — retries, autoscaling, clients backing off — which the models ignore.
  • Multi-stage systems need queueing networks, which get complicated quickly.
  • Easy to compute a precise number from inputs you guessed.

Concrete use cases

"CPU is only at 85%"

A service is at 85% utilisation and p99 latency has tripled, with no code change. Nothing is broken: W = S/(1−ρ) says 85% is already a 6.7× multiplier, up from 5× at 80%. The fix is to target 70%, and the graph that would have warned you is concurrency, not CPU.

Sizing a connection pool for a latency target

Rather than guessing, measure service time and arrival rate, then solve M/M/c for the number of connections that keeps queueing under 10 ms. Usually it is far smaller than the configured value, and the smaller number is faster because it bounds the queue.

Pricing session affinity

A team wants sticky sessions for cache locality. Queueing maths puts a number on it: at ρ = 0.8, pinning requests to one of ten servers takes queueing from 0.18×S to 4×S. The cache hit rate has to be worth that, and now the argument can be had with numbers.

Finding that variability, not capacity, is the problem

p99 is terrible at a comfortable 60% utilisation. The coefficient of variation of service time turns out to be 4 — a few enormous customers. Kingman says the wait is dominated by that term, so paginating the expensive endpoint fixes what doubling the fleet would not have.

Explaining why the restart did not help

After an overload the service stays slow even though traffic is back to normal. At ρ ≥ 1 the queue grew without bound, and the backlog is still being drained. The model says there was never a stable worse-state to settle into — only shedding or draining ends it.

When to use / when not to

use it for the order of magnitude and the shape of the curve — never for three significant figures

Use it when…

  • You are choosing a utilisation target, a pool size or a replica count.
  • Latency got worse without any code change, and you need to know why.
  • You want to compare adding capacity against reducing variability before spending money.
  • You are deciding between shared and dedicated resources — pooling has a number.
  • You need to explain to someone why 95% utilisation is not a good thing.

Avoid it when…

  • You need the tail rather than the mean. Use simulation or measured percentiles.
  • The system is already overloaded. Use load shedding — no steady state exists to model.
  • Arrivals are strongly correlated (retry storms, cron spikes). Use simulation with your real trace.
  • The path crosses many stages with feedback. Use load testing; queueing networks get hard fast.
  • You do not have measured service times. Use back-of-the-envelope estimates first, and label them as such.

Common mistakes & gotchas

Treating utilisation as linear"We're at 80%, so we have 20% headroom" is false. That last 20% of capacity carries four times the latency cost of everything before it, and the curve is vertical by 95%.
Fix: target 60–75% for interactive work and treat the remainder as latency headroom. Reserve high utilisation for batch jobs, where nobody is waiting.
Using CPU as ρCPU is a poor proxy for utilisation in anything that waits on I/O, and it stays unremarkable until the moment the queue explodes — which is far too late to be a useful signal.
Fix: measure concurrency in flight against your concurrency limit, or queue sojourn time. Both are proportional to what users feel.
Ignoring variabilityTwo systems at identical utilisation with identical mean service times can differ tenfold in waiting time. Capacity planning that uses only averages will be wrong in exactly the cases that matter.
Fix: compute the coefficient of variation of your service times. Above 2, attack variability — caps, pagination, separate pools — before buying hardware.
Dedicated queues per workerPer-worker inboxes, round-robin routing and sticky sessions all leave servers idle while other queues have work. At ρ = 0.8 across three servers that is roughly four times the queueing delay for free.
Fix: pool wherever the servers are interchangeable — shared work queue, least-connections balancing, one shared pool. Where you cannot, know what it costs.
Applying the formulas above ρ = 1Every result here assumes a steady state. At ρ ≥ 1 there is no equilibrium, the queue grows linearly forever, and a computed "average wait" is meaningless.
Fix: check ρ < 1 first. Above it, the only questions are how fast the backlog grows and how you reduce arrivals.
Quoting the mean to usersThe formulas give average waiting time. Your SLO is about p99, and with a heavy tail the p99 can be twenty times the mean.
Fix: use the formulas for direction and the simulator or real measurements for the tail. Never promise a percentile derived from a mean.
Forgetting that retries change λThe model assumes arrivals are independent of the system's state. Retries make them depend on it, so latency rises, retries arrive, λ rises, latency rises further — a loop the equations cannot see.
Fix: model the retry multiplier explicitly, or simulate. And cap retries with a budget so the feedback loop stays bounded.
Precision from guessed inputsComputing a wait of 47.3 ms from an arrival rate somebody estimated in a meeting gives a number with three significant figures and no information.
Fix: treat outputs as orders of magnitude. The valuable result is the shape — that 90% costs twice what 80% does — not the decimal places.

  • Pick Little's Law when you have two of L, λ, W and want the third — it always holds, even where these models do not.
  • Pick simulation as soon as you need a percentile, a priority scheme or anything with retries in it.
  • Pick load testing to validate — the model tells you where to look, the test tells you whether you were right.
  • Pick the USL when the question is about scaling out rather than about waiting in line.
  • Pick back-of-the-envelope first; reach for queueing theory the moment the answer depends on how loaded the system is.
