GraphQL

One endpoint, one typed schema, and the client decides what comes back — which moves both the power and the problems to the server.

As of Nov 2026 · examples use Hot Chocolate (.NET) and Strawberry (Python)

A REST API decides the shape of every response. A mobile screen that needs a user, their last three orders and each order's line items either calls three endpoints and stitches, or waits for a backend team to build a custom one. GraphQL inverts that: the server publishes a typed graph of what exists, and each client asks for exactly the fields it wants in a single request.

Everything is one HTTP endpoint, usually POST /graphql. The server holds a schema written in SDL, and a resolver for each field that knows how to produce it. Execution walks the query field by field, calling resolvers, and assembles a response whose shape mirrors the query exactly.

The cost of that flexibility is that the server can no longer predict its own workload. A three-line query can become ten thousand database calls; the N+1 problem is not an edge case but the default behaviour you must actively defeat; HTTP caching largely stops applying; and "can this user read this field?" becomes a per-field question. None of that is fatal, and all of it is work you must do deliberately.

Architecture / mental model

A typed facade over whatever you already have — with execution, batching and cost control as the server's new responsibilities.

Key concepts

SchemaThe typed description of everything that exists, written in SDL — the whole contract between client and server.
ResolverThe function that produces one field's value — called once per object, not once per query.
ExecutionHow the server walks the query: parents before children, siblings in parallel, errors bubbling up through nullable fields.
N+1 problemOne query for the list, then one more for each item — the default behaviour of a naive resolver tree.
DataLoaderA per-request batching and deduplicating cache that collapses N calls into one.
NullabilityEvery field is nullable unless marked ! — and non-null is a promise that propagates failure upward.
ErrorsPartial data with an errors array, returned under HTTP 200 — which breaks a lot of client assumptions.
PaginationCursor-based connections, because offsets break on a graph that changes while you page through it.
Query costAnalysing how expensive a query is before running it, and refusing the ones that are too expensive.
Persisted queriesRegistering allowed operations ahead of time and sending an id instead of a document.
IntrospectionThe schema querying itself — what powers tooling, and what hands an attacker a map.
Field authorizationPermission checks per field, because one request can touch twenty types across three services.
CachingHTTP caching mostly stops working; a normalised client cache replaces it.
Schema evolutionNo v1 and v2 — you add fields, deprecate old ones, and watch who still uses them.
SubscriptionsServer-pushed updates over a persistent transport, for the cases polling cannot cover.
FederationComposing one graph from several independently owned subgraphs.

Schema & code

The schema

type Query {
  user(id: ID!): User
  users(first: Int! = 20, after: String): UserConnection!   # bounded by default
  search(term: String!, first: Int! = 20): [SearchResult!]!
}

type Mutation {
  createOrder(input: CreateOrderInput!): CreateOrderPayload!  # input + payload, always
}

type User {
  id: ID!                      # stable and global: client caches depend on it
  name: String!
  email: String @auth(requires: SELF_OR_ADMIN)   # authorization is per FIELD
  company: Company             # nullable: it comes from another service
  posts(first: Int! = 10, after: String): PostConnection!
}

type Post {
  id: ID!
  title: String!
  author: User!                # the cycle — and the reason depth limits exist
}

type UserConnection {          # Relay-style: cursors survive inserts and deletes
  edges: [UserEdge!]!
  pageInfo: PageInfo!
  totalCount: Int
}
type UserEdge { cursor: String!  node: User! }
type PageInfo { hasNextPage: Boolean!  endCursor: String }

union SearchResult = User | Post | Company

input CreateOrderInput { customerId: ID!  lines: [OrderLineInput!]!  idempotencyKey: String! }

type CreateOrderPayload {      # expected failures as data, not as errors
  order: Order
  problems: [UserError!]!
}
type UserError { field: String  message: String!  code: ErrorCode! }
Every decision here matters later: bounded list arguments, a stable id, nullable cross-service fields, and expected failures modelled as types.

Resolvers, and the batching that makes them survivable

// C# — Hot Chocolate: resolvers plus a DataLoader
[QueryType]
public static class UserQueries
{
    public static Task<User?> GetUser(ID id, UserByIdDataLoader loader, CancellationToken ct)
        => loader.LoadAsync(id, ct);

    [UsePaging(MaxPageSize = 100)]            // the schema-level cap on list size
    public static IQueryable<User> GetUsers(AppDbContext db) => db.Users.OrderBy(u => u.Id);
}

[ObjectType<User>]
public static partial class UserNode
{
    // called ONCE PER USER — with 50 users this runs 50 times
    public static Task<Company?> GetCompany(
        [Parent] User user, CompanyByIdDataLoader loader, CancellationToken ct)
        => loader.LoadAsync(user.CompanyId, ct);

    [Authorize(Policy = "SelfOrAdmin")]       // per-field authorization
    public static string? GetEmail([Parent] User user) => user.Email;
}

// the DataLoader: one batch call for all the keys gathered in this tick
internal static class CompanyDataLoaders
{
    [DataLoader]
    public static async Task<Dictionary<Guid, Company>> GetCompanyByIdAsync(
        IReadOnlyList<Guid> ids, AppDbContext db, CancellationToken ct)
        => await db.Companies
                   .Where(c => ids.Contains(c.Id))      // 50 lookups → one IN clause
                   .ToDictionaryAsync(c => c.Id, ct);
}
The resolver runs per object; the DataLoader turns those N calls into one. Registering it per request is what keeps one user's data out of another's response.
# Python — Strawberry, with the same two ideas
import strawberry
from strawberry.dataloader import DataLoader

async def load_companies(ids: list[str]) -> list[Company | None]:
    rows = await db.fetch("SELECT * FROM companies WHERE id = ANY($1)", ids)
    by_id = {r["id"]: Company(**r) for r in rows}
    return [by_id.get(i) for i in ids]          # MUST align with the key order

@strawberry.type
class User:
    id: strawberry.ID
    name: str

    @strawberry.field
    async def company(self, info: strawberry.Info) -> Company | None:
        return await info.context["company_loader"].load(self.company_id)

    @strawberry.field
    async def posts(self, info: strawberry.Info, first: int = 10) -> list[Post]:
        first = min(first, 100)                 # cap it here too, not only in the schema
        return await info.context["posts_loader"].load((self.id, first))

async def get_context():
    return {                                    # a NEW loader per request — never module-level
        "company_loader": DataLoader(load_fn=load_companies),
        "posts_loader": DataLoader(load_fn=load_posts),
    }

schema = strawberry.Schema(query=Query, extensions=[QueryDepthLimiter(max_depth=10)])
Two rules carry across both languages: build loaders per request, and return batch results in the same order as the keys.

Defending the endpoint

// C# — the production configuration, which is mostly about saying "no"
builder.Services
    .AddGraphQLServer()
    .AddQueryType()
    .AddAuthorization()
    .AddProjections().AddFiltering().AddSorting()
    .ModifyPagingOptions(o =>
    {
        o.MaxPageSize = 100;                 // no unbounded lists
        o.DefaultPageSize = 20;
        o.RequirePagingBoundaries = true;    // "first" or "last" is mandatory
    })
    .ModifyCostOptions(o =>
    {
        o.MaxFieldCost = 1_000;              // complexity, not just depth
        o.MaxTypeCost = 1_000;
        o.EnforceCostLimits = true;
    })
    .ModifyRequestOptions(o =>
    {
        o.ExecutionTimeout = TimeSpan.FromSeconds(10);
        o.IncludeExceptionDetails = builder.Environment.IsDevelopment();   // never in production
    })
    .DisableIntrospection(!builder.Environment.IsDevelopment())
    .UsePersistedOperationPipeline();        // only registered documents are allowed to run
Paging boundaries, a cost limit, a timeout, no introspection and trusted documents. Each line closes a failure mode that is otherwise wide open.

npx graphql-inspector diff schema-main.graphql schema-branch.graphql
# ✖  Field User.email removed            BREAKING
# ⚠  Field User.fullName deprecated      DANGEROUS
The diff belongs in CI. Breaking changes should fail a build, not a client app three weeks later.
# what an expensive query looks like — and why depth alone does not catch it
query LooksHarmless {
  users(first: 100) {            # ×100
    edges { node {
      posts(first: 100) {        # ×100 → 10,000
        edges { node {
          comments(first: 100) { # ×100 → 1,000,000 field resolutions
            edges { node { author { name } } }
  } } } } } }
}
# depth: 9 — passes a max-depth of 10
# complexity: 100 × 100 × 100 = 1,000,000 points — rejected at validation, before any resolver runs
Four nested list fields with innocent-looking arguments. This is the query that takes a production database down, and it is rejected in microseconds by a cost rule.

Pros & cons

Pros

  • Clients fetch exactly what they need in one request — no over-fetching, no waterfalls.
  • A strongly typed schema that is validated at query time and generates client types for free.
  • Evolution without versions: add fields freely, deprecate with measured usage before removing.
  • Excellent tooling: introspection, GraphiQL, code generation, schema diffing in CI.
  • Many clients with different needs are served by one backend and one team.
  • Normalised client caches keep views consistent after a mutation, automatically.
  • A facade over heterogeneous backends — databases, REST services, search — behind one contract.

Cons

  • The client determines the server's workload, so cost analysis is mandatory rather than optional.
  • N+1 is the default behaviour and must be actively defeated on every nested field.
  • HTTP and CDN caching largely stop applying.
  • Authorization is per field and per traversal path, which is more surface than per endpoint.
  • 200-with-errors breaks naive monitoring and naive clients alike.
  • File uploads, binary payloads and plain browser caching all need extra machinery.
  • Real conceptual overhead for a team that only needs five endpoints.

Concrete use cases

Many clients, one backend

Web, iOS, Android, a watch app and a partner integration all need different slices of the same data. Each asks for its own fields, and shipping a new screen does not require a backend change or a new endpoint.

Killing the request waterfall

A mobile screen previously made five sequential REST calls because each depended on the last. One GraphQL query returns the whole tree in a single round trip, which on a high-latency connection is the difference between 1.8 s and 300 ms.

A facade over a messy estate

Four internal services, two databases and a search cluster, with no consistent conventions. A GraphQL layer presents one typed graph to product teams while the mess behind it is refactored at its own pace — a typed Backend-for-Frontend.

Retiring a field with evidence

User.fullName is deprecated and per-field usage is tracked. Six months later it is genuinely at zero and is removed — a decision made from data rather than from hope, which REST response bodies never allow.

A public API with trusted clients

Partners integrate against one endpoint with introspection-driven tooling, while persisted operations and complexity budgets keep the workload predictable and per-partner limits meaningful.

When to use / when not to

one client and one team? REST. five clients and one backend team? this is what it's for.

Use it when…

  • Several clients need different shapes of the same data and are evolving at different speeds.
  • Screens need deeply related data and REST produces waterfalls or over-fetching.
  • Client teams iterate faster than the backend can ship endpoints.
  • A typed contract with generated client code is worth real effort to you.
  • You are unifying several backends behind one API surface.

Avoid it when…

  • One client, a handful of endpoints, a stable shape. Use REST — it will be faster to build and to run.
  • Service-to-service calls where latency and typed contracts matter most. Use gRPC.
  • The payload is large, binary or streamed — files, video, bulk export. Use plain HTTP.
  • CDN caching of public responses is central to your performance. Use REST with cache headers.
  • The real need is one tailored API per client surface. Use a Backend-for-Frontend.
  • Nobody will own cost limits, batching and field authorization. Without those it is an outage waiting for a curious client.

Common mistakes & gotchas

No DataLoaderA list of 50 users with a nested field issues 51 queries, and a second level of nesting makes it a thousand. It is invisible in development with three rows of test data and catastrophic in production.
Fix: a DataLoader for every field that fetches by key, constructed per request. Log round trips per GraphQL request and fail CI above a threshold — that is how you catch it before users do.
No cost or depth limitA client — curious, buggy or hostile — sends a nested query over a cyclic schema. Depth 9 with four list fields of 100 is a million field resolutions from a 10-line document.
Fix: enforce max depth and a complexity score that multiplies by list arguments, cap first in the schema, add an execution timeout, and prefer persisted operations for first-party clients.
Monitoring on HTTP statusEvery response is 200, including the ones where half the fields failed. Dashboards show perfect availability while the product is broken.
Fix: alert on the errors array and on per-field error rates, and record the resolver path on each error so you can see which field is failing.
Non-null everywhere[Post!]! looks tidy, so it is used throughout. One post whose author lookup fails nullifies the item, which nullifies the list, which nullifies the user — and a whole screen goes blank over one bad row.
Fix: reserve ! for values you genuinely always have. Anything fetched from another service is nullable, and the client renders a partial result instead of nothing.
Introspection and exception details in productionThe public endpoint publishes every type, field and description, and stack traces appear in the errors array when a resolver throws.
Fix: disable introspection outside development, never include exception details, and distribute the schema to your own builds as a file.
Authorization only at the entry pointorder(id:) checks that the caller owns the order, but Order.customer.billingDetails is reachable from a different root field that nobody thought about.
Fix: authorize on the object being returned, not only on the entry field, and enforce row-level rules in the data layer as a backstop.
A schema that mirrors the databaseTables become types, columns become fields, join tables leak into the graph. Clients end up assembling domain concepts themselves, and the schema is now coupled to the storage layout.
Fix: design the graph around how clients think — Order.total, User.unreadCount — and let resolvers do the mapping. The whole point is a contract that outlives the storage.
Unbounded list fieldsposts: [Post!]! with no arguments means "all of them". It works for two years and then one account has 400,000.
Fix: every list is a paginated connection with a required, capped first. Make the server reject a missing paging boundary rather than defaulting to everything.
Mutations that return a bare scalardeleteUser: Boolean! cannot report why it failed, cannot return the updated state, and gives the client cache nothing to update.
Fix: one input type and one payload type per mutation, with the affected objects and a typed problems list. Expected failures belong in data, not in errors.
Reaching for federation too earlyThree services and one team adopt a gateway, a supergraph and composition checks. Now every deploy can fail at composition time and every slow query needs a query plan to debug.
Fix: start with one schema. Federate when several teams genuinely need independent ownership of parts of the graph — it is an organisational solution, not a technical one.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs GraphQL
GraphQLmany clients, deeply related dataMedium–Highopen spec, free servers—
RESTmost APIs, most of the timeLowfreeServer fixes the shape; HTTP caching just works; over-fetching and waterfalls are yours to manage
gRPCservice-to-serviceMediumfreeTyped RPC over HTTP/2 with codegen; fastest, and awkward from a browser
Backend-for-Frontenda few known clientsLow–MediumfreeOne tailored API per client, in plain code; no query language and no cost analysis
ODataqueryable REST over entitiesMediumfreeQuery language on top of REST, keeping URLs and HTTP caching
tRPCTypeScript on both endsVery lowfreeEnd-to-end types with no schema language — and no cross-language story
GraphQL federationmany teams, one graphHighfree / managedSame model, distributed ownership, plus a query planner in the request path
  • Pick REST unless you can name the clients that need different shapes — it is the right default and caching alone often decides it.
  • Pick gRPC for internal service-to-service calls where latency and typed contracts matter more than client flexibility.
  • Pick a BFF when there are two or three known client surfaces; it gets you most of the benefit for a fraction of the machinery.
  • Pick tRPC if both ends are TypeScript and will stay that way.
  • Pick federation only when several teams must own parts of one graph independently.
