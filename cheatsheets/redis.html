Redis

An in-memory data structure server: a key-value store that answers in microseconds.

As of Nov 2026 · latest release line 8.10

Redis keeps all its data in RAM and exposes it over a simple TCP protocol. Instead of tables and rows you work with keys, and each key holds a data structure: a string, hash, list, set, sorted set, stream, JSON document or vector set. Because nothing has to be read from disk, typical reads and writes take well under a millisecond.

Commands run one at a time on a single main thread, so each command is atomic without locks. Data can be persisted to disk (snapshots and/or an append-only log), copied to replicas, and split across nodes with Redis Cluster. Keys can carry a time-to-live, which makes Redis a natural cache.

It is most often used next to a primary database, not instead of one: as a cache, session store, rate limiter, leaderboard, job queue or message bus. Since Redis 8, the former "Redis Stack" features (JSON, search and query, time series, probabilistic structures) ship in the core, under a tri-license (AGPLv3, RSALv2 or SSPLv1).

Architecture / mental model

Think of Redis as a giant hash map in RAM that speaks over the network. Everything else (disk, replicas, Sentinel, Cluster) exists to make that map survive restarts, scale reads, or grow beyond one machine.

Key concepts

keyA binary-safe string that names a value, by convention namespaced with colons: user:1, cart:7. Max 512 MB, but keep keys short.
keyspaceThe set of all keys in a database, stored in one big in-memory hash table. Lookups are O(1).
data typesWhat a key holds: String, Hash, List, Set, Sorted set, Stream, Bitmap, HyperLogLog, Geo, JSON, Vector set. Each has its own commands.
TTL / EXPIREA time-to-live on a key. When it runs out, Redis deletes the key. The basis of caching and sessions.
maxmemory + evictionThe RAM cap. When it is reached, the maxmemory-policy decides what to drop (e.g. allkeys-lru) or to reject writes (noeviction).
atomicityCommands run one at a time on the main thread, so a single command like INCR never races with another.
pipeliningSend many commands without waiting for each reply. Cuts network round trips; usually the biggest client-side speedup.
MULTI / EXECA transaction: queued commands run together with nothing interleaved. There is no rollback if one fails.
Lua / FunctionsServer-side scripts that run atomically. Use them for read-modify-write logic, such as rate limiters.
RDBPoint-in-time snapshot of the whole dataset to disk. Compact and fast to load, but you lose writes made since the last snapshot.
AOFAppend-only file: every write command is logged. With appendfsync everysec, at most about 1 second of writes is lost on a crash.
replicationReplicas keep an asynchronous copy of a primary. They serve reads and can be promoted if the primary fails.
SentinelProcesses that monitor a primary and its replicas, run automatic failover and tell clients the new primary's address.
Cluster / hash slotRedis Cluster shards keys over 16,384 slots (CRC16(key) mod 16384). {tags} in a key force related keys into the same slot.
Pub/Sub vs StreamsPub/Sub is fire-and-forget broadcast. Streams are a persistent, append-only log with consumer groups and acknowledgements.

Essential commands & syntax

Setup

docker run -d --name redis -p 6379:6379 redis:8
Run a local Redis server.
redis-cli -h localhost -p 6379 PING
Connect from the CLI. Answers PONG.
import redis
r = redis.Redis(decode_responses=True)
r.set("user:1", "Ada", ex=60)
Python (pip install redis). decode_responses returns str instead of bytes.

Keys & strings

SET session:9f "{...}" EX 1800 NX
Set with a 30-minute TTL, only if the key does not exist. NX also gives you a simple lock.
GET session:9f
Read a value. Returns (nil) if it is missing or expired.
INCR views:home
Atomic counter. Also INCRBY and DECR.
EXPIRE cart:7 3600 · TTL cart:7
Set or inspect a TTL in seconds. -1 means no TTL, -2 means no key.
UNLINK big:key
Delete without blocking: memory is freed in the background. Prefer it over DEL for large keys.
SCAN 0 MATCH user:* COUNT 100
Iterate keys incrementally. Never use KEYS * in production.

Data structures

HSET user:1 name Ada role admin
HGETALL user:1
Hash: an object with fields. Update one field without rewriting the rest.
LPUSH jobs '{"id":42}'
BRPOP jobs 0
List as a queue. BRPOP blocks until a job arrives.
SADD tags:42 redis cache
SISMEMBER tags:42 redis
Set: unique members and O(1) membership tests.
ZADD board 1500 ada 1320 bob
ZRANGE board 0 9 REV WITHSCORES
Sorted set: the top-10 leaderboard in one call.
XADD orders * id 42 total 19.90
XREADGROUP GROUP billing w1 COUNT 10 STREAMS orders >
Stream: a durable event log consumed by groups, with XACK to acknowledge.
PUBLISH chat:room1 "hi" · SUBSCRIBE chat:room1
Pub/Sub: live fan-out. Clients that are not connected miss the message.

Inspect & debug

INFO memory
Used memory, fragmentation and peak usage. INFO alone shows every section.
SLOWLOG GET 10
The 10 slowest recent commands. Usually the first stop when latency rises.
redis-cli --bigkeys
Finds the largest keys per type. Big keys cause latency spikes.
CONFIG GET maxmemory-policy
Shows the eviction policy. Check it before you rely on Redis as a cache.
MONITOR
Streams every command the server receives. Use it in development only: it is expensive.

Pros & cons

Pros

  • Sub-millisecond reads and writes, because the data lives in RAM.
  • Rich data structures: a counter, queue or leaderboard is a single command, not custom code.
  • Single-command atomicity without locks.
  • Built-in TTLs and eviction make caching almost free to implement.
  • Simple to run: one binary, one config file, mature clients for every language.
  • Scales out with replicas (for reads) and Cluster (for data size and writes).

Cons

  • The dataset must fit in RAM, and RAM costs much more than disk.
  • Durability is a trade-off: at best you lose about 1 s of writes, and replication is async.
  • No SQL, no joins, no secondary indexes unless you use the Query Engine or build them yourself.
  • One slow command (big DEL, KEYS *, a long Lua script) blocks every client.
  • Cluster restricts multi-key operations to keys in the same hash slot.
  • License changes (2024 to 2025) pushed some vendors to the Valkey fork. Check your legal constraints.

Concrete use cases

Caching database queries

An e-commerce site caches product pages with SET product:42 … EX 300. Most reads skip PostgreSQL entirely, so the database handles writes and cold reads only.

Sessions & login tokens

A web app behind a load balancer stores sessions as hashes with a TTL. Any server can read any session, and idle sessions expire on their own.

Rate limiting

An API counts requests with INCR rl:{user}:{minute} plus EXPIRE, or a Lua sliding window. It blocks a client after N calls with one atomic round trip.

Leaderboards & rankings

A mobile game keeps scores in a sorted set. ZINCRBY updates a score, and ZRANGE … REV or ZRANK answer "top 10" and "my position" in O(log N).

Background jobs & events

Python workers (RQ, Celery with a Redis broker) pull tasks from lists. Microservices exchange events through Streams with consumer groups and retries.

When to use / when not to

Rule of thumb: Redis is a speed layer, not your source of truth.

Use it when…

  • You need a fast cache in front of a slower database or API.
  • Data is short-lived or rebuildable: sessions, tokens, counters, feature flags.
  • You need shared state across many app instances, such as locks, rate limits or queues.
  • Your access pattern is "by key" and latency matters more than flexible queries.
  • You need real-time rankings, presence or lightweight messaging.

Avoid it when…

  • It would be the only copy of critical data, like orders or payments. Use PostgreSQL.
  • You need ad-hoc queries, joins or reporting. Use a relational DB or warehouse.
  • The dataset is much larger than affordable RAM. Use a disk-based store.
  • You need a replayable, high-volume event log kept for weeks. Use Kafka.
  • The app is a single process with a small dataset. An in-process cache (functools.lru_cache) is enough.

Common mistakes & gotchas

The first two bite almost everyone at least once!
Running KEYS * in productionIt is O(N) and blocks the single thread. With millions of keys, every client stalls for seconds.
Fix: use SCAN with MATCH and COUNT.
Cache keys without a TTLMemory fills up. With the default noeviction policy, writes start failing with OOM errors.
Fix: always set EX on cache keys, and set maxmemory plus allkeys-lru (or allkeys-lfu) for pure caches.
Treating Redis as a durable database by defaultWith RDB snapshots only, a crash loses everything written since the last snapshot, possibly minutes of data.
Fix: enable AOF with everysec, keep the source of truth in a real DB, and test restores.
Big keys and O(N) commandsA 2 GB hash or HGETALL on 1M fields blocks the server and saturates the network.
Fix: split data into smaller keys, use HSCAN/SSCAN, and delete with UNLINK.
Using Pub/Sub for things that must not be lostA subscriber that is offline or restarting never sees the message.
Fix: use Streams with consumer groups and XACK.
Cache stampede on a hot keyWhen a popular key expires, thousands of requests miss at the same moment and hit the database together.
Fix: add random jitter to TTLs, refresh early, or let one request rebuild the value behind a SET NX lock.
Expecting MULTI to roll backIf one command fails at runtime, the others still run. There is no rollback.
Fix: validate inputs first, or use a Lua script or Function for all-or-nothing logic.
Exposing port 6379 to the internetUnprotected Redis instances are scanned and compromised within hours.
Fix: bind to a private network, enable ACL users and passwords, and use TLS.

  • Pick Valkey if you want Redis semantics under a BSD license, or your cloud's managed service is Valkey-based.
  • Pick Memcached if all you need is a plain key → blob cache and you want the simplest possible thing.
  • Pick Dragonfly if one huge node with many cores is easier for you to run than a Redis Cluster.
  • Pick Kafka if events must be kept and replayed by many consumers over days or weeks.
  • Pick PostgreSQL (no cache at all) if your load is modest. One fewer moving part beats a cache you don't need.
