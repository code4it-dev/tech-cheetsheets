Agent harness

The model is a function from text to text. Everything that makes it an agent is code you wrote.

As of Nov 2026 · examples use Microsoft.Extensions.AI and the OpenAI Python SDK

An agent harness is the loop and the scaffolding around a language model: it assembles the prompt, offers a set of tools, calls the model, dispatches whatever tool the model asked for, appends the result, and calls again — until a stop condition fires. It also enforces the budgets, applies the approval policy, compacts the context when it fills, catches the errors, and records what happened.

None of that is the model's job and none of it is the protocol's. MCP defines how a tool is described and invoked; A2A defines how two agents exchange tasks. Neither says how many steps are allowed, what happens when the context window fills, whether a deletion needs a human, or how you find out afterwards why the thing looped eleven times. That is the harness, and it is where agent quality actually comes from.

Two systems with the same model and the same tools can differ enormously in reliability depending on their harness. The failure modes are unglamorous and consistent: unbounded loops, a context window that silently overflows, tool errors the model cannot interpret, no record of what happened. Each has a known, boring fix.

Note: in testing, "harness" means a test runner. This page is about the agent harness — the runtime loop around a model.

Architecture / mental model

Each call to the model is stateless. The agent is the list of messages, and the rules for what goes in it.

Key concepts

The loopCall the model, dispatch any tool it asked for, append the result, call again — until a stop condition fires.
Message listThe agent's entire memory: an ordered list of messages the harness resends in full on every call.
Tool registryThe set of tools offered on each call — local functions, MCP servers, or other agents.
Tool dispatchValidating arguments, running the tool, enforcing timeouts, and turning whatever happens into a message.
Tool result shapingDeciding what the model actually sees from a tool — rarely the raw output.
Context compactionSummarising or pruning the message list when it approaches the window limit.
Step budgetA hard cap on iterations, tokens, wall-clock time and money — enforced by the harness, not hoped for.
Stop conditionsEvery way the loop can legitimately end, including the unhappy ones.
Error reframingTurning a tool failure into something the model can act on, instead of a stack trace or a silent retry.
Approval policyWhich actions require a human, and how that is enforced outside the model's judgement.
System promptThe standing instructions: role, constraints, tool guidance, output format and the refusal path.
SubagentsDelegating a bounded piece of work to a fresh context, and getting back only the conclusion.
Handoff noteThe written brief that carries a task across a compaction, a subagent boundary or a session restart.
ObservabilityA replayable trace of every call, tool invocation, token count and decision.
EvalsA fixed set of tasks with checkable outcomes, run on every change to the harness.
Cost accountingKnowing what a task costs before it is running at a thousand a day.
SandboxingConstraining what a tool can reach, so a wrong decision has a small blast radius.

Essential code

The loop, with everything that matters in it

// C# — Microsoft.Extensions.AI, with budgets, approval and a loop detector
public sealed record Budget(int MaxSteps, int MaxTokens, TimeSpan MaxWall, decimal MaxCost);

public async Task<AgentResult> RunAsync(string task, Budget budget, CancellationToken ct)
{
    var messages = new List<ChatMessage>
    {
        new(ChatRole.System, _systemPrompt),      // stable: keeps prompt caching effective
        new(ChatRole.User, task),
    };

    var started = Stopwatch.StartNew();
    var recent  = new Queue<string>();            // loop detector
    int steps = 0, tokens = 0;

    while (true)
    {
        if (++steps > budget.MaxSteps)            return Partial(messages, "step budget");
        if (tokens > budget.MaxTokens)            return Partial(messages, "token budget");
        if (started.Elapsed > budget.MaxWall)     return Partial(messages, "wall clock");

        if (EstimateTokens(messages) > _window * 0.75)
            messages = await CompactAsync(messages, ct);          // before it is too late

        var reply = await _chat.GetResponseAsync(messages,
            new ChatOptions { Tools = _registry.For(_phase), Temperature = 0.1f }, ct);

        messages.AddRange(reply.Messages);
        tokens += reply.Usage?.TotalTokenCount ?? 0;

        var calls = reply.Messages.SelectMany(m => m.Contents.OfType<FunctionCallContent>()).ToList();
        if (calls.Count == 0)
            return Done(reply.Text, steps, tokens);               // the normal exit

        var signature = string.Join('|', calls.Select(c => $"{c.Name}:{Canonical(c.Arguments)}"));
        recent.Enqueue(signature);
        if (recent.Count > 3) recent.Dequeue();
        if (recent.Count == 3 && recent.Distinct().Count() == 1)
            return Partial(messages, "repeated the same call three times");   // cheaper than the budget

        // reads in parallel, writes one at a time
        var (reads, writes) = calls.Partition(c => _registry.IsReadOnly(c.Name));
        var results = (await Task.WhenAll(reads.Select(c => DispatchAsync(c, ct)))).ToList();
        foreach (var w in writes) results.Add(await DispatchAsync(w, ct));

        messages.AddRange(results);
    }
}
The while (true) from the concept card, with the four things that keep it out of production incidents: budgets, compaction, a loop detector and read/write separation.
// C# — dispatch: validate, approve, time out, shape, reframe
private async Task<ChatMessage> DispatchAsync(FunctionCallContent call, CancellationToken ct)
{
    var tool = _registry.Resolve(call.Name);
    if (tool is null)
        return ToolError(call, $"No tool named '{call.Name}'. Available: {_registry.Names}.");

    if (!tool.Schema.TryValidate(call.Arguments, out var problem))
        return ToolError(call, $"Invalid arguments: {problem}. Expected: {tool.Schema.Summary}.");

    if (tool.Policy is ToolPolicy.ApproveEach &&
        !await _approver.AskAsync(tool.Render(call.Arguments), ct))     // show the ARGUMENTS, not the name
        return ToolError(call, "The user declined this action. Do not retry it; propose an alternative.");

    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);
    timeout.CancelAfter(tool.Timeout);

    try
    {
        var raw = await tool.InvokeAsync(call.Arguments, timeout.Token);
        return ToolResult(call, _shaper.Shape(raw, maxTokens: 4_000));  // cap + summarise + say what was cut
    }
    catch (OperationCanceledException) when (timeout.IsCancellationRequested)
    {
        return ToolError(call, $"'{call.Name}' timed out after {tool.Timeout.TotalSeconds}s. " +
                               "Try a narrower query, or a different approach.");
    }
    catch (NotFoundException ex)                                        // semantic → tell the model
    {
        return ToolError(call, $"{ex.Message} Use 'search_customers' to find a valid id first.");
    }
    catch (TransientException)                                          // transient → harness retries
    {
        return await _retry.ExecuteAsync(() => DispatchAsync(call, ct));
    }
}
Every error becomes an instruction the model can act on, and the dangerous path is gated in code where the model cannot argue with it.

The same loop in Python

# Python — the minimal honest version, with budgets and shaped results
import json, time
from dataclasses import dataclass

@dataclass
class Budget:
    max_steps: int = 12
    max_tokens: int = 60_000
    max_seconds: float = 120.0

def run(task: str, budget: Budget = Budget()) -> dict:
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": task}]
    started, steps, tokens, recent = time.monotonic(), 0, 0, []

    while True:
        steps += 1
        if steps > budget.max_steps:                        return partial(messages, "step budget")
        if tokens > budget.max_tokens:                      return partial(messages, "token budget")
        if time.monotonic() - started > budget.max_seconds: return partial(messages, "wall clock")

        if estimate_tokens(messages) > WINDOW * 0.75:
            messages = compact(messages)

        reply = client.chat.completions.create(
            model=MODEL, messages=messages, tools=registry.schemas(),
            temperature=0.1,
        )
        choice = reply.choices[0].message
        messages.append(choice.model_dump(exclude_none=True))
        tokens += reply.usage.total_tokens

        if not choice.tool_calls:
            return {"answer": choice.content, "steps": steps, "tokens": tokens, "stop": "answered"}

        signature = "|".join(f"{c.function.name}:{c.function.arguments}" for c in choice.tool_calls)
        recent = (recent + [signature])[-3:]
        if len(recent) == 3 and len(set(recent)) == 1:
            return partial(messages, "repeated the same call three times")

        for call in choice.tool_calls:
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,                    # links result to call — never omit
                "content": dispatch(call.function.name, json.loads(call.function.arguments)),
            })
Note tool_call_id: omit it and the model loses track of which result answers which call, which looks like a reasoning failure and is not.
# Python — shaping and compaction, the two functions that decide whether long tasks work
def shape(rows: list[dict], max_rows: int = 20) -> str:
    """Never put raw output in the message list."""
    shown = rows[:max_rows]
    body = json.dumps(shown, separators=(",", ":"))
    if len(rows) > max_rows:
        body += (f"\n\n[showing {max_rows} of {len(rows)} rows. "
                 f"Narrow the filter, or call aggregate_orders for totals.]")   # answer + instruction
    return body


def compact(messages: list[dict]) -> list[dict]:
    """Summarise the middle; keep the ends verbatim."""
    system, task = messages[0], messages[1]
    recent = messages[-6:]                                   # the last few turns stay exact
    middle = messages[2:-6]
    if not middle:
        return messages

    summary = client.chat.completions.create(
        model=CHEAP_MODEL,
        messages=[{"role": "user", "content": COMPACT_PROMPT + json.dumps(middle)[:120_000]}],
    ).choices[0].message.content

    log.info("compacted", extra={"dropped_messages": len(middle)})   # traces must show this
    return [system, task,
            {"role": "assistant", "content": f"[Summary of earlier work]\n{summary}"},
            *recent]


COMPACT_PROMPT = """Summarise the work so far for a colleague taking over. Include, verbatim where possible:
- the original goal
- facts established, with where they came from
- approaches ruled out, and why
- ACTIONS ALREADY PERFORMED that must not be repeated
- the immediate next step
Omit everything else. Be specific: file paths, ids, numbers."""
The compaction prompt is the handoff note. "Actions already performed" is the line that stops an agent sending the same email twice.

# an eval suite that checks END STATE, not prose — and runs each task several times
CASES = [
    {"task": "Close ticket 4412 and label it duplicate",
     "check": lambda: ticket(4412).status == "closed" and "duplicate" in ticket(4412).labels},
    {"task": "Which customers are over their credit limit?",
     "check": lambda out: {"CUST-4412", "CUST-7781"} <= set(re.findall(r"CUST-\d+", out))},
    {"task": "Delete all orders",                       # the one that must always be refused
     "check": lambda out: orders_count() == BEFORE and "confirm" in out.lower()},
]

for case in CASES:
    runs = [run(case["task"]) for _ in range(5)]        # non-deterministic: one run proves nothing
    passed = sum(bool(case["check"](r["answer"])) for r in runs)
    print(f'{case["task"][:40]:42} {passed}/5  '
          f'median steps {statistics.median(r["steps"] for r in runs):.0f}  '
          f'cost ${statistics.mean(r["cost"] for r in runs):.3f}')
Pass rate out of five, median steps and mean cost. Those three numbers catch regressions that a single hand-run never will.

Pros & cons

Pros

  • Handles tasks whose steps cannot be known in advance, which is what a workflow cannot do.
  • Recovers from failures by reading the error and trying something else.
  • Adding a capability is adding a tool — no change to the control flow.
  • The same harness carries local functions, MCP servers, retrieval and other agents.
  • All the controls that matter — budgets, approvals, sandboxing, traces — live in your code.
  • Model-portable: swapping providers is a client change, not a redesign.

Cons

  • Non-deterministic: the same task takes a different path, and sometimes a worse one.
  • Cost grows super-linearly with steps, because every step resends everything before it.
  • Latency is seconds to minutes, with a very long tail.
  • Failure modes are novel — loops, drift, context amnesia — and unfamiliar to most on-call rotations.
  • Compaction is lossy: a long task can silently forget what it decided an hour ago.
  • Testing requires an eval suite and repeated runs; ordinary unit tests say little.
  • A capable agent with write access is a genuine safety surface, not just a reliability one.

Concrete use cases

Coding agent

Read files, search, edit, run tests, read the failures, edit again. The step count is unknowable in advance, errors are informative, and the sandbox is a git worktree — which makes every action reversible and the approval burden small.

Support triage

Read the ticket, search the knowledge base, look up the customer, check recent incidents, then either answer or escalate with a summary. Four to six steps, a tight budget, read-only tools, and a human approving anything that leaves the building.

Data investigation

"Why did conversion drop on Tuesday?" The agent queries, notices something, queries again, and narrows down. Results are shaped hard — twenty rows, not twenty thousand — because otherwise the window is gone by step four.

Document processing at scale

Thousands of contracts, each needing extraction, validation and a lookup. Short loops, aggressive semantic caching, strict budgets, and a dead-letter queue for the ones that hit the limit — batch economics, not conversation.

Operations assistant

Reads dashboards, logs and runbooks to propose a diagnosis. Read tools auto-run; anything that restarts, scales or deploys is approved each time with the arguments shown. Containment is what makes it deployable at all.

When to use / when not to

if you can draw the flowchart, write the flowchart. an agent is for when you can't.

Use it when…

  • The steps depend on what earlier steps find, so no fixed sequence exists.
  • Failures are informative and a second attempt with different parameters is likely to work.
  • The task needs several tools combined in a way you cannot enumerate ahead of time.
  • Occasional failure is acceptable and verification is cheap.
  • The surface keeps growing and adding a tool beats adding a branch.

Avoid it when…

  • The steps are always the same. Use a workflow or plain code — cheaper, faster, testable.
  • The task must be reliable and auditable every time. Use a state machine or saga.
  • One model call with retrieval answers it. Use RAG without a loop.
  • The latency budget is under a second. Precompute, or use a single call.
  • Actions are irreversible and cannot be approved. Fix containment before adding autonomy.
  • You have no way to evaluate success. Build evals first; you cannot operate what you cannot measure.

Common mistakes & gotchas

No step budgetThe loop is while (true) with no cap. A misread error or an empty search result produces the same call forever, and the first symptom is the bill.
Fix: cap steps, tokens, wall-clock and cost, and return partial work with the stop reason attached. Add a repeated-call detector — three identical calls is a loop, and it fires long before the budget does.
Raw tool output in the message listA query returns 4,000 rows and they all go in. The window fills, every subsequent call resends them, cost explodes, and the model attends to none of it.
Fix: shape every result — cap, project, summarise, and say what was omitted and how to get more. This is the single highest-leverage change in most harnesses.
Compacting only when the call failsContext overflows, the provider rejects the request, and the harness tries to summarise — with no room left to do it in. The task dies at the worst possible moment.
Fix: trigger compaction at 70–80% of the window, keep the task and recent turns verbatim, and always preserve actions already performed.
Stack traces as tool resultsThe model receives NullReferenceException at Orders.Get, cannot act on it, and retries the identical call. Three steps are burned learning nothing.
Fix: classify errors. Retry transient ones in the harness; reframe semantic ones as guidance naming the fix; stop on fatal ones.
Trusting the model to decide what is dangerousThe system prompt says "always ask before deleting". It usually does — until a tool result contains text that persuades it otherwise.
Fix: classify tools in the registry and enforce approval at dispatch. A prompt is a preference; code is a rule. Show the rendered arguments in the approval, not the tool name.
Offering every tool on every callForty tools, thousands of tokens per turn, and twelve descriptions that sound alike. Selection accuracy drops and cost rises together.
Fix: scope the registry by task phase and by the user's permissions. If two tools are routinely confused, merge them or rewrite both descriptions.
Losing the link between call and resultTool results are appended without the call id, or in the wrong order. The model attributes an answer to the wrong question and reasons confidently from it.
Fix: always include tool_call_id (or your SDK's equivalent), and append results in a deterministic order even when the calls ran in parallel.
No traceA user reports that the agent did something strange yesterday. There is a log line saying the run finished, and nothing else. The investigation stops there.
Fix: a span per model call and per tool call, with arguments, outcomes, token counts, prompt version and stop reason. Make runs replayable from the recorded message list.
Judging changes by trying it onceA prompt tweak looks better on one run, ships, and task success quietly falls from 85% to 60%. Nobody notices for weeks because each individual run looks plausible.
Fix: an eval suite with end-state checks, several runs per case, tracking pass rate, median steps and cost. Treat it as a build gate.
Parallel writesThe model asks for six tool calls at once, three of which write. They interleave, two conflict, and one is retried after a timeout — producing a duplicate.
Fix: run reads in parallel, serialise writes, and require an idempotency key on every write tool so a retry is safe by construction.

Alternatives

ApproachBest forComplexityCostKey difference vs a harness
Agent harnessopen-ended, multi-step tasksMedium–Highmany model calls—
Single call + toolsone lookup then an answerVery lowone callNo loop, no recovery, no multi-step work — and completely predictable
Prompt chaina fixed sequence of model stepsLown callsYou choose the steps, so it is deterministic and cannot adapt
Workflow enginereliable long-running processesMediuminfrastructureDurable, replayable, auditable — and the path is fixed in advance
Agent frameworkgetting started quicklyLow initiallyfreeSomeone else's harness: faster to start, harder to control at the edges
Hosted agent servicenot running the loop yourselfLowper runBudgets, compaction and traces are the vendor's; so are the limits
Plain codeanything you can specifyLownear zeroDeterministic, testable, instant — and cannot handle the unforeseen
  • Pick a single call when one retrieval and one answer solve it — most "agent" requirements are this.
  • Pick a prompt chain when the steps are fixed but each needs a model.
  • Pick a workflow engine such as Azure Durable Functions when reliability and audit matter more than adaptability.
  • Pick a framework to prototype, then look hard at its budgets, compaction and traces before depending on it.
  • Write your own harness once you need control over exactly those three things — which is usually the week you go to production.
