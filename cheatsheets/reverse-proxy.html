Reverse proxy

One public door in front of many private rooms — and the only place where "every request" is a thing you can say.

As of Nov 2026 · examples use nginx, Envoy, Caddy, Traefik and YARP

A forward proxy sits in front of clients and hides them from the internet. A reverse proxy sits in front of servers and hides them: clients connect to it, believing it is the application, and it decides which backend actually handles the request. Same machinery, opposite direction, completely different job.

What it buys you is a single place where cross-cutting work happens. TLS is terminated once, so certificates live in one process instead of in every service. Routing by host and path means one domain can front twenty services. Headers are normalised, request size is capped, timeouts are enforced, responses are compressed and cached, and the client never learns an internal address or port.

Every serious HTTP deployment has one, usually without calling it that: an nginx container, a Kubernetes ingress controller, an Envoy sidecar, an API gateway, a CDN edge. They differ in features and configuration language, not in concept — and the concepts that bite (trusted header chains, buffering, upstream keepalive, timeout stacking) are the same everywhere.

Architecture / mental model

One public endpoint, many private ones — plus a single place to put everything that is not business logic.

Key concepts

Reverse vs forward proxyA forward proxy represents clients to the internet; a reverse proxy represents servers to clients.
TLS terminationDecrypting HTTPS at the proxy so everything behind it can be plain HTTP — or re-encrypted.
SNIThe hostname the client announces in the TLS handshake, before any HTTP exists.
Upstream poolThe named set of backend addresses a route forwards to, with a balancing policy and health checks.
Virtual host routingChoosing a route from the Host header, the path, and sometimes a method or header.
Path rewritingChanging the request path between the public URL and the one the backend expects.
X-Forwarded headersThe hop-by-hop headers that tell the backend who the real client was and how they connected.
Trusted proxy chainThe rule that decides which forwarded addresses to believe and which to discard.
PROXY protocolA small preamble that carries the real client address on connections where headers are not available.
KeepaliveReusing upstream connections across requests instead of dialling a new one every time.
BufferingWhether the proxy holds the whole request or response in memory before passing it on.
Retries and timeoutsThe proxy's own deadlines and second attempts, which stack with everyone else's.
Health checksHow the proxy decides an upstream should stop receiving traffic.
Streaming and upgradesWebSockets, SSE and gRPC need the proxy to step out of the way rather than parse and buffer.
Edge policyThe cross-cutting rules — size limits, rate limits, compression, caching, security headers — applied in one place.
Rate limiting at the edgeRejecting excess traffic before it reaches a backend that would have queued it.
Graceful reloadApplying new configuration without dropping the connections already in flight.
Ingress controllerA reverse proxy whose configuration is generated from Kubernetes objects instead of a file.

Essential config & code

nginx — the baseline everyone meets

# a complete, defensible server block
upstream orders {
    least_conn;
    server 10.0.2.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.2.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 64;                       # without this, a new TCP connection per request
}

server {
    listen 443 ssl;
    http2 on;
    server_name shop.example;

    ssl_certificate     /etc/ssl/shop.pem;
    ssl_certificate_key /etc/ssl/shop.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    client_max_body_size 10m;           # reject huge bodies before the app sees them
    add_header Strict-Transport-Security "max-age=31536000" always;

    location /api/ {
        proxy_pass http://orders/;      # the trailing slash strips "/api" — it matters

        proxy_http_version 1.1;         # required for upstream keepalive
        proxy_set_header Connection "";

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Request-Id      $request_id;

        proxy_connect_timeout 2s;
        proxy_read_timeout    15s;
        proxy_next_upstream   error timeout;   # NOT on http_500 — that can duplicate writes
    }
}
Everything here earns its place: the keepalive pair, the forwarded headers, the body cap and timeouts that are not the defaults.
# the routes that need the defaults switched off
location /events {                      # server-sent events / token streams
    proxy_pass http://ai;
    proxy_buffering off;                # otherwise the whole stream arrives at the end
    proxy_cache off;
    proxy_read_timeout 1h;
    add_header X-Accel-Buffering no;
}

location /ws {                          # websockets
    proxy_pass http://realtime;
    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;           # default 60s is why the socket "randomly" drops
}

location /uploads {
    proxy_pass http://media;
    proxy_request_buffering off;        # stream the body through; no retries possible
    client_max_body_size 2g;
}
Three exceptions, each scoped to one location. Applying any of them globally removes a protection you want everywhere else.
nginx -t                       # validate before you reload. always.
nginx -s reload                # fork new workers, drain the old ones, no dropped connections
nginx -T | grep -A5 "location /api"   # dump the FULL effective config, includes resolved

curl -sI https://shop.example/api/orders/77 -H 'X-Forwarded-For: 1.2.3.4'   # try to spoof
curl -s --http2 -o /dev/null -w '%{http_version} %{time_total}\n' https://shop.example/
nginx -T is the one to remember: it prints what is actually in effect, not what you think you wrote.

Declarative alternatives

# Caddy — automatic HTTPS, and the forwarded headers are set for you
shop.example {
    encode gzip zstd
    request_body { max_size 10MB }

    handle_path /api/* {
        reverse_proxy 10.0.2.11:8080 10.0.2.12:8080 {
            lb_policy       least_conn
            health_uri      /healthz
            health_interval 5s
            transport http { read_timeout 15s }
        }
    }

    handle /events* {
        reverse_proxy 10.0.3.11:8080 { flush_interval -1 }   # -1 = stream, do not buffer
    }

    handle { reverse_proxy 10.0.1.11:8080 }
}
Certificates are obtained and renewed automatically, and handle_path strips the prefix without the trailing-slash trap.
# Kubernetes Gateway API — the typed successor to Ingress annotations
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: orders }
spec:
  parentRefs: [{ name: public-gateway }]
  hostnames: ["shop.example"]
  rules:
    - matches:
        - path: { type: PathPrefix, value: /api/ }
          headers: [{ name: x-canary, value: "1" }]      # header-based canary
      backendRefs: [{ name: orders-canary, port: 8080 }]
    - matches: [{ path: { type: PathPrefix, value: /api/ } }]
      filters:
        - type: URLRewrite
          urlRewrite: { path: { type: ReplacePrefixMatch, replacePrefixMatch: / } }
      backendRefs:
        - { name: orders, port: 8080, weight: 90 }
        - { name: orders-next, port: 8080, weight: 10 }   # 10% weighted rollout
      timeouts: { request: 15s }
Same concepts — match, rewrite, pool, timeout — expressed as resources an operator can review and a controller can apply.

A reverse proxy in your own process

// C# — YARP: a reverse proxy as ASP.NET Core middleware
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddReverseProxy()
    .LoadFromMemory(
        routes:
        [
            new RouteConfig
            {
                RouteId = "orders",
                ClusterId = "orders",
                Match = new RouteMatch { Hosts = ["shop.example"], Path = "/api/{**rest}" },
                Transforms =
                [
                    new() { ["PathRemovePrefix"] = "/api" },
                    new() { ["RequestHeader"] = "X-Forwarded-Proto", ["Set"] = "https" },
                ],
            },
        ],
        clusters:
        [
            new ClusterConfig
            {
                ClusterId = "orders",
                LoadBalancingPolicy = "PowerOfTwoChoices",
                HealthCheck = new() { Active = new() { Enabled = true, Path = "/healthz" } },
                Destinations = new Dictionary<string, DestinationConfig>
                {
                    ["d1"] = new() { Address = "http://10.0.2.11:8080/" },
                    ["d2"] = new() { Address = "http://10.0.2.12:8080/" },
                },
            },
        ]);

var app = builder.Build();
app.UseRateLimiter();            // edge policy, in C#, before the proxy runs
app.MapReverseProxy();
app.Run();
Worth it when routing depends on your own domain logic — tenant lookups, feature flags, custom auth — rather than on static rules.
# Python — a minimal streaming proxy with Starlette + httpx
import httpx
from starlette.applications import Starlette
from starlette.background import BackgroundTask
from starlette.responses import StreamingResponse
from starlette.routing import Route

client = httpx.AsyncClient(
    base_url="http://10.0.2.11:8080",
    timeout=httpx.Timeout(connect=2.0, read=15.0, write=15.0, pool=5.0),
    limits=httpx.Limits(max_keepalive_connections=64),   # keepalive, as in nginx
)

HOP_BY_HOP = {"connection", "keep-alive", "transfer-encoding", "upgrade", "te", "trailer"}

async def proxy(request):
    headers = {k: v for k, v in request.headers.items() if k.lower() not in HOP_BY_HOP}
    headers["x-forwarded-for"] = request.client.host        # set, not append: we are the edge
    headers["x-forwarded-proto"] = request.url.scheme

    upstream = client.build_request(
        request.method,
        request.url.path.removeprefix("/api"),
        headers=headers,
        params=request.query_params,
        content=request.stream(),                            # stream, do not buffer
    )
    response = await client.send(upstream, stream=True)
    return StreamingResponse(
        response.aiter_raw(),
        status_code=response.status_code,
        headers={k: v for k, v in response.headers.items() if k.lower() not in HOP_BY_HOP},
        background=BackgroundTask(response.aclose),
    )

app = Starlette(routes=[Route("/api/{path:path}", proxy, methods=["GET", "POST"])])
The parts a real proxy also has to get right: hop-by-hop headers stripped, bodies streamed, the forwarded chain set at the edge, and the upstream response closed.

Pros & cons

Pros

  • One public endpoint and one certificate store, however many services exist behind it.
  • Cross-cutting policy — TLS, limits, compression, caching, security headers — implemented once.
  • Backends are unreachable from the internet, with no ports, versions or topology exposed.
  • Routing, canaries and blue/green become configuration rather than deployments.
  • Buffering shields application threads from slow clients.
  • Protocol modernisation (HTTP/2, HTTP/3, TLS 1.3) happens at the edge, not in every service.
  • A single, consistent access log for every request in the system.

Cons

  • A single point of failure and a single blast radius — one bad config is a total outage.
  • Two connections where there was one, so every timeout, buffer and keepalive is now stacked.
  • Client identity must be reconstructed from headers you have to decide whether to trust.
  • Adds a hop: a little latency, and another process to run, patch and tune.
  • Terminating TLS means the proxy sees everything in clear text.
  • Defaults optimised for ordinary HTTP quietly break WebSockets, SSE and large uploads.
  • Configuration languages are quirky and under-tested compared with application code.

Concrete use cases

One domain, many services

A platform exposes /, /api/ and /static/ from three teams and three deployments. The proxy routes by prefix, so the public URL structure is decoupled from the internal topology and a service can be split or merged without the browser noticing.

TLS and certificate consolidation

Twenty internal services, none of which should handle certificates. The proxy terminates TLS, renews via ACME automatically, and talks plain HTTP inside the network — so adding a service means adding a route, not a certificate workflow.

Canary by header, then by weight

A new version is deployed alongside the old. Requests with x-canary: 1 go to it, then 10% of all traffic by weight, then 50%. The entire rollout is proxy configuration, instantly reversible, with no deployment involved.

Protecting a legacy backend

An old application cannot handle large bodies, slow clients or HTTP/2. A proxy in front caps body size, buffers responses, speaks modern protocols to the internet and plain HTTP/1.1 to the application — which is left untouched.

Static assets off the application

Hashed bundles are served from the proxy's cache with a one-year immutable TTL, and never reach the application at all. Backend request volume falls by most of its total and the origin only sees real work.

When to use / when not to

if you have more than one service and one domain, you already need one.

Use it when…

  • More than one service must live behind one hostname.
  • TLS, compression, caching or rate limiting should be configured once rather than per service.
  • Backends must not be directly reachable from the internet.
  • You want routing changes — canaries, maintenance pages, blue/green — without deploying code.
  • Clients are slow or hostile and application threads are expensive.
  • You need one access log and one request id across everything.

Avoid it when…

  • The protocol is not HTTP — a database, a broker, raw TCP. Use an L4 load balancer.
  • End-to-end encryption must be preserved with no middlebox reading traffic. Use TLS passthrough.
  • You need per-request balancing for internal gRPC and want no extra hop. Use client-side balancing or a sidecar.
  • You are buying developer portals, quotas, API keys and monetisation. Use an API gateway such as Azure API Management.
  • It is a single service on a single machine with a certificate already handled by the platform. Skip the hop.
  • The need is client-side aggregation of several APIs. Use a Backend-for-Frontend.

Common mistakes & gotchas

Trusting X-Forwarded-ForThe app reads the leftmost entry and calls it the client. A request carrying X-Forwarded-For: 1.2.3.4 bypasses every rate limit, ban list and geo-rule, and poisons the audit log.
Fix: count hops from the right, trusting exactly the proxies you operate, and have the outermost one strip inbound copies. Configure your framework's known-proxy list explicitly — the default is never right.
No upstream keepalivenginx opens a fresh TCP connection to the backend for every request, because keepalive is off unless configured. Latency rises, ports exhaust under load, and the backend's accept queue does unnecessary work.
Fix: add keepalive 64; to the upstream block, set proxy_http_version 1.1 and clear the Connection header. Keep the proxy's idle timeout shorter than the backend's.
Streaming routes behind default bufferingServer-sent events, progress output and LLM token streams arrive all at once when the response finishes. Everything "works" but feels broken, and nothing in the logs is unusual.
Fix: proxy_buffering off on those routes only, plus X-Accel-Buffering: no from the backend and a read timeout measured in hours.
The trailing slash in proxy_passproxy_pass http://api; keeps the matched prefix, proxy_pass http://api/; strips it. One character decides whether the backend receives /api/orders or /orders, and the error is a 404 that looks like a routing bug.
Fix: pick the form deliberately and assert it in a smoke test. Caddy's handle_path and the Gateway API's ReplacePrefixMatch make the intent explicit instead.
Missing X-Forwarded-ProtoThe app sees plain HTTP, decides the request is insecure, and issues a redirect to HTTPS — which the proxy terminates and forwards as HTTP again. Infinite redirect loop, only in production.
Fix: set X-Forwarded-Proto $scheme at the proxy and enable forwarded-header processing in the framework, so redirects and Secure cookies use the original scheme.
Retrying non-idempotent requestsproxy_next_upstream includes http_500 or non_idempotent, so a POST the backend already processed is replayed on another instance. Duplicate orders, duplicate charges.
Fix: retry only on connect errors and timeouts before any bytes were sent, cap attempts at one, and make write endpoints idempotent with an idempotency key.
Timeouts that increase outwardThe backend gives up after 30 s, the proxy after 60 s, the client after 10 s. The client has long gone, the proxy still waits, the backend still works, and the capacity is spent on a result nobody will read.
Fix: deadlines must shrink as you go inward — client > proxy > backend — and the proxy should propagate the remaining budget rather than inventing its own.
DNS resolved once at startupThe upstream is a DNS name. The backend scales or moves, the IP changes, and the proxy keeps sending traffic to an address nobody is listening on until someone restarts it.
Fix: configure a resolver with a TTL (nginx needs a resolver directive and a variable in proxy_pass), or use service discovery rather than plain DNS.
Config reloads nobody validatesA typo ships, the reload fails or applies a half-correct ruleset, and every service behind the proxy is affected at once. The proxy is the one component with no bulkhead.
Fix: validate in CI (nginx -t, envoy --mode validate), review proxy config like application code, and roll it out to one instance before the fleet.

  • Pick Caddy for a small estate where automatic HTTPS and a short config file are worth more than tuning knobs.
  • Pick Envoy when configuration must change at runtime from an API, or when gRPC and advanced policy matter.
  • Pick an API gateway when the consumers are external and you need keys, quotas and a portal.
  • Pick a CDN as the outermost layer whenever traffic is global and cacheable — then a reverse proxy behind it.
  • Pick YARP when routing depends on data only your application has.
