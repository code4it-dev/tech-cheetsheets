Backend-for-Frontend

One backend per experience, so no client has to negotiate with a general-purpose API.

As of Nov 2026 · the pattern is stable; examples are .NET 10 (LTS) and ASP.NET Core

A single general-purpose API has to serve a desktop web app, a mobile app, a smart TV and a partner integration — and each of them wants a different shape. The usual outcome is an API that suits none of them: the mobile app downloads 28 KB to display a name, makes six round trips to paint one screen, and carries the orchestration logic in a binary you cannot update for the 20% of users who never upgrade.

A Backend-for-Frontend is a thin server-side layer dedicated to one client, owned and deployed by the team that owns that client. It exposes endpoints shaped like screens rather than like resources, fans out to the downstream services inside the datacenter where a call costs milliseconds, and returns exactly what the UI renders — nothing more.

It is not the only way to solve this. An API gateway can aggregate with configuration, and GraphQL lets the client declare the shape instead. Those answer the same question with different trade-offs around ownership, logic and caching, which is what the four animations below compare — on the same screen, the same six services and the same network.

Architecture / mental model

The BFF is part of the frontend, running on a server. It ships with the client, changes with the client, and is thrown away when the client is.

Three things worth pulling out of that:

  • The win is the round trip, not the bytes. Every option that gets to one round trip lands within milliseconds of the others. The shared API is slow because of six sequential 150 ms waits, and no amount of payload trimming fixes that.
  • The real difference is ownership. A BFF lets the mobile team change the screen's data without filing a ticket; a gateway puts a platform team in the path; GraphQL puts a shared schema in the path. Pick based on which queue you want to stand in.
  • GraphQL and BFFs are not opposites. A common end state is a GraphQL BFF: one per client, each exposing a schema shaped for that client over the same services. You get declarative shaping without a schema that every team must agree on.

Key concepts

BFFA server-side component dedicated to one client, owned by that client's team and shaped around its screens rather than around domain resources.
experience APIAn endpoint shaped like a screen — GET /mobile/home — rather than like a resource. The thing a BFF actually exposes.
over-fetchingReceiving far more than the screen renders: the full user aggregate when you needed a name. Wasteful on mobile, and it ties you to a model you do not control.
under-fetchingThe opposite: the response does not contain what you need next, so you make another call — and another. This is what turns one screen into six round trips.
chattinessThe number of round trips a screen costs. On mobile this dominates everything else, so it is the number to design against.
aggregationCalling several services in parallel and combining the results. The BFF's main job, and the reason it belongs near the services rather than near the user.
response shapingReturning exactly the fields the screen renders, in the structure it renders them. What turns 180 KB into 4 KB.
ownershipThe BFF is owned, deployed and on-called by the team that owns the client. This is the defining property, not an organisational detail.
tail amplificationThe BFF waits for the slowest of its downstream calls, so its p99 is much worse than any single service's. The cost of fan-out.
partial failureOne downstream is down, and the screen still renders without that panel. A BFF is the natural place to decide this, because it knows what the screen can live without.
caching in a BFFThe BFF is an excellent cache point: it knows the screen, the user and what may be shared. Done wrong, it is where you leak one user's data to another.
authenticationThe BFF sits between a browser or app and the services, which makes it the right place to swap a cookie for a token and to keep tokens off the client entirely.
versioningA BFF can change as often as its client — but on mobile the old client never goes away, so it must serve several app versions at once.
duplicationThree BFFs calling the same five services will contain similar code. Some of that duplication is the price of the pattern; some of it is a mistake.
downstream couplingThe BFF depends on the services it calls, so their breaking changes become its problem. A thin BFF makes this manageable; a thick one does not.
GraphQLThe main alternative: one endpoint, a typed schema, and the client declares the shape. Solves over- and under-fetching without a backend per client.

Code & syntax

A BFF endpoint, end to end

app.MapGet("/mobile/home", async (
    ClaimsPrincipal user, IProfileApi profile, IBasketApi basket,
    IRecommendationApi recs, ILoyaltyApi loyalty, CancellationToken ct) =>
{
    var userId = user.GetUserId();

    var profileTask = profile.GetAsync(userId, ct);           // start everything first
    var basketTask  = basket.GetAsync(userId, ct);
    var recsTask    = Safe(() => recs.TopAsync(userId, 6, ct), Array.Empty<Rec>());
    var loyaltyTask = Safe(() => loyalty.GetAsync(userId, ct), null);

    await Task.WhenAll(profileTask, basketTask, recsTask, loyaltyTask);

    return Results.Ok(new HomeScreen(
        Greeting: $"Good evening, {profileTask.Result.FirstName}",
        Basket:   new(basketTask.Result.Items.Count, Money(basketTask.Result.Total)),
        Panels:   BuildPanels(recsTask.Result, loyaltyTask.Result)));
}).RequireAuthorization();
One wave of parallel calls, optional panels degraded safely, and a response shaped like the screen.
static async Task<T> Safe<T>(Func<Task<T>> call, T fallback)
{
    try { return await call(); }
    catch (Exception ex) when (ex is TimeoutException or HttpRequestException)
    { return fallback; }
}
The whole of partial failure. Log and count every fallback, or missing panels become invisible.
builder.Services.AddHttpClient<IRecommendationApi, RecommendationApi>(c =>
{
    c.BaseAddress = new Uri(cfg["Services:Recommendations"]!);
    c.Timeout = TimeSpan.FromMilliseconds(300);     // shorter than your own SLO
})
.AddStandardResilienceHandler();
A tight per-downstream timeout is what stops one slow service defining the screen's latency.
app.MapGet("/mobile/home", Handler)
   .CacheOutput(p => p.Expire(TimeSpan.FromSeconds(15)).VaryByValue(ctx =>
        new KeyValuePair<string,string>("u", ctx.User.GetUserId())));
Caching an authenticated screen: the user id must be in the key, or you serve one user's home page to another.

Browser SPA: cookie in, token out

builder.Services.AddBff();
builder.Services.AddAuthentication(o =>
{
    o.DefaultScheme          = CookieAuthenticationDefaults.AuthenticationScheme;
    o.DefaultChallengeScheme = "oidc";
})
.AddCookie(o => { o.Cookie.HttpOnly = true; o.Cookie.SameSite = SameSiteMode.Strict; })
.AddOpenIdConnect("oidc", o => { o.ResponseType = "code"; o.SaveTokens = true; });
The browser holds only an HttpOnly cookie; the access token never reaches JavaScript.
app.UseAuthentication();
app.UseBff();
app.UseAuthorization();
app.MapBffManagementEndpoints();                     // /bff/login, /bff/logout, /bff/user
app.MapRemoteBffApiEndpoint("/api/orders", "https://orders.internal")
   .RequireAccessToken(TokenType.User);              // swaps the cookie for a bearer token
Proxying with token exchange, so the SPA calls same-origin paths and never sees a token.

GraphQL, for comparison

query Home {
  me { displayName avatarUrl }
  basket { count total }
  recommendations(limit: 6) { id title price }
}
One request, one round trip, and only the fields the screen draws.
builder.Services
    .AddGraphQLServer()
    .AddQueryType<Query>()
    .AddDataLoader<ProductByIdDataLoader>()          // batching: the N+1 fix
    .ModifyRequestOptions(o => o.ExecutionTimeout = TimeSpan.FromSeconds(5))
    .AddMaxExecutionDepthRule(8)                      // stop pathological queries
    .UsePersistedOperationPipeline();                 // only allow queries you shipped
The four things a production GraphQL endpoint needs that a BFF gets for free: batching, a timeout, a depth limit and an allow-list.

Pros & cons

Pros

  • Collapses a screen from six round trips to one, which on mobile is the whole performance story.
  • The client team ships data changes itself, with no ticket and no other team's sprint.
  • Payloads shrink by an order of magnitude because the response is built for one layout.
  • Orchestration moves out of an app binary you cannot update into a service you deploy hourly.
  • Partial failure becomes a product decision: the screen renders without the panel that broke.
  • For browser apps, tokens stay server-side behind an HttpOnly cookie.

Cons

  • Another service per client to build, deploy, monitor and be on call for.
  • Fan-out means the BFF inherits a worse tail than any single downstream service.
  • Similar code appears in every BFF, and the urge to share it undoes the independence.
  • It is one more place a downstream breaking change can land.
  • Without real ownership it degrades into a second API with an extra hop.
  • Mobile forces you to serve old app versions, so compatibility branches accumulate.

Concrete use cases

A mobile home screen on a bad connection

Six services, three dependent waves, 180 KB and about 700 ms before anything renders on a congested 4G link. A mobile BFF collapses it to one request returning 4 KB: the device waits for one 150 ms round trip while the fan-out happens at 5 ms a hop inside the datacenter.

A browser SPA that must not hold tokens

A banking SPA cannot keep access tokens where a third-party script could reach them. A BFF holds the tokens server-side, gives the browser an HttpOnly cookie, and proxies API calls with token exchange. The SPA only ever calls same-origin paths, and a compromised dependency finds nothing worth stealing.

Smart TV with a very different screen

The TV app renders eight rails of artwork and no text-heavy detail, and it runs on hardware that struggles to parse large JSON. Its own BFF returns a tiny payload with pre-selected image variants at exactly the right resolution, while the mobile and web BFFs keep returning what their screens need.

Strangling a legacy backend

A monolith exposes an awkward SOAP-shaped API that the new React app should never see. A BFF fronts it, translating into clean JSON per screen. As capabilities move out of the monolith, the BFF repoints one call at a time — the frontend never knows a migration is happening.

Shipping a redesign without an app release

Marketing wants to reorder the home screen panels for a campaign. Because the BFF decides panel order and visibility, the change is a deployment on Tuesday rather than an app-store submission and a two-week wait for users to update.

When to use / when not to

If the client team can't deploy it, it isn't a BFF — it's just another API.

Use it when…

  • Two or more clients want genuinely different shapes from the same services.
  • A screen needs several services and your users are on mobile networks.
  • The client team can own, deploy and be on call for a service.
  • You are building a browser SPA and want tokens out of JavaScript.
  • Orchestration currently lives in an app binary you cannot update quickly.
  • You are strangling a legacy backend and want the frontend insulated from the migration.

Avoid it when…

  • You have one client. A BFF and your API would be the same thing — just build the API.
  • Clients want the same shape. Shape it once in a shared API and skip the layer.
  • The client team cannot run a service. Use gateway aggregation or GraphQL instead.
  • You need only cross-cutting concerns — auth, rate limits, routing. Use an API gateway.
  • Clients are numerous and unpredictable, like public integrators. Use a documented public API, or GraphQL.
  • You would put domain rules in it. Those belong in the services, or you will have four versions of them.

Common mistakes & gotchas

The BFF becomes a shared API againThe web team needs something the mobile BFF already returns, so they call it. Six months later three clients depend on it, it cannot change without coordination, and you have rebuilt the problem with an extra hop.
Fix: one BFF per experience, and an explicit rule that a BFF has exactly one consumer. If two clients need the same thing, the capability belongs in a downstream service, not in somebody's BFF.
Business logic creeps in"Gold tier needs 2,000 points" gets implemented in the mobile BFF because it was quick. The web BFF implements it slightly differently, and now the rule has two versions and no owner.
Fix: hold the line between presentation and domain. Deciding which panel to show is presentation; deciding what makes a customer gold is domain and lives in the loyalty service.
Awaiting calls one at a timevar a = await X(); var b = await Y(); turns a one-wave fan-out into a chain. The BFF is now as slow as the sum of its downstreams, which can be slower than the chatty client it replaced.
Fix: start every independent call before awaiting any of them, then Task.WhenAll. Add a test that fails if the handler's wall time exceeds the slowest downstream by more than a small margin.
No per-downstream timeoutOne service degrades from 40 ms to 9 seconds. The BFF has no timeout, so every home screen takes 9 seconds, the thread pool fills, and the BFF takes down screens that did not even need that service.
Fix: every downstream call gets a timeout shorter than your own latency objective, plus a fallback for anything the screen can live without. Budget the whole screen first, then divide it.
Caching an authenticated screen without the user in the keyCache-Control: public on /mobile/home, or an output cache keyed only on the path. A shared cache serves one customer's basket and loyalty points to the next one.
Fix: private, no-store for anything personal, and when you do cache server-side, key on user id plus screen plus locale plus app version. Review every cache directive on a BFF as a security change.
Forgetting old app versionsA field is renamed to match a redesign. Users on last year's build get a blank panel, and because mobile clients never fully turn over, the complaints arrive for months.
Fix: additive changes by default; a new path when a screen is genuinely redesigned. Track the version distribution, declare a support window, and put a deletion date on every compatibility branch.
Extracting a shared BFF library too earlyThree BFFs look similar, so the common parts move into Bff.Common. Within a year every change needs a lockstep upgrade across three teams — the exact coordination the pattern was supposed to remove.
Fix: share plumbing (clients, auth, tracing, resilience defaults), duplicate product (shapes, panel rules, fallbacks). When a shared library grows a per-client flag, copy the code back out.
Chaining BFFsA BFF calls another BFF because it already aggregates something useful. Now one screen depends on two fan-outs, the tails multiply, and no single dashboard shows the real latency.
Fix: keep aggregation one level deep — BFF to services, never BFF to BFF. If two BFFs need the same composition, that composition is a domain service.

ApproachBest forComplexityWho owns itKey difference vs a BFF
BFF per clientseveral clients with different screensMediumthe client team—
One shared APIa single client, or clients that agreeLowa platform teamNo extra layer; every client gets a compromise shape
API gateway aggregationsimple composition plus cross-cutting concernsLow–mediuma platform teamConfiguration not code, so there is nowhere to put a decision
GraphQLmany clients, fast-changing shapesMedium–higha shared schemaThe client declares the shape; no backend per client, but caching and cost control get harder
GraphQL BFFwanting bothMedium–highthe client teamA GraphQL schema per client — declarative shaping without org-wide negotiation
Server-driven UIscreens that must change without a releaseHighthe client teamThe BFF returns layout as well as data; maximum flexibility, hardest to reason about
Edge functionspersonalisation close to the userMediumthe client teamA BFF deployed at the edge; great for a cached shell, poor for fan-out to one region
  • Pick one shared API if you have one client, or if the clients genuinely want the same data. The simplest thing that works.
  • Pick gateway aggregation if the composition is mechanical and no client team can run a service.
  • Pick GraphQL when client needs change faster than you can ship backends, and you can afford batching, depth limits and persisted queries.
  • Pick a GraphQL BFF if you want declarative shaping without a schema every team has to agree on. Often the best of both.
  • Note where these sit: a gateway in front for auth and rate limits, a BFF behind it per client, domain services behind that, is a perfectly ordinary stack.
