A2A

MCP is how an agent reaches a tool. A2A is how an agent hires another agent — and never learns how it works.

As of Nov 2026 · spec 1.0.0 · stewarded by the Linux Foundation / Agentic AI Foundation

Agent2Agent standardises what happens when one autonomous agent needs work done by another that it did not build, cannot see inside, and may not even share a company with. The remote agent is opaque: no shared memory, no shared tools, no exposed prompt or plan. You send it a request, it gives you a task, and you follow that task to a conclusion.

Mechanically it is small. Every agent publishes an Agent Card at /.well-known/agent-card.json describing its skills, its transports and how to authenticate. A client picks an interface, calls SendMessage, and receives either an immediate Message or a Task with an id. The task moves through a defined lifecycle, emits status and artifact updates over SSE, and can pause to ask for input or for authorization.

Version 1.0.0 is a real break from the 0.x drafts most tutorials show: method names are PascalCase (SendMessage, not message/send), the card lists supportedInterfaces instead of a single url, and task states are enum constants such as TASK_STATE_WORKING. Check which version a counterparty speaks before debugging anything else.

Architecture / mental model

A2A goes across between peers; MCP goes down to tools. Most real systems use both, in that arrangement.

Key concepts

Agent CardThe public JSON document at /.well-known/agent-card.json that describes what an agent can do and how to reach it.
SkillA named capability advertised on the card — the unit a client matches against when choosing an agent.
supportedInterfacesThe ordered list of endpoints and protocol bindings the agent speaks — first entry is preferred.
TaskThe unit of work: server-created, identified, stateful, and followed rather than awaited.
TaskStateThe nine enum values a task moves through, four of them terminal and two of them pauses.
contextIdThe server-generated id that groups related tasks and messages into one ongoing interaction.
Message and PartWhat the two sides exchange: a role, and a list of parts that may be text, bytes, a URL or structured data.
ArtifactA durable output of a task, as opposed to the conversational messages that produced it.
SendMessageThe method that starts or continues work — PascalCase in 1.0.0, not the 0.x slash form.
StreamingServer-sent events carrying status and artifact updates while a task runs.
Push notificationsWebhook delivery of task updates, for clients that cannot hold a connection open for an hour.
Security schemesHow a client authenticates: declared on the card, obtained out of band, sent on every request.
In-task authAUTH_REQUIRED: the remote agent needs credentials for a third system, mid-task.
Card signingJWS signatures over the agent card, so a client can verify it was published by who it claims.
Version negotiationThe A2A-Version header, and why 1.0.0 breaks 0.x clients.
Opaque agentsThe design rule that makes A2A different: you exchange tasks, never internals.
A2A vs MCPComplementary, not competing: one connects agents to tools, the other connects agents to agents.

Each frame wraps a StreamResponse: exactly one of task, message, statusUpdate or artifactUpdate, in generation order.

A client that follows the task to the end

// C# — discover, send, stream, and handle the pauses
record Interface(string Url, string ProtocolBinding, string ProtocolVersion);
record AgentCard(string Name, Interface[] SupportedInterfaces, Capabilities Capabilities);

static readonly string[] Supported = ["JSONRPC", "HTTP+JSON"];     // we don't speak gRPC

var card = await http.GetFromJsonAsync<AgentCard>(
    "https://visa.example.com/.well-known/agent-card.json");

// the spec's rule: first entry is preferred; take the first one we support
var iface = card!.SupportedInterfaces.First(i => Supported.Contains(i.ProtocolBinding));

var task = await SendMessageAsync(iface.Url, "Assess eligibility: Italian citizen…");

while (true)
{
    switch (task.Status.State)
    {
        case "TASK_STATE_COMPLETED":
            return task.Artifacts;                          // the deliverable

        case "TASK_STATE_INPUT_REQUIRED":
            var answer = await AskTheHumanAsync(task.Status.Message);
            task = await SendMessageAsync(iface.Url, answer,
                                          taskId: task.Id, contextId: task.ContextId);
            continue;                                        // same task, same context

        case "TASK_STATE_AUTH_REQUIRED":
            await RunConsentFlowAsync(task.Status.Message);  // reaching this state is NOT a grant
            task = await GetTaskAsync(iface.Url, task.Id);
            continue;

        case "TASK_STATE_FAILED":                            // it tried — a retry may work
            throw new AgentFailedException(task.Status.Message);

        case "TASK_STATE_REJECTED":                          // it declined — do NOT retry unchanged
        case "TASK_STATE_CANCELED":
            throw new AgentRefusedException(task.Status.Message);

        default:                                             // SUBMITTED / WORKING
            await Task.Delay(TimeSpan.FromSeconds(2));
            task = await GetTaskAsync(iface.Url, task.Id);
            continue;
    }
}
The loop is the integration. Every state has a different correct response, and conflating FAILED with REJECTED is how you build a retry storm.
# Python — the streaming client, plus an idempotent push-notification webhook
import json, httpx
from fastapi import FastAPI, Header, HTTPException

async def stream_task(url: str, text: str, token: str):
    payload = {"jsonrpc": "2.0", "id": 1, "method": "SendStreamingMessage",
               "params": {"message": {"messageId": new_id(), "role": "ROLE_USER",
                                      "parts": [{"text": text}]}}}
    headers = {"Authorization": f"Bearer {token}", "A2A-Version": "1.0",
               "Accept": "text/event-stream"}

    async with httpx.AsyncClient(timeout=None) as client:          # no read timeout on a stream
        async with client.stream("POST", url, json=payload, headers=headers) as r:
            async for line in r.aiter_lines():
                if not line.startswith("data: "):
                    continue
                result = json.loads(line[6:])["result"]
                if "statusUpdate" in result:
                    yield ("status", result["statusUpdate"]["status"]["state"])
                elif "artifactUpdate" in result:
                    yield ("artifact", result["artifactUpdate"]["artifact"])

# --- the webhook side: delivery is AT-LEAST-ONCE ---
app = FastAPI()
seen: set[str] = set()                                             # use Redis in production

@app.post("/a2a/push")
async def push(body: dict, authorization: str = Header(default="")):
    if authorization != f"Bearer {WEBHOOK_TOKEN}":                 # the agent authenticates to US
        raise HTTPException(401)

    update = body.get("statusUpdate") or body.get("artifactUpdate") or {}
    key = f'{update.get("taskId")}:{body.get("messageId") or update.get("status", {}).get("timestamp")}'
    if key in seen:
        return {"ok": True}                                        # duplicate: ack and ignore
    seen.add(key)

    task = await get_task(update["taskId"])                        # confirm; don't trust the payload
    await handle(task)
    return {"ok": True}
Two things people skip: authenticating the inbound webhook, and re-reading the task instead of acting on a payload that may be a duplicate or a replay.

Pros & cons

Pros

  • Agents from different vendors, languages and clouds can collaborate without a shared runtime.
  • Discovery is one HTTP GET, and the card is readable by a human as well as a machine.
  • Tasks are built for long-running work: states, interruptions, progress and durable artifacts.
  • Multimodal by default — text, files, URLs and structured data in one message.
  • Three bindings over the same semantics, so you can pick JSON-RPC, gRPC or REST to suit your estate.
  • Opacity is a feature across organisational boundaries: neither side exposes prompts, tools or data.
  • Vendor-neutral governance under the Linux Foundation, with broad platform support.

Cons

  • Heavier than a function call: discovery, task state, streaming and webhooks for one delegation.
  • Opacity cuts both ways — debugging a wrong answer across the boundary is genuinely hard.
  • Skills are prose, so capability matching is fuzzy and failures are semantic rather than typed.
  • 1.0.0 renamed methods, card fields and state values; most published examples are 0.x.
  • Non-determinism compounds: two agents, two loops, two sets of retries.
  • Cost and latency are opaque too — you are paying for someone else's token spend.
  • The ecosystem of genuinely useful public agents is still thin compared with MCP servers.

Concrete use cases

Cross-company delegation

A travel platform's agent delegates visa assessment to a specialist provider's agent. Neither exposes its tools or data; the card describes the skill, the task carries the request, and the artifact is a document the platform can store and show.

Specialist agents inside one company

A support agent hands a pricing question to the pricing team's agent and a legal question to legal's. Each team deploys, versions and secures its own agent independently — the integration is a card URL, not a shared codebase.

Long-running research

A task that runs for forty minutes, emits progress, streams a report artifact in chunks, and pauses once to ask which market to prioritise. Request/response could not express any of that; the task lifecycle expresses all of it.

Human-in-the-loop compliance

A task reaches AUTH_REQUIRED because the remote agent needs consent to query a government system. The client drives the consent flow with the actual human, then continues the same task — the pause is in the protocol, not bolted on.

An agent marketplace

Signed agent cards indexed in a registry, searchable by skill tags. An orchestrator picks an agent at runtime by capability rather than by hard-coded URL, and verifies the signature before sending it anything.

When to use / when not to

across a trust boundary → A2A. inside your own process → just call the function.

Use it when…

  • The other side is an autonomous agent you do not own and cannot see inside.
  • Work is long-running, may produce artifacts, and may need to pause for input or consent.
  • Agents are built by different teams or vendors in different stacks.
  • You want capability discovery at runtime rather than hard-coded endpoints.
  • Neither side may expose its prompts, tools, data or credentials to the other.

Avoid it when…

  • You are exposing a system, database or API to a model. Use MCP.
  • Both "agents" live in one codebase. Use a function call — a protocol buys nothing.
  • The interaction is a typed request/response with a schema. Use gRPC or REST.
  • You need determinism, step limits and full observability. Use an agent harness you control.
  • Latency budgets are tight — discovery, task creation and polling all cost round trips.
  • Only one consumer will ever exist. Integrate directly and revisit when there is a second.

Common mistakes & gotchas

Writing 0.x method names against a 1.0 agentmessage/send and tasks/get return method-not-found, and the error gives no hint that the names were renamed to SendMessage and GetTask.
Fix: read protocolVersion on the chosen interface, send A2A-Version, and use the PascalCase names. An unsupported version should come back as a 400 with application/problem+json, which is a far clearer signal.
Treating the response as a valueClient code awaits SendMessage and reads a result. Sometimes it gets a Message and works; sometimes it gets a Task in SUBMITTED and silently returns nothing useful.
Fix: branch on which you received, and for a task run the follow loop to a terminal state. Both shapes are normal and both must be handled.
Conflating FAILED, REJECTED and CANCELEDAll three are terminal, so the client retries all of them. REJECTED means the agent declined the request — retrying unchanged is a loop that will never succeed, and may be billed each time.
Fix: retry FAILED with backoff, never retry REJECTED without changing the request, and treat CANCELED as someone's deliberate decision.
Inventing task or context idsA client generates a taskId to correlate work. The server rejects it, or worse, a mismatched contextId and taskId pair is refused for reasons that are hard to read.
Fix: both ids are server-generated. Store what you are given and send it back unchanged; carry contextId forward only for genuine follow-ups.
Streaming behind a buffering proxyThe SSE stream produces nothing for twenty minutes and then everything at once, because a reverse proxy buffered the response. The agent looks broken and is not.
Fix: disable response buffering on the streaming route, keep read timeouts long, and fall back to push notifications for genuinely long tasks.
Trusting push notificationsThe webhook accepts any POST and acts on the payload. Delivery is at-least-once, so duplicates double-process — and an unauthenticated endpoint will happily act on a forged one.
Fix: authenticate the inbound call with the token you registered, deduplicate on task id plus event identity, and call GetTask to confirm before doing anything irreversible.
Ignoring the card's interface orderThe client picks gRPC because it is listed, or hard-codes the first URL it saw. Both ignore the rule that the first entry is preferred among those you support — and that a declared tenant must be sent.
Fix: filter supportedInterfaces to the bindings you implement, take the earliest, and propagate tenant exactly as declared or omit it entirely.
Unsigned cards fetched over an unverified pathThe card says where to send work and what the agent claims. Fetched without verification, a substituted card redirects every delegation to someone else's endpoint.
Fix: HTTPS with certificate verification, verify the JWS signatures where present, and pin the issuer for agents you depend on.
No budget on delegated workA remote agent runs for an hour on its own schedule, spending your money under a contract you did not read closely. Nothing in the protocol caps it for you.
Fix: set your own deadline, call CancelTask when it passes, and keep per-counterparty budgets and timeouts the way you would for any external dependency.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs A2A
A2Aagents collaborating across boundariesMediumopen, Apache 2.0—
MCPconnecting a model to tools and dataMediumopen specTyped tool calls you define, not opaque peers; the two compose
Direct REST / gRPCa typed, deterministic serviceLowfreeNo discovery, no task lifecycle, no interruptions — and far simpler
One multi-agent frameworkagents you own, in one runtimeLow–MediumfreeShared memory and full visibility, but only within that framework
Message queueasynchronous work at scaleMediuminfrastructureDurable delivery and decoupling, but you define every message and state yourself
Workflow enginelong-running deterministic processesMedium–Highinfrastructure or serviceDurable, replayable orchestration of steps you control, not autonomous peers
  • Pick MCP when the other side is a system you are exposing rather than an agent that reasons.
  • Pick direct REST or gRPC when the request has a schema and the answer is deterministic.
  • Pick a framework when you own every agent and want shared state and end-to-end traces.
  • Pick a workflow engine such as Azure Durable Functions when the process must be reliable and replayable rather than autonomous.
  • Use A2A with MCP: A2A across the boundary, MCP from each agent down to its own tools.
