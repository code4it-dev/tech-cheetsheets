gRPC

A typed method call that happens to cross a network — with HTTP/2 doing the multiplexing and protobuf doing the bytes.

As of Nov 2026 · examples use proto3, grpc-dotnet and grpcio

gRPC starts from a .proto file: a service, its methods, and the message types they exchange. A code generator turns that into a server base class and a client stub in every language you need, so calling a remote service looks like calling an object — while the contract stays a single file both sides compile against.

Underneath, each call is one HTTP/2 stream. The method is the path (/orders.OrderService/GetOrder), metadata are headers, the body is a sequence of length-prefixed protobuf messages, and the outcome arrives in trailers — headers sent after the body — which is how a stream that already began can still report a failure. Because a stream can carry many messages in either direction, four call shapes exist: unary, server streaming, client streaming and bidirectional.

What you gain is speed, small payloads, generated clients in a dozen languages, first-class streaming, and deadlines that propagate through a call chain. What you pay is a build step, a binary wire format you cannot read with curl, awkwardness from browsers, and a load-balancing problem that catches almost everyone: long-lived HTTP/2 connections do not spread across backends by themselves.

Architecture / mental model

A contract file, two generated halves, and one long-lived HTTP/2 connection carrying every call as its own stream.

Key concepts

Protocol BuffersThe IDL and the binary wire format: a schema both sides compile, and bytes neither side can read by eye.
Field numbersThe small integers that are the real identity of every field — names are only for humans.
The four call typesUnary, server streaming, client streaming and bidirectional — all on one HTTP/2 stream.
HTTP/2 streamsEach call is an independent stream on a shared connection — which is both the performance story and the load-balancing problem.
Status and trailersThe outcome arrives after the body, in trailers — a design choice with wide consequences.
MetadataKey-value pairs sent as HTTP/2 headers: auth tokens, trace context, tenant ids.
DeadlinesAn absolute point in time, sent with the call and propagated down the chain — not a per-hop timeout.
CancellationWhen a caller gives up, the whole subtree finds out and stops working.
ChannelThe client-side object holding the connection, name resolution and load-balancing policy — expensive, and meant to be shared.
Load balancingSpreading calls across backends when one connection carries all of them.
RetriesConfigured declaratively in the service config, with a budget — not hand-written at every call site.
Flow controlHTTP/2 windows stopping a fast producer from overwhelming a slow consumer, per stream and per connection.
InterceptorsMiddleware for calls: auth, logging, tracing, retries and error mapping in one place.
gRPC-WebHow browsers call gRPC at all, and why it cannot be the same protocol.
JSON transcodingServing the same service as a REST/JSON API from annotations in the proto file.
ReflectionThe server describing its own services at runtime, which is what makes grpcurl possible.
Message sizeThe 4 MB default receive limit, and why hitting it means you wanted streaming.
Schema evolutionAdding fields is safe, changing numbers and types is not, and both sides must be able to deploy independently.

Proto & code

The contract

syntax = "proto3";
package orders.v1;                       // version in the package: v2 can coexist

import "google/protobuf/timestamp.proto";

service OrderService {
  rpc GetOrder       (GetOrderRequest)    returns (Order);                 // unary
  rpc ListOrders     (ListOrdersRequest)  returns (stream Order);          // server streaming
  rpc ImportOrders   (stream Order)       returns (ImportSummary);         // client streaming
  rpc WatchOrders    (stream WatchRequest) returns (stream OrderEvent);    // bidirectional
}

message Order {
  reserved 4, 7 to 9;                    // deleted fields: never reuse these numbers
  reserved "legacy_total";

  string id                        = 1;  // 1-15 cost one byte — spend them on hot fields
  string customer_id               = 2;
  int64  total_cents               = 3;  // money as integer minor units, never float
  OrderStatus status               = 5;
  google.protobuf.Timestamp placed = 6;
  repeated OrderLine lines         = 10;
}

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;          // zero value MUST be the unknown case
  ORDER_STATUS_DRAFT       = 1;
  ORDER_STATUS_PLACED      = 2;
  ORDER_STATUS_SHIPPED     = 3;
}

message GetOrderRequest  { string id = 1; }
message ListOrdersRequest { string customer_id = 1; int32 page_size = 2; string page_token = 3; }
Four conventions that save years: version in the package, reserved numbers, an UNSPECIFIED zero enum value, and money as integers.

Server and client

// C# — the server: override the generated base, map errors to real status codes
public sealed class OrderServiceImpl(IOrderRepository repo) : OrderService.OrderServiceBase
{
    public override async Task<Order> GetOrder(GetOrderRequest request, ServerCallContext context)
    {
        if (string.IsNullOrWhiteSpace(request.Id))
            throw new RpcException(new Status(StatusCode.InvalidArgument, "id is required"));

        // honour the caller's deadline and cancellation all the way down
        var order = await repo.FindAsync(request.Id, context.CancellationToken);

        return order is null
            ? throw new RpcException(new Status(StatusCode.NotFound, $"no order {request.Id}"))
            : order.ToProto();
    }

    public override async Task ListOrders(ListOrdersRequest request,
        IServerStreamWriter<Order> responseStream, ServerCallContext context)
    {
        await foreach (var order in repo.StreamAsync(request.CustomerId, context.CancellationToken))
            await responseStream.WriteAsync(order.ToProto());   // awaiting = flow control works
    }
}

// Program.cs
builder.Services.AddGrpc(o => o.MaxReceiveMessageSize = 4 * 1024 * 1024);
builder.Services.AddGrpcHealthChecks();
var app = builder.Build();
app.MapGrpcService<OrderServiceImpl>();
app.MapGrpcHealthChecksService();
if (app.Environment.IsDevelopment()) app.MapGrpcReflectionService();   // dev only
Two things carry the reliability: mapping exceptions to meaningful status codes, and passing context.CancellationToken into every downstream call.
// C# — the client: ONE channel for the process, with retries and load balancing
builder.Services
    .AddGrpcClient<OrderService.OrderServiceClient>(o =>
    {
        o.Address = new Uri("dns:///orders.internal:5001");    // all addresses, not one VIP
    })
    .ConfigureChannel(c =>
    {
        c.Credentials = ChannelCredentials.SecureSsl;
        c.ServiceConfig = new ServiceConfig
        {
            LoadBalancingConfigs = { new RoundRobinConfig() }, // default is pick_first: ONE backend
            MethodConfigs =
            {
                new MethodConfig
                {
                    Names = { MethodName.Default },
                    RetryPolicy = new RetryPolicy
                    {
                        MaxAttempts = 3,
                        InitialBackoff = TimeSpan.FromMilliseconds(100),
                        MaxBackoff = TimeSpan.FromSeconds(1),
                        BackoffMultiplier = 2,
                        RetryableStatusCodes = { StatusCode.Unavailable },   // NOT Internal, NOT Aborted
                    },
                },
            },
        };
    });

// at the call site: always a deadline. the default is infinity.
var order = await client.GetOrderAsync(
    new GetOrderRequest { Id = "ORD-9802" },
    deadline: DateTime.UtcNow.AddMilliseconds(500),
    cancellationToken: ct);
Three defaults that need changing in every deployment: pick_first, no retry policy, and an infinite deadline.
# Python — async server and client, same contract
import grpc
from grpc import aio
import orders_pb2, orders_pb2_grpc

class OrderService(orders_pb2_grpc.OrderServiceServicer):
    async def GetOrder(self, request, context: aio.ServicerContext) -> orders_pb2.Order:
        if not request.id:
            await context.abort(grpc.StatusCode.INVALID_ARGUMENT, "id is required")

        remaining = context.time_remaining()            # the caller's budget, in seconds
        order = await repo.find(request.id, timeout=remaining)
        if order is None:
            await context.abort(grpc.StatusCode.NOT_FOUND, f"no order {request.id}")
        return order.to_proto()

    async def ListOrders(self, request, context):
        async for order in repo.stream(request.customer_id):
            if context.cancelled():                     # the caller gave up: stop working
                return
            yield order.to_proto()

# the client: one channel per target, reused for the process lifetime
channel = aio.insecure_channel(
    "dns:///orders.internal:5001",
    options=[("grpc.lb_policy_name", "round_robin"),
             ("grpc.max_receive_message_length", 4 * 1024 * 1024),
             ("grpc.keepalive_time_ms", 30_000)],
)
client = orders_pb2_grpc.OrderServiceStub(channel)

order = await client.GetOrder(orders_pb2.GetOrderRequest(id="ORD-9802"), timeout=0.5)
context.time_remaining() is the propagated budget — pass it to whatever you call next instead of inventing a new timeout.

grpcurl -plaintext localhost:5001 list
grpcurl -plaintext localhost:5001 list orders.v1.OrderService
grpcurl -plaintext localhost:5001 describe orders.v1.Order

grpcurl -plaintext -d '{"id":"ORD-9802"}' \
        -H 'authorization: Bearer TOKEN' \
        -max-time 2 \
        localhost:5001 orders.v1.OrderService/GetOrder

# without reflection, compile a descriptor set and point at it
buf build -o descriptors.binpb
grpcurl -protoset descriptors.binpb -d '{"id":"ORD-9802"}' orders.internal:5001 orders.v1.OrderService/GetOrder

# health check — the standard service probes and balancers use
grpcurl -plaintext localhost:5001 grpc.health.v1.Health/Check
Reflection is what makes gRPC debuggable at all; without it you cannot hand-construct a request, because there are no field names on the wire.
# diagnosing the classic problems
GRPC_VERBOSITY=debug GRPC_TRACE=http,channel,subchannel ./myclient   # what the channel is doing

# "gRPC is slow" — is one backend taking everything?
kubectl exec deploy/client -- grpcurl -plaintext localhost:5001 grpc.health.v1.Health/Check
kubectl top pods -l app=orders        # 90% CPU on ONE pod and idle on the others = L4 balancing

# headless Service: returns every pod IP, so round_robin has something to round-robin over
kubectl get endpoints orders-headless -o wide
If one pod is hot and the rest idle while connection counts look even, it is connection-level balancing — not a capacity problem.

Pros & cons

Pros

  • Small, fast payloads: typically 3–10× smaller than JSON and much quicker to parse.
  • One contract generates typed clients and servers in a dozen languages.
  • HTTP/2 multiplexing: thousands of concurrent calls over one connection, no head-of-line blocking.
  • Streaming in all four directions is first-class, with transport-level flow control.
  • Deadlines and cancellation propagate through the call tree automatically.
  • Retries, backoff, retry budgets and load-balancing policy are declarative configuration.
  • A rich, precise status code vocabulary that makes correct client behaviour possible.

Cons

  • Binary on the wire: no curl, no readable logs, no debugging without the schema.
  • A code-generation step in every build, in every language.
  • Browsers need gRPC-Web, which drops client and bidirectional streaming.
  • L4 load balancers do not spread load, and the failure is invisible on connection metrics.
  • Proxies, gateways and WAFs need explicit HTTP/2 and trailer support.
  • HTTP-status-based monitoring reports healthy while every call fails.
  • Breaking changes to field numbers corrupt data silently rather than failing loudly.

Concrete use cases

Internal service-to-service calls

Twenty services in four languages. One proto repository is the contract, clients are generated, deadlines propagate across the whole call tree, and payloads are a fraction of the JSON equivalent — which at a million calls a minute is real money.

Streaming a large result set

An export that would be a 300 MB JSON response becomes a server-streaming call: the client processes records as they arrive, neither side buffers the whole thing, and flow control stops a fast producer from drowning a slow consumer.

Telemetry ingestion

Thousands of agents each hold one connection and client-stream metrics continuously. One connection per agent, no per-request handshake, and backpressure handled by the transport rather than by an application queue.

Control planes

A bidirectional stream between a central controller and every node: config pushed down, state reported up, on one long-lived connection. It is the model xDS uses, and the reason service meshes are built this way.

One service, two surfaces

Internal callers use native gRPC; the browser and partners get REST and JSON through transcoding annotations in the same proto file. One implementation, one contract, no duplicated handlers.

When to use / when not to

inside the fence: gRPC. facing the public internet: think hard, then probably REST.

Use it when…

  • Services call each other frequently and latency and payload size matter.
  • Several languages must share one contract, with generated clients.
  • Streaming is part of the problem rather than an afterthought.
  • You want deadlines, cancellation and retry budgets from the platform rather than from your code.
  • Both sides of the wire are yours, so a binary format costs nothing in discoverability.

Avoid it when…

  • Browsers are a primary client. Use REST, or JSON transcoding in front of the same service.
  • You are publishing a public API for third parties. Use REST — curl and a browser tab are the real onboarding path.
  • Clients need to choose their own response shape. Use GraphQL.
  • Traffic is naturally asynchronous and should survive a restart. Use a message broker.
  • Your infrastructure cannot do HTTP/2 end to end, including trailers. Fix that first.
  • It is two services and a handful of calls. The build step and tooling will cost more than they save.

Common mistakes & gotchas

No deadlineThe default is infinity. A slow dependency means calls that never return, threads and connections held for ever, and an outage that spreads upstream one service at a time.
Fix: set a deadline on every call, propagate the remaining budget downstream instead of starting a fresh timeout, and alert on DEADLINE_EXCEEDED rates per method.
A channel per callEach call does DNS, TCP and TLS, so latency is dominated by setup, ports run out under load, and HTTP/2 multiplexing never happens at all.
Fix: one channel per target for the process lifetime. In .NET use AddGrpcClient; in Python create the channel at startup and share it.
Behind an L4 load balancerConnections distribute perfectly and requests do not distribute at all. One backend sits at 90% CPU, newly scaled pods receive nothing, and every connection-based dashboard looks healthy.
Fix: client-side round_robin over a headless DNS name, or an L7 proxy or sidecar balancing per request. If neither is possible, set a maximum connection age so clients re-dial.
Reusing a field numberField 4 was legacy_total and is now discount_code. An old client's integer is parsed as a string. No error, no log line — just wrong data in production.
Fix: reserved every deleted number and name, and run buf breaking in CI against the deployed schema.
Everything is UNKNOWNUnhandled exceptions all surface as status 2. Callers cannot distinguish a bad request from a transient failure, so they either retry everything or nothing.
Fix: a server interceptor that maps domain exceptions to proper codes — INVALID_ARGUMENT, NOT_FOUND, FAILED_PRECONDITION, UNAVAILABLE — and never leak stack traces in the message.
Retrying unsafe codesINTERNAL and ABORTED are added to the retry policy because they look transient. A mutation that already ran is replayed, and an order is placed twice.
Fix: retry UNAVAILABLE, and RESOURCE_EXHAUSTED with backoff. Make mutations idempotent with a key, and keep the retry throttling budget enabled.
Ignoring the cancellation tokenThe caller gave up two seconds ago; the handler is still querying the database and will serialise a response nobody will read. Under load, all the capacity is spent on abandoned work.
Fix: thread ServerCallContext.CancellationToken (or check context.cancelled()) into every downstream call and loop. It is free load shedding.
Monitoring HTTP statusEvery gRPC response is HTTP 200, including failures — the real outcome is in the grpc-status trailer. Dashboards show 100% availability during a complete outage.
Fix: instrument on grpc-status per method, and make sure your proxy and APM actually read trailers rather than the response line.
Raising the message size limitA response exceeds 4 MB, so the limit is raised to 100 MB. Now both sides allocate 100 MB buffers, the call cannot report progress, and cancelling it frees nothing.
Fix: switch to server streaming with 32–256 KB messages. Raise the limit only when a single logical message genuinely is that large — and consider object storage with a signed URL instead.
Keepalive that gets you bannedA client pings every five seconds to detect dead connections. The server's keepalive enforcement considers that abusive and sends GOAWAY with ENHANCE_YOUR_CALM, so connections drop constantly.
Fix: keep client ping intervals at 30 seconds or more, and configure the server's minimum permitted interval to match. Both sides must agree.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs gRPC
gRPCinternal service-to-service, streamingMediumfree, Apache 2.0—
REST + JSONpublic APIs, browsers, anything debuggableLowfreeHuman-readable, cacheable, universal — larger, slower, untyped
GraphQLmany clients wanting different shapesMedium–HighfreeClient chooses the response; server-chosen here, and far more predictable
Message brokerasynchronous, durable workMediuminfrastructureDecoupled and replayable; not a request/response call at all
WebSocket + custom protocolbrowser-facing real timeMediumfreeWorks everywhere in a browser; you invent framing, typing and error handling
Thriftexisting Thrift estatesMediumfreeSimilar idea, smaller ecosystem, no HTTP/2 streaming story
Cap'n Proto / FlatBufferszero-copy, latency-criticalHighfreeNo parse step at all; much smaller ecosystems and tooling
  • Pick REST for anything public or browser-facing — or expose both from one proto with JSON transcoding.
  • Pick GraphQL when the problem is clients needing different slices of related data, not raw call efficiency.
  • Pick a broker such as Kafka when the work should survive the caller going away.
  • Pick WebSockets when the real-time client is a browser and gRPC-Web's limits bite.
  • Use gRPC and REST together: native gRPC inside, transcoded JSON at the edge. It is the common and comfortable arrangement.
