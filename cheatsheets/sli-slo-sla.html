SLI, SLO & SLA

Measure what users feel, promise a number you can keep, sign only what you can afford to break.

As of Nov 2026 · vocabulary from Google SRE; examples use Prometheus, OpenSLO and Sloth

"Is the service up?" is not a question with an answer. Something is always failing for someone, so the only honest version is "what fraction of the things users tried actually worked, and is that fraction good enough?" The three letters answer that in order: an SLI is the measurement, an SLO is the target you hold yourselves to, and an SLA is the much weaker promise you make to a customer with money attached.

The mechanism that makes them useful is the error budget: the difference between 100% and your SLO. A 99.9% objective over 28 days is not "do not fail" — it is an explicit allowance of about 40 minutes of failure, or 0.1% of requests, that you are free to spend on deploys, migrations and risk. When the budget is healthy you ship; when it is gone you stop shipping and fix things. That turns an argument about feelings into arithmetic.

This is the backbone of SRE practice at Google, and it has been copied nearly everywhere: the same three terms show up in cloud provider contracts, in platform team charters and in tools like Prometheus, Datadog, Grafana and Nobl9. None of it requires a big organisation — a single team with one SLI per critical user journey already gets most of the benefit.

Architecture / mental model

One journey, one ratio, one target, one budget — and a contract that always sits a comfortable step below what you actually aim for.

Key concepts

SLIA Service Level Indicator: a ratio of good events to valid events, expressed as a percentage of things that worked.
Valid eventsThe denominator: the events that count towards the SLI at all. Everything else is excluded, not counted as bad.
SLOA Service Level Objective: the target value of an SLI over a stated window, chosen internally and with no contractual force.
SLAA Service Level Agreement: a contract with a customer stating a service level and the financial consequence of missing it.
Error budgetThe amount of unreliability the SLO permits in a window: 100% minus the SLO, expressed in bad events or in minutes.
Burn rateHow fast the error budget is being consumed, relative to the rate that would exactly exhaust it over the full window.
Availability SLIThe share of valid requests that did not fail: the default SLI, and usually the first one a team writes.
Latency SLIThe share of requests served faster than a threshold — a ratio, not a percentile.
Rolling windowThe trailing period the SLI is evaluated over — typically 28 days, moving forward continuously instead of resetting.
NinesShorthand for availability targets — 99.9% is "three nines" — and the downtime each one allows.
Critical user journeyA specific thing a user is trying to accomplish, used as the unit an SLI is defined around. Often abbreviated CUJ.
Error budget policyThe agreement, written before anything breaks, that says what the team does at each level of budget consumption.
Multi-window alertAn alert that fires only when a high burn rate shows up in both a long qualifying window and a short confirming window.
Composite availabilityWhat happens to a target when a journey depends on several services in series: the availabilities multiply.
Service creditsThe usual remedy in an SLA: a percentage of the bill refunded when the target is missed, capped and claimed by the customer.

Essential formulas & queries

Arithmetic

error_budget   = 1 - SLO                      # 99.9% -> 0.001
budget_minutes = (1 - SLO) * window_minutes   # 0.001 * 40320 = 40.3 min
budget_events  = (1 - SLO) * valid_events     # 0.001 * 40M   = 40,000
Turn an objective into a spendable allowance, in time or in events.
burn_rate = observed_error_rate / (1 - SLO)
# 1.44% errors against a 99.9% SLO -> 0.0144 / 0.001 = 14.4x
time_to_exhaustion = window * budget_remaining / burn_rate
Burn rate, and how long you have left at the current rate.
journey_availability = A1 * A2 * A3         # series: 0.999^3 = 99.70%
redundant_pair       = 1 - (1 - A) ** 2     # parallel: 99% -> 99.99%
Composite availability for dependencies in series and in parallel.

Alert rules

- alert: CheckoutBudgetBurnFast
  expr: |
    slo:burn_rate1h{slo="checkout"} > 14.4
    and
    slo:burn_rate5m{slo="checkout"} > 14.4
  for: 2m
  labels:
    severity: page
  annotations:
    summary: "2% of the 28d budget burned in an hour"
Fast burn: long window qualifies, short window confirms it is still happening. Pages.
- alert: CheckoutBudgetBurnSlow
  expr: |
    slo:burn_rate1d{slo="checkout"} > 3
    and
    slo:burn_rate2h{slo="checkout"} > 3
  for: 15m
  labels:
    severity: ticket
Slow burn: a leak that would exhaust the budget in about ten days. Creates work, does not wake anyone.

Declaring SLOs as code

apiVersion: openslo/v1
kind: SLO
metadata:
  name: checkout-availability
spec:
  service: checkout
  objectives:
    - displayName: non-5xx
      target: 0.999
  timeWindow:
    - duration: 28d
      isRolling: true
OpenSLO: a vendor-neutral YAML spec for an SLO, reviewable in a pull request.
sloth generate -i slos.yaml -o rules.yaml
promtool check rules rules.yaml
Generate the recording and alerting rules from an SLO definition, then validate them before committing.

Python

WINDOW_MIN = 28 * 24 * 60          # 40320

def budget(slo: float) -> float:
    return (1 - slo) * WINDOW_MIN

def burn(errors: int, valid: int, slo: float) -> float:
    return (errors / valid) / (1 - slo)

def hours_left(remaining: float, burn_rate: float) -> float:
    return (WINDOW_MIN / 60) * remaining / burn_rate

print(f"{budget(0.999):.1f} min")                 # 40.3 min
print(f"{burn(1440, 100_000, 0.999):.1f}x")       # 14.4x
print(f"{hours_left(0.75, 14.4):.1f} h left")     # 35.0 h left
The whole model in ten lines — enough to sanity-check any SLO dashboard.

Pros & cons

Pros

  • Replaces "the site feels slow" with a number both engineering and product can act on.
  • The error budget makes the reliability-versus-velocity trade-off explicit and pre-agreed, instead of relitigated per incident.
  • Burn-rate alerts cut pager noise sharply: you are woken for budget damage, not for every threshold crossing.
  • Scale-free — the same thresholds work for 10 rps and 10,000 rps.
  • Gives a principled answer to "should we invest in reliability this quarter?": look at how often the budget ran out.
  • Forces the question "what are users actually trying to do?" before the question "which dashboard?".

Cons

  • Useless without an error budget policy that someone actually enforces; otherwise it is a prettier dashboard.
  • Low-traffic services give statistically meaningless ratios — 200 requests a day cannot measure three nines.
  • Picking the denominator is subtle, and sloppy exclusions make the SLO unfalsifiable.
  • Needs reliable, high-cardinality telemetry retained over long windows, which is not free to store.
  • Easy to proliferate: 40 SLOs across 40 microservices tells you nothing a user would recognise.
  • Targets copied from other companies ("we want four nines") are almost always unaffordable and quickly ignored.

Concrete use cases

Ending the release-freeze argument

A payments team argues before every release about whether it is safe to ship. They define one SLO on the checkout journey and an error budget policy: above 50% remaining, ship; below 20%, only fixes. The argument becomes a glance at a number, and the freeze now ends automatically when the window rolls forward.

Cutting pager noise

An on-call rotation is paged 30 times a month by static "error rate above 1% for 5 minutes" rules, mostly for blips. Replacing them with two multi-window burn-rate alerts — 14.4× paging, 3× ticketing — drops pages to a handful, and every remaining one corresponds to real budget being destroyed.

Setting a contract you can survive

Sales wants to promise 99.99% to land an enterprise deal. Measurement shows the service delivers 99.93% and depends on three components at 99.9% each, so composite maths caps the journey near 99.7%. The team signs a 99.5% SLA with a 99.9% internal SLO, and funds the redundancy work needed before the next tier is offered.

Prioritising reliability work

A platform team cannot justify a quarter of hardening work. They show that the budget was exhausted in four of the last six windows, always from the same two causes. That converts "we should improve reliability" into a costed, bounded project with a measurable exit condition.

Making a batch pipeline accountable

A nightly export has no requests to count, so the SLI becomes freshness: the share of days the file landed before 06:00, over a rolling 90 days. A 98% target gives roughly two acceptable late days a quarter — and a clear signal when the third one happens.

When to use / when not to

one SLI per user journey, one policy per budget — everything else is reporting

Use it when…

  • Users feel the difference between working and broken, and someone is on call for it.
  • Traffic is high enough that a ratio is meaningful — roughly thousands of events per window per objective.
  • You need to arbitrate between shipping speed and stability repeatedly, not once.
  • You are about to sign a contract and need to know what you can actually deliver.
  • Alert fatigue is a problem and your thresholds are static.

Avoid it when…

  • The service handles a handful of events per day. Use simple uptime checks and a synthetic probe instead.
  • Nobody will enforce the budget. Use a plain incident review process — an unenforced SLO is worse than none.
  • What you care about is per-record correctness, not aggregate success. Use data quality checks and reconciliation.
  • You are measuring an internal component nobody consumes directly. Use the consuming journey's SLO and derive a component budget from it.
  • The system is pre-product-market-fit and changing weekly. Use basic error alerts and rate limiting until the shape settles.

Common mistakes & gotchas

Setting the SLA equal to the SLOIf the contract promises exactly what you aim for internally, the first ordinary bad week triggers credits and there is no room left to be merely imperfect.
Fix: keep at least one step of gap. Internal 99.95%, contractual 99.9%, and never quote the internal number to a customer.
Measuring at the wrong placeApplication-level metrics cannot see the outage where the pods crash-looped and the load balancer returned 503: the requests never reached your code, so the SLI looks perfect during the incident.
Fix: measure at the ingress or load balancer at minimum, and reconcile against a synthetic probe that exercises DNS and TLS too.
Treating a p99 as a latency SLIPercentiles cannot be averaged or summed, so a p99-based objective cannot be aggregated across services or converted into a budget of bad events.
Fix: define latency as "x% of requests faster than T". Keep the percentile chart for debugging, not for the objective.
An SLO per microserviceForty green service dashboards while checkout is broken is the normal outcome: no individual service owns the user's experience.
Fix: start from three to five critical user journeys. Derive component targets from them, not the other way round.
Excluding your way to successEvery incident ends with another exclusion — maintenance windows, "customer-caused", a bad region — until the SLI can no longer go down.
Fix: list exclusions in one reviewed document, require a reason for each, and track how much traffic the exclusions remove.
Alerting on the window, not the burn"SLO breached over 28 days" fires once the damage is already done and then stays firing for weeks; it is a report, not an alert.
Fix: alert on multi-window burn rate (14.4× and 6× to page, 3× and 1× to ticket) and keep the 28-day number on a dashboard.
Ignoring dependency mathsPromising 99.99% for a journey that traverses four components each promising 99.9% is arithmetically impossible — the ceiling is about 99.6%.
Fix: multiply the component availabilities first. If the product is below your target, add redundancy or graceful degradation before you set the number.
A budget that never gets spentConsistently finishing a window at 99.999% against a 99.9% SLO is not a triumph; it means you are over-engineering, deploying too cautiously or measuring something users do not care about.
Fix: tighten the SLO, or deliberately spend the budget on faster releases, chaos testing or a migration you have been postponing.

ApproachBest forComplexityCost / licenseKey difference vs SLI/SLO/SLA
SLI / SLO / SLAuser-facing services with real trafficMediumfree concept; cost is telemetry—
Uptime monitoringsmall sites, status pagesLowa few $/monthBinary up/down from one probe; no budget, no user-weighted ratio
ApdexAPM latency summariesLowbundled with APMSingle blended score with satisfied/tolerating bands; not spendable, hides the shape
MTBF / MTTRhardware, physical operationsLowfreeMeasures incidents, not request outcomes; blind to partial degradation
DORA metricsdelivery performance of a teamMediumfreeMeasures how you ship, not what users experience; complementary, not a substitute
Synthetic monitoringjourneys with little organic trafficMediumper-check pricingGenerates its own events, so it works at low volume but reflects a robot, not users
  • Pick uptime monitoring if the service is small, traffic is thin and "is it reachable?" is genuinely the whole question.
  • Pick Apdex if you already live inside an APM tool and want a quick latency summary rather than an enforceable target.
  • Pick MTBF/MTTR if you are reporting on incident response maturity rather than on service quality.
  • Pick DORA metrics alongside SLOs — they answer "how fast do we ship?" while the budget answers "may we?".
  • Pick synthetic monitoring as the SLI source when a critical journey simply does not get enough real traffic to measure.
