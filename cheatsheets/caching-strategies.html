Caching strategies

Keep the answer near the question — and decide, up front, how wrong you are willing to be.

As of Nov 2026 · patterns are timeless; the examples are .NET 9+, Redis and HTTP

A cache is a second copy of data, placed closer to the reader than the system of record. It converts a slow, expensive, contended operation — a join across three tables, a call to a partner API, rendering a PDF — into a key lookup that costs a fraction of a millisecond. Done well, it is the single highest-leverage performance change available to most systems.

The strategy is not "use Redis". It is the set of four decisions you make about that second copy: who fills it (cache-aside, read-through, refresh-ahead), what happens on writes (write-through, write-behind, write-around, or just invalidate), when entries die (TTL, eviction policy, explicit invalidation), and how stale is too stale. Get those wrong and a cache turns a correctness problem into an intermittent, unreproducible one.

Caches exist at every layer at once: CPU and ORM caches inside a process, an in-memory cache per instance, a shared distributed cache such as Redis, a CDN at the edge, and the browser. Each layer has its own hit ratio, its own staleness, and its own invalidation problem — which is why "just add a cache" is rarely a one-line change.

Architecture / mental model

A cache is not a layer you add; it is four decisions you make. The last one — how stale a value may be — determines the other three.

How it works

Six patterns, all drawn in the same three boxes — your app, the cache, PostgreSQL — so you can see exactly which arrow moves and who waits. The first three are read paths (who fills the cache); the last three are write paths (what happens to the cache when data changes). A comparison follows at the end.

Comparing them

The read paths differ in where the loading code lives and who pays for a miss. The write paths differ in what the cache holds afterwards and what you can lose.

The things that are easy to miss until you see them side by side:

  • Cache-aside and read-through have the same read path. The arrows differ only in who owns the loading code — your call site, or the cache library. The real difference shows up under concurrency: 500 simultaneous misses run 500 queries with cache-aside, and one with read-through.
  • Write-through and write-behind differ by one word: await. That one word is the difference between a 16 ms write that can never be lost and a 0.3 ms write that can.
  • Write-around is the one that deletes rather than writes. That is not laziness — a DEL is idempotent and can never be stale, while a SET can store a value you computed before someone else's update. The invalidation deep dive animates exactly that failure.
  • They compose. The common production combination is cache-aside reads + write-around writes + a TTL as a backstop, which is what most codebases end up with whether or not anyone named it.

The failure mode all three read paths share

Cache stampede: one expiry, a thousand misses

Key concepts

hit ratioThe fraction of lookups answered by the cache. It decides the average latency and, more importantly, how much load reaches the thing behind it.
cache-asideAlso "lazy loading". Your code checks the cache, and on a miss reads the source and populates the cache itself. The cache knows nothing about the database.
read-throughThe cache sits in front of the source and loads missing entries itself. Your code only ever talks to the cache.
write-throughWrites go to the cache and to the source synchronously, before the caller is acknowledged. Cache and database never disagree.
write-behindAlso "write-back". The write is acknowledged as soon as the cache holds it, and flushed to the source later, usually in batches.
write-aroundWrites go straight to the source and simply invalidate (or skip) the cache. The entry is only populated when somebody actually reads it.
refresh-aheadRefresh popular entries before they expire, in the background, so that no user request ever pays for a miss.
TTLTime to live: how long an entry may be served before it is discarded. The simplest, most robust correctness backstop you have.
eviction policyWhat gets thrown out when the cache is full: least recently used, least frequently used, FIFO, or something smarter. Eviction is not expiry.
invalidationRemoving or replacing an entry because the underlying data changed. The hard half of caching, and the source of the subtlest bugs.
cache stampedeAlso "dogpile" or "thundering herd". A hot key expires and every concurrent request misses at once, hitting the source with the full, uncached load.
stale-while-revalidateServe the expired value immediately and refresh it in the background. Latency stays flat; the price is a bounded window of known staleness.
negative cachingCaching the fact that something does not exist, so that repeated lookups for missing keys do not hammer the source.
cache hierarchySeveral caches in series — browser, CDN, in-process, distributed — each with its own hit ratio, TTL and invalidation story.
key designThe cache has no schema, so the key naming convention is the schema. It decides cardinality, invalidation granularity and hit ratio.
consistencyHow far the cached copy may drift from the source, and for how long. This is a product decision wearing a technical costume.
HTTP cachingThe cache you get for free: Cache-Control, ETag and conditional requests, honoured by browsers, proxies and CDNs without any code.

Essential commands & syntax

.NET — HybridCache (read-through, two tiers, stampede-safe)

builder.Services.AddStackExchangeRedisCache(o => o.Configuration = conn);
builder.Services.AddHybridCache(o =>
{
    o.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration      = TimeSpan.FromMinutes(5),   // distributed (L2)
        LocalCacheExpiration = TimeSpan.FromSeconds(20)  // in-process (L1)
    };
});
Registers the L1 + L2 cache. L1 keeps a short TTL because it cannot be invalidated reliably.
var product = await cache.GetOrCreateAsync(
    $"product:{id}:v3",
    async ct => await db.LoadProductAsync(id, ct),
    tags: [$"product:{id}"], cancellationToken: ct);
Read-through with built-in single-flight: 500 concurrent callers run the factory once.
await cache.RemoveByTagAsync($"product:{id}");
Tag invalidation: drops every cached view derived from that product, across both tiers.
await cache.SetAsync(key, value, new HybridCacheEntryOptions
    { Expiration = TimeSpan.FromMinutes(5), Flags = HybridCacheEntryFlags.DisableLocalCache });
Writes to the distributed tier only — for values that must not linger in a process-local copy.

.NET — the lower-level pieces

services.AddMemoryCache();
cache.Set("flags", value, new MemoryCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(30),
    Size = 1
});
In-process only. Set SizeLimit on the cache and Size per entry, or it grows until the process dies.
await distributed.SetStringAsync(key, json, new DistributedCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5),
    SlidingExpiration = TimeSpan.FromMinutes(1)
});
Classic cache-aside against Redis. No stampede protection — you add that yourself.
app.UseOutputCache();
app.MapGet("/products", Handler).CacheOutput(p => p.Expire(TimeSpan.FromSeconds(30)).Tag("products"));
// later:  await outputCacheStore.EvictByTagAsync("products", ct);
Caches the whole rendered response server-side, with tag-based eviction.

Redis — the cache primitives

SET product:42 "{...}" EX 300
Store with a 5-minute TTL. Add jitter to 300 so sibling keys do not expire together.
SET lock:product:42 1 NX EX 10
Single-flight lock: only the first caller gets OK and rebuilds; the rest wait or serve stale.
GET product:42
TTL product:42
DEL product:42
Read, check the remaining life, invalidate. DEL on write, never SET.
CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lru
Cap the memory and choose what gets evicted. A pure cache wants allkeys-lru or allkeys-lfu.
INFO stats | grep -E "keyspace_hits|keyspace_misses|evicted_keys"
The three numbers that tell you whether the cache is working, too small, or pointless.

HTTP and CDN

Cache-Control: public, max-age=60, stale-while-revalidate=600, stale-if-error=86400
Fresh for a minute, served stale while refreshing for ten, and kept alive for a day if the origin is down.
Cache-Control: private, no-store
The correct header for anything personal. no-cache is not this.
curl -sI https://example.com/api/products | grep -iE "cache-control|age|etag|x-cache"
Checks what is actually being sent and whether the CDN reports a hit. Age tells you how long it has been cached.

Python — cache-aside with stampede protection

import json, random, redis
r = redis.Redis()

def get_product(pid, ttl=300):
    key = f"product:{pid}:v3"
    if (hit := r.get(key)) is not None:
        return json.loads(hit)
    if r.set(f"lock:{key}", 1, nx=True, ex=10):          # single-flight
        value = load_from_db(pid)
        r.set(key, json.dumps(value), ex=ttl + random.randint(0, 30))  # jitter
        r.delete(f"lock:{key}")
        return value
    time.sleep(0.05)                                      # someone else is rebuilding
    return get_product(pid, ttl)
The whole pattern in one function: lookup, lock, load, jittered TTL, back off if another worker is already rebuilding.

Pros & cons

Pros

  • Latency improvements of 10–1000x on read paths, usually for a few dozen lines of code.
  • Takes load off the hardest component to scale: the database.
  • Defers expensive scaling work — a cache is far cheaper than a read replica or a shard.
  • Absorbs traffic spikes that would otherwise require autoscaling you cannot do fast enough.
  • With stale-if-error, it keeps the product readable through a complete backend outage.
  • Cuts cost directly when the cached thing is metered: a partner API, an LLM call, an egress charge.

Cons

  • Every cache introduces staleness, and staleness bugs are intermittent and hard to reproduce.
  • Invalidation is genuinely hard, and gets harder with each layer you add.
  • It hides a performance problem rather than fixing it — a missing index stays missing.
  • A cold or flushed cache can take down a system that has quietly been running at 50x its true capacity.
  • A distributed cache is one more thing to operate, secure, size and fail over.
  • Debugging gets harder: "works for me" now also means "my cache has a different copy".

Concrete use cases

Product catalogue on an e-commerce site

The product page joins six tables and renders at 180 ms. Cache-aside against Redis with a 10-minute TTL takes it to 3 ms and removes 98% of the database read load. Writes from the back office publish an outbox event that deletes the key by tag, so a price change is visible in under a second rather than in ten minutes.

Feature flags and configuration

Every request reads a dozen flags. A process-local MemoryCache with a 15-second absolute TTL means the flag service sees four requests per minute per instance instead of thousands per second, and a kill switch still takes effect within 15 seconds — the staleness budget written into the design.

Write-heavy counters

A video platform counts views. Writing each view to the database would be 40,000 writes per second of contention on one row. The counter is incremented in Redis and flushed as a write-behind batch every two seconds, turning it into roughly one UPDATE per video per flush. Losing two seconds of view counts in a crash is acceptable; losing two seconds of payments would not be.

Expensive third-party API

A geocoding provider charges per call and takes 400 ms. Addresses barely change, so results are cached for 30 days keyed by the normalised address string, with negative results cached for an hour. The hit ratio settles at 94%, which is also a 94% reduction in the bill.

CDN in front of an API

A public read-only endpoint serves the same JSON to millions of clients. Cache-Control: public, max-age=60, stale-while-revalidate=600 moves almost all of that traffic to the edge. Origin traffic becomes one request per point of presence per minute, and stale-if-error keeps the endpoint answering during a deploy that goes wrong.

When to use / when not to

Cache when reads outnumber writes and a slightly old answer is still a good answer.

Cache when…

  • The same value is read far more often than it changes — a read:write ratio above roughly 10:1.
  • Computing it is expensive: joins, aggregations, rendering, a remote call.
  • A value that is a few seconds or minutes old is still correct enough for the user.
  • Traffic is spiky and the source cannot be scaled up fast enough to follow it.
  • The source is metered or rate-limited and you need to stay under the cap.
  • You can name the invalidation trigger. If you cannot, at least pick a TTL you can defend.

Avoid it when…

  • Staleness is a correctness bug: balances, stock at checkout, permissions. Read the source, or use a short-TTL write-through with synchronous invalidation.
  • Every key is read once — per-request or per-user-session data. A cache here is pure overhead; fix the query instead.
  • The real problem is a missing index or an N+1. Fix the query; a cache just hides it until the cache misses.
  • The data is written far more often than read. Use write-around, or do not cache at all.
  • You would be caching personal data in a shared layer. Use private, no-store and per-user in-memory scope.
  • The source is already fast and not the bottleneck. Measure first; a cache in front of a 2 ms query buys nothing but bugs.

Common mistakes & gotchas

Updating the cache on write instead of deleting the keyTwo concurrent writers, or a slow reader racing a writer, can leave the older value in the cache, where it survives until the TTL. The invalidation deep dive animates exactly how.
Fix: delete on write and let the next read repopulate. If you must write through, include a version or timestamp and only overwrite when yours is newer.
No jitter on TTLsKeys created together expire together. A warm-up script, a deploy or a bulk import produces a synchronised wave of misses that the database experiences as a traffic spike from nowhere.
Fix: ttl = base + random(0, base * 0.1) everywhere. It costs one line and removes a whole class of incident.
No stampede protection on a hot keyThe homepage key expires and 2,000 in-flight requests all miss, all run the same 300 ms query, and exhaust the connection pool. The cache was doing its job right up to the moment it stopped.
Fix: single-flight (HybridCache does it for you, or a Redis SET NX lock), plus stale-while-revalidate so nobody waits at all.
An unbounded in-process cacheMemoryCache with no SizeLimit, or a plain ConcurrentDictionary used as a cache, grows until the container is OOM-killed. It usually survives testing and dies in production on a long-running pod.
Fix: always set a size limit and an absolute expiry, and give every entry a Size. Track evictions: if they are zero and memory is climbing, the cache is not bounded.
Caching per-user data under a shared keyA key like dashboard:summary that was written while user A was logged in gets served to user B. This is a data breach, not a bug, and CDNs make it a public one.
Fix: put the identity in the key, or mark the response private, no-store. Audit every public cache header on an authenticated route.
Caching errors and timeoutsA dependency times out, the code caches the empty result for five minutes, and a 2-second blip becomes a 5-minute outage that recovers on its own just as you start investigating.
Fix: only cache successful responses, and cache deliberate "not found" results with a short, separate TTL. Never cache an exception or a timeout.
No plan for a cold cacheA Redis failover, a flush or a deploy that bumps the key version sends 100% of traffic to a database sized for 2%. The cache coming back does not help, because the database is already saturated.
Fix: warm the top keys on startup, roll key-version changes gradually, and keep a concurrency limit in front of the database so a cold cache degrades instead of collapsing.
Forgetting that serialized shapes changeA new field is added to the cached DTO, the old JSON deserializes into a type that no longer matches, and the service throws on every cache hit until the TTL drains.
Fix: put a version segment in every key (product:42:v3) and bump it in the same commit that changes the shape.

Alternatives

ApproachBest forComplexityCostKey difference vs caching
Cachingrepeated reads of expensive, slowly changing dataLow–mediumcheap: memory—
Fix the query / add an indexa slow path that is slow for a findable reasonLowfreeMakes the source genuinely fast instead of avoiding it; no staleness at all
Read replicasread-heavy relational workloadsMediumanother database instanceFull query power on fresh-ish data; replication lag replaces TTL staleness
Materialized viewexpensive aggregations over stable dataMediumstorage + refresh costLives in the database, refreshed on a schedule; consistent and queryable
Precompute on writefan-out-on-write feeds, leaderboardsMedium–highwrite amplificationReads are always ready and always correct; writes get much more expensive
CDN / edge cachestatic assets and public responsesLowbandwidthSame idea, moved to the network edge; cannot cache personalised responses
Event-driven projectionsread models that must stay close to the sourceHighinfrastructureThe source pushes changes (Apache Kafka, CDC) instead of the reader polling or expiring
  • Fix the query first. A cache in front of an unindexed query is a liability you will discover on the day the cache is cold.
  • Pick read replicas if you need full query flexibility on nearly-fresh data rather than key lookups.
  • Pick a materialized view if the expensive thing is an aggregation and the database can refresh it for you.
  • Pick precompute-on-write if reads vastly outnumber writes and staleness is unacceptable.
  • Pick event-driven projections if invalidation keeps being the bug, and you would rather be told about changes than guess at TTLs.
  • These compose: a CDN in front of an application cache in front of an indexed query against a read replica is an ordinary production system.
