Model Context Protocol

A standard socket between a model and everything it is allowed to touch — so N×M integrations become N+M.

As of Nov 2026 · spec revision 2026-07-28 (stateless) · prior: 2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05

Before MCP, every assistant wired itself to every system by hand: one bespoke integration per model per tool. MCP replaces that with one protocol. A server exposes tools (things a model can do), resources (things it can read) and prompts (templates a user can invoke); any compliant client can discover and use them, whichever model sits behind it.

Messages are JSON-RPC 2.0 over one of two transports: stdio for a local process, Streamable HTTP for a remote service. The methods are few and boring on purpose — tools/list, tools/call, resources/read, prompts/get, server/discover — and the interesting content lives in the JSON Schemas and descriptions a server publishes for its tools.

The 2026-07-28 revision is the one to design against, and it is a real break from what most tutorials show. The protocol is now stateless: the initialize handshake and protocol sessions are gone, every request carries its own version and capabilities in _meta, and server-to-client requests have been replaced by multi round-trip requests. Roots, Sampling and Logging are deprecated.

Architecture / mental model

USB-C for model integrations: one plug shape, many devices, and the host decides what gets plugged in.

Key concepts

Hosts and serversThe host runs the model and owns policy; it creates one client per server; each server fronts one system.
Stateless coreSince 2026-07-28 there is no handshake and no session: every request carries its own version and capabilities.
_meta fieldsThe per-request envelope that carries protocol version, client capabilities and identity now that sessions are gone.
server/discoverThe method every server must implement, telling a client which versions, capabilities and extensions it supports.
ToolA named, schema-described action a model may invoke — the primitive that makes MCP interesting.
Tool descriptionThe prose the model reads to decide whether to call your tool — effectively a prompt you ship.
ResourceReadable content identified by a URI — files, rows, documents — that the host chooses to put in context.
PromptA named, parameterised message template the server offers and the user explicitly invokes.
Multi round-trip requestHow a server asks for something mid-call now that it cannot send requests to the client.
ElicitationThe client capability that lets a server ask the user a structured question mid-call.
Streamable HTTPThe remote transport: one endpoint, POST only, replying with JSON or an SSE stream.
stdio transportThe local transport: the host launches the server as a child process and talks over its pipes.
AuthorizationOptional in general, but for HTTP transports it is OAuth 2.1 with resource indicators and audience-bound tokens.
Trust boundaryConnecting a server grants a model the ability to act through it — with that server's credentials.
Tool poisoningInstructions hidden in tool descriptions or results that steer the model into doing something else.
ExtensionsOpt-in capabilities outside the core, negotiated by both sides — including Tasks, Skills and Apps.
DeprecationsRoots, Sampling, Logging and HTTP+SSE are on the way out, with a twelve-month minimum window.

Writing a server

// C# — ModelContextProtocol SDK, stdio transport
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using ModelContextProtocol.Server;
using System.ComponentModel;

var builder = Host.CreateApplicationBuilder(args);

builder.Logging.AddConsole(o => o.LogToStandardErrorThreshold = LogLevel.Trace);  // stderr ONLY

builder.Services
    .AddMcpServer()
    .WithStdioServerTransport()
    .WithToolsFromAssembly();

await builder.Build().RunAsync();

[McpServerToolType]
public static class OrderTools
{
    [McpServerTool(Name = "query_unpaid_orders")]
    [Description("""
        Returns unpaid orders for one customer, newest first, at most 100 rows.
        Use search_customers first if you only have a name, not an id.
        Returns an empty list if the customer exists but owes nothing.
        """)]
    public static async Task<IReadOnlyList<OrderSummary>> QueryUnpaidOrders(
        OrdersDb db,
        [Description("Customer id, e.g. CUST-4412")] string customerId,
        [Description("Maximum rows to return, 1-100")] int limit = 20,
        CancellationToken ct = default)
    {
        if (limit is < 1 or > 100)
            throw new ArgumentOutOfRangeException(nameof(limit), "limit must be between 1 and 100");

        return await db.Orders
            .Where(o => o.CustomerId == customerId && o.Status == OrderStatus.Unpaid)
            .OrderByDescending(o => o.CreatedAt)
            .Take(limit)
            .Select(o => new OrderSummary(o.Id, o.Total, o.CreatedAt))  // summarise: do NOT return rows
            .ToListAsync(ct);
    }
}
The description is the prompt. The bounded limit, the projection and the stderr-only logging are the three things people get wrong.
# Python — the official SDK's FastMCP server
import logging, sys
from dataclasses import dataclass
from mcp.server.fastmcp import FastMCP

logging.basicConfig(stream=sys.stderr, level=logging.INFO)   # stderr ONLY — stdout is the protocol

mcp = FastMCP("orders")

@dataclass
class OrderSummary:
    id: str
    total_eur: float
    created_at: str

@mcp.tool()
async def query_unpaid_orders(customer_id: str, limit: int = 20) -> list[OrderSummary]:
    """Return unpaid orders for one customer, newest first, at most 100 rows.

    Use search_customers first if you only have a name, not an id.
    Returns an empty list if the customer exists but owes nothing.
    """
    if not 1 <= limit <= 100:
        raise ValueError("limit must be between 1 and 100")

    rows = await db.fetch(
        "SELECT id, total, created_at FROM orders "
        "WHERE customer_id = $1 AND status = 'unpaid' "
        "ORDER BY created_at DESC LIMIT $2",
        customer_id, limit,                                   # parameterised: the schema is not a filter
    )
    return [OrderSummary(r["id"], float(r["total"]), r["created_at"].isoformat()) for r in rows]

if __name__ == "__main__":
    mcp.run()        # stdio by default
The docstring becomes the tool description and the type hints become the JSON Schema — which is why both deserve care.

What the protocol looks like

// tools/call on the 2026-07-28 revision — no handshake, version in _meta and in the header
// POST /mcp
//   Accept: application/json, text/event-stream
//   MCP-Protocol-Version: 2026-07-28
//   Authorization: Bearer eyJhbGciOi…
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "query_unpaid_orders",
    "arguments": { "customerId": "CUST-4412", "limit": 20 },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": { "elicitation": {} },
      "io.modelcontextprotocol/clientInfo": { "name": "my-ide", "version": "3.1" },
      "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
    }
  }
}
Every request is self-contained: no session id, no prior initialize, and a trace context that joins your existing spans.
// the two shapes a result can take
{ "jsonrpc": "2.0", "id": 7, "result": {
    "resultType": "complete",
    "content": [ { "type": "text", "text": "3 unpaid orders totalling €1,284.00" } ],
    "_meta": { "io.modelcontextprotocol/serverInfo": { "name": "orders", "version": "2.4.0" } } } }

// …or the server needs something first:
{ "jsonrpc": "2.0", "id": 8, "result": {
    "resultType": "input_required",
    "inputRequests": [ {
        "name": "elicitation/create",
        "params": { "message": "Refund €240.00 to CUST-4412?",
                    "requestedSchema": { "type": "object",
                      "properties": { "confirm": { "type": "boolean" } },
                      "required": ["confirm"] } } } ] } }

// the client collects the answer and retries the SAME request with:
//   "params": { …, "inputResponses": [ { "name": "elicitation/create",
//                                        "result": { "confirm": true } } ] }
Multi round-trip requests: the client always initiates, so a tool handler must be able to be entered twice for one logical call.

    }
  }

Note the credential: a read-only DSN. The narrowest credential that still works is the single most effective control you have.
# a remote server is an ordinary HTTP service — curl it like one
curl -sS https://mcp.example.com/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2026-07-28' \
  -H "Authorization: Bearer $TOKEN" \
  --data '{"jsonrpc":"2.0","id":1,"method":"tools/list",
           "params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28"}}}'

# discovery for authorization (RFC 9728) — where the client learns which AS to use
curl -sS https://mcp.example.com/.well-known/oauth-protected-resource | jq .
Because the protocol is stateless, a single curl is a valid client — which makes remote servers easy to test and to monitor.

Pros & cons

Pros

  • One integration serves every compliant host, so N×M becomes N+M.
  • Capabilities are discovered at runtime: a new tool appears without a client release.
  • Credentials stay in the server, never in the model's context or the host's config.
  • The stateless revision makes remote servers ordinary, horizontally scalable HTTP services.
  • Transport-agnostic: the same server code runs locally over stdio or remotely over HTTP.
  • Broad adoption across vendors, with SDKs in C#, Python, TypeScript, Java, Go, Kotlin and more.
  • JSON-RPC and JSON Schema are dull, well-understood and easy to debug with curl.

Cons

  • Connecting a server grants real power to a model — a genuine supply-chain decision.
  • Tool descriptions and results enter the context window, so an untrusted server can inject instructions.
  • Every tool costs tokens on every turn; twenty servers is a context problem before it is a capability.
  • The 2026-07-28 revision is a breaking change, and clients and servers on different revisions may not interoperate.
  • Roots, Sampling and Logging are deprecated, which invalidates a lot of published material.
  • No standard answer for multi-step orchestration, memory or planning — that is the harness's problem.
  • Quality varies wildly: many public servers are thin API wrappers with poor descriptions.

Concrete use cases

Read-only database access

An analyst asks questions in natural language; the server exposes list_tables, describe_table and run_select against a read-only role with a row cap and a statement timeout. The model never sees a credential and cannot write, so the worst case is an expensive query.

Internal knowledge in the IDE

A server wraps the company wiki and runbooks, exposing a search tool and resource templates. Engineers get grounded answers where they work, and permissions are enforced by the server against the user's own token rather than by the model.

Ticketing and issue workflows

Create, comment, transition and link issues through one server. Read tools run unattended; write tools require elicitation confirming the exact change, which is what makes an agent usable on a real backlog.

One server, many hosts

A platform team ships a single deployments server. It is used from the IDE assistant, the chat bot and an automated agent runtime — three very different hosts, one integration, one audit log.

Retrieval as a tool

A RAG pipeline is exposed as a single search_docs tool. The model decides when to search and with what query, which turns single-shot retrieval into agentic retrieval without changing the pipeline.

When to use / when not to

if exactly one app will ever call it, you want a function. MCP is for the second caller.

Use it when…

  • Several hosts, or several models, need the same capability.
  • The capability should be discoverable at runtime rather than compiled into a client.
  • Credentials must live outside the model's context and outside the host.
  • You want one audited boundary around what a model may do to a system.
  • You are publishing an integration for other people's assistants to use.

Avoid it when…

  • One application calls one function. Use native tool calling in your own code.
  • The need is agents coordinating with other agents as peers. Use A2A.
  • You want the workflow itself — planning, retries, memory, budgets. Use an agent harness.
  • The data is static and fits the prompt. Use a resource attachment or plain context.
  • Latency is critical and the tool is a trivial local computation. Call it directly.
  • You cannot vet the server. Do not connect it — there is no safe way to use an untrusted one.

Common mistakes & gotchas

Writing to stdout in a stdio serverOne print(), Console.WriteLine or library banner lands in the middle of the JSON-RPC stream. The client reports a parse error and disconnects, and the cause is invisible in the host's logs.
Fix: send every diagnostic to stderr, and configure third-party libraries to do the same. On stdio, stdout belongs to the protocol alone.
Building against the old handshakeCode follows a tutorial that opens with initialize and carries Mcp-Session-Id. On a 2026-07-28 server those are gone, and version mismatches surface as -32020 rather than as something readable.
Fix: check which revision your SDK targets, send _meta and the MCP-Protocol-Version header consistently, and call server/discover when you need to know what a peer supports.
One tool per API endpointA REST API with 60 endpoints becomes a server with 60 tools. The catalogue alone fills thousands of tokens on every turn, and the model picks the wrong one because twelve descriptions sound alike.
Fix: expose tasks, not endpoints. Five to fifteen well-named tools that each complete something useful beat a faithful mapping of the API surface.
Returning raw dataA query tool returns 2,000 rows of JSON. The context window fills, cost multiplies, and the model summarises badly what the server could have summarised exactly.
Fix: cap results, project to the fields that matter, and return a short summary plus a pointer. If the model needs more, give it a second tool to drill in.
Vague tool descriptions"Searches the system." The model calls it for everything, or never calls it, and no prompt engineering in the host can fix a description it reads as authoritative.
Fix: say what it does, when to prefer it over its neighbours, what each argument means and what comes back — including limits and the empty case.
Over-privileged credentialsThe server connects as the database owner because that was the connection string on hand. A hallucinated or injected call now has write access to everything.
Fix: a dedicated read-only role, a scoped token, a single directory, a statement timeout. Separate read servers from write servers so one approval does not grant both.
Trusting tool outputA tool fetches a web page or reads a ticket, and the content contains instructions. The model follows them, because to it the result is just more context.
Fix: treat every tool result as untrusted data. Keep write capabilities out of servers that ingest external content, and require explicit approval for destructive actions.
Unbounded or non-cancellable toolsA tool runs a slow query with no timeout. The host shows a spinner, the user cancels, and the work carries on holding a connection.
Fix: honour the cancellation token in every handler, set server-side timeouts and row limits, and report progress for anything long.
Ignoring the audience on tokensA remote server accepts any valid-looking bearer token. A token issued for a different MCP server is replayed against it and works.
Fix: validate that the token's audience is this server, publish protected resource metadata, and require the resource parameter from clients as the specification does.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs MCP
MCPreusable model↔system integrationsMediumopen spec, free SDKs—
Native tool callingone app, a handful of functionsVery lowfreeNo discovery, no reuse, no process boundary — and nothing to vet
A2Aagents delegating to agentsMediumopen, Linux FoundationPeers exchanging tasks, not a model calling tools; the two compose
OpenAPI + a generatorwrapping an existing REST APILowfreeEndpoint-shaped, not task-shaped; no prompts, resources or elicitation
Framework pluginsstaying inside one ecosystemLowfreeTied to that framework and language; no cross-host reuse
Vendor plugin systemsone vendor's assistantLowvendor termsWorks only there; deployment and review are the vendor's
  • Pick native tool calling when the tool will only ever be used by the application that defines it.
  • Pick A2A when the other side is an autonomous agent with its own loop, not a system you are exposing.
  • Pick an OpenAPI wrapper as a starting point, then collapse it into task-shaped tools — the generated version rarely works well as-is.
  • Use MCP and A2A together: A2A between agents, MCP from each agent down to its own tools.
