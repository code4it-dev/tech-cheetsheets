Modular monolith

One deployable, with walls the compiler actually enforces.

As of Nov 2026 · the pattern is stable; examples are .NET 10 (LTS), ASP.NET Core and EF Core

A layered monolith organises code by technical role — controllers, services, repositories — which means a business concept like "billing" is smeared across every layer and nothing stops one feature from reaching into another's data. Over a few years that becomes the big ball of mud everybody has worked in.

Microservices fix the coupling by making boundaries physical: you cannot call another team's class because it is in another process. But you pay for that wall with network latency, partial failure, distributed transactions, a deployment pipeline per service, and an operational burden most teams are not staffed for.

A modular monolith takes the boundary discipline and leaves out the network. The system is split by business capability — Orders, Billing, Shipping — each module exposing a small public contract and hiding everything else, owning its own tables, and talking to its neighbours only through those contracts. It all compiles into one deployable and runs in one process, so a cross-module call is a method call. The boundary is enforced by the compiler and by architecture tests rather than by a firewall — and when a module genuinely needs to become a service, the contract is already there.

Comparing them

The three options are not a scale from bad to good. They are three different places to put the same wall, with different bills attached.

What the table is really saying:

  • The modular monolith shares a column with the layered one and a column with microservices. It takes the mechanics of the first (one deploy, one transaction, no partial failure) and the discipline of the second (owned data, explicit contracts). That is the whole trick, and it is why it is a sensible default rather than a compromise.
  • The row that matters most is "moving a boundary". Early on you will get the boundaries wrong — everybody does. In a modular monolith that costs a refactor; in microservices it costs a migration and a coordinated release across two teams. Adopt the architecture whose mistakes are cheap.
  • Microservices buy independent scaling and independent deployment. If you do not currently need either, you are paying the whole bill for none of the goods — and animation 4 shows you can buy them later, one module at a time.

Key concepts

moduleA business capability with its own code, its own data and a small public surface. The unit everything else on this page is about.
public contractThe interface and DTOs a module exposes, usually in a project of their own that contains no implementation. The only legal way in.
internalsEverything behind the contract: services, repositories, entities, mappers. Marked internal so other modules physically cannot reference them.
boundary enforcementMaking a violation fail the build rather than depend on someone noticing it in review. Without this, a modular monolith decays into a layered one.
module-owned schemaEach module owns its tables and nobody else reads them directly. The database is where modular monoliths most often leak.
in-process messagingPublishing an event instead of calling an interface. Removes the compile-time reference, at the cost of making the flow harder to follow.
transaction boundaryThe thing a modular monolith still has and microservices do not: several modules writing inside one database transaction.
bounded contextThe DDD idea underneath: a boundary within which a word means exactly one thing. Modules work when they follow these seams.
vertical sliceOrganising a module's code by feature — request, handler, validation, data access together — rather than by technical layer.
composition rootThe single place that knows every module's implementation and wires it up. The only code allowed to reference everything.
shared kernelThe small set of types genuinely common to every module: ids, money, dates, result types. Useful, and the most abused project in the solution.
anti-corruption layerA translation layer at a module's edge so another context's model — or a legacy system's — does not leak into yours.
extraction pathTurning a module into a service by implementing its existing contract remotely. The reason to build a modular monolith even if you believe you will end up distributed.
cyclic dependenciesOrders needs Billing and Billing needs Orders. The most common sign that two modules are really one, or that one is missing.
testing per moduleEach module gets its own test project that exercises it through its contract, with no other module loaded.
observability per moduleTagging logs, traces and metrics with the module that produced them, so you can answer "which part is slow" without process boundaries to separate them.

Code & structure

Solution layout

src/
  Shop.Host/                 // composition root: references every module, contains no logic
  Shop.SharedKernel/         // Money, TenantId, Result<T> — tiny, depends on nothing
  Modules/
    Orders/
      Orders.Contracts/      // IOrdersApi + DTOs. Referenced by other modules.
      Orders/                // everything internal. Referenced only by the host.
      Orders.Tests/
    Billing/
      Billing.Contracts/
      Billing/
      Billing.Tests/
tests/
  Shop.ArchitectureTests/    // the rules that keep the above true
Two projects per module plus tests. The split between .Contracts and the implementation is what makes internal meaningful.
dotnet new classlib -o src/Modules/Billing/Billing.Contracts
dotnet new classlib -o src/Modules/Billing/Billing
dotnet add src/Modules/Billing/Billing reference src/Modules/Billing/Billing.Contracts
dotnet add src/Modules/Orders/Orders reference src/Modules/Billing/Billing.Contracts
Orders references Billing's contracts only. It must never reference Billing itself.

The boundary, in code

// Billing.Contracts — public
public interface IBillingApi
{
    Task<ChargeResult> ChargeAsync(ChargeRequest request, CancellationToken ct);
}

// Billing — internal, invisible to every other module
internal sealed class BillingService(BillingDbContext db, ILogger<BillingService> log) : IBillingApi
{
    public async Task<ChargeResult> ChargeAsync(ChargeRequest r, CancellationToken ct) { /* ... */ }
}
The only type anyone outside Billing can name is the interface.
public static class BillingModule
{
    public static IServiceCollection AddBilling(this IServiceCollection s, IConfiguration cfg)
    {
        s.AddScoped<IBillingApi, BillingService>();
        s.AddDbContext<BillingDbContext>(o => o.UseNpgsql(cfg.GetConnectionString("Default")));
        return s;
    }
}
One registration method per module. The host calls it and learns nothing else about Billing.
builder.Services
    .AddOrders(builder.Configuration)
    .AddBilling(builder.Configuration)
    .AddShipping(builder.Configuration);
The entire composition root. Swapping a module for a remote implementation is a change on one of these lines.
protected override void OnModelCreating(ModelBuilder b)
{
    b.HasDefaultSchema("billing");
    b.ApplyConfigurationsFromAssembly(typeof(BillingDbContext).Assembly);
}
One DbContext per module, each confined to its own schema. No module maps another's tables.

Architecture tests — the rules that keep it true

dotnet add tests/Shop.ArchitectureTests package NetArchTest.Rules
NetArchTest or ArchUnitNET. Add this on day one, while there is nothing to fix.
[Fact]
public void Orders_does_not_depend_on_Billing_internals()
{
    var result = Types.InAssembly(typeof(OrderService).Assembly)
        .Should().NotHaveDependencyOn("Shop.Modules.Billing")
        .GetResult();
    Assert.True(result.IsSuccessful, string.Join(", ", result.FailingTypeNames ?? []));
}
The rule that makes the whole pattern real. Everything else is a convention.
[Fact]
public void Nothing_depends_on_the_host() =>
    Assert.True(Types.InAssemblies(ModuleAssemblies)
        .Should().NotHaveDependencyOn("Shop.Host").GetResult().IsSuccessful);
The host may know everything; nothing may know the host.
[Fact]
public void Module_types_are_internal() =>
    Assert.Empty(Types.InAssembly(typeof(BillingService).Assembly)
        .That().ArePublic().And().DoNotHaveName(nameof(BillingModule))
        .GetTypes());
Catches the public that someone added "just for a test".

Events, when a contract is the wrong shape

// Orders publishes a fact and names nobody
await _publisher.Publish(new OrderPlaced(order.Id, order.Total), ct);

// Billing subscribes, in its own module
internal sealed class ChargeOnOrderPlaced(IBillingApi billing) : INotificationHandler<OrderPlaced>
{
    public Task Handle(OrderPlaced e, CancellationToken ct) => billing.ChargeAsync(new(e.OrderId, e.Total, "EUR"), ct);
}
In-process dispatch, no serialization, no broker. The event type lives in the publisher's contracts project.
// outbox: atomic with the write, dispatched after commit
db.Outbox.Add(new OutboxMessage(typeof(OrderPlaced).FullName!, JsonSerializer.Serialize(evt)));
await db.SaveChangesAsync(ct);    // order + event committed together
The only pattern that is both atomic with your write and safe to retry — and exactly what you need when the module leaves the process.

Pros & cons

Pros

  • One build, one deploy, one log stream, one debugger — a new developer is productive in a day.
  • Cross-module work stays inside a single database transaction, so no sagas and no compensation.
  • Boundaries are enforced by the compiler, which never forgets and never approves a pull request anyway.
  • Getting a boundary wrong costs a refactor rather than a data migration and a cross-team release.
  • Calls between modules cost nanoseconds, so there is no fan-out tail to design around.
  • Each module can be extracted later, one at a time, with the contract already in place.

Cons

  • Discipline is the only thing holding it up — without architecture tests it decays into a layered monolith.
  • You cannot scale or deploy one module independently; a hot module means scaling everything.
  • One process means one blast radius: a memory leak or a runaway thread takes the whole system down.
  • Everything is in one language and one runtime, so "use Go for this bit" is off the table.
  • Large teams contend on one repository, one pipeline and one release train.
  • The database is a shared resource, and a cross-schema query is always one lazy pull request away.

Concrete use cases

A startup that expects to grow

Four engineers building a B2B product. Microservices would cost them a pipeline, a service mesh and an on-call rota they cannot staff; a layered monolith would cost them a rewrite in three years. Six modules in one solution, with architecture tests from the first commit, give them boundaries they can move cheaply while the domain is still being discovered.

Escaping a ball of mud without a rewrite

A ten-year-old ASP.NET application with one 400-table database. Instead of a rewrite, the team draws module boundaries on paper, moves tables into schemas one capability at a time, introduces a contract per capability, and adds an architecture test the moment each module is clean. No big-bang release, and the system stays shippable throughout.

Retreating from premature microservices

A team of eight is running fourteen services, most deployed together because they change together. They merge the ones that share a release into modules in one host, keeping the existing interfaces as module contracts. Latency drops, the saga code disappears, and the two services that genuinely scale differently stay separate.

Extracting the one module that needs it

A document-rendering module is CPU-bound and occasionally needs thirty machines for twenty minutes, while the rest of the system is happy on three. It already sits behind IRenderingApi, so it is extracted into a service and a queue; the calling code changes on one line of registration. Nothing else is distributed.

A regulated product with one compliance boundary

Payment data must live in a separately audited store with its own access controls. The Payments module gets its own schema, its own database user and its own audit log while staying in the same process, which satisfies the auditor without forcing the other eleven modules into a distributed architecture.

When to use / when not to

Pick the architecture whose mistakes are cheapest — you will make some.

Use it when…

  • You have between one and ten teams and no proven need for independent deployment.
  • The domain is still moving and boundaries will need to be redrawn.
  • Business operations span several capabilities and you want them in one transaction.
  • You are breaking up a ball of mud and cannot stop shipping while you do it.
  • Your operational maturity does not yet include tracing, service discovery and a per-service on-call rota.
  • You want the option of microservices later without paying for them now.

Avoid it when…

  • Parts of the system genuinely need independent scaling or release cadence. Use microservices for those parts only.
  • Teams must deploy without coordinating. One pipeline is a real constraint — use separate services.
  • Different parts need different runtimes or languages. One process means one runtime.
  • The application is small and will stay small. Use a layered monolith; modules would be ceremony.
  • A component has a hard isolation requirement — untrusted plugins, a separate compliance boundary at the process level. Use a separate process.
  • Nobody will maintain the architecture tests. Without enforcement this is just a monolith with optimistic folder names.

Common mistakes & gotchas

Modules named after layersApi, Services, Data, Domain as "modules" is the layered monolith with extra project files. Every feature still touches every module, so nothing has been decoupled.
Fix: name modules after things the business says out loud — Orders, Billing, Shipping. If a typical change touches more than one module, the boundary is in the wrong place.
No architecture testsThe boundaries hold for about four months, then a deadline arrives and someone adds a project reference. Nothing fails, the pull request is approved, and the next shortcut is easier to justify.
Fix: write the dependency rules as tests on day one, while they all pass. A boundary that is not asserted in CI is a preference, not an architecture.
Joining across module schemasThe C# is immaculate and OrderReportQuery joins orders.orders to billing.invoices because it was quicker. The modules are now coupled at the only layer nobody is testing.
Fix: one DbContext per module, each mapping only its own schema, and a per-module database user with grants on nothing else. For reports, have the owning module expose the data or build a read model.
A shared kernel that eats the domainCommon starts with Money and ends up holding Customer, Order and a base repository. Everything references it, so every module is transitively coupled to every other.
Fix: keep it to primitives with no business rules, add an architecture test asserting it depends on nothing, and when something looks shared, let both modules keep their own version until the third one appears.
Exposing entities through the contractIBillingApi returns a Invoice entity with lazy-loaded navigation properties. Callers now depend on your schema, and the module cannot be extracted without breaking them.
Fix: return records built for the contract. The test is animation 4: could you implement this interface over HTTP without changing the caller? If not, it is leaking.
Every interaction becomes an eventDirect calls are replaced with events everywhere "for decoupling". Now no stack trace shows the flow, "what happens when an order is placed" is a grep, and ordering bugs appear under load.
Fix: default to a contract call; use an event only when the publisher genuinely does not care who listens or what happens. Decoupling that you cannot read is not decoupling.
Extracting a module because the count got largeTwelve modules feels like it should be twelve services. The team distributes a system with no scaling problem and acquires sagas, retries, tracing and a deployment matrix in exchange for nothing.
Fix: extract on evidence from your per-module metrics — a different scaling profile, a different release cadence, or a team genuinely blocked. Module count is not evidence.
One DbContext for the whole applicationIt maps every table, so any module can query any other's data with full IntelliSense support. The most convenient possible way to destroy the boundaries.
Fix: a DbContext per module, registered by that module, mapping only its own entities. Migrations per module too, so each one owns its schema history.

Alternatives

ApproachBest forComplexityOps costKey difference vs a modular monolith
Modular monolithmost products, 1–10 teamsMediumLow—
Layered monolithsmall apps, one team, short horizonLowLowNo enforced boundaries; faster to start, far harder to change after year two
Microservicesmany teams, genuinely different scalingHighHighIndependent deploy and scale, bought with network failure and distributed data
Vertical slice architectureorganising code inside a moduleLowLowNot a competitor — it is how you lay out each module internally
Spring Modulith / modulith frameworksteams wanting the pattern with toolingMediumLowSame pattern with built-in verification and documentation; JVM
Serverless functionsspiky, event-driven, small units of workMediumMediumDeployment unit per function; excellent for glue, poor for a cohesive domain
Distributed monolithnobody — it is what you get by accidentHighHighServices that must deploy together: every cost of microservices, none of the benefits
  • Pick a layered monolith if the application is genuinely small and you would rather have speed now than optionality later.
  • Pick microservices when you can name the service, the scaling problem and the team that is blocked — all three.
  • Use vertical slices inside your modules; the two ideas are complementary, not alternatives.
  • Watch for the distributed monolith. If your services always release together, you have one system in several processes and should consider merging them back into modules.
  • The usual healthy end state is a modular monolith plus two or three extracted services — not a choice between the extremes.
