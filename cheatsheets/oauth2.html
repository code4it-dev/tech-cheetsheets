OAuth 2.0

A way to let an app act on your behalf without ever showing it your password.

As of Nov 2026 · RFC 6749 (2012), PKCE RFC 7636, Security BCP RFC 9700 · OAuth 2.1 is still an IETF draft (rev 16)

OAuth 2.0 solves one problem: a third-party application needs to use an API as you, and handing it your password is unacceptable. Instead the app redirects you to the service you already trust, you authenticate and consent there, and the app receives a narrowly scoped, short-lived access token. It never sees your credentials, the token can be limited to "read my calendar", and it can be revoked without changing your password.

The framework defines four roles — resource owner (you), client (the app), authorization server (issues tokens) and resource server (the API) — and several flows for getting a token. In 2026 the honest summary is that there are only two you should normally use: authorization code with PKCE for anything acting on behalf of a user, and client credentials for machine-to-machine. The implicit and password grants are removed in the OAuth 2.1 draft and should be treated as deleted.

The most common misunderstanding is worth stating plainly: OAuth 2.0 is authorization, not authentication. An access token says "the bearer may read this calendar" — it does not reliably say who the user is, and using one as proof of identity is a well-known vulnerability class. The layer that does identity is OpenID Connect, which is built on top of this.

Key concepts

Resource ownerThe person who owns the data and grants consent — usually the end user, sitting in front of a browser.
ClientThe application requesting access. Public if it cannot keep a secret, confidential if it can.
Authorization serverThe component that authenticates the user, collects consent and issues tokens. The only place credentials are ever entered.
Resource serverThe API holding the data. It validates the token and enforces scope — and should never call the authorization server per request.
Authorization code flowThe redirect-based flow where the browser carries a short-lived code and the client swaps it for tokens on a back channel.
PKCEProof Key for Code Exchange: the client proves at the token endpoint that it is the same client that started the flow.
Access tokenThe credential the client presents to the API. Short-lived, scoped, and treated as a password by anyone who holds it.
Refresh tokenA long-lived credential used to obtain new access tokens without involving the user again.
Refresh token rotationIssuing a new refresh token on every use and invalidating the old one, so a replayed token exposes the theft.
ScopeThe permissions a token carries, requested by the client and approved by the user.
Redirect URIWhere the authorization server sends the browser back. Registered in advance and matched exactly.
state parameterAn opaque, unguessable value the client sends and checks on return — the CSRF defence for the flow itself.
Client credentialsThe machine-to-machine flow: the client authenticates as itself and gets a token, with no user involved.
Device authorization flowFor input-constrained devices: the device shows a code, you approve it on your phone.
Token introspection & revocationEndpoints for asking whether an opaque token is still valid, and for actively killing one.
AudienceWhich API a token was minted for — and the check that stops one service replaying your token at another.
Sender-constrained tokensBinding a token to the client that obtained it, so a stolen copy is useless — DPoP or mTLS.

PKCE, in C#

static (string Verifier, string Challenge) Pkce()
{
    var bytes = RandomNumberGenerator.GetBytes(32);          // 43 chars once encoded
    var verifier = Base64UrlEncode(bytes);
    var challenge = Base64UrlEncode(SHA256.HashData(Encoding.ASCII.GetBytes(verifier)));
    return (verifier, challenge);
}

// Base64URL: standard Base64 with +/ swapped for -_ and the padding removed
static string Base64UrlEncode(byte[] b) =>
    Convert.ToBase64String(b).TrimEnd('=').Replace('+', '-').Replace('/', '_');
Keep the verifier in the session and send only the challenge. Getting the Base64URL encoding wrong is the most common PKCE bug.
import base64, hashlib, secrets

def pkce() -> tuple[str, str]:
    verifier  = base64.urlsafe_b64encode(secrets.token_bytes(32)).rstrip(b"=").decode()
    digest    = hashlib.sha256(verifier.encode("ascii")).digest()
    challenge = base64.urlsafe_b64encode(digest).rstrip(b"=").decode()
    return verifier, challenge

# secrets, never random — the verifier must be unguessable
The same in Python. urlsafe_b64encode already does the character swap; you only have to strip the padding.

Being a client

// Server-side web app: the framework runs the whole flow for you
builder.Services
    .AddAuthentication(o =>
    {
        o.DefaultScheme          = CookieAuthenticationDefaults.AuthenticationScheme;
        o.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
    })
    .AddCookie()
    .AddOpenIdConnect(o =>
    {
        o.Authority    = "https://login.example.com";
        o.ClientId     = "s6BhdRkqt3";
        o.ClientSecret = builder.Configuration["Oidc:Secret"];
        o.ResponseType = "code";          // authorization code, never "token"
        o.UsePkce      = true;            // on by default; never turn it off
        o.SaveTokens   = true;            // keep tokens server-side, not in the browser
        o.Scope.Add("calendar.read");
        o.Scope.Add("offline_access");    // ask for a refresh token explicitly
    });
Hand-rolling redirects, state and code exchange is how subtle bugs get in. Use the framework's handler and configure it correctly.
# Python, with Authlib — same flow, same rules
oauth = OAuth()
oauth.register(
    name="example",
    server_metadata_url="https://login.example.com/.well-known/openid-configuration",
    client_id="s6BhdRkqt3",
    client_secret=os.environ["OIDC_SECRET"],
    client_kwargs={"scope": "openid calendar.read offline_access",
                   "code_challenge_method": "S256"},   # PKCE on
)

@app.get("/login")
async def login(request: Request):
    return await oauth.example.authorize_redirect(request, REDIRECT_URI)

@app.get("/callback")
async def callback(request: Request):
    token = await oauth.example.authorize_access_token(request)   # verifies state + PKCE
    request.session["tokens"] = token                             # server-side session
Authlib checks state and the PKCE verifier for you. Storing tokens in the server session keeps the browser out of it.

Machine to machine

// No user, no redirect — and ideally no secret either
var credential = new DefaultAzureCredential();             // managed identity
var token = await credential.GetTokenAsync(
    new TokenRequestContext(["api://orders/.default"]));

// Or, with any authorization server:
var form = new FormUrlEncodedContent(new Dictionary<string, string>
{
    ["grant_type"]    = "client_credentials",
    ["client_id"]     = clientId,
    ["client_secret"] = secret,            // prefer a private-key JWT or mTLS
    ["scope"]         = "orders.read",
});
var res = await http.PostAsync("https://login.example.com/token", form);
A managed or workload identity is strictly better than a secret: there is no credential to leak, rotate or commit.
import httpx

async def service_token() -> str:
    async with httpx.AsyncClient() as http:
        res = await http.post("https://login.example.com/token", data={
            "grant_type": "client_credentials",
            "client_id": CLIENT_ID,
            "client_secret": os.environ["CLIENT_SECRET"],
            "scope": "orders.read",
        })
        res.raise_for_status()
        return res.json()["access_token"]

# cache it until shortly before `expires_in` — do not fetch one per request
Caching matters: a token request per API call turns the authorization server into your hardest dependency.

Validate audience and scope, not just the signature. A valid token minted for another API is still the wrong token.

Discovery

curl -s https://login.example.com/.well-known/openid-configuration | jq '{
  authorization_endpoint, token_endpoint, jwks_uri,
  code_challenge_methods_supported, grant_types_supported
}'
Never hard-code endpoints or keys. Discovery plus a cached JWKS is what lets the provider rotate signing keys without breaking you.

Pros & cons

Pros

  • Third-party apps never see the user's password, and access can be revoked independently of it.
  • Scopes let a user grant narrow access instead of all-or-nothing.
  • Short-lived bearer tokens validate locally, so APIs scale without a shared session store.
  • Universally implemented — every identity provider and HTTP client already speaks it.
  • Separates the identity provider from the APIs, so authentication is built once.
  • The same framework covers users, devices and machine-to-machine traffic.

Cons

  • A framework rather than a protocol: many options, and several historically bad ones.
  • Bearer tokens are passwords in practice — theft means full access until expiry.
  • Revocation is not immediate with JWTs unless you add introspection or very short lifetimes.
  • Easy to misuse as authentication, which is a documented vulnerability class.
  • Redirect URI and state handling are fiddly and security-critical.
  • Token storage in browsers and mobile apps has no genuinely good answer without a backend.

Concrete use cases

"Connect your calendar"

A scheduling tool needs read access to a user's calendar. Authorization code with PKCE gets a token scoped to calendar.read only; the user can revoke it from their account page, and the tool never had a password to leak.

A nightly job calling an internal API

No user is present, so client credentials with a workload identity issues a token scoped to orders.read. No secret exists anywhere, and the API enforces the scope without knowing anything about the job.

A CLI that should not ask for a password

The device authorization flow prints a short code and a URL. The developer approves it in a browser they already trust, and the CLI receives a token with the scopes it asked for — no password prompt, no long-lived personal token pasted into a config file.

A SPA that should not hold tokens

Rather than storing tokens in the browser where any XSS can read them, the SPA talks to a BFF that runs the code flow, keeps the tokens server-side and gives the browser only an httpOnly session cookie.

Partner API access

A partner integrates once against your authorization server, receives narrowly scoped tokens per customer, and you can revoke one customer's access without touching anyone else's — something shared API keys cannot express.

When to use / when not to

authorization code + PKCE, or client credentials. if you are writing anything else, check why.

Use it when…

  • A third-party or first-party app needs to call an API on a user's behalf.
  • You want revocable, scoped, time-limited access instead of shared credentials.
  • Several apps and APIs should share one identity provider.
  • Services need to authenticate to each other without embedded passwords.
  • You need an audit trail of which app did what, on whose behalf.

Avoid it when…

  • You only need to know who the user is. Use OpenID Connect — OAuth alone is not authentication.
  • It is a single server-rendered app with its own users. Use a session cookie; OAuth adds nothing.
  • Two internal services need to trust each other on a private network. Use mTLS, which is simpler and stronger.
  • You are tempted by the password grant. Use authorization code with PKCE; ROPC is removed from the 2.1 draft.
  • You would have to write the authorization server. Use an existing provider — this is not a build-it-yourself component.

Common mistakes & gotchas

Using an access token as proof of identityAn access token is addressed to an API, not to you. Accepting one as "the user is logged in" lets a token obtained by a different app for a different purpose be replayed at your login endpoint.
Fix: use OpenID Connect and validate the ID token, including aud, iss and nonce. Never parse an access token for identity.
Skipping the audience checkValidating only the signature means any token your issuer ever minted — for any API, for any client — is accepted. One service can then replay a token at another and act as the user.
Fix: always validate aud against your own identifier, and use token exchange rather than forwarding a token to a downstream service.
Tokens in browser storagelocalStorage is readable by any script on the page, so one XSS or one compromised dependency is a full account takeover for the token's lifetime.
Fix: put a BFF in front of the SPA so tokens stay server-side and the browser only gets an httpOnly, SameSite cookie.
Wildcard or loose redirect URIsPrefix matching, wildcards and open redirects on the registered host all let an attacker have the authorization code delivered to them.
Fix: exact string matching, HTTPS everywhere except localhost, and audit the registered host for open redirects.
No state, or never checking itGenerating state and then not comparing it on the callback is the same as not having it, and leaves the flow open to CSRF and account-linking attacks.
Fix: store it in the session, compare on return, reject on mismatch. PKCE does not cover this — it protects the code, not the session.
Long-lived access tokensA 24-hour access token means a stolen token is valid for 24 hours, and with JWTs you usually cannot revoke it.
Fix: minutes for access tokens, with a rotating refresh token for continuity. If you need instant revocation, add introspection and accept the dependency.
Treating scopes as an authorization modelinvoices:read says the app may attempt to read invoices. It does not say this user may read that invoice, and APIs that stop at the scope check leak data across tenants.
Fix: check the scope at the edge and the actual permission in the domain. Scopes are delegation, not row-level security.
Implicit flow, stillReturning tokens directly in the redirect puts them in the URL, the history and the referrer, with no way to use a refresh token safely. It was removed from the 2.1 draft.
Fix: authorization code with PKCE works in SPAs and mobile apps and is strictly better. If a tutorial says response_type=token, it predates 2019.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs OAuth 2.0
OAuth 2.0delegated access to APIsMediumfree; a provider to run or buy—
OpenID Connectknowing who the user isMediumfreeAn identity layer on top of OAuth; adds the ID token. Not an alternative — the other half
Session cookiesone app, its own usersLowfreeServer-side session, no tokens, no third parties; simpler and perfectly correct for a monolith
API keyssimple server-to-serverVery lowfreeOne long-lived shared secret: no user context, no expiry, no scopes, hard to rotate
mTLSservice-to-service on your own networkMediumcertificate infrastructureIdentity at the transport layer; strong, but no user delegation and no scopes
SAML 2.0enterprise SSO to web appsHighfreeXML and browser POSTs, predates APIs; still common in enterprise SSO, poor fit for mobile and APIs
PATsscripts and CIVery lowfreeA long-lived user-scoped token; convenient and routinely leaked in repositories
  • Pick OpenID Connect whenever the question is "who is this?" — you will almost always want both.
  • Pick session cookies for a single application with its own login; OAuth buys you nothing there.
  • Pick mTLS for internal service-to-service calls where no user is being represented.
  • Pick SAML only when an enterprise customer requires it; new systems should not start there.
  • Pick API keys for low-risk, non-user-scoped access — and set an expiry even though nothing forces you to.
