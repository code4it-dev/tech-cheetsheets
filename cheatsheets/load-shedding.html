Load shedding

Past capacity you will fail some requests whatever you do. Shedding is choosing which ones, instead of letting the overload choose for you.

As of Nov 2026 · examples in C#, Go, Envoy and Python; the arithmetic is from queueing theory

When demand exceeds capacity, a naive system does not serve its capacity and reject the rest. It serves far less than its capacity: queues grow past client timeouts so work is thrown away after being paid for, clients retry and double the arrival rate, and memory pressure makes every remaining request more expensive. Offered load goes up and useful output goes down. That is congestion collapse, and it is the normal behaviour of a system with no admission control.

Load shedding is the deliberate alternative: detect that you are past capacity, and refuse a fraction of the work immediately and cheaply so the rest can be served properly. A rejection costs perhaps 0.1 ms; a request that times out after two seconds has consumed two seconds of capacity first. That ratio — roughly four orders of magnitude — is the whole reason the technique works.

It is easy to confuse with its neighbours. Rate limiting enforces a per-client quota agreed in advance, whether or not you are busy. Backpressure carries the "I am full" signal upstream but does not decide what to sacrifice. Circuit breakers protect a caller from a failing dependency. Load shedding is specifically about your own health and which work you abandon — and the good version prioritises by business value, not by who happened to arrive first.

Key concepts

Load sheddingDeliberately refusing a portion of incoming work, quickly and cheaply, so the remainder can be served within its SLO.
GoodputRequests completed successfully and within their deadline — the only throughput number that means anything under overload.
Congestion collapseThe regime where offered load rises and useful output falls — the failure shedding exists to prevent.
Admission controlThe component that decides, before any real work begins, whether a request gets a slot.
Priority classesLabelling traffic by business value so that shedding sacrifices the least important work first.
Criticality propagationCarrying the priority of the originating request through every downstream call, so the whole chain sheds consistently.
Shedding signalThe measurement that decides when to start refusing — and the choice that determines whether shedding helps or flaps.
Queue sojournHow long a request has already waited — the signal that stays correct when capacity changes underneath you.
Cost-aware sheddingRejecting before the expensive part, and accounting for the fact that not all requests cost the same.
Fail fastRefusing in a fraction of a millisecond, which is what makes shedding cheap enough to work.
Retry-AfterTelling the client when to come back, so your fast rejection does not become their fast retry loop.
BrownoutShedding part of a response rather than the whole request — degrade the answer instead of refusing it.
FairnessMaking sure shedding does not fall entirely on one tenant, region or unlucky client.
HysteresisDifferent thresholds for starting and stopping, so the system does not oscillate between shedding and not shedding.
Where to shedAt the edge, in the service, or in a sidecar — each sees different information and can take different action.
Measuring itShed rate, goodput and the SLO — because shedding that nobody measures looks exactly like an outage.

Essential code patterns

The smallest useful shedder

// a concurrency limit is load shedding in six lines
private readonly SemaphoreSlim _slots = new(60);   // L = λ × W, by Little's Law

app.Use(async (ctx, next) =>
{
    if (!_slots.Wait(0))                            // no waiting: admit or refuse now
    {
        Metrics.Shed.WithLabels(Class(ctx)).Inc();
        ctx.Response.StatusCode = 503;
        ctx.Response.Headers.RetryAfter = "1";
        return;                                     // ~0.1 ms, before anything expensive
    }
    try { await next(ctx); } finally { _slots.Release(); }
});
Registered first in the pipeline so a rejection happens before auth, model binding or any database work.

Shed by priority

static int Threshold(Criticality c) => c switch
{
    Criticality.Critical   => 100,   // admit until the limit is genuinely gone
    Criticality.Standard   =>  85,
    Criticality.Background =>  60,   // gives up its slot early
    Criticality.Batch      =>  40,
};

var usedPct = 100 * _inFlight / _limit;
if (usedPct > Threshold(criticality)) return Shed(ctx);
One limit, four watermarks: background traffic disappears long before checkout is ever touched.

x-criticality: critical
grpc-timeout: 800m

# and a service may never RAISE it — background work cannot

Without propagation the edge protects checkout while an inner service sheds it anyway.

Shed on queue latency, not depth

// CoDel-style: how long has the oldest item been waiting?
type Item struct{ Req *http.Request; Enqueued time.Time }

func (q *Queue) admit(it Item) bool {
    if time.Since(q.oldest()) > 20*time.Millisecond {   // target sojourn
        return false                                     // we are behind: shed
    }
    return q.push(it)
}

// on dequeue, discard work whose caller has already gone
if time.Now().After(it.Deadline) { metrics.DeadWork.Inc(); continue }
Sojourn time adapts automatically when capacity changes; a depth threshold has to be retuned every time.

At the proxy

# Envoy — shed before the request reaches the application at all
overload_manager:
  resource_monitors:
    - name: envoy.resource_monitors.fixed_heap
      typed_config: { max_heap_size_bytes: 2147483648 }
  actions:
    - name: envoy.overload_actions.stop_accepting_requests
      triggers:
        - name: envoy.resource_monitors.fixed_heap
          threshold: { value: 0.95 }
Uniform protection for every service behind the proxy, with no application changes.
# nginx — crude but effective, and already installed
limit_conn_zone $binary_remote_addr zone=perip:10m;
limit_conn      perip 20;
limit_req_zone  $binary_remote_addr zone=rl:10m rate=100r/s;
limit_req       zone=rl burst=50 nodelay;
limit_req_status 503;
Per-client connection and request limits. Blunt — no priority awareness — but it beats having nothing.

Hysteresis and ramping

# shed a growing fraction instead of flipping a switch
def shed_fraction(sojourn_ms, target=20, ceiling=200):
    if sojourn_ms <= target:
        return 0.0
    return min(1.0, (sojourn_ms - target) / (ceiling - target))

if random.random() < shed_fraction(current_sojourn_ms):
    raise Shed(503, retry_after=1)
A ramp rather than a cliff: at 110 ms of sojourn you shed half, not everything, and the system settles instead of oscillating.

Pros & cons

Pros

  • Keeps goodput flat at capacity instead of collapsing toward zero under overload.
  • Lets you protect what matters: 100% of checkout rather than two thirds of everything.
  • Rejections are roughly 20,000× cheaper than timeouts, so protection costs almost nothing.
  • Fast failures give clients a chance to back off before a retry storm forms.
  • Keeps latency inside the SLO for admitted traffic, which preserves the error budget.
  • Buys the minutes autoscaling needs to add real capacity.

Cons

  • Users are refused on purpose, which needs an explicit product decision rather than an engineering one.
  • Priority classes require business agreement and must be propagated across every service.
  • Bad signals shed too early (wasting capacity) or too late (after collapse has begun).
  • Without hysteresis it flaps, producing wildly inconsistent behaviour for clients.
  • Rejections can look like an outage on dashboards unless counted separately.
  • Can mask under-provisioning: a system that sheds every day needs capacity, not more shedding.

Concrete use cases

Flash sale at 10× normal traffic

Capacity is 1,000 a second and 10,000 arrive. Without shedding, goodput falls to a few hundred and nobody can check out. With priority shedding, every checkout succeeds at normal latency while browse and recommendations are refused with a one-second Retry-After.

A dependency slows and takes everything with it

The pricing service goes from 20 ms to 800 ms. A concurrency limit per dependency means pricing calls queue and shed on their own, while the rest of the site — which does not need pricing — keeps serving at full speed.

One tenant's batch job

A customer starts a bulk export at 09:00 and consumes all the shared capacity. Per-tenant concurrency limits cap their share; their export is shed down to a trickle with Retry-After, and the other 400 tenants never notice.

Recovering from a cold cache

After a deploy, the cache is empty and every request hits the database, so effective capacity is a tenth of normal. Shedding on queue sojourn time detects this immediately, admits 10%, and lets the cache refill — instead of all traffic timing out while the database is hammered.

Protecting a write path from a read storm

A crawler hits expensive search endpoints. Cost-aware limits give search its own small pool, so the crawler exhausts search capacity only and order placement is untouched.

When to use / when not to

decide the priority order before the incident — at 03:00 it is not a design discussion

Use it when…

  • Demand can exceed capacity, even briefly — spikes, sales, retries, a slow dependency.
  • Some traffic is genuinely more valuable than other traffic.
  • You would rather serve 1,000 users well than 3,000 users badly.
  • Clients retry, so a slow failure is much more expensive than a fast one.
  • Autoscaling exists but takes minutes, and you need to survive the first two.

Avoid it when…

  • The producer can simply be slowed down. Use backpressure — nobody needs to be refused.
  • The issue is one client's quota, not your health. Use rate limiting.
  • A dependency is failing rather than slow. Use a circuit breaker.
  • You are shedding every day. Use more capacity — shedding is masking under-provisioning.
  • Every request is equally critical and must complete. Use a queue with a real SLA, and accept the latency.

Common mistakes & gotchas

Shedding after the expensive workA 503 returned after authentication, a database read and a downstream call costs exactly as much as a successful request. You have added a status code, not protection.
Fix: admission control goes first in the pipeline. Classify from headers, check one counter, reject. Everything expensive lives below that line.
Shedding on CPUCPU saturates late, moves in jumps, and tells you nothing when you are blocked on I/O — so you shed long after latency has already breached the SLO.
Fix: shed on queue sojourn time, or on concurrency in flight. Both are proportional to the thing users actually feel.
No priority classesRandom shedding destroys a third of your checkout traffic in order to protect a third of your recommendation traffic.
Fix: classify at the edge, propagate the class downstream, and give each class its own watermark so background work disappears first.
FlappingOne threshold means you shed, recover, shed, recover — several times a second — and clients see wildly inconsistent behaviour from one request to the next.
Fix: separate thresholds for entering and leaving, a smoothed signal, and a ramped shed fraction rather than an on/off switch.
Counting shed requests as errorsYour error-rate panel shows 70% failure and someone declares a sev-1, when the system is doing precisely what it was designed to do.
Fix: a distinct shed_total metric with class and reason labels, shown beside goodput. Keep them out of the error panel, but do count them against the SLI.
Forgetting Retry-AfterA rejection that costs 0.1 ms is wonderful until the client retries immediately, at which point you have built an extremely efficient way to be attacked by your own users.
Fix: always send Retry-After, require jittered exponential backoff in clients, and cap retries with a budget of around 10% of normal traffic.
Treating all requests as equal costShedding by request count protects you poorly when one report query costs as much as a thousand key lookups.
Fix: per-endpoint limits, weighted admission, or a separate smaller pool for expensive routes.
Shedding as a substitute for capacityA service that sheds a little every afternoon is not resilient; it is under-provisioned, and the shedding is hiding it.
Fix: alert when shedding happens outside genuine incidents. Shedding is for the minutes before autoscaling catches up, not for every Tuesday.

Alternatives

MechanismBest forComplexityCost / licenseKey difference vs load shedding
Load sheddingsurviving overload with goodput intactMediumfree—
Backpressurea producer that can be slowedLowfreePropagates "full" upstream; nobody has to be refused if the producer can wait
Rate limitingquotas, fairness, abuseLowfreeA contract fixed in advance, applied regardless of your current health
Circuit breakera dependency that is failingLowfreeProtects the caller from somebody else's failure, not yourself from your own load
Graceful degradationkeeping users served with lessMediumfreeDrops parts of a response instead of whole requests; pairs with shedding rather than replacing it
Autoscalingload that persists for minutesMediummore instancesAdds real capacity; far too slow for a spike, and bounded by downstream limits
Queue everythingasync work with no user waitingLowfreeDefers instead of refusing; only valid when nobody is watching a progress bar
  • Pick backpressure first when the producer is yours and can simply go slower.
  • Pick rate limiting for per-client fairness; most systems need both, for different reasons.
  • Pick graceful degradation for user-facing traffic — a lighter page beats an error page.
  • Pick autoscaling as the medium-term answer, with shedding covering the first minutes.
  • Pick queueing only when the work is genuinely asynchronous; for a waiting user a queue is just a slow rejection.
