Graceful degradation

Most of your page is optional. An outage should cost the user those parts, not all of them.

As of Nov 2026 · the product half of resilience engineering; examples in C# and TypeScript

A product page calls eight services: catalogue, pricing, stock, reviews, recommendations, personalisation, loyalty points and recently-viewed. Written naively, the page needs all eight, so its availability is the product of theirs — eight dependencies at 99.9% give 99.2%, which is six hours of downtime a year caused entirely by multiplication. Yet only two of those services are needed to sell anything.

Graceful degradation is the discipline of deciding, in advance, which parts of a feature are critical and which are optional, and making the optional ones fail invisibly. The reviews service going down should remove a reviews panel, not a revenue stream. Done well, the page's availability stops being the product of eight numbers and becomes the product of two.

It is the layer above the mechanics. A circuit breaker turns a slow failure into a fast one; load shedding decides which requests to refuse; backpressure bounds the queues. Graceful degradation decides what the user actually sees when those fire — and that is a product decision, which is why it fails most often not for technical reasons but because nobody ever asked the question.

Architecture / mental model

No extra hardware, no new replicas. The improvement comes entirely from deciding which failures are allowed to be the page's failure.

Key concepts

Graceful degradationDesigning a feature so that losing part of it costs the user that part, rather than the whole thing.
Critical dependencyOne whose failure genuinely means the feature cannot work — and the list is almost always shorter than the code implies.
Optional dependencyOne whose failure should change the page and not break it — the large majority, once you look.
Availability multiplicationThe arithmetic that makes this worth doing: mandatory dependencies in series multiply, and the result falls fast.
Fallback ladderAn ordered list of progressively worse but still useful answers, tried in turn before giving up.
Stale-while-errorServing the last known good value when the source is unavailable — usually the highest-value rung on the ladder.
Static stabilityDesigning so that a failure causes the system to keep doing what it was already doing, rather than needing something to work.
Fail softThe implementation rule for optional dependencies: their failure must be unable to reach the response.
Degradation levelsNamed, testable modes — full, reduced, minimal, read-only — rather than an unbounded space of partial failures.
Feature flagsThe manual control: turning expensive features off deliberately during an incident, rather than waiting for them to fail.
Hard failThe decision to show an honest error rather than a plausible-looking wrong answer.
Honest signallingTelling the user what is missing, in their terms, instead of silently showing less.
Progressive enhancementThe front-end sibling: build the working baseline first, then layer improvements that may not arrive.
Testing degradationDegraded paths only work if they are exercised — and they are the least exercised code you own.
Game dayDeliberately breaking a dependency in production, with everyone watching, to find out what actually happens.
Measuring degradationTracking which mode you are in, so "degraded" is a state you can see rather than infer.

Essential code patterns

Separate the critical from the optional

// critical: if these fail, there is no page — so let them throw
var product = await _catalogue.GetAsync(id, ct);
var price   = await _pricing.GetAsync(id, ct);

// optional: each one isolated, and unable to break the render
var reviews = await Optional(() => _reviews.GetAsync(id, ct));
var recs    = await Optional(() => _recs.GetAsync(id, ct),  fallback: Bestsellers);
var stock   = await Optional(() => _stock.GetAsync(id, ct), fallback: CachedStock);

return View(new ProductPage(product, price, reviews, recs, stock));
The classification is visible in the code. A reviewer can see at a glance which failures are allowed to reach the user.
static async Task<T?> Optional<T>(Func<Task<T>> call, Func<T>? fallback = null)
{
    try
    {
        using var cts = new CancellationTokenSource(TimeSpan.FromMilliseconds(200));
        return await call();                        // its own tight budget
    }
    catch (Exception ex)                            // timeout, breaker-open, anything
    {
        Metrics.FallbackUsed.WithLabels(typeof(T).Name).Inc();
        Log.Information(ex, "optional dependency degraded");   // information, not error
        return fallback is null ? default : fallback();
    }
}
A 200 ms budget matters as much as the catch: an optional call with no timeout does not break the page, it just makes it slow — which users experience as broken anyway.
async def optional(coro, *, fallback=None, timeout=0.2):
    """An optional dependency: may be absent, may never break the render."""
    try:
        return await asyncio.wait_for(coro, timeout)   # its own tight budget
    except Exception as exc:                            # timeout, breaker open, anything
        metrics.fallback_used.labels(type(exc).__name__).inc()
        log.info("optional dependency degraded", exc_info=exc)
        return fallback

# critical: let these propagate — without them there is no page
product, price = await asyncio.gather(catalogue.get(sku), pricing.get(sku))

# optional: each isolated, none able to break the render
reviews = await optional(reviews_api.get(sku))
recs    = await optional(recs_api.get(sku), fallback=BESTSELLERS)
The timeout matters as much as the except: an optional call with no budget does not break the page, it just makes it slow.

The fallback ladder

async Task<Price?> GetPrice(string sku, CancellationToken ct)
{
    if (await _cache.TryGetFresh(sku) is { } fresh) return fresh;   // 2 · fresh cache

    try { return await _pricing.GetAsync(sku, ct); }                // 1 · live
    catch (Exception)
    {
        if (await _cache.TryGetStale(sku, maxAge: TimeSpan.FromHours(1)) is { } stale)
            return stale with { IsStale = true };                   // 3 · stale cache
        return null;                                                // 5 · hide the price
    }
}
// note: no rung 4 here. Inventing a price would be worse than showing none.
Most code implements rung 1 and rung 5 only, and throws away the most valuable options in between.
# HTTP does rungs 2 and 3 for you
Cache-Control: max-age=60, stale-while-revalidate=600, stale-if-error=3600

# stale-if-error: if the origin fails, keep serving the cached copy
# for up to an hour rather than returning an error page
One header turns a CDN into a degradation layer. `stale-if-error` is the highest-value rung for read-heavy sites.

Named levels, not 256 combinations

public enum RenderLevel { Full, Reduced, Minimal, ReadOnly }

RenderLevel Current() =>
    _db.IsFailingOver          ? RenderLevel.ReadOnly :
    _load.InFlight > 0.90 * _limit ? RenderLevel.Minimal  :
    _flags.IsOff("recs") || _recsBreaker.IsOpen ? RenderLevel.Reduced :
    RenderLevel.Full;

Metrics.RenderLevel.WithLabels(level.ToString()).Inc();   // see it, don't infer it
Four named states you can screenshot, test and rehearse — instead of an unbounded space of partial failures nobody has ever seen.

Never block the render on the front end

// critical data is server-rendered; optional panels arrive later, or never
const reviews = useQuery({
  queryKey: ['reviews', sku],
  queryFn:  () => fetchReviews(sku, { signal: AbortSignal.timeout(2000) }),
  retry: false,                 // never retry on a user's critical path
});

if (reviews.isError) return null;      // the panel disappears; the page does not
Returning null is the design. A panel that throws on an empty list has moved the failure rather than handled it.
<!-- third-party scripts are optional dependencies too -->
<script src="https://cdn.example/widget.js" async defer
        onerror="window.__widgetUnavailable = true"></script>
<!-- never render-blocking, never awaited, never on the critical path -->
A synchronous third-party tag makes an external vendor a critical dependency of your checkout, usually without anyone deciding that.

Prove it works

[Theory]
[InlineData("reviews")] [InlineData("recs")]
[InlineData("stock")]   [InlineData("loyalty")]
public async Task Page_still_sells_when_optional_dependency_is_down(string dep)
{
    _harness.Break(dep);                       // fault injection

    var page = await _client.GetAsync("/p/nikon-z6-iii");

    page.StatusCode.Should().Be(HttpStatusCode.OK);
    page.Should().Contain("Add to basket");    // the critical path survives
    page.Should().Contain("£1,999");
}
One test per optional dependency. This is the cheapest insurance in the whole pattern, and the thing almost nobody writes.

What to measure

render_level_total{level="full|reduced|minimal|readonly"}
fallback_used_total{dep="reviews",rung="omit"}
sli_journey_success{journey="purchase"}      # could the user still buy?
sli_experience_full{journey="purchase"}      # did they get everything?

# alert: render_level{level!="full"} sustained for > 1 h
# (otherwise a feature stays quietly degraded for months)
Two SLIs, deliberately. The first protects the business; the second stops permanent silent degradation nobody notices.

Pros & cons

Pros

  • Breaks the availability multiplication: your page stops inheriting every dependency's downtime.
  • Far cheaper than the alternative — classification and error handling instead of replicas and regions.
  • Turns most incidents into partial, survivable events rather than outages.
  • Protects revenue specifically, because the critical path is identified and defended.
  • Gives operators deliberate levers (flags, levels) during an incident.
  • Forces a useful conversation about what the product actually needs.

Cons

  • Degraded paths are rarely executed, so they rot silently unless tested.
  • More code paths and more states to reason about and screenshot.
  • Requires product decisions that engineering cannot make alone.
  • Silent degradation can hide a broken feature for months.
  • Stale data is wrong data — acceptable for a price, dangerous for a balance.
  • Tempting to over-apply: some things genuinely must fail loudly.

Concrete use cases

Reviews down, sales unaffected

The reviews service fails for forty minutes. Previously this returned a 500 on every product page. With the panel marked optional and wrapped in a 200 ms timeout, pages render without a reviews section and conversion is statistically unchanged. Nobody is paged.

Pricing degraded, not dead

The pricing service becomes slow. The page serves prices from cache up to an hour old with a small "prices updated 14:02" note. Customers keep buying at prices that are correct to within an hour, instead of seeing an error page.

Database failover: read-only mode

A primary fails over, taking writes out for three minutes. The site enters read-only: browsing, search and account viewing all work; the basket shows "we can't take orders for a few minutes". Three minutes of partial service instead of three minutes of nothing.

Capacity reclaimed by switching features off

During a traffic spike, operators flip flags to disable the heavy search ranker and personalisation. Effective capacity rises roughly 40% within seconds, and the site serves everyone with slightly less relevant results — a far better outcome than shedding a third of users.

A third-party tag taking down checkout

An analytics vendor's CDN stalls and the synchronous script tag blocks rendering on every page. Moving it to async with an error handler converts a vendor outage from a site outage into a gap in the analytics data.

When to use / when not to

list your dependencies, mark each critical or optional — that one-hour exercise is most of the value

Use it when…

  • A feature calls more than two services, so availability multiplication is working against you.
  • Some of what you show is genuinely optional — which is nearly always true of a page.
  • Partial service is meaningfully better than no service for the business.
  • You have expensive features that could be switched off to reclaim capacity.
  • Your SLO is higher than the product of your dependencies' SLOs.

Avoid it when…

  • A wrong answer is worse than no answer. Use a hard fail — fraud, authorisation, payments.
  • Everything in the response is genuinely required. Use redundancy and accept the multiplication.
  • The problem is your own overload, not a dependency. Use load shedding — though degrading first is usually kinder.
  • You cannot test the degraded paths. Use fewer fallbacks, well exercised, rather than many that rot.
  • It would hide a chronic failure. Use alerting on degraded mode so silent degradation cannot become permanent.

Common mistakes & gotchas

Optional dependencies that can break the pageMarked optional in the design document and awaited without a timeout in the code, so its failure still returns a 500. This is the single most common degradation bug.
Fix: wrap every optional call — its own timeout, its own breaker, a nullable result — and add one test per dependency asserting the critical path still works.
No timeout on an optional callIt does not fail your page; it makes it take eight seconds. Users cannot tell the difference between slow and broken, so you got the worst of both.
Fix: give optional calls a tight budget — 100–300 ms — and treat exceeding it as absence. Slow is a failure mode too.
Fallbacks that were never executedThe static default references a product deleted a year ago, the cached shape has drifted, and the empty-state template throws. Discovered at the worst possible moment.
Fix: unit-test each fallback, integration-test each named level, inject faults in staging, and run an announced game day in production.
Degrading something correctness-criticalThe fraud check times out, so the code "degrades" by approving the payment. That is not resilience; it is a security incident with good manners.
Fix: decide fail-open or fail-closed per dependency and write it next to the classification. Correctness paths fail closed, always.
Silent permanent degradationA panel breaks, the fallback hides it, nobody notices for four months — and the dashboards show 100% availability the whole time.
Fix: alert when degraded mode persists beyond an hour, and keep a second SLI for "got the full experience" alongside "completed the task".
Stale data with no label and no limitAn hour-old price is fine. An hour-old account balance shown as current is a support ticket, and an hour-old permission check is a breach.
Fix: set a maximum staleness per data type, label it where a user might act on it, and never serve stale authorisation data at all.
Too many modes to testEight optional dependencies give 256 combinations. Nobody tests 256 things, so in practice none of them are tested.
Fix: collapse to three or four named levels, make each a test fixture, and assert the critical journey in every one.
Third-party scripts as hidden critical dependenciesA synchronous vendor tag makes an external CDN a blocking dependency of your checkout, and nobody ever decided that it should be.
Fix: load third-party scripts async with an error handler, never block render on them, and audit the tags on your critical pages.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs graceful degradation
Graceful degradationfeatures with optional partsMediumfree; cost is testing—
Redundancycritical dependenciesMediummore infrastructureMakes the dependency more available instead of needing it less; the only option when nothing is optional
Circuit breakerfailing dependenciesLowfreeSupplies the fast, clean failure that degradation then acts on — a prerequisite, not an alternative
Load sheddingyour own overloadMediumfreeRefuses whole requests; degradation serves a smaller response to everyone
Cachingread-heavy dataLowa cache nodeProvides the stale rungs of the ladder; stale-if-error is degradation in a header
Hard failcorrectness-critical pathsVery lowfreeThe correct answer when a wrong result costs money or safety
Queue it for laterwrites that can be asyncMediumfreeAccepts now, completes later; only works when the user does not need the result immediately
  • Pick redundancy for the two or three genuinely critical dependencies — there is nothing to degrade to.
  • Pick a circuit breaker underneath this: degradation needs a fast, deterministic failure to react to.
  • Pick caching as the mechanism for the middle rungs; stale-if-error is the cheapest win available.
  • Pick load shedding when the problem is volume rather than a broken dependency — but degrade before you shed.
  • Pick a hard fail whenever a plausible-looking wrong answer would be worse than an honest error.
