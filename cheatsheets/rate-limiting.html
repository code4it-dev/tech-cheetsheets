Rate limiting

Say no on purpose, before the system says no by falling over.

As of Nov 2026 · the algorithms are stable; only the implementations move

Every service has a capacity. Rate limiting is the decision, taken on each request, of whether this caller may proceed now — and the cheap, predictable rejection (429 Too Many Requests) when they may not. Without it, one buggy retry loop, one scraper or one noisy tenant consumes the capacity everybody else is paying for.

All the common algorithms answer the same question — "how many requests has this key made recently?" — and differ only in how they measure "recently" and how much burst they forgive. Fixed window counts per clock minute; sliding window smooths the boundary; token bucket saves up credit for bursts; leaky bucket flattens bursts into a constant output rate; GCRA gets the same answer from a single timestamp.

You meet rate limiting in three places at once: at the edge (CDN, API gateway, nginx), in the application (ASP.NET Core's RateLimiter middleware, Envoy, a Redis script), and on the client side as the retry and backoff logic that has to live with somebody else's limits. The algorithms below are the same in all three.

Architecture / mental model

Limit twice: coarsely at the edge so floods never reach your code, and precisely in the app where you know who the caller is and what they paid for.

How it works

Every algorithm below is fed exactly the same nine requests, from one API key, against the same limit of 5 per minute. Only the bookkeeping differs — and it produces a different set of rejections each time. Step through them in order and then read the comparison at the end.

Three things fall out of that table that are hard to see from the descriptions alone:

  • The fixed window and the token bucket both allowed eight requests — but rejected different ones. The fixed window refused number 6 because a clock ticked, then waved through three more a second later. The token bucket let 6 through because the caller had been quiet for 28 seconds, and refused 9 because the sustained rate really had been exceeded. Only one of those is a limiter measuring what it claims to measure.
  • GCRA and the token bucket are the same algorithm. Identical verdicts, identical retry-after, from one timestamp instead of a counter plus a timestamp. If your store makes a single atomic value easier than a hash, prefer GCRA.
  • The leaky bucket is not in the same business as the others. It never returned an error; it converted the excess into 56 seconds of latency. That is the right trade only when the thing behind it is more fragile than the caller is impatient.

Choosing, in one line each:

  • Sliding window counter for a public API. Near-exact, two integers, no boundary burst. This is the default.
  • Token bucket (or GCRA) when bursts are legitimate, or when you want to charge expensive endpoints more than one token.
  • Sliding window log for small, high-value limits where every single call matters — login attempts, one-time codes, payments.
  • Fixed window for internal APIs with generous limits, where the cheapest correct-ish thing wins.
  • Leaky bucket in front of something fragile, when added latency is cheaper than a rejection.

Key concepts

limit and windowThe policy itself: N requests per unit of time, e.g. 100 / minute. Everything else is how you measure the window.
quota keyWhat you count per: API key, user id, tenant, IP, endpoint, or a combination. Choosing it wrong is the most common design mistake.
fixed window counterOne counter per clock period: INCR a key named after the current minute, reject above the limit, let it expire. The cheapest correct-ish option.
sliding window logStore the timestamp of every request, drop the ones older than the window, count what is left. Exact, and the most expensive.
sliding window counterTwo fixed windows, weighted: prev x overlap + current. Nearly as accurate as the log, at the cost of a fixed window.
token bucketA bucket refills at a constant rate up to a capacity; each request spends one token. Capacity sets the burst, refill rate sets the sustained rate.
leaky bucketArrivals queue in a bucket that drains at a fixed rate; overflow is dropped. Output is perfectly smooth, at the price of added latency.
GCRAGeneric Cell Rate Algorithm: a leaky bucket stored as a single timestamp, the "theoretical arrival time". One field, exact, no boundary burst.
burstHow far above the sustained rate a caller may go for a short time. Some burst is a feature: it absorbs page loads that fire ten calls at once.
429 and Retry-AfterThe HTTP contract: status 429, a Retry-After header in seconds, and RateLimit-* headers so clients can self-regulate before being rejected.
distributed countersWith n instances behind a load balancer the counter must be shared and the check must be atomic, usually one Redis round trip running a Lua script.
local vs centralizedCount per instance (fast, approximate, drifts with autoscaling) or in a shared store (exact, adds a network hop). Many systems do both.
concurrency limitingCapping requests in flight with a semaphore rather than requests per second. Often the limit that actually protects you.
load sheddingDropping work when the system itself is in trouble, regardless of whose quota it is. A rate limit is a contract; shedding is survival.
backpressurePushing the "slow down" signal upstream instead of silently queueing. A bounded queue that blocks the producer is backpressure; an unbounded one is a time bomb.
jitterRandomness added to retry delays and to window or cache expiry so that clients do not all come back at the same instant.

Essential commands & syntax

ASP.NET Core (built-in middleware)

builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    o.AddFixedWindowLimiter("fixed", opt =>
    {
        opt.PermitLimit = 100;
        opt.Window = TimeSpan.FromMinutes(1);
        opt.QueueLimit = 0;
    });
});
app.UseRateLimiter();
A fixed-window limiter named fixed that rejects instead of queueing.
o.AddTokenBucketLimiter("burst", opt =>
{
    opt.TokenLimit = 20;                               // burst capacity
    opt.TokensPerPeriod = 5;                           // sustained rate
    opt.ReplenishmentPeriod = TimeSpan.FromSeconds(1);
    opt.AutoReplenishment = true;
});
Token bucket: 5 requests/second sustained, up to 20 in a burst.
o.AddPolicy("per-tenant", ctx => RateLimitPartition.GetSlidingWindowLimiter(
    partitionKey: ctx.User.FindFirst("tenant")?.Value
                  ?? ctx.Connection.RemoteIpAddress!.ToString(),
    _ => new SlidingWindowRateLimiterOptions
         { PermitLimit = 600, Window = TimeSpan.FromMinutes(1), SegmentsPerWindow = 6 }));
A sliding window partitioned per tenant, falling back to the caller's IP.
app.MapGet("/reports/{id}", Handler).RequireRateLimiting("per-tenant");
Applies a named policy to one endpoint; [EnableRateLimiting] does the same on controllers.
o.OnRejected = async (ctx, _) =>
{
    if (ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retry))
        ctx.HttpContext.Response.Headers.RetryAfter = ((int)retry.TotalSeconds).ToString();
};
Adds the Retry-After header, which the framework does not send by default.

Redis (shared counters across instances)

INCR rl:acme:202611101005
EXPIRE rl:acme:202611101005 120 NX
Fixed window: one counter per minute, self-cleaning. NX keeps the first TTL.

Sliding window log: trim, count, record. Wrap it in a Lua script to make it atomic.

# -> 0 16 30 -1 2   (allowed, remaining, limit, retry_after, reset_after)
GCRA in one command via the redis-cell module: burst 15, 30 per 60 s.
EVALSHA $sha 1 rl:acme $(date +%s) 5 20
Runs the token-bucket Lua script atomically: one round trip, no race.

Edge and proxy

limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
server {
  location /api/ {
    limit_req zone=api burst=20 nodelay;
    limit_req_status 429;
  }
}
nginx leaky bucket: 10 r/s per IP, 20 burst served immediately with nodelay. A 10 MB zone holds roughly 160k addresses.
limit_req zone=api burst=20;      # without nodelay
Same limit, but the burst is queued and released at 10 r/s: the shaping form of a leaky bucket.
<rate-limit-by-key calls="600" renewal-period="60"
    counter-key="@(context.Subscription.Id)"
    remaining-calls-header-name="RateLimit-Remaining" />
An Azure API Management policy: a per-subscription limit enforced before your code runs.

Python, client side (living with someone else's limit)

import random, time, httpx

def call(url, attempt=0):
    r = httpx.get(url)
    if r.status_code == 429 and attempt < 5:
        wait = float(r.headers.get("Retry-After", 0)) or min(60, 2 ** attempt)
        time.sleep(random.uniform(0, wait))      # full jitter
        return call(url, attempt + 1)
    return r
Honours Retry-After, falls back to exponential backoff, jitters so retries never synchronise, and gives up.
r.headers["RateLimit-Remaining"]   # slow down before you are rejected
Read the budget on successful responses: the cheapest way to never see a 429.

Pros & cons

Pros

  • Turns an unbounded failure (everything times out) into a bounded, explainable one (some calls get a 429).
  • Rejection is orders of magnitude cheaper than service, so you can say no to far more traffic than you could ever serve.
  • Fairness between tenants: one customer's bad deploy stops being everyone's incident.
  • Caps cost directly when per-request spend is real — LLM tokens, SMS, metered third-party APIs.
  • A credible defence against credential stuffing, scraping and enumeration, at almost no engineering cost.
  • The policy is a documented contract, so client authors can build correct backoff instead of guessing.

Cons

  • A shared counter puts a network hop and a hard dependency on the hot path of every request.
  • Limits are guesses until measured: too tight breaks correct clients, too loose protects nothing.
  • Rate limits do not protect against slow dependencies — only a concurrency limit does.
  • Keys are gameable: IPs rotate, accounts are free, and NAT makes IP limits punish innocents.
  • Rejections push work onto clients, and badly written clients answer a 429 with more retries.
  • Many layers of limiter (CDN, gateway, app, connection pool) interact in ways nobody has modelled.

Concrete use cases

Public API with paid tiers

A SaaS sells Free (60 req/min), Pro (600) and Enterprise (6,000). A token bucket keyed on the API key, with capacity around a tenth of the minute limit, allows natural page-load bursts while enforcing the sustained rate. RateLimit-* headers on every response let customers build their own dashboards, and upgrade when they see themselves hitting the ceiling.

Login endpoint under credential stuffing

An attacker tries one password against a million accounts from a botnet. An IP limit alone fails (thousands of IPs) and an account limit alone fails (one attempt each). Two limiters in series — 10 attempts per 15 min per account and 50 per hour per IP, with a sliding window log for exactness — make the attack uneconomic while a user who mistypes twice notices nothing.

Protecting a legacy backend

An ERP accepts 20 writes per second before it starts timing out. The integration service puts a queueing leaky bucket in front: bursts from the webshop queue up and drain at 18/s, with a bounded queue that returns 503 when full. The ERP never sees a spike, and the webshop sees a few seconds of extra latency instead of a failed sync.

Fan-out to a metered third party

A fleet of workers on Kubernetes calls a geocoding API billed per request and capped at 500/s for the whole account. Per-pod limits overshoot whenever the deployment scales, so the workers share one Redis token bucket at 450/s, leaving 10% of headroom. The limiter doubles as the cost cap.

Shedding load during an incident

A payments service degrades when its database fails over. A concurrency limiter caps in-flight requests at 200; beyond that, requests tagged background (reconciliation, reporting) are shed with 503 while interactive checkout traffic is still served. The service stays up at reduced function instead of queueing itself to death.

When to use / when not to

If you can't name the key and the number, you don't have a rate limit — you have a vibe.

Use it when…

  • The endpoint is reachable by anyone on the internet, authenticated or not.
  • One caller can plausibly consume capacity that other callers paid for.
  • A request costs real money: LLM tokens, SMS, a metered partner API.
  • The endpoint is a known abuse target: login, signup, password reset, search, export.
  • You depend on something with a published limit you must not exceed as a fleet.
  • You need a hard answer to "what happens when traffic is 10x normal?"

Avoid it when…

  • The real risk is slow dependencies, not request volume. Use a concurrency limit / bulkhead plus timeouts.
  • The caller is one trusted internal service with predictable traffic. Use capacity planning and alerts; a limit there only adds an outage mode.
  • Work is already pull-based through a queue. The consumer's own pace is the limit, so use Apache Kafka or a job queue, not an HTTP limiter.
  • You only want to bound cost after the fact. Use budgets and quota alerts, not per-request rejection.
  • Traffic is bursty by design and must not be dropped. Use a bounded queue and process asynchronously.
  • You cannot identify callers at all. Fix authentication first, or you are only limiting IP addresses.

Common mistakes & gotchas

Read, decide, then increment — in two round tripsTwo instances both read 99 against a limit of 100 and both allow. Under load this leaks far more than it looks, because the window of the race is a whole network round trip.
Fix: make the check-and-update one atomic operation — a Lua script, CL.THROTTLE, or a single INCR whose return value is the decision.
Dividing the global limit by the instance count"6,000/min across 10 pods, so 600 each" breaks the moment the load balancer is uneven or Kubernetes scales to 12. Some callers get rejected at half the advertised limit.
Fix: use a shared store for anything customer-facing, or a local bucket that reconciles with a shared allowance. If you must divide, over-provision each share and accept the overshoot.
Rejecting with no Retry-AfterThe client cannot tell whether to come back in 1 second or 10 minutes, so it retries immediately — turning one rejection into a retry storm that keeps the limit permanently exhausted.
Fix: always send Retry-After plus RateLimit-Remaining and RateLimit-Reset, including on successful responses so clients can slow down pre-emptively.
Counting after the expensive workThe limiter sits behind authentication, deserialisation and a database lookup, so each rejected request still costs most of a served one. Under attack the limiter itself becomes the bottleneck.
Fix: limit as early as the key allows — IP at the edge, API key right after a cheap token check — and keep the 429 response body tiny.
Trusting X-Forwarded-For blindlyAnyone can send that header. If your limiter reads the leftmost value, an attacker rotates a fake IP per request and the per-IP limit never triggers.
Fix: take the client IP from the rightmost trusted hop, configure your proxy's known-networks list (ForwardedHeadersOptions.KnownProxies in ASP.NET Core), and limit IPv6 by /64 rather than by full address.
No decision about what happens when the store is downRedis blips and either every request is rejected (fail-closed, a self-inflicted outage) or every request is allowed (fail-open, undefended) — whichever your library happened to choose.
Fix: choose per endpoint, write it down, and test it. Fail open for ordinary read APIs with a short timeout; fail closed for login and anything that spends money.
Health checks sharing the limitProbes, synthetic monitors and admin tooling consume quota, so a traffic spike makes your monitoring go red for the wrong reason — or hides a real outage behind 429s.
Fix: exempt health and readiness endpoints explicitly, and give internal service accounts their own key and their own policy.
Counting requests when the cost varies 100xA limit of 100/min treats a cached key lookup and a 30-second report export identically, so the cheap path is throttled while the expensive one still melts the database.
Fix: use a weighted token bucket — charge tokens proportional to cost — or add a separate, much tighter limit on the expensive routes.

Alternatives

ApproachBest forComplexityCost / licenseKey difference vs a rate limit
Rate limitingfairness, abuse, cost caps per callerLow–mediumfree in most frameworks—
Concurrency limit / bulkheadprotecting threads, pools and slow dependenciesLowfree (Polly, semaphores)Caps work in flight, not per second; survives latency spikes a rate limit ignores
Circuit breakera dependency that is already failingLowfree (Polly, Resilience4j)Reacts to errors, not volume; stops calling rather than stops being called
Queue + async processingbursty work that must not be droppedMediuminfrastructure costDefers instead of rejecting; changes the API contract to asynchronous
Autoscalinggenuine, paid-for growth in demandMediumpay per instanceBuys capacity instead of refusing work; too slow for a sudden burst, unbounded in cost
CAPTCHA / proof of workbots on signup and login flowsMediumfree to paidRaises the price per attempt instead of capping the count; hurts real users too
WAF / bot managementdistributed abuse from rotating IPsMedium–highpaid serviceIdentifies who to block from behaviour; a rate limit only counts
  • Pick a concurrency limit if your incidents start with "the database got slow" rather than "traffic spiked".
  • Pick a circuit breaker if you are the caller and the thing you call is unhealthy.
  • Pick a queue if dropping the request is unacceptable and the client can be told "accepted, check back later".
  • Pick autoscaling if the extra traffic is revenue and you would rather pay than reject.
  • Pick a WAF if the abuse already rotates across thousands of IPs and accounts; counting alone cannot see it.
  • In practice, production systems run a rate limit and a concurrency limit and a circuit breaker. They fail differently, so they cover for each other.
