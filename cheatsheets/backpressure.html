Backpressure

When a fast producer meets a slow consumer, the queue between them is not a solution. It is where the outage is hiding.

As of Nov 2026 · examples in C#, Go, Java and Python; the idea is as old as TCP

A producer sends 1,000 requests a second to a consumer that can handle 800. That mismatch does not go away because you put a queue in the middle — the queue just absorbs it, growing by 200 items every second, converting a throughput problem into a latency problem and eventually into an out-of-memory crash. Backpressure is the mechanism that makes the mismatch visible at the producer instead of hiding it in RAM.

Mechanically it is almost always the same thing: bound the queue, then decide what happens when it is full. The consumer stops accepting, the producer's send blocks or fails, and that signal propagates upstream until it reaches somebody who can actually do something — slow down, buy more capacity, or refuse the work. Sophisticated versions make the signal explicit rather than implicit: TCP's receive window, Reactive Streams' request(n), gRPC flow control and Kafka's fetch limits are all the consumer telling the producer exactly how much it may send.

It is worth being precise about what backpressure is not. It does not create capacity, and on its own it does not decide what to drop — it only moves the problem to where a decision can be made. Deciding to refuse work is load shedding; protecting a caller from a failing dependency is a circuit breaker; limiting one client's share is rate limiting. Backpressure is the plumbing that makes all three possible.

Architecture / mental model

The queue is where the mismatch goes. Bounding it does not create capacity — it forces somebody to decide, while the decision is still cheap.

Key concepts

BackpressureThe signal that a consumer cannot keep up, propagated upstream so the producer slows down instead of the queue growing.
Bounded queueA buffer with a maximum size, which is what turns "the queue grows" into an actual signal.
Unbounded queueThe default in most libraries, and a reliable way to turn a small overload into a crash.
Little's LawL = λW — the arithmetic that converts a queue depth into a latency, and therefore sizes every buffer you own.
Demand signallingExplicit backpressure: the consumer tells the producer exactly how many items it may send.
Credit-based flow controlThe concrete protocol behind demand signalling: a window of permits that the consumer replenishes as it drains.
Queue latencyHow long an item waits, which matters far more than how many items are waiting.
Dead workProcessing requests whose callers have already given up — the main reason an overloaded system never recovers.
Retry amplificationClients retrying a slow system, multiplying the arrival rate exactly when it is least able to cope.
Concurrency limitCapping how many requests are in flight at once — the most practical backpressure mechanism in a service.
Adaptive concurrencyDiscovering the right limit at runtime by watching latency, instead of configuring a number that is wrong by next quarter.
Head-of-line blockingOne slow item at the front of a queue delaying everything behind it, however fast those would have been.
BufferbloatThe networking name for the same mistake: oversized buffers destroying latency while preserving throughput.
Non-blocking backpressureSignalling fullness without parking a thread — essential in async and event-driven runtimes.
Lossy backpressureWhen you cannot slow the producer — sensors, market data, user events — so you drop deliberately instead.
End-to-end backpressureThe signal is only useful if it reaches a component that can act — usually the edge, or the job scheduler.
Queue as a shock absorberThe legitimate use: absorbing short bursts, with a bound set by how long a burst can last.

Essential code patterns

Bound the queue

// .NET — the bound and the full-policy are one decision
var ch = Channel.CreateBounded<Job>(new BoundedChannelOptions(capacity: 20)
{
    FullMode = BoundedChannelFullMode.Wait,   // Wait | DropOldest | DropNewest | DropWrite
    SingleReader = true,
});

// producer: yields instead of blocking a thread
if (!ch.Writer.TryWrite(job))
    await ch.Writer.WriteAsync(job, ct);      // completes when there is room
`CreateUnbounded` is the same API with the safety removed. Choosing a capacity forces you to choose a full-policy too.
// Go — a buffered channel IS the bounded queue; select gives you the policy
jobs := make(chan Job, 20)

select {
case jobs <- job:            // room available
default:
    shed(job)                 // full: drop, and say so
}
An unbuffered channel blocks until a receiver is ready, which is the strictest and often the most honest backpressure available.
# Python asyncio — maxsize is the whole mechanism
q = asyncio.Queue(maxsize=20)

try:
    q.put_nowait(job)            # raises QueueFull instead of growing
except asyncio.QueueFull:
    metrics.shed.inc()
    raise HTTPException(503, headers={"Retry-After": "1"})
`asyncio.Queue()` with no maxsize is unbounded. The default is the bug.

Limit concurrency instead of rate

// a semaphore is backpressure in four lines
private readonly SemaphoreSlim _limit = new(initialCount: 60);   // L = λ × W = 1000/s × 60ms

if (!await _limit.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
    return Results.StatusCode(503);          // fail fast, do not queue

try     { return await Handle(req, ct); }
finally { _limit.Release(); }
Sized by Little's Law, with a short acquisition timeout so a rejected request costs 50 ms rather than a full client timeout.
# Envoy — concurrency limiting and adaptive limits at the proxy
http_filters:
  - name: envoy.filters.http.adaptive_concurrency
    typed_config:
      gradient_controller_config:
        concurrency_limit_params: { max_concurrency_limit: 200 }
        min_rtt_calc_params: { interval: 30s, request_count: 50 }
The proxy measures minimum round-trip time and shrinks the limit as latency rises — TCP congestion control applied to HTTP.

Discard dead work

// deadline travels with the request; check it on dequeue
var job = await ch.Reader.ReadAsync(ct);

if (job.DeadlineUtc < DateTime.UtcNow)
{
    metrics.DeadWork.Inc();
    continue;              // the caller has already given up — do not pay for it
}
One comparison recovers all the capacity an overloaded system wastes on abandoned requests.
// gRPC and HTTP already carry deadlines — propagate, never invent
grpc-timeout: 800m                 // gRPC
traceparent / X-Request-Deadline   // or your own convention
// each hop passes the REMAINING budget, not a fresh one
A service that starts a fresh timeout on every hop guarantees total latency is the sum of all of them.

Message consumers

# Kafka — fetch less, and pause when you fall behind
max.poll.records=100            # bound the batch
max.poll.interval.ms=300000     # exceed it and you are kicked from the group

# in code: stop fetching rather than buffering in memory
consumer.pause(assignment)      # lag grows in the broker, where it is safe
consumer.resume(assignment)
Consumer lag is backpressure you can see. Letting it build in the broker is correct; buffering it in your heap is not.
# RabbitMQ / AMQP — prefetch is the credit window
channel.basic_qos(prefetch_count=20)   # at most 20 unacked per consumer
# default is unlimited: the broker will happily push you into an OOM
`prefetch_count` is credit-based flow control under another name — and its default is the unbounded one.

Reactive streams

// Java / Reactor — the subscriber states its demand
flux.limitRate(100)                         // request(100), then 75 more each time
    .onBackpressureDrop(job -> shed(job))   // explicit policy, not a silent buffer
    .concatMap(this::handle);               // one at a time; no hidden fan-out
`onBackpressureBuffer()` with no bound re-creates the original problem inside the stream library.

What to measure

queue_sojourn_seconds{quantile="0.99"}   # what users feel — alert on this
queue_depth                              # memory pressure only
queue_oldest_item_age_seconds            # are we falling behind right now?
enqueue_rejected_total                   # backpressure is engaging
concurrency_limit / concurrency_in_use   # how close to the wall
Depth alone pages too early or far too late. Sojourn time is the metric that corresponds to the user's experience.

Pros & cons

Pros

  • Bounds latency by bounding queue depth — Little's Law does the rest automatically.
  • Turns a silent, delayed memory crash into an immediate, visible, attributable signal.
  • Makes overload fail fast, which removes most of the fuel for retry amplification.
  • Adapts to dependency slowdowns on its own when expressed as a concurrency limit.
  • Costs almost nothing: usually a capacity argument and a full-policy.
  • Prevents wasted work by rejecting before expensive processing rather than after.

Cons

  • It does not create capacity — it only decides where the pain surfaces.
  • A bound that is too small turns normal bursts into spurious rejections.
  • Blocking producers can deadlock if the producer is also, indirectly, the consumer.
  • The signal is useless unless it reaches a layer that can actually act on it.
  • Some producers cannot be slowed at all, so you need a drop policy as well.
  • Requires deadline propagation to be fully effective, which is a cross-team change.

Concrete use cases

The service that dies an hour after the spike

Traffic rises 20% at 09:00 and the service OOMs at 10:15 with no errors in between. An unbounded work queue had been absorbing the difference the whole time. Bounding it at 200 items turns the same event into a visible 3% rejection rate and no restart.

Consumer lag that became a heap problem

A Kafka consumer prefetches aggressively and buffers in memory to "smooth things out". When the downstream API slows, the heap fills. Reducing max.poll.records and pausing the partitions lets the lag accumulate in the broker, where it is cheap, observable and recoverable.

An ingestion pipeline faster than its sink

A file importer reads 50,000 rows a second into a database that writes 8,000. A bounded channel between them makes the reader wait, so memory stays flat and the import takes exactly as long as the database allows — which it was always going to.

Market data that must never queue

Price ticks arrive faster than the UI can render. The producer cannot be slowed, so a one-slot conflating buffer keeps only the latest price per instrument: no backlog, no stale renders, and no loss that matters.

Fast failure at the edge

During a database incident, requests used to time out after two seconds, so clients retried and tripled the load. A concurrency limit at the edge now returns 503 with Retry-After in under a millisecond; the database recovers because the stampede never forms.

When to use / when not to

find every queue you own, write down its bound — the ones you cannot name are the dangerous ones

Use it when…

  • A producer can outpace a consumer, even occasionally — which is nearly always.
  • There is a queue, buffer, pool or channel anywhere in the path.
  • Latency matters and you need a hard upper bound rather than a hopeful average.
  • The system must survive a dependency becoming slow rather than failing outright.
  • You are consuming from a broker, a stream or a file faster than you can write.

Avoid it when…

  • The producer genuinely cannot slow down. Use a bounded buffer with an explicit drop or conflation policy.
  • The real problem is one client's abuse. Use rate limiting for fairness and quotas.
  • The dependency is failing rather than slow. Use a circuit breaker so you stop calling it at all.
  • You need to choose which work to sacrifice. Use load shedding with priority classes.
  • Blocking the producer would deadlock a cycle. Use a non-blocking signal plus shedding.

Common mistakes & gotchas

The default is unboundednew LinkedBlockingQueue<>(), asyncio.Queue(), Channel.CreateUnbounded(), an executor's work queue, a list used "just as a buffer" — all grow until the process dies.
Fix: audit every queue, channel, pool and buffer, and give each an explicit capacity. If you cannot justify a number, you have not understood that part of the system.
Sizing the queue by what fits in memoryA 100,000-item buffer on a consumer doing 800 a second is a 125-second queueing delay. Every client has timed out ninety times over before the last item is touched.
Fix: size from a latency budget — L = λ × W. A 25 ms budget at 800/s is 20 items, not 100,000.
Moving the bloat instead of removing itYou bound the service's queue, and the gateway in front of it quietly buffers instead. Total latency is unchanged and now the problem is somebody else's dashboard.
Fix: propagate the signal to a layer that can act — return 503 at the edge, or slow a batch job down. Test it: when the database is slow, does the user get a fast error or a long timeout?
Processing requests nobody is waiting forOnce queueing delay exceeds the client timeout, utilisation stays at 100% while goodput falls to zero, and the system cannot climb out.
Fix: propagate deadlines and check them on dequeue. Consider LIFO under overload — serving the freshest request first means some succeed instead of all failing.
Blocking the event loopCalling a blocking put on a full queue inside an async runtime stops every other task on that thread, converting local backpressure into a total stall.
Fix: use the non-blocking idiom — TryWrite, select with default, WaitToWriteAsync, the drain event — and shed when you cannot wait.
Backpressure deadlockA blocks because B's queue is full; B is waiting on a response from A. Both stop forever, and no error is logged anywhere.
Fix: never block a producer that is in the same dependency cycle as its consumer. Use bounded-plus-reject, or separate pools so the cycle cannot close.
Retrying into an overloaded systemFast rejections are a feature, but a client that retries them immediately converts your careful shedding into a tight loop.
Fix: send Retry-After, require jittered exponential backoff, and cap retries with a budget so they cannot exceed a few percent of normal traffic.
Alerting on depth instead of wait timeDepth thresholds are meaningless without a drain rate: 10,000 can be healthy and 50 can be an outage.
Fix: measure sojourn time and the age of the oldest item. Alert on those; keep depth for memory-pressure monitoring.

Alternatives

MechanismBest forComplexityCost / licenseKey difference vs backpressure
Backpressuremaking a rate mismatch visible and boundedLowfree—
Load sheddingchoosing what to sacrifice under overloadMediumfreeDecides which work to refuse; backpressure only says "full"
Rate limitingfairness, quotas, abuse controlLowfreePer-client budget set in advance; blind to how loaded you actually are
Circuit breakera dependency that is failing, not merely slowLowfreeProtects the caller by stopping calls entirely; backpressure keeps flowing, slower
Autoscalingsustained load growthMediummore instancesAdds real capacity, but minutes too late for a spike — complementary, not a substitute
Bigger buffergenuinely short burstsVery lowmemoryAbsorbs bursts; hides persistent mismatch until it becomes an OOM
Batchingper-item overhead dominatingLowfreeRaises throughput so the mismatch may disappear; adds latency of its own
  • Pick load shedding for the decision that follows backpressure — the two are a pair, not alternatives.
  • Pick rate limiting when the question is "how much is this client entitled to?", not "am I full?".
  • Pick a circuit breaker when the downstream is erroring; backpressure assumes it still works, just slowly.
  • Pick autoscaling for load that persists for minutes; backpressure covers the seconds before it arrives.
  • Pick batching if per-item overhead is the bottleneck — sometimes the mismatch is an efficiency problem, not a capacity one.
